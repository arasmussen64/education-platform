Designer's brief, 2026-11-11. Shared lab pattern, prototype findings ("finding N"), check recipes ("R1" to "R8") and network-lab base requirements ("N1" to "N11"): [frr-labs-common.md](frr-labs-common.md). ## 1. What the learner will be able to do

- Explain what source NAT, masquerading and destination NAT (port forwarding) change in a packet, where in the nftables path each happens, and how connection tracking translates the replies back with no rule of their own; read a `conntrack -L` entry's two tuples.
- Write a NAT gateway's rules in nftables (source NAT scoped to the outside interface, destination NAT for a published service, the forward rules NAT needs), keep the client's real address visible to a published server, and make it all survive a reboot.
- Size NAT for a connection count: ports per public address, the "per destination" rule, addresses needed, VMs per address on Google Cloud, and what port hold-down and idle timeouts do to the numbers, on all three clouds.
- Recognise port exhaustion from its evidence (timeouts, not refusals; `conntrack -S`; each cloud's metric) and choose the remedy that fits.
- Say when to avoid NAT: IPv6, private paths to cloud services, published services behind a load balancer, and the cost per gigabyte; and when NAT is the right tool (overlapping address ranges).

**The six-month core.** NAT rewrites addresses and conntrack remembers the rewrite, so replies need no rule; a published server sees the real client only if nothing source-NATs the inbound traffic. A NAT's capacity is ports per address **per destination**; exhaustion shows as timeouts; the first fix is fewer new connections, the second more addresses (or ports per VM on Google). NAT costs money per gigabyte and has a private or IPv6 alternative more often than people think.

## 2. Prerequisites and terms

**`prerequisites: [csa.net.routing, csa.net.ipv6]`**. Routing for "the internet has no route back to a private address" and the forward path; IPv6 because the topic's last skill builds on topic 25's "why IPv6 egress doesn't use NAT" (an egress-only gateway instead).

**Builds on, for the writer.** `csa.linux.net-tools`: ports and the ephemeral range (32768 to 60999, 28,232 ports), `TIME-WAIT` of 60 seconds, nftables hooks (`prerouting`, `forward`, `postrouting`), `policy drop`, `ct state established,related accept`, `conntrack -L`, saving to `/etc/nftables.conf` and checking it in a scratch namespace, and one sentence each on masquerading containers and DNAT for published ports (`mcq-netns-veth`). `csa.linux.hardening`: forwarding in `/etc/sysctl.d/`. `csa.net.cidr`: the RFC 1918 private ranges. `csa.net.routing`: return paths, `ip route get`, black holes. `csa.net.ipv6`: dual stack and egress without NAT.

**Terms this topic defines:** NAT; source NAT (SNAT) and masquerading (SNAT to whatever address the outgoing interface has); destination NAT (DNAT, port forwarding); PAT or NAPT (many inside addresses share one outside address by port; what every home router and cloud NAT gateway does); the 5-tuple (protocol, source address and port, destination address and port); conntrack's original and reply tuples; a translation; port exhaustion; idle timeout (how long a NAT remembers a quiet connection); port hold-down (cool-down: how long a closed connection's port waits before reuse to the same destination); "unique destination" (destination address, port and protocol); endpoint-independent mapping (RFC 4787's term: the same inside address and port keep the same outside address and port whatever the destination); managed NAT gateway (AWS NAT gateway, Azure NAT Gateway, Google Cloud NAT); carrier-grade NAT and the shared address space `100.64.0.0/10` (RFC 6598); NAT64 (one sentence); gateway endpoint and private endpoint (one sentence each; Module 11 teaches them).

## 4. Lesson plan

The lesson supplies what no single resource does: the packet drawn before and after each rewrite, the "per destination" idea with a picture, and the three clouds' numbers side by side.

1. **Why NAT exists, in two minutes** (resource N3, Computerphile, optional; N2's first minutes for the vocabulary). Private addresses (RFC 1918, from `csa.net.cidr`) aren't routed on the internet, so a reply to 10.1.0.10 has nowhere to go; NAT puts a public address on the way out.
2. **Source NAT, one packet at a time** (resource N1, Practical Networking "Dynamic PAT", 15 min, the main resource). *Picture in words:* the office laptop's packet leaves as `10.1.0.10:51000 → 203.0.113.10:443`; the gateway rewrites the source to `198.51.100.2:20007` and writes the pair in its table; the reply comes back to `198.51.100.2:20007`, the gateway looks it up and rewrites the destination back to `10.1.0.10:51000`. The table is conntrack (Module 1), and `conntrack -L` shows both tuples: the original as the laptop sent it, the reply as the server sent it. No rule is needed for replies. Masquerading is SNAT to "whatever address the outgoing interface has", for a gateway whose public address can change; `snat to` names a fixed one.
3. **Where in the path** (Module 1's hook diagram, extended). DNAT happens in `prerouting`, before the routing decision, so the router routes the packet to its new destination; SNAT happens in `postrouting`, after routing, so filtering in `forward` still sees the inside address. The filter table's `forward` chain must let published traffic in (`ct status dnat accept`); that line is the one people forget.
4. **Destination NAT and what the server sees.** A published port (`dnat to 10.1.0.20:8443` for traffic arriving on `wan` port 443) keeps the customer's address as the source, so the app's logs and rate limiter see real customers. A masquerade rule written without `oifname "wan"` also rewrites traffic going **into** the LAN, and the app then sees every customer as the gateway (`10.1.0.1`), the prototype's captured result. Hairpinning (an inside client using the public address) is mentioned in one sentence and left out of the labs.
5. **How many connections? The per-destination rule** (resources N5, N6, N7, N8). *Picture in words:* a NAT keeps its translations apart by the whole 5-tuple, so two connections can share the same public address and port as long as they go to different destinations; only connections to the **same** destination address, port and protocol each need their own port. The clouds' numbers, side by side (section 5): AWS, 55,000 simultaneous connections per address per unique destination, up to 8 addresses on a zonal gateway (32 per zone on the newer regional one); Azure, 64,512 SNAT ports per public address, up to 16 addresses, "up to 50,000 concurrent connections per public IP address to the same destination endpoint", 2 million connections in all; Google, 64,512 ports per NAT address handed out to VMs in blocks (64 per VM by default with static allocation), so a NAT address serves 1,008 VMs at the default. **Where the clouds differ:** AWS and Azure share an address's ports among all clients on demand; Google reserves ports per VM, so one busy VM can run out while the address has ports to spare, which Linux does too (finding 11): one client to one destination uses one address of a range.
6. **Time holds ports too.** A port isn't free the moment a connection closes: Azure holds it 65 seconds after a FIN (16 after a reset) before reusing it to the same destination; Linux's `TIME-WAIT` is 60 seconds (Module 1). And a NAT forgets a quiet connection after its idle timeout: AWS 350 seconds (then it sends a reset to the inside host), Azure 4 minutes by default for TCP (configurable to 120), Google 1,200 seconds for established TCP. Long idle timeouts tie up ports; short ones cut quiet connections (topic 28 teaches keepalives). The arithmetic: a client making 20 short connections a second to one API, with a 65-second hold-down, has 1,300 ports tied up at any moment.
7. **Port exhaustion, and how it looks** (prototype, finding 11; resources N7, N5, N8). New connections to the busy destination **time out** (the gateway drops the SYN; nothing refuses it), existing connections carry on, connections elsewhere still work. On Linux, `conntrack -S` counts `insert_failed`; on AWS the gateway's `ErrorPortAllocation` metric is above zero; on Azure `SNAT Connection Count` filtered to Failed; on Google `dropped_sent_packets_count` with reason `OUT_OF_RESOURCES`. **Remedies, in order of how much they help:** stop opening a new connection per request (pooling, HTTP keep-alive); add public addresses where they help (AWS, Azure; on Google raise ports per VM or turn on dynamic port allocation, because more addresses don't help a VM that has used its block); shorten idle timeouts; send traffic to cloud services through a private path that needs no NAT at all.
8. **When not to NAT** (resource N9's cost lines; topic 25 recalled). IPv6 hosts reach the internet through an egress-only gateway with no translation; S3 and DynamoDB through an AWS gateway endpoint cost nothing per gigabyte, against $0.045 per GB through a NAT gateway (AWS's Ohio example, read 2026-11-11), and need no ports; a published service with several servers belongs behind a load balancer, not a DNAT rule per server; any log or rule that must see the real client breaks if something source-NATs inbound traffic. And when NAT is right: two networks with overlapping ranges (a merger), a partner that allow-lists one outbound address, carrier-grade NAT at ISPs (and why `100.64.0.0/10` is not a range to pick for a cloud network: Azure's route tables drop it by default).
9. **The clouds' NAT gateways in one table** (no lab: Module 11's `csa.cnet.egress` builds them): what each is called, how it's priced, what it scales on, its idle timeout, its exhaustion metric (section 5's facts).

**Read now, in this order:** N1 (15 min), N4, the nftables wiki's NAT page (9 min), N5, Azure's SNAT page (10 min), and the parts of N7 and N8 the lesson names (10 min). N2, N3, N6 and N9 are "more resources".

## 7. Practice ladder

**The NAT lab's network** (shared by every NAT lab; prototyped as namespaces in `prototypes/frr/nat/`, to be built with the gateway in the main namespace as section 1 of the common brief says): the lab machine is the shop's **gateway**, with `lan` (a bridge, 10.1.0.1/24) holding `office` 10.1.0.10 and `app` 10.1.0.20 (the shop's web app on 8443, which prints and logs each client's address; a database on 5432; SSH on 22), and `wan` (198.51.100.2/24, and 198.51.100.3 where a lab says) toward `inet`, the lab's internet (198.51.100.1 and 203.0.113.1), which holds `srv` 203.0.113.10 (a web server on 80 that logs client addresses, and the payment provider on 443, holding connections and accepting them only from addresses it was told to allow) and `client` 203.0.113.20 (a customer). `network.sh` replaces the gateway's default route with `default via 198.51.100.1 dev wan`, so `ip route` reads like a real gateway's; the prompt says `eth0` is Docker's and not part of the lab. `inet` has no route to 10.0.0.0/8: private addresses aren't routed on the internet. Every NAT lab starts with Module 1's style of filter on the gateway (`forward` policy drop, `ct state established,related accept`, `iifname "lan" oifname "wan" accept`) unless it says otherwise.

1. **`example-watch-the-translation`** (worked example, systemd). Labelled steps:
   1. *The problem.* `on office curl -m 3 http://203.0.113.10/` times out; `sudo tcpdump -nn -i wan` shows packets leaving from 10.1.0.10 and nothing coming back.
   2. *Source NAT.* `sudo nft add table ip nat`, a `postrouting` chain (`type nat hook postrouting priority srcnat; policy accept;`), `oifname "wan" masquerade`. The curl works; tcpdump on `lan` and on `wan` side by side show the source rewritten.
   3. *Read the translation.* `sudo conntrack -L -p tcp --dport 80`: the original tuple from 10.1.0.10, the reply tuple to 198.51.100.2 and a port the gateway chose.
   4. *Publish the app.* A `prerouting` chain (`type nat hook prerouting priority dstnat`), `iifname "wan" tcp dport 443 dnat to 10.1.0.20:8443`. `on client curl -m 3 http://198.51.100.2:443/` times out: the `forward` chain drops it. Add `ct status dnat accept`. Now it answers `you are 203.0.113.20`.
   5. *The classic mistake, on purpose.* Replace the masquerade rule with one that has no `oifname`: the app now says `you are 10.1.0.1`. Put `oifname "wan"` back.
   6. *Run a NAT out of ports.* Add, before the masquerade, `oifname "wan" ip protocol tcp tcp dport 9000 snat to 198.51.100.2:20000-20009` (ten ports); `on office holdconns 15 203.0.113.10 9000`: 10 open, 5 time out; `sudo conntrack -S` shows `insert_failed`; `on office holdconns 5 203.0.113.10 9001` all open (another destination). Delete the ten-port rule.
   7. *Make it last.* `sudo nft list ruleset`, written into `/etc/nftables.conf` under `flush ruleset` (Module 1's form), `sudo systemctl enable nftables`; `net.ipv4.ip_forward = 1` in `/etc/sysctl.d/90-gateway.conf`.
   Checks: the office reaches srv's web server and srv's log shows 198.51.100.2 (R8); a customer reaches the app through 198.51.100.2:443 and the app's log shows 203.0.113.20; the office holds 50 connections to srv:9000 at once (no ten-port rule left); the rules are saved and nftables enabled (R8's scratch-namespace comparison); forwarding is set in `/etc/sysctl.d/`. Wrong fixes: `masquerade-everywhere.sh`, `tiny-range-left.sh`, `not-saved.sh`.
2. **`conntrack-two-tuples`** (predict_shell, `snat-and-dnat`, captured). File: the captured ESTABLISHED line. Command: `awk '{print $5, $7, "->", $10, $12}' conntrack.txt` (the writer pins the fields so the output reads `src=10.1.0.10 sport=38620 -> dst=198.51.100.2 dport=20007`). Explanation: what the laptop sent, what the server answers to; the gateway maps one to the other.
3. **`mcq-hooks-for-nat`** (mcq, `snat-and-dnat`). Why is DNAT done in `prerouting` and SNAT in `postrouting`? Right: "DNAT must change the destination before the router chooses a route; SNAT changes the source after it". Wrong: "prerouting runs faster, and DNAT must keep up with incoming traffic"; "SNAT needs to see the reply first, and replies reach postrouting"; "nftables allows only one NAT chain per hook, so the two are split".
4. **`mcq-replies-need-no-rule`** (mcq, `snat-and-dnat`). The gateway has only `oifname "wan" masquerade`; how do replies reach the office laptop? Right: "conntrack remembers the translation and reverses it on every reply". Wrong: "a matching reverse rule is added automatically in prerouting"; "the server sends replies to the laptop's private address directly"; "the default route on the gateway sends everything back to the LAN".
5. **`mcq-what-the-app-sees`** (mcq, `snat-and-dnat`, captured result). A gateway has `masquerade` with no interface named, and DNAT for the app. The app's log shows every customer as 10.1.0.1. Right: "The masquerade rule also rewrites traffic going into the LAN, so the app sees the gateway". Wrong: "The DNAT rule hides the customer's address because it rewrites the whole packet"; "The app is behind a second NAT that the shop's ISP runs for all its customers"; "conntrack merges connections from different customers into one entry".
6. **`mcq-masquerade-or-snat`** (mcq, `nat-rules`). When is `masquerade` the better choice than `snat to`? Right: "When the outside address can change, as on a link that gets it by DHCP". Wrong ones: "When there are several outside addresses to spread connections over"; "When published services must keep the client's address"; "When the gateway must translate UDP as well as TCP".
7. **`mcq-dnat-needs-forward`** (mcq, `nat-rules`). DNAT rule present, published port times out, `forward` is policy drop with `ct state established,related accept` and `iifname "lan" oifname "wan" accept`. Right: "No rule accepts the first packet of a published connection; it needs `ct status dnat accept`". Wrong: "DNAT rules in prerouting are skipped when the forward policy is drop"; "The app must listen on port 443, the public port, not on 8443"; "The established,related rule should come after the DNAT rule in the chain".
8. **`mcq-port-range-protocol`** (mcq, `nat-rules`, captured error). `snat to 198.51.100.2:20000-20009` with no protocol named fails with `transport protocol mapping is only valid after transport protocol match`. Right: "A port only exists for TCP or UDP, so the rule must say which first". Wrong: "Port ranges can only be used with masquerade, not snat"; "The range must start at 1024 or above to be allowed"; "Ranges need the `random` flag before nftables accepts them".
9. **`nft-nat-ruleset`** (predict_shell, `nat-rules`, constructed in `nft list ruleset` form). A ruleset with an `inet filter` table and an `ip nat` table (one dnat, two snat/masquerade rules). Command: `grep -o 'hook [a-z]* priority [a-z]*' ruleset.txt; grep -cE 'dnat|snat|masquerade' ruleset.txt`. The learner predicts the hook lines and the count; the explanation reads each chain.

### Explain (20 minutes)

**Prompt.** A team is moving 200 VMs into private subnets behind a cloud NAT gateway, and one of them calls a payment API thousands of times a minute. Explain, in your own words: what source NAT does to an outbound connection and how the replies find their way back; what destination NAT does and what the server behind it sees; what limits how many connections a NAT can carry, and how you'd size it for that API on one cloud of your choice; how port exhaustion would show itself and what you'd try first; and when you'd avoid NAT altogether.

**Rubric.**

| id | Required | Description |
| --- | --- | --- |
| `snat-conntrack` | yes | SNAT rewrites the source address (and port) to the NAT's public address after routing; the NAT records the mapping (conntrack on Linux) and reverses it on replies, so replies need no rule |
| `dnat-client` | yes | DNAT rewrites the destination before routing to reach an inside server, which still sees the client's real address unless something also source-NATs the inbound traffic (a masquerade rule not limited to the outside interface) |
| `sizing` | yes | Capacity is ports per public address **per unique destination** (address, port, protocol); one cloud's numbers stated correctly (AWS 55,000 per address per destination, up to 8 addresses; Azure 64,512 ports per address, up to 16, or its 50,000 per destination; Google 64,512 per address shared in per-VM blocks, 64 by default); a sum for the API's connections; that ports stay held after close (hold-down, `TIME-WAIT`) and while idle |
| `exhaustion` | yes | New connections to the busy destination time out while others work; the evidence (`insert_failed`, or that cloud's metric); first fix: reuse connections; then more addresses (or ports per VM on Google), shorter idle timeouts |
| `avoid` | yes | At least one correct case: IPv6 with an egress-only gateway; a private or gateway endpoint for cloud services (no ports, no per-GB NAT charge); a load balancer for inbound services; and one case where NAT is right (overlapping ranges, an allow-listed outbound address) |
