# The FRR labs: what topics 26, 27 and 34 share

Designer's brief, 2026-11-11, for `csa.net.routing` (26), `csa.net.nat` (27), `csa.net.bgp` (34) and the proposed `csa.net.bgp-steering` (34b, see `csa.net.bgp.md`, section 0). This file holds what the four topic briefs share: the lab pattern, what it needs from the network-lab base, what the prototypes proved, the check recipes, and cost. Each topic brief refers here instead of repeating it.

Prototypes, captured output and timings: `prototypes/frr/` (its `README.md` lists them; `CAPTURES.md` holds real output for recall items).

## 1. The pattern in one paragraph

A routing lab is a **systemd lab** (`lab: { init: systemd }`), because network namespaces need the privileged container and FRR needs systemd to start one routing process per router. Every machine of the lab (routers and hosts) is a network namespace made at boot, joined by veth pairs named after the neighbour at the other end (on r1, the link to r2 is called `r2`). Each **router** runs its own FRR instance inside its namespace (`frr@r1.service`, configuration in `/etc/frr/r1/frr.conf`); each **host** is a bare namespace with an address and a default route. The learner works from the container's main namespace ("lab", the console) with three commands: `router NAME` opens that router's console (FRR's `vtysh`, a Cisco-style shell), `on NAME COMMAND` runs a Linux command on any machine (`on office traceroute -n 10.3.0.10`), and `lab-link A B down|up` cuts or restores a link to test failover. A router's configuration survives a reboot only when it is saved (`write memory`), exactly as on a real router; the namespaces and addresses are scenery, rebuilt at every boot.

NAT labs differ in one way: the NAT gateway is the container's **main namespace** ("lab" itself), so its firewall and NAT live in `/etc/nftables.conf` loaded by `nftables.service`, and forwarding in `/etc/sysctl.d/`, which is exactly what Module 1 taught (`csa.linux.net-tools`, `csa.linux.hardening`). Only its LAN hosts and the "internet" are namespaces.

## 2. What these labs need from the network-lab base

The network-lab base is another designer's; these are the requirements, each proved in the prototype, with the smallest version that would do. Where the base already provides the thing in another form, the base's form wins and these labs adapt.

| # | Need | Smallest version (proved in `prototypes/frr/`) |
| --- | --- | --- |
| N1 | FRR in the image | A second `RUN` line, identical in every Module 3 routing lab: `apt-get install -y --no-install-recommends frr frr-pythontools`, then `systemctl disable frr` (no router in the main namespace) and `usermod -a -G frr,frrvty learner`. Ubuntu's own package (8.4.4-1.1ubuntu6.8 in noble's main, security-supported); 24 MB, 10.5 s. See finding 1 for why not FRR's own repository. If the base's second line carries other Module 3 packages (strongSwan, a DNS server), FRR joins that line. |
| N2 | A topology made at boot | `network.sh` run by a oneshot `lab-network.service` (`DefaultDependencies=no`, `Before=network.target`), as Module 1's labs do: `ip netns add` for each machine, a `link NS1 IF1 ADDR1 NS2 IF2 ADDR2` helper that makes a veth pair across two namespaces and addresses both ends, default routes for hosts. A declarative topology file read by one shared script would be better (every Module 3 lab would share the script and differ only in the file); the prototypes used a hand-written `network.sh` per lab. |
| N3 | Kernel settings set, never inherited | `network.sh` sets, in every namespace: `net.ipv4.ip_forward` (1 on routers, 0 on hosts), then `net.ipv4.conf.all.rp_filter` and `conf.default.rp_filter` (0 unless a lab is about reverse-path filtering). Order matters: the kernel documents that writing `ip_forward` resets other per-interface settings to their defaults (docs.kernel.org, ip-sysctl, read 2026-11-11), so forwarding goes first. A lab that uses ECMP also sets `net.ipv4.fib_multipath_hash_policy`. See finding 4. |
| N4 | One FRR instance per router | Per router: `/etc/frr/NAME/daemons` (Ubuntu's file with `bgpd=yes` where needed, `bfdd=yes` where needed, and `watchfrr_options="--netns"`, which makes the daemons run inside the namespace of the same name), `/etc/frr/NAME/frr.conf`, `/etc/frr/NAME/vtysh.conf` (`service integrated-vtysh-config`); `frr@NAME.service` enabled by a symlink in `multi-user.target.wants`; the files owned `frr:frr`, mode `u=rwX,g=rwX,o=`. Router names have **no hyphen** (finding 2). |
| N5 | A drop-in for `frr@.service` | `/etc/systemd/system/frr@.service.d/lab.conf`: `After=` and `Requires=lab-network.service`, and `ExecStart=` replaced by `/usr/bin/unshare --uts /bin/sh -c 'hostname %I && domainname "(none)" && exec /usr/lib/frr/frrinit.sh start %I'`, so each router has a hostname of its own (finding 3). |
| N6 | `router NAME [vtysh args]` | `exec sudo nsenter --uts --target "$(cat /run/frr/NAME/watchfrr.pid)" vtysh -N NAME "$@"`, with a one-line error when no such router runs. The prompt then reads `r1#`, not `lab#`. |
| N7 | `on NAME COMMAND` | `exec sudo ip netns exec "$1" "${@:2}"`: Module 1's `from-office` and Module 2's `on-dc`, generalised. |
| N8 | `lab-link MACHINE INTERFACE down\|up\|silent\|restore` | The interface is named after the neighbour at its far end (`lab-link r1 r3 down`), or after the link when two links join the same pair of routers (`lab-link edge dx1 down`). `down`/`up`: `ip -n MACHINE link set INTERFACE down/up` (a veth pair loses carrier on both ends, which routers notice at once). `silent`: an nftables table in the far machine's namespace dropping everything that arrives over that link while the link stays up (a dead path the routers can't see); `restore` removes it. The labs use it to teach the difference between a failure a router sees and one it doesn't (finding 9). Scenery: it touches only the link, never a router's configuration. |
| N9 | `looking-glass NAME 'show ...'` (BGP labs) | Runs `router NAME -c` for commands that start with `show` and refuses anything else, so the learner can read an ISP's or the cloud's router the way real networks publish looking glasses, without being invited to configure it. The learner has `sudo`, so the checks still prove the far side untouched (recipe R6). |
| N10 | Two connection helpers (NAT labs) | `holdconns N HOST PORT [SECONDS]`: opens N TCP connections **in parallel** (non-blocking sockets, one shared 3-second deadline) and holds them, printing `opened X of N`; the prototype's sequential version took 2 s per failure, which would make a check with 100 failures take minutes. `holdserver PORT...`: accepts and holds connections. Both are Python 3 (in the shared layer), scenery, under `/usr/local/bin/`. |
| N11 | A check helper | `/usr/local/lib/lab/bgp-best ROUTER PREFIX`: prints the best path's next hop, `selectionReason`, local preference, MED and AS path from `show bgp ipv4 unicast PREFIX json` on one line, or `none`. And `/usr/local/lib/lab/frr-saved ROUTER`: recipe R2. Checks call them so that no check carries thirty lines of inline Python. They only read. |

Not needed: IPv6 in the namespaces (FRR prints `no ipv6 forwarding` and nothing else depends on it), netem, MPLS, VRFs, kernel modules beyond those Module 1's labs already use, except NAT's (finding 11).

## 3. What the prototypes proved (findings)

Each finding was tried on Docker Desktop 29.8.2 (Windows, WSL 2 kernel 6.18.33.2, cgroup v2) on 2026-11-11, with the containers started exactly as `tools/labcheck.py` starts a systemd lab (`--privileged --cgroupns=private --tmpfs /run --tmpfs /run/lock ... /sbin/init`).

1. **Ubuntu's FRR 8.4.4, not FRR's own repository.** `deb.frrouting.org` serves FRR 10.7.1 for noble (its `Release` file dated 2026-08-31, components `frr-stable`, `frr-10.7` and older). Ubuntu's 8.4.4 has everything these topics need (static routes with distances and blackholes, BGP with route-maps, prefix-lists, communities, route reflection, `bgp ebgp-requires-policy`, BFD, multiple instances with `--netns`, `frr-reload.py --pathspace`), comes from the same archive as every other package in the image (no key, no third-party host that a weekly CI build depends on), and gets Ubuntu's security updates. The cost: the learner must read **FRR 8.4's documentation** (`docs.frrouting.org/en/stable-8.4/`, which exists and was read for this brief), and JSON keys may differ from 10.x. If a later topic needs FRR 10 (EVPN, SRv6), switch then, pinned to a numbered component (`frr-10.7`), never `frr-stable`, and rewrite the checks' JSON reads.
2. **Router names without a hyphen.** `frr@.service` passes `%I` (the unescaped instance name) to `frrinit.sh`, and systemd unescapes `-` to `/`: `frr@isp-a` looked for `/etc/frr/isp/a/daemons` and failed. Use `ispa`, `r1`, `edge`.
3. **Each router needs its own hostname.** Without a UTS namespace of its own, every FRR instance took the container's hostname: every prompt said `lab#`, every router's saved config said `hostname lab`, and every BGP peer showed its neighbours as `lab` in `show bgp ... json`. The drop-in in N5 fixed all three. `vtysh` itself must run in the router's UTS namespace too (N6), or its prompt still says `lab#`.
4. **Kernel defaults differ by machine, so set them.** A namespace made inside the lab container on Docker Desktop inherited `rp_filter=2` (loose) on `all` and `default`, `ip_forward=1`, IPv6 forwarding 0. Ubuntu runners set `rp_filter=2` through systemd's `50-default.conf` and Docker sets `ip_forward=1` on the host, so CI will probably agree, but "probably" is not a contract: N3 sets them. `net.core.devconf_inherit_init_net` is not visible inside a namespace, so a lab can't even check what it would inherit.
5. **Timings.** Boot to `running`: 2.7 to 4.3 s. BGP converged (every path present at the far router) 4.4 to 5.3 s after boot, with `timers bgp 3 9` and `neighbor X timers connect 5` in every seeded config (FRR's default connect-retry is 120 s: a router that starts before its neighbour would otherwise wait two minutes). A route-map newly applied to a neighbour took effect at the far router in 0.2 s; a route-map **edited in place** took 5.1 s, FRR's route-map delay timer (`RMAP_DEFAULT_UPDATE_TIMER 5` in 8.4's `bgpd/bgpd.h`; the 8.4 user guide doesn't mention it). Making a neighbour a route-reflector client took 4.3 s. `docker restart` took 12.5 to 13.5 s (systemd ignores the TERM signal Docker sends, so Docker waits its 10 seconds and kills it), plus 5 s to converge.
6. **Failover.** A floating static route took over 74 ms after a link lost carrier; BGP rerouted in 73 ms after the same cut (FRR's `bgp fast-external-failover`, on by default) and returned to the primary 1.3 s after the link came back. A dead path with the link still up (`lab-link silent`) was a permanent black hole for static routes; BGP noticed when its 9-second hold timer ran out (traffic back after 11.2 s); with BFD at 300 ms × 3 (FRR's `bfdd`), traffic was back after 1.08 s.
7. **Ties must not be decided by time.** Two equal eBGP paths were decided by `"selectionReason":"Older Path"`: whichever session came up first. That varies run to run, so a wrong fix could pass by chance. Every seeded router config carries `bgp bestpath compare-routerid`, or the topology makes the default winner deterministic (unequal AS paths); and every lab that asks the learner to make path X preferred makes sure X **loses** without the learner's change. With `compare-routerid` and two sessions to the same router, the tie fell to the lower neighbour address (`"Neighbor IP"`).
8. **Saved or not, checked without a reboot.** `/usr/lib/frr/frr-reload.py --test --pathspace NAME /etc/frr/NAME/frr.conf` compares the running configuration with the saved file and prints nothing when they match (0.33 s). Run in the container's UTS namespace it always reported `no hostname lab`/`no domainname localdomain` differences; run in the router's (`nsenter --uts --target <watchfrr pid>`) it printed nothing after a `write memory`, and the missing lines after an unsaved change. It compares meaning, not text, so a learner who edits `frr.conf` by hand and restarts `frr@NAME` also passes, provided the file was first written by FRR (seed files are generated with `write memory` at authoring time so they carry FRR's own lines, such as `no ipv6 forwarding`). It prints harmless `SyntaxWarning`s on Python 3.12 to stderr. **Restart trial:** a saved change (prefix filter and prepend) was back after `docker restart`; an unsaved local-preference change was gone.
9. **RFC 8212 is FRR's default.** With FRR's "traditional" defaults, `bgp ebgp-requires-policy` is on: an eBGP session with no inbound or outbound route-map comes up (`Established`) but exchanges nothing, shown as `(Policy)` in both prefix columns of `show bgp summary` and `"peerState": "Policy"` in its JSON. This is a fine teaching moment and a natural debug fault; `no bgp ebgp-requires-policy` is the security-weakening shortcut every BGP lab's checks reject.
10. **`network` needs a route.** FRR announces a `network` prefix only if that exact prefix is in the routing table (import check, on in 8.4 for both profiles per the user guide). A typo (`/25` for a `/24` that is connected) silently announces nothing.
11. **NAT behaves as the clouds' documentation says, with one Linux twist.** In the NAT prototype (namespaces, nftables 1.0.9): a 10-port SNAT range admitted 10 of 15 simultaneous connections to one destination; the other 5 **timed out** (no reset: the SYN was dropped) and `conntrack -S` counted `insert_failed`; at the same time 5 connections to a **different destination port** all opened, reusing the same NAT port, which is the "per unique destination" rule AWS and Azure state. The twist: with **two** public addresses in the range (`snat to A-B:ports`, with or without `random` or `fully-random`), one client to one destination still got only one address's ports, because Linux maps a client to one address. More addresses help many clients, not one busy client: Google Cloud NAT's per-VM allocation behaves the same way, AWS's NAT gateway (per its documentation) does not. nftables refuses a port range without a protocol match (`transport protocol mapping is only valid after transport protocol match`), so a rule with ports needs `ip protocol tcp` or `meta l4proto tcp`.
12. **Asymmetric paths and black holes are visible to checks.** A stateful firewall that sees only one direction: ping works, TCP times out, `ct state invalid` drops count up, the conntrack entry stays `[UNREPLIED]`. Strict reverse-path filtering: `TcpExtIPReversePathFilter` counts up in `nstat`. Forwarding off: `IpInAddrErrors` counts up, no ICMP back. A blackhole route: silence, and `ip route get` answers `RTNETLINK answers: Invalid argument`. No route: `!N` in traceroute and `Network is unreachable` from `ip route get`. A loop: traceroute alternating two addresses, ping `Time to live exceeded`. ECMP with one dead path: per-connection failures with `fib_multipath_hash_policy=1`, all-or-nothing per client pair with `=0` (`CAPTURES.md`).
13. **traceroute can show `*` for a hop that works**, because routers rate-limit ICMP. Checks never require every hop to answer; they read `ip route get` on each router and send traffic end to end.

## 4. Check recipes

Every routing lab's checks are built from these. All run as root in the main namespace. The README's rules apply: a check that finds something wrong prints why and exits 0; descriptions state end states; no description of a debug lab names a fault.

- **R1, the forwarding decision.** `ip -n R route get ADDRESS` on each router of a path, compared with the expected next hop; and traffic end to end (`ip netns exec office curl -s -m 3 ...` or `nc -z -w 2`). The kernel's answer, not FRR's, is what packets follow.
- **R2, saved.** `nsenter --uts --target "$(cat /run/frr/R/watchfrr.pid)" /usr/lib/frr/frr-reload.py --test --pathspace R /etc/frr/R/frr.conf 2>/dev/null` prints nothing. Rejects every runtime-only fix (`wrong/not-saved.sh` in every build and debug).
- **R3, no hand-made kernel routes.** `ip -n R -j route show` (iproute2's JSON) holds no route whose `protocol` is `boot` (what `ip route add` makes); FRR's routes say `static` or `bgp`. Rejects `on r1 ip route add ...`, which works until the next boot. Read with `python3 -c` (no `jq` in the image).
- **R4, BGP state.** `show bgp summary json` (`state`, `pfxRcd`, `pfxSnt`), `show bgp ipv4 unicast PREFIX json` (`paths[].bestpath.overall`, `nexthops[0].ip`, `locPrf`, `metric`, `aspath.string`, `community.string`), and on the far router `show bgp ipv4 unicast neighbors ADDR routes json` (what it accepted from us). Through `bgp-best` (N11). Because an in-place route-map edit takes 5 s to reach a peer (finding 5), every BGP check **retries for up to 15 s** before failing (a loop, never a `sleep 15`).
- **R5, failover by the check.** A check may cut a link to prove a backup works, because no reading of the configuration can (a backup can point the wrong way). It uses `lab-link`, restores in an `EXIT` trap, waits for the primary path to come back before it exits, and has `timeout: 60`. This is a deliberate, documented exception to "checks only read": it changes nothing the learner made, and leaves the lab as it found it. Order such checks last in `checks.yaml`.
- **R6, the far side untouched.** For routers the learner must not change (ISPs, the cloud): `sha256sum /etc/frr/R/frr.conf` against a value saved at build time, and R2 on that router (so a running-config change shows too).
- **R7, policy kept.** `router R -c 'show running-config'` must not contain `no bgp ebgp-requires-policy`, must not contain a route-map that permits everything toward an ISP (read through R4 instead: the far side accepted exactly the expected prefixes).
- **R8, NAT (main namespace).** As Module 1: what gets through, from the right side, with listeners of the check's own on unrequested ports; what the server saw (`holdserver`-style servers that log the client address, or the app's own log); `conntrack -L -p tcp --dport N` for the translation; `/etc/nftables.conf` loaded into a scratch namespace and compared with `nft -s list ruleset` (Module 1's `persisted` check, copied); `/etc/sysctl.d/` holding the forwarding setting and `systemctl is-enabled nftables`.

## 6. Cost: images, CI time, money

- **Money:** none. Every routing, NAT and BGP lab runs locally. Direct Connect, ExpressRoute and Cloud Interconnect are taught from their documentation and modelled in FRR (the spec's "stand-ins for what one person can't buy").
- **Image:** 355 MB per lab image, of which only the 24 MB FRR layer and a few kilobytes of scenery are new; all routing labs share the base layers with every Module 1 and 2 systemd lab.
- **CI time per lab** (estimated from the prototype, not measured under `labcheck test`): each contract container is about 4 s to boot, up to 6 s to converge, 5 to 25 s of checks (the failover checks are the slow ones), 1 s to remove: 15 to 35 s. A lab with 6 wrong fixes runs 8 containers: 2 to 5 minutes. The four topics hold 20 labs (2 of them plain) and 105 wrong fixes (routing 27, NAT 27, BGP 26, steering 25): roughly 145 container runs, about 70 minutes of runner time by the briefs' per-lab estimates, which the Labs job's four shards (four labs at a time each) absorb as about 5 more minutes per shard. The steering topic's build and debug are the slowest (failover checks and a one-minute retry). Keep wrong fixes to what the checks need (each brief lists exactly those).

## 8. Rules for the writers of these four topics

- **Multiple choice:** the briefs draft every choice as a full sentence of the same shape, but nobody has measured them. Before anything else the writer measures each item against the validator's rules (right answer at most 1.5 times the longest wrong one; right answer the longest in no more than half a topic's items) and the README's softer aims (within 1.3 times; longest in about a third). Items whose choices are lists ("AWS: …; Azure: …; Google: …") are the likeliest to fail.
- **Captured or constructed:** an item built on `prototypes/frr/CAPTURES.md` is "captured (FRR 8.4.4 on Ubuntu 24.04, 2026-11-11)"; an item whose numbers were made up in a real format is "constructed". Timings and uptimes in captured output are kept as captured, never "improved".
- **Debug prompts** give purpose, symptoms and the number of faults; the intended design may be stated (each debug brief marks what may be said). No check description, failure message or seeded comment names a fault (README, step 4; #235: checks shown only after a first try).
- **Every rule a prompt states has a check and a `wrong/*.sh`** (the briefs list them); the far routers' "not yours" rule is R6.
- **The restart trial** (README): apply the solution, `docker restart` the container (12 to 14 s, then about 5 s for BGP), run the checks again. Everything in these labs that matters is in `frr.conf`, `/etc/nftables.conf` or `/etc/sysctl.d/`, so every check should pass after it; a check that fails after the trial is a bug in the lab.
- **Prove each lab under `labcheck test` before writing its lesson text**, as Module 2's brief asked for its labs.

## 9. For Checkpoint 3's designer

Checkpoint 3's debug is "a local network of routers, a DNS server and an app" with "an intermittent outage caused by three faults". The prototypes found two intermittent mechanisms a check can see, and one silent one: ECMP with one dead path and `fib_multipath_hash_policy=1` (8 of 20 connections worked: per-connection failures; with `=0`, all or nothing per client pair); a BGP session torn down by a neighbour's maximum-prefix limit and retried every minute (34b's debug; tried: `Idle (PfxCt)`, "will restart in 51 seconds" eight seconds after the teardown, though the re-establishment itself wasn't timed); and a path that dies silently under a static route while its backup sits unused. Each needs its sysctl or timer set explicitly (N3), and each has evidence a learner can find (`ip route show` listing two next hops, `show bgp neighbors`' last reset, `lab-link silent`'s missing replies).

## 10. Open questions shared by the four topics

1. **Ubuntu's FRR 8.4.4 or FRR's 10.7?** Recommendation: Ubuntu's (finding 1). Best learning experience is a working, supported router with documentation that matches it; 8.4's documentation exists. Free either way.
2. **May a check cut a link (R5)?** Recommendation: yes, as specified (restore in a trap, wait for recovery, last in the file). A backup route can only be proved by failing the primary; reading the config passes a backup that points into a loop. It changes no learner work, the same standing as Module 1's throwaway listeners.
3. **Hostnames by UTS namespace (N5) or accept `lab#` everywhere?** Recommendation: the drop-in. Four prompts that all say `lab#` are a real source of confusion for a beginner configuring the wrong router.
