# Topic 26: `csa.net.routing`, Routing

Designer's brief, 2026-11-11. Shared lab pattern, prototype findings (cited as "finding N"), check recipes ("R1" to "R8") and the network-lab base requirements ("N1" to "N11"): [frr-labs-common.md](frr-labs-common.md). Captured output for items: `prototypes/frr/CAPTURES.md`.

## 1. What the learner will be able to do

- Read a routing table (a Linux router's `ip route`, FRR's `show ip route`, an AWS, Azure or Google Cloud route table) and say where a packet to a given address goes and why: the longest matching prefix, the default route only when nothing else matches, and which source wins when two routes have the same prefix.
- Write static routes on a router (FRR), including a floating backup and a blackhole, save them, and tell the router's candidate routes (its RIB) from the ones the kernel forwards with (its FIB).
- Say when static routes are enough and when a routing protocol is needed, from what each does when a link fails loudly or silently, and how the clouds mix static route tables with routes learned by BGP.
- Remember that the reply is a separate routing decision, recognise an asymmetric path, and explain what it breaks (a stateful firewall, strict reverse-path filtering).
- Find where packets disappear with traceroute, `ip route get`, tcpdump and counters, and name the cause from the evidence.

**The six-month core.** Shown any route table, say where a packet goes (longest prefix first; the tie-break of that platform second). Remember "the way back is its own route". Know the five ways packets vanish and the one command that shows each. Know that a static route can't see a silent failure.

## 3. Skills

| Skill | What it covers |
| --- | --- |
| `longest-prefix-match` | Predict the route and next hop for a destination from a real table: the longest matching prefix wins; the default route only when nothing else matches; an address can sit inside a short prefix and outside a longer one that "looks closer". When prefixes are equal, the route's source decides: FRR's distance (connected 0, static 1, eBGP 20, iBGP 200; 255 is never installed); AWS (static, then prefix lists, then propagated: Direct Connect BGP, VPN static, VPN BGP); Azure (user-defined, then BGP, then system, except that routes for the virtual network and its peerings beat even a longer BGP route); Google (subnet routes first and can't be overridden, then most specific, then priority) |
| `static-routes` | Write static routes in FRR (`ip route PREFIX NEXT-HOP [DISTANCE]`), floating backups with a higher distance, blackhole and reject routes on purpose; save them (`write memory`); read FRR's RIB (`>*` selected, `[distance/metric]`) against the kernel's FIB (`ip route`, `ip route get`) |
| `static-or-dynamic` | When static routes are enough (few routes, one way out, a stub) and when a routing protocol is needed (redundant paths, many prefixes, change); what each does when a link fails loudly (carrier lost) or silently (link up, path dead); how the clouds combine static route tables with routes propagated from gateways that speak BGP |
| `return-path` | Every router decides alone, so a reply needs a route of its own back; asymmetric paths; why a stateful firewall that sees one direction drops the connection (ping can still work) and why strict reverse-path filtering drops the replies; where this bites in the cloud (network virtual appliances, hub and spoke) and the two fixes (symmetric routes, or source NAT with its cost) |
| `find-the-black-hole` | Find where packets die and why: no route (`!N`, `Network is unreachable`), a blackhole route (silence; `ip route get` refuses), a reject route (`!H`), forwarding off (silence; `IpInAddrErrors` climbs), a missing return route (requests arrive, replies never leave), a loop (traceroute alternates two addresses, `Time to live exceeded`), a cloud VM that isn't allowed to forward; with traceroute from the source, `ip route get` at each hop, tcpdump on each interface, `nstat` |

No calculation skill: ADR-0024's three-estimate rule doesn't apply. One estimate item (a loop's crossings) gives the review pool a typed answer of another kind.

## 4. Lesson plan

The lesson supplies what no resource does for a beginner: the routing table read as nested boxes, the hop-by-hop picture with the return trip drawn separately, and a single table of "how packets vanish". Times are the learner's.

1. **What a router does, and the one idea everything else hangs on** (resource R2, Practical Networking "Everything Routers do, Part 2", 15 min). A router reads only the destination address, looks it up in its table, and hands the packet to the next hop. *Picture in words:* a chain of sorting offices, each with its own list "addresses starting like this go to that office"; no office knows the whole route, and none remembers the letter afterwards. Routing (building the list) is different from forwarding (using it).
2. **The routing table** (recap of Module 1's `ip route`; FRR's `show ip route` introduced). A route is a prefix, a next hop and an interface. Connected routes appear by themselves for every address a router has; static routes are typed in; the default route `0.0.0.0/0` matches everything. FRR's codes: `C` connected, `S` static, `B` BGP, `>` selected, `*` installed in the kernel, `[1/0]` distance and metric.
3. **Longest-prefix match** (resource R1, Practical Networking "Route Precedence", 15 min, its first part; resource R3, the Systems Approach's "IP Forwarding Revisited", 2 min). *Picture in words:* each prefix is a box of addresses; boxes nest (a `/24` inside a `/16` inside `0.0.0.0/0`); the packet goes to the **smallest box that contains its address**. The lesson walks one table of five routes with three addresses, including one that sits in a `/22` but outside the `/24` whose numbers "look closer", and names the three wrong ways: the first match in the list, the route whose numbers look most like the address, and the shortest prefix.
4. **When two routes have the same prefix** (R1, its second part: administrative distance and metric). The route's source decides. FRR's table (connected 0, static 1, eBGP 20, OSPF 110, iBGP 200; 255 means "never install"). **Where the clouds differ** (resources R6 to R8): AWS uses longest prefix, then static over prefix-list over propagated routes, and among propagated, Direct Connect BGP over VPN static over VPN BGP; Azure uses longest prefix, then user-defined over BGP over system routes, with one exception a learner will meet (routes for the virtual network itself and its peerings win even against a longer BGP route); Google puts subnet routes first and won't let a static route overlap one, then most specific, then priority, and spreads equal routes (ECMP) only within one kind.
5. **RIB and FIB.** FRR keeps every candidate (a backup that isn't in use shows `S` without `>*`); the kernel holds only winners; `ip route get ADDRESS` asks the kernel what it would do, which is what packets actually follow.
6. **Static routes in FRR** (resource R5, FRR 8.4's static routing page, 6 min). `router r1`, `configure terminal`, `ip route 10.3.0.0/24 10.0.13.2`, `end`, `write memory`. A **floating static**: the same prefix through another next hop with a higher distance (`... 10.0.12.2 200`), installed only when the primary disappears. A **blackhole** (`ip route 10.0.0.0/8 blackhole`) drops silently; a **reject** route answers with ICMP unreachable. The lesson warns about one trap found in the prototype: FRR's static page shows a "high-distance blackhole" at distance 255, but FRR's own administrative-distance table says 255 is never installed, and the prototype confirmed it (section 5, fact F7). Running against saved configuration: an unsaved change is gone after a reboot.
7. **Static or dynamic.** A static route only knows what its own router can see: if the link loses carrier, the route disappears and a floating backup takes over in milliseconds (finding 6: 74 ms); if the path dies with the link still up, the static route keeps sending traffic into the hole forever. A routing protocol has neighbours tell each other what they can reach, notices a neighbour going quiet, and reroutes (BGP is topic 34; this lesson names OSPF and BGP only as examples). **Where the clouds sit:** a cloud subnet's route table is mostly static entries you write; routes from a VPN or circuit gateway arrive by BGP and are "propagated" into it (AWS's word; Azure calls them BGP routes, Google dynamic routes). Choosing: static for a stub with one way out, a handful of routes, or a route that must never move; dynamic for redundant paths and prefixes that change.
8. **The return path** (resource R10, optional, Azure's asymmetric-routing page). The reply is a new packet with its own destination; every router on the way back looks it up afresh. *Picture in words:* the outbound trip and the return trip drawn as two separate arrows that may use different roads. When they differ, a **stateful firewall** on only one road sees half a conversation: it saw the SYN, never the SYN-ACK, so the client's next packet looks invalid and is dropped. Ping still works (each echo is its own little exchange the firewall allows), which is what makes the fault confusing. **Strict reverse-path filtering** (resource R9, the kernel's `rp_filter`) drops a packet arriving on an interface the router wouldn't use to reach its source. Fixes: make the routes symmetric, or source-NAT at the firewall so replies must come back through it (topic 27 teaches NAT and its cost: the server no longer sees the client's address).
9. **How packets vanish, and what shows it** (the lesson's own table, built from the prototype's captured evidence):

   | Cause | What the sender sees | What shows it |
   | --- | --- | --- |
   | No route | `!N` at the last hop that answers; `Network is unreachable` | `ip route get` on that router |
   | Blackhole route | silence | `ip route get` answers `Invalid argument`; `show ip route` says `blackhole` |
   | Reject route | `!H` | `show ip route` says `ICMP unreachable` |
   | Forwarding off | silence from the first hop on | `IpInAddrErrors` climbing in `nstat`; `sysctl net.ipv4.ip_forward` is 0 |
   | Missing return route | requests time out; nothing comes back | tcpdump at the far end: requests arrive, replies leave toward nowhere or never leave |
   | Loop | traceroute alternates two addresses; ping says `Time to live exceeded` | `ip route get` on the two routers points at each other |

   The method: traceroute from the source to find the last hop that answers; `ip route get` on that router and the next; tcpdump on the interfaces either side to see where packets stop; then read the config. traceroute can show `*` for a hop that works (routers rate-limit ICMP).
10. **A VM as a router in the cloud** (resources R11). The cloud drops traffic a VM sends or receives for addresses not its own unless told otherwise: AWS's source/destination check must be stopped; Azure needs "Enable IP forwarding" on each network interface and forwarding in the operating system; Google needs `canIpForward` on the instance and forwarding in the operating system. A missing flag is a black hole with no log on the VM.
11. **ECMP, in one paragraph.** Two equal routes are both installed and flows are spread by a hash; if one path is dead, some connections fail and others don't, which looks intermittent (finding 12). Checkpoint 3's designer may use this.

**Read now, in this order:** R1, R2, R3 (12 min) and the cloud section the lesson points to in R6 to R8 (10 min). R4, R9, R10 and R11 are "more resources".

## 7. Practice ladder

Labs are systemd labs on the shared pattern unless marked "plain". Recall items whose files come from `CAPTURES.md` are labelled captured; the rest constructed.

**The triangle** (used by the worked example and the fill-in; built in `prototypes/frr/routing/`): office `10.1.0.10/24` behind r1 (`lan` 10.1.0.1), store `10.2.0.10/24` behind r2, dc `10.3.0.10/24` behind r3; links r1–r2 `10.0.12.0/30`, r1–r3 `10.0.13.0/30`, r2–r3 `10.0.23.0/30`, each interface named after the router at the other end. The dc host runs a small web server on port 80.

1. **`example-follow-the-route`** (worked example, systemd, the triangle with empty router configs). Labelled steps:
   1. *See the gap.* `on office traceroute -n 10.3.0.10` stops at hop 1 with `!N`; `router r1` then `show ip route`: connected routes only; `ip -n r1 route get 10.3.0.10`: `Network is unreachable`.
   2. *Add a route.* On r1: `configure terminal`, `ip route 10.3.0.0/24 10.0.13.2`, `end`. traceroute now shows r1 then nothing.
   3. *The way back.* `on dc tcpdump -nn -i eth0 icmp` in a second shell while the office pings: requests arrive, replies leave for r3, which has no route to the office. Add `ip route 10.1.0.0/24 10.0.13.1` on r3. Ping works.
   4. *Longest prefix, live.* On r1 add `ip route 10.3.0.128/25 10.0.12.2`; `ip -n r1 route get 10.3.0.10` and `... 10.3.0.200` give different next hops; remove it again (`no ip route ...`).
   5. *All six routes and their backups.* Primary routes over the direct links on all three routers, and a floating backup (distance 200) through the third router for each. `show ip route` shows each backup as `S` without `>*`.
   6. *A loud failure.* `lab-link r1 r3 down`: within a second the office reaches the dc through r2 (`traceroute` shows 10.0.12.2); `show ip route 10.3.0.0/24` on r1 shows the distance-200 route selected. `lab-link r1 r3 up`.
   7. *A silent failure.* `lab-link r1 r3 silent`: the link stays up, r1 keeps its route, the office's ping to the dc fails forever: static routes can't see this. `lab-link r1 r3 restore`.
   8. *Save.* `write memory` on all three routers.
   Checks: office reaches dc and store (R1); each pair's primary route uses the direct link (`ip route get` on r1, r2, r3); a distance-200 backup for each remote site exists on each router and isn't selected (`show ip route json`); saved on all three (R2); no kernel-only routes (R3). Wrong fixes: `not-saved.sh`, `no-return-route.sh` (r3 has no route back: the office's ping fails), `kernel-route.sh` (r1's routes added with `on r1 ip route add`).
2. **`lpm-kernel-table`** (mcq, `longest-prefix-match`). Table (as `ip route` prints it): `default via 192.0.2.1 dev wan`, `10.20.0.0/16 via 10.0.0.2 dev core`, `10.20.4.0/22 via 10.0.0.6 dev branch`, `10.20.5.0/24 via 10.0.0.10 dev lab`, `10.20.5.128/25 via 10.0.0.14 dev dmz`. "A packet to 10.20.5.9: which next hop does the kernel send it to?" Choices (each written as a full sentence of the same shape): "10.0.0.10, through the /24 route for 10.20.5.0" (right); "10.0.0.14, through the /25 route for 10.20.5.128, the longest prefix in the table"; "10.0.0.6, through the /22 route, because it is the first specific route that contains the address"; "192.0.2.1, through the default route, because no route lists 10.20.5.9 itself". Explanation: the /25 covers .128 to .255 only; the /24 and /22 both contain .9 and the /24 is longer.
3. **`lpm-not-in-the-longest`** (mcq, `longest-prefix-match`). Same table, packet to 10.20.7.200. Right: the /22 via 10.0.0.6 (10.20.4.0 to 10.20.7.255). Wrong: the /24 (whose third number "looks closest" but covers only 10.20.5.x), the /16, the default. The explanation shows the /22's range worked out with `csa.net.cidr`'s method.
4. **`lpm-three-addresses`** (predict_shell, `longest-prefix-match`). Files: `routes.txt` (seven routes in `ip route` form, nested /8, /16, /20, /24, a `blackhole` /24 and a default) and `next-hop`, the reference solution of `write-next-hop` (item 22) copied verbatim. Command: `bash next-hop routes.txt 10.1.2.3 10.1.130.7 172.16.0.1`. The prompt says what the script does ("prints, for each address, the route the kernel would use") and the format of its output; the learner types the three lines. The writer chooses addresses so that one falls in the blackhole, one is caught only by a /20 and not the /24 nearer in value, one by the default only. The validator proves the output in real bash.
5. **`rib-selected-routes`** (predict_shell, `static-routes`, captured). File: the seven `show ip route` lines from `CAPTURES.md` (routing prototype, r1 with floating statics). Command: `awk '$1 == "S>*" {sub(",", "", $5); print $2, $5}' routes.txt; grep -c '^S ' routes.txt`. Output: the two selected static routes with their next hops, then `2` (backups). Explanation: `S` with `>*` is selected and in the kernel; `[200/0]` routes wait.
6. **`mcq-distance-tie`** (mcq, `longest-prefix-match`). An FRR router has `S 10.50.0.0/16 [1/0] via 10.0.0.2` and `B 10.50.0.0/16 [20/0] via 192.0.2.6`. Which does the kernel use? Right: "The static route, because its distance of 1 is lower than eBGP's 20". Wrong: "The BGP route, because a route learned from a neighbour is newer than one typed in"; "Both, sharing the traffic, because the two routes have the same prefix length"; "The BGP route, because routes with a next hop on another network are preferred". (Equal lengths: each about 75 characters.)
7. **`mcq-floating-static`** (mcq, `static-routes`). r1 has `ip route 10.3.0.0/24 10.0.13.2` and `ip route 10.3.0.0/24 10.0.12.2 200`. What does the second line do while the r1–r3 link is up? Right: "Nothing yet: FRR keeps it as a candidate and installs it only if the first route goes". Wrong: "It shares the traffic with the first route, because both lead to the same network"; "It replaces the first route, because the line typed later wins in FRR"; "It sends one packet in two hundred through r2, to keep the backup path tested".
8. **`mcq-distance-255`** (mcq, `static-routes`). A colleague's backup route is `ip route 10.3.0.0/24 10.0.12.2 255`, "so it's the least preferred". The primary link fails. Right: "Nothing takes over: a route at distance 255 is never installed, so 10.3.0.0/24 has no route". Wrong: "The backup takes over within a second, the same as at any distance above 1"; "The backup takes over once the primary's hold timer of three minutes has run out"; "FRR refuses the line when it's typed, so the colleague would have seen an error". ### Explain (20 minutes)

**Prompt.** A colleague says: "Routing is simple: each router knows the whole path to every network, and if a link breaks the network sorts itself out." Explain, in your own words: how a router decides where to send one packet, including what happens when several routes match and when two routes have the same prefix; why the reply is a separate decision, and what goes wrong when it takes a different path; when static routes are enough and when you'd want a routing protocol, including what each does when a link fails without going down; how you'd find where packets are disappearing, and two different causes you might find; and one way a cloud's route table chooses differently from a Linux router.

**Rubric.**

| id | Required | Description |
| --- | --- | --- |
| `lpm` | yes | Each router looks up only the destination; the longest matching prefix wins, the default route only when nothing else matches; for equal prefixes the route's source decides (administrative distance: connected before static before eBGP), not the order of the lines |
| `return-path` | yes | Each router decides alone and knows only the next hop; the reply is routed afresh and may take another path; a stateful firewall that sees only one direction drops the connection (ping can still work), and strict reverse-path filtering drops replies on the "wrong" interface; fix with symmetric routes or source NAT at the firewall |
| `static-dynamic` | yes | Static routes suit a stub or a few routes and need a floating backup for failover; they react only to failures their own router sees (carrier lost), not a path that dies silently; a routing protocol exchanges reachability, notices a silent neighbour and reroutes, at the cost of complexity |
| `black-hole-hunt` | yes | A method: traceroute from the source, then `ip route get` (or the table) on the last router that answers and the next, tcpdump either side; at least two causes told apart by their evidence (no route: unreachable; blackhole or forwarding off: silence; missing return route: requests arrive, replies don't; loop: TTL exceeded and alternating hops) |
| `cloud-tables` | yes | One correct cloud difference: AWS prefers static over propagated routes for the same prefix; Azure prefers UDR, then BGP, then system routes, but keeps the VNet's own routes even against a longer BGP route; Google uses subnet routes first and lets no static route overlap them; or a VM must be allowed to forward (source/destination check, IP forwarding, canIpForward) |
| `floating` | no | A floating static route at a higher distance, and the trap that distance 255 is never installed |
