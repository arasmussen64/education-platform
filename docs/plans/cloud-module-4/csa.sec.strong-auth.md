## 1. What the learner will be able to do

1. Say which MFA methods a phishing site can defeat and why: a password, a one-time code, a push and a text message can all be typed into or approved for a site that relays them to the real one in real time, so the attacker gets the session. A security key or passkey (FIDO2/WebAuthn) signs a challenge that the browser binds to the real site's name and the server checks, so a relay gets nothing it can use. Place each method on NIST SP 800-63B-4's levels (synced passkeys at AAL2, device-bound keys at AAL3).
2. Require a strength of authentication for a role, not just offer it: configure an identity provider so admins can only finish signing in with a security key while staff may use an app code, read which methods a sign-in used from the token's `amr` claim, and explain why adding passkeys does nothing while a phishable method still lets an admin in.
3. Write conditional-access policies in Microsoft Entra's own format (assignments, conditions on sign-in risk, device compliance, location and client app, grant controls) and predict the outcome of any sign-in: every applicable policy must be satisfied, a block wins, an exclusion beats an inclusion, a report-only policy is reported and never enforced. Know what each costs (P1, P2) and what the free tier gives (security defaults).
4. Keep a break-glass path that doesn't weaken anything: two cloud-only emergency accounts with their own phishing-resistant keys (different from the admins' daily method), excluded only from the policies that block or restrict, through one dedicated group nobody else is in, with an alert on every use and a drill at least every 90 days; prove with checks that the accounts get in when the normal path fails and that nobody else gained a way round the policies.
5. Roll a policy out without locking anyone out: report-only first, What If for the cases you can't wait for, an excluded admin, and the numbers (how long one code is valid, the odds of guessing one, how many sign-ins a report-only week says you'd block).

**The six-month core.**

- **Phishing-resistant means bound to the real site.** The browser puts the site's real origin into what the key signs, and the key only answers for the site it was registered with; the server checks both. Passwords, one-time codes, push approvals and text messages carry no such binding, so a relay site collects them and the attacker logs in, often by stealing the session cookie. FIDO2 security keys, passkeys and smart-card certificates are phishing-resistant; synced passkeys reach AAL2, device-bound keys AAL3.
- **Enforce the strength, don't offer it.** While any phishable method still lets an admin in, the phisher picks that one.
- **Conditional access is if-then:** if this user (or group, or role), for this app, under these conditions (sign-in risk, device, location, client), then block, or grant only with these controls (MFA, an authentication strength, a compliant device). Every policy that applies must be satisfied; any block wins; an exclusion beats an inclusion; report-only and What If come before enforcement. Entra needs P1 for it and P2 for risk; without them, security defaults.
- **Break glass:** two cloud-only accounts, passkeys kept in safes and different from daily admin methods, excluded through one dedicated group from blocking and restricting policies only, an alert on every sign-in, a drill at least every 90 days. Azure's mandatory MFA applies to them too.

## 4. Lesson plan

About 2,300 words (18 minutes).

1. **A phishing site that beats MFA (lesson only, then CISA's fact sheet).** The story the worked example then runs for real: an email sends Bob to `login.shop-help.test`, which shows the shop's real sign-in page because it fetches it live from `login.shop.test` and passes Bob's answers back; it has a valid certificate (Module 3: a CA vouches for the name, not for the intent). Bob types his password and his app code; the relay forwards both within the 30 seconds the code lasts, keeps the session cookie the real site hands back, and the attacker uses the cookie. MFA happened; it didn't help. CISA's "Implementing Phishing-Resistant MFA" (October 2022, 5 pages, about 11 minutes, the main resource): its table from strongest to weakest, FIDO/WebAuthn and PKI at the top, then app codes and push with number matching ("vulnerable to phishing"), then push without number matching (push bombing), then SMS and voice (phishing, SS7, SIM swap).
2. **Why a security key can't be relayed (webauthn.guide's "Registration" and "Authentication", then the lesson).** The picture in words: registering a key is like the key and the shop agreeing a secret handshake *for this shop's name only*. At sign-in the shop sends a fresh challenge; the browser wraps it with the address it is really on and the key signs both. On the phishing site the browser is on `login.shop-help.test`: it refuses to ask the key for `login.shop.test` (the RP ID must be the page's own name or a parent of it), and the key has no handshake for `login.shop-help.test`. Even a broken browser that lied wouldn't help: the shop checks the origin in what was signed (tried: Keycloak refused with `webauthn-error-bad-origin`). There's nothing to type, so nothing to steal. NIST SP 800-63B-4 §3.2.5 calls the two halves **channel binding** and **verifier name binding**; read that section and the AAL table (§2.2 to §2.3, about 8 minutes): AAL2 "SHALL offer at least one phishing-resistant authentication option", AAL3 requires a phishing-resistant authenticator with a non-exportable key, and **syncable authenticators** (passkeys copied between your devices through a cloud account) "SHALL NOT be used at AAL3". Passkeys in one paragraph (passkeys.dev's "What are passkeys?"): a WebAuthn credential that can replace the password; synced ones are convenient and recoverable, device-bound ones (a hardware security key) can't be copied. One paragraph on **registration**: the moment a new key is added is the weak moment, because something weaker has to prove it's you; Entra's Temporary Access Pass exists for that (one sentence), and the lab shows a new admin able to register a key with a password alone.
3. **Offering isn't requiring (Keycloak's "Conditions in conditional flows", then the lesson).** In an identity provider, a **flow** decides what a sign-in must pass. The worked example's flow: password, then, *if the user has the admin role*, a security key `REQUIRED`; otherwise an app code. Two ways it goes wrong, both tried: the key and the code side by side as `ALTERNATIVE` (the phisher picks the code), and a condition naming a role that doesn't exist (`admins` for `admin`), which skips the whole sub-flow and lets admins in with a password alone. The token tells you what happened: `amr` lists the methods (`["pwd","hwk"]`), which an app or a check can read.
4. **Conditional access (Microsoft's "What is Conditional Access?" and "Building a Conditional Access policy", 14 minutes).** "If-then statements": if a user wants this app under these conditions, then they must do this. The lesson draws the evaluation as a two-pass checklist, from the second page: first **which policies apply** (every assignment of a policy must match: users or groups or roles, the app, the conditions; an exclusion beats an inclusion), then **what they demand**: any block ends it; otherwise every applicable policy's controls must be met, each policy's own controls ANDed unless it says "one of". Signals: user, app, IP location, device (compliant means Intune says so; the device proves who it is with a certificate, as Module 3's client certificates did), real-time **sign-in risk** and calculated **user risk** (ID Protection, which needs P2). The policy's JSON in Microsoft Graph's own shape, which the labs use (`conditions.users.includeRoles`, `excludeGroups`, `applications.includeApplications`, `signInRiskLevels`, `clientAppTypes`, `grantControls.operator` and `builtInControls`, `state`). Authentication strengths (Microsoft's page, its table, 5 minutes): MFA, passwordless MFA, and phishing-resistant MFA (Windows Hello for Business or platform credential, FIDO2 security key, certificate-based multifactor).
5. **What it costs and the free path (Microsoft's pages; the lesson's box).** Conditional Access needs Entra ID P1 ($7.00 per user per month, paid yearly, on Microsoft's price page on 2026-11-12); risk-based policies need P2 ($10.00). Without either: **security defaults**, free, on or off: everyone registers for MFA (Authenticator with number matching, or another app's codes), admins always do MFA, legacy authentication is blocked. The owner's $150 Azure credit is for Azure resources; P1 is a licence bought through Microsoft 365's commerce, so the course doesn't assume it (section 12). Then the other two clouds in one table, worded from their pages:

   | | AWS | Azure | Google Cloud |
   | --- | --- | --- | --- |
   | Phishing-resistant MFA for people | IAM: passkeys and security keys ("We recommend that you use phishing-resistant MFA such as passkeys and security keys whenever possible"); MFA enforced for every root user; up to 8 MFA devices; SMS MFA no longer offered | Entra: passkeys (FIDO2), Windows Hello for Business, certificate-based authentication; authentication strengths require them per app | 2-Step Verification with security keys among the methods; mandatory for Google Cloud console users (personal accounts from 2025-05-12, non-SSO Cloud Identity from 2026-10-20) |
   | Conditions on device and context | no per-sign-in policy engine in IAM; IAM Identity Center's MFA settings, and condition keys such as `aws:MultiFactorAuthPresent` in policies; Verified Access for apps | Conditional Access (P1), risk (P2) | Access Context Manager access levels (IP, device attributes through Endpoint Verification, region), enforced by IAP, VPC Service Controls and IAM Conditions; device-type levels need a paid enterprise subscription |
   | Mandatory MFA for administration | root users | Azure portal and admin centers (from October 2024), Azure CLI, PowerShell, IaC and REST create/update/delete (from 2025-10-01); no opt-out, only postponement | the console requirement above |

6. **Break glass (Microsoft's "Manage emergency access accounts", its "Create" steps, "Conditional Access considerations" and "Security guardrails summary", 10 minutes).** Why they exist (federation down, the MFA service or phone network down, the last admin gone, PIM approvals with no approver). The design as a checklist, from the page. Then the part a beginner needs spelled out: "excluded from conditional access" doesn't mean "unprotected". The account's own credential is a passkey only, kept in a safe; the exclusion is through **one** group whose only members are the emergency accounts, so a later edit can't slip a normal admin in; every sign-in raises an alert someone reads; and the drill proves both that it gets in and that nothing else does. Azure's mandatory MFA applies to them too, which is why the method is a passkey.
7. **Rolling out without locking yourself out (report-only and What If pages, 6 minutes).** Report-only evaluates and logs (`Report-only: Success`, `Failure`, `User action required`, `Not applied`) but never prompts or blocks; What If evaluates one imagined sign-in, including report-only policies, and for each policy that doesn't apply reports "the first condition that wasn't satisfied". Microsoft's lockout warning: exclude at least one admin from an all-users policy until it's proven. The numbers: a TOTP code lasts 30 seconds, and servers usually accept a neighbouring step for clock drift (Keycloak's default look-ahead window is 1, tried; the writer confirms in Keycloak's OTP policy documentation whether it counts both directions before the lesson says "either side"), so a code can work for 60 to 90 seconds, long enough for any relay; six digits are a million codes, so five guesses before lockout is 1 in 200,000, which is why the risk is relay, not guessing; and Keycloak's brute-force detection is **off** by default (tried), which the build turns on.
8. **Recap:** the six-month core.

## 7. Practice ladder

Four labs run an identity provider (the identity-lab base, section 10) and one is a plain lab on the policy-lab base (topic 40's brief, A1). Identity labs: `runtime: lab`, `lab: { init: systemd, restart_trial: true }`. Their machines, on the network-lab base's model: **`idp`** (Keycloak, `keycloak@idp`, realm `shop`, serving `https://login.shop.test` with a certificate from the lab's CA), **`office`** (an employee's laptop: `signin`, the scripted browser with a software security key, keys and app secrets as files in each person's folder), and where a lab needs them **`phish`** (the relay at `https://login.shop-help.test`, with a certificate from the same CA, scenery) and **`attacker`** (scenery, runs `attacker-replay`). The realm's configuration is one file on `idp`, `/etc/keycloak/realms/shop.json`; `sudo realm-apply shop` loads it into the running server, `realm-saved shop` says whether the running server equals the file, and `kc-flows shop` draws the sign-in flows as a tree. Conditional-access policies are JSON files in `/etc/shop/ca/`, one per policy, in Microsoft Graph's shape, and **`ca-whatif`** evaluates a sign-in against them, reading users, groups and roles from the realm file ("modelled on Entra's Conditional Access as its documentation describes it", said on every page that shows it).

Security keys and app secrets are **made at image build time** (`make-key`, tried), never committed; the realm file in the repository holds no key material, and the image's build step adds the public halves.

### 7.1 `example-phish-two-ways` (worked example, identity lab), skills `phishing-resistance`, `authentication-strength`, `conditional-access`

Labelled steps (the "Before your first identity lab" note at the top is the identity base's):

1. **Bob signs in.** `on office signin https://login.shop.test/realms/shop bob` (his password and app secret are in his folder; the tool says each step: `password`, `typed the authenticator app's code`, `signed in: {"amr": ["pwd", "otp"]}`).
2. **Bob clicks the link in the email.** The same command with `https://login.shop-help.test/...`: it works, and Bob saw nothing odd (valid certificate, the shop's own page). `on phish tail /var/log/relay.log`: his password, his code and the session cookie the real site gave him. `on attacker attacker-replay`: `signed in as bob without a password or a code`.
3. **Alice signs in with her security key.** `amr: ["pwd", "hwk"]`.
4. **Alice clicks the same link.** `browser: refused: the page on login.shop-help.test asked for a key for login.shop.test`. Nothing reached the relay but her password, which alone gets nobody in.
5. **What if the browser were fooled?** `signin ... --report-origin https://login.shop-help.test` against the real site: refused; `journalctl -u keycloak@idp | grep bad-origin` shows Keycloak's own check.
6. **Offering isn't requiring.** `on office signin ... bob --register-key` adds a key for Bob; then repeat step 2: the relay still wins, because Bob's app code still lets him in. `kc-flows shop` shows why: for staff, key and code are alternatives.
7. **The conditional-access view.** `cat /etc/shop/ca/20-admins-phishing-resistant.json`; `ca-whatif alice admin-app methods=pwd,otp` prints `block (can't sign in with phishingResistant)` and the applied policies; with `methods=pwd,hwk`, `allow after phishingResistant`; `ca-whatif bob admin-app risk=high` shows the high-risk block (tried with the prototype's evaluator, output as in section 5's prototype runs).

Checks: `bob-was-relayed` (the relay log holds a captured session from this boot), `alice-not-relayed`, `bob-has-a-key`, `whatif-ran` (light; a worked example opens no follow-ups). Wrong fix: one (`skipped-the-key.sh`). The learner's own key registration in step 6 is kept by the file database across a restart (section 10, N2), so the restart trial passes. Minutes: 30.

### 8.3 Explain

**Prompt (draft):** "Your company's admins use passwords and an authenticator app, and an attacker has just phished one of them anyway. Explain, in your own words: how a phishing site gets past one-time codes, and what makes a security key or passkey different; how you'd make admins use keys without leaving the old way open; the conditional-access policies you'd write for admins, for everyone, and for a payments app, how they combine and what they'd cost on Entra; and how you'd keep an emergency way in that doesn't become the weak spot, and prove it."

**Rubric:** `relay` (required: a relay passes the password and code to the real site in time, or keeps the session cookie); `origin-binding` (required: the browser binds the key's signature to the real site and the key answers only for the site it registered with; the server checks; nothing to type means nothing to steal); `require-not-offer` (required: remove the phishable path for admins, e.g. a strength or a flow that only a key can finish; first registration needs a strong proof); `ca-evaluation` (required: every applicable policy must be satisfied, block wins, exclusions beat inclusions, report-only and What If first; P1, risk P2, security defaults otherwise); `break-glass` (required: two cloud-only accounts, passkeys different from daily methods, excluded only via a dedicated group from blocking or restricting policies, alerts on every use, drills every 90 days, and a test that others gained no way round); `clouds-differ` (optional: AWS root MFA and passkeys, Google's mandatory 2SV and access levels).

## 11. Cost and time

**Money: none.** Every lab is local. Entra's Conditional Access needs a P1 licence the course doesn't assume (section 12, question 1).

## 12. Open questions, each with a recommendation

1. **Entra Conditional Access for real?** It needs P1; the free path is security defaults, which can't be customised. A free Entra tenant with P1 and P2 exists for those who qualify: the Microsoft 365 Developer Program's E5 sandbox (G19), whose qualifying paths include a Visual Studio Professional or Enterprise subscription. A $150 monthly Azure credit is what Visual Studio Enterprise gives, but the repository doesn't record where the owner's credit comes from. **Recommendation:** the proofs are local (Keycloak for the sign-in, `ca-whatif` modelled on Entra's documented rules). Add one owner-queue item, not blocking anything: "If your Azure credit comes with a Visual Studio subscription, you may qualify for a free Microsoft 365 E5 developer tenant (it needs a billing account linked, which it says costs nothing). With it, an optional page could walk you through the same five policies in report-only in real Entra, with the What If tool." Setting up that tenant is the owner's, and nothing in Module 4 waits for it. Don't use the P2 trial: no Microsoft page read states its terms, and a forum report says it bills if not cancelled.
2. **Keycloak or another identity provider?** The identity-base designer decides. **Recommendation:** whichever is chosen must meet N1 to N11; Keycloak met every need tried here, including the two this topic can't do without (WebAuthn with a software key, and conditional flows by role).
3. **Device compliance and sign-in risk in the identity labs, or only in `ca-whatif`?** A real enforcing gate (an app that reads the token's `amr`, a device certificate and a risk feed, and applies the policy files) would make the build's conditional-access part live. **Recommendation:** not now. `ca-whatif` evaluates the learner's own policy files on generated sign-ins, which tests the judgement the spec names, at a fraction of the platform work; the lesson says plainly that it is a model. Revisit for Module 10's `csa.iam.azure-rbac` or topic 47 (zero trust), whose identity-aware proxy is a natural place for a gate.
4. **Realm file with `realm-apply`, or live changes through Keycloak's admin CLI?** Live changes persist in the file database, so the restart trial wouldn't catch a live-only fix. **Recommendation:** the file is the configuration (as `nginx.conf` and `frr.conf` were in Module 3), `realm-apply` loads it, `realm-saved` is the check that reads the lasting place, and a `wrong/live-only.sh` proves it.
5. **HTTPS in the identity labs.** WebAuthn needs a secure context; the prototype used HTTP with a cookie workaround. **Recommendation:** HTTPS from the lab's CA (Module 3 taught it), which also makes the worked example's best lesson real: the phishing site's padlock is valid too. Try it first in the identity base.
6. **A real-cloud lab for passkeys on AWS (free)?** AWS IAM supports passkeys for IAM users at no charge, but registering one needs a real authenticator and the AWS console, which `signin` can't drive, and Claude never creates anything in the owner's accounts. **Recommendation:** no; Module 10 sets up the owner's real admin sign-ins with keys, where it belongs.
