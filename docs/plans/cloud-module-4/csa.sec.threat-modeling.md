# Topic 39: `csa.sec.threat-modeling`, Threat modeling

Designer's brief, 2026-11-12 (designer key `threat-modeling-zero-trust`; this file and [csa.sec.zero-trust.md](csa.sec.zero-trust.md)). Prototypes are in `prototypes/tm-zt/`: `tmlab/` (the checker `tm-check`, the build's design, reference and 16 wrong models, the debug's model and fix), `tmlab/write/` (the write lab's generator, reference script and six wrong scripts, fuzzed 200 times), `tmbuild/` (the build as a plain lab, kept its contract with the restart trial under `tools/contract.py`, a stand-in for `labcheck test` because the repository is read-only here) and `contract-tm-build2.log`.

## 1. What the learner will be able to do

- Say what is being built before saying what can go wrong: draw a system as a **data-flow diagram** (external entities, processes, data stores, data flows) in **trust zones**, and mark every flow that crosses a **trust boundary**.
- Run **STRIDE** over the flows that cross a boundary, element by element, and write each threat as a sentence that names who can do what and what it leads to (AWS Threat Composer's grammar, shortened).
- **Rank** threats by a stated method (likelihood times impact on the design's own 1-to-3 scales; OWASP's 0-to-9 averaging as the longer version), and say what such a ranking leaves out.
- Choose a **response** for each risk (mitigate, eliminate, transfer, accept), and name a control whose kind actually answers the threat's STRIDE letter.
- Draw an **attack tree** for the worst risk (AND and OR nodes) and work out the attacker's cheapest path, and what a countermeasure does to it.
- Use **MITRE ATT&CK**'s cloud matrices (IaaS, Identity Provider, SaaS, Office Suite) to name the technique an attacker would use, citing the version, and bring **abuse cases** (attacker stories with an acceptance test) into a design review.

**The six-month core.** Four questions in order: what are we working on, what can go wrong, what are we going to do about it, did we do a good enough job. Draw the flows and the zones first; threats cluster where trust changes. STRIDE is a checklist of six properties (authentication, integrity, non-repudiation, confidentiality, availability, authorization), and a control only counts if it restores the property the threat breaks (encryption doesn't stop spoofing). Rank with a stated method and know it is ordinal and blind to cost. An attack tree's OR takes the cheapest child, AND adds them up. ATT&CK describes what attackers have done (look it up, cite the version); STRIDE prompts what could go wrong in a design.

## 4. Lesson plan

The lesson supplies what no single free resource does for a beginner: one worked system drawn as text and as a picture-in-words, the STRIDE-per-element table and the control-kind table side by side, the line format the labs use, and the clouds' part (shared responsibility, the ATT&CK cloud platforms, the providers' own threat-modeling tools).

1. **Why model at all, and the four questions** (T2, the Threat Modeling Manifesto, 9 min; T1's "Overview"). Design flaws are cheapest to fix before the code exists; the four questions in order. *What the lesson adds:* the four questions as the four parts of every lab file (diagram; threats; controls; checks that it holds), so the structure is visible from the first lab.
2. **What are we working on: the DFD** (T1, "System Modeling"; T3, Microsoft Learn's DFD module, optional). *Picture in words:* a booking site drawn as boxes in rows, the internet on the left, the company's cloud network in the middle, the cloud's storage service on the right; arrows from whoever starts the conversation; dashed lines where the zone changes. The four kinds with one test each: a process **changes or decides** something; a data store **keeps** something until asked; an external entity is **outside your control** (a person, a partner's system, a SaaS); a data flow **moves** data and is drawn from the side that starts it. A message queue is a store; a scheduled job is a process; a payment provider's API is an external entity.
3. **Trust boundaries.** A boundary is where the level of trust changes: between the internet and your network, between you and a partner, between your account and a provider-managed service, between a public subnet and a private one. *Where the clouds differ:* each provider's shared responsibility model puts the boundary in a different place for each service kind (a VM: you own the OS; a managed database: the provider does), so "the cloud" is not one zone (S1, S2, S3).
4. **What can go wrong: STRIDE** (T1, "Threat Identification"; T4, Microsoft Learn's framework module, the six category units, about 20 min). The six letters, the property each breaks and the usual controls (the table in section 5, F4 and F5). **STRIDE per element**, Microsoft's mapping: external entity S R; process S T R I D E; data store T R I D; data flow T I D. *The lesson's rule for its labs:* every flow that crosses a boundary gets all six letters reviewed as an interaction (the flow and the element it enters), and each review is a threat or a `none` line with its reason. Writing a threat: AWS Threat Composer's grammar (T7), shortened to "A/An WHO can DO WHAT, leading to WHAT": "An attacker on the internet can post fake delivery reports to /hooks/sms, and a fake STOP cancels patients' appointments".
5. **The lab format, one record a line** (no resource: the lesson's own). `zone`, `element`, `flow`, `threat`, `none`, `control`, `accept`, `top`, `attack`, `goal`/`node`/`leaf`/`cheapest`, `abuse`/`test`, each first word saying what the line is (section 7's format table). It reads like a diagram in text and awk can read it, which the write lab does. Real teams draw in OWASP Threat Dragon (T8) or Microsoft's Threat Modeling Tool, or keep models as code (OWASP pytm, Threagile, Threat Composer's JSON); the lesson names them in one paragraph and says the thinking transfers, the format doesn't.
6. **Ranking** (T1, "Response and Mitigations"; T5, OWASP Risk Rating Methodology, the "Step 4" and "Determining severity" parts, 8 min). Risk = likelihood x impact on stated scales; the lab designs print their scales (3: anyone on the internet can try it; 2: needs an account or a foothold; 1: needs an insider with admin rights), so ratings are decisions a reader can check. OWASP's longer method: eight likelihood factors and eight impact factors scored 0 to 9 and averaged, LOW below 3, MEDIUM below 6, HIGH from 6, then a severity table. *What the lesson adds:* why the numbers are ordinal (a 3 x 2 and a 2 x 3 are both 6 and aren't the same risk), and that the method ignores the effort to fix (T1 says so).
7. **What are we going to do about it** (T1, the four responses, from Shostack). Mitigate, eliminate (remove the feature), transfer (to a party that carries it: insurance, a provider; it doesn't lower likelihood or impact), accept (written down, with a reason, for a risk below the line). *The table the lesson supplies:* each letter beside the control kinds that answer it (F5), and the classic mismatch on purpose: "we use TLS" answers I and T on the wire, never S at the login.
8. **Attack trees** (T6, Schneier's "Attack Trees", 11 min). Root = the attacker's goal; OR children are alternatives, AND children are steps all needed; leaves carry a cost (or "possible/impossible", or a probability). *Picture in words:* the safe example as an indented outline. The cheapest path: OR takes its cheapest child, AND adds its children. A countermeasure that raises one leaf's cost may move the cheapest path elsewhere and help less than it seemed (Schneier's bribe example). Probabilities: AND multiplies independent steps; OR is 1 minus the product of the failures (the lesson states the independence assumption).
9. **MITRE ATT&CK for cloud** (T9, ATT&CK's "Get Started", 6 min; T10, the IaaS matrix, skimmed, 6 min). Tactics are the why (Initial Access, Credential Access, Exfiltration ...; 15 in Enterprise in v20.1), techniques the how, with IDs (`T1078.004 Valid Accounts: Cloud Accounts`). The cloud matrices: Office Suite, Identity Provider, SaaS, IaaS. *What the lesson adds:* ATT&CK is what attackers have done, gathered from real incidents, used to check detections and to name threats precisely; STRIDE is a design-time prompt. And IDs move: v19 (April 2026) split Defense Evasion into Stealth and Defense Impairment, and `T1562.008` (disable cloud logs) now redirects to `T1685.002`, so a model names the ATT&CK version it used.
10. **Abuse cases in design reviews** (T11, OWASP's Abuse Case Cheat Sheet, optional). An abuse case is a user story turned round: "As an attacker, I send STOP for other patients' numbers so that their appointments are cancelled", with an acceptance test the team can run ("a delivery report without a valid signature is refused with 401 and changes nothing"). *Honest note the lesson carries:* OWASP archived the cheat sheet because "abuse cases are rarely used in practice"; the lesson presents them as the bridge from a threat model into a backlog and a test, which is where design reviews usually lose threats.
11. **Did we do a good enough job.** A model is a living file: re-run it when the design changes (a new partner, a new flow), check every high risk has a control that fits and a test that shows it, and that the top line still holds. *Where the clouds differ:* AWS publishes Threat Composer (open source) and a threat-modeling workshop; Microsoft ships the free Threat Modeling Tool (Windows) and the Learn path; Google publishes its "shared fate" framing rather than a tool (S3). None of them is needed for the labs.

**Read now, in this order:** T1 (15 min, the main resource), T2 (9), T4's six category units (20), T5's two parts (8), T6 (11), T9 and T10 (12). T3, T7, T8 and T11 are "more resources".

## 7. The lab format, the checker, and the labs' shape

**Why not Threat Dragon's JSON, pytm or Threagile.** Threat Dragon is a GUI; its JSON stores diagram coordinates, and a lab container has no browser. pytm models are Python programs, and the learner may not know Python before Module 6. Threagile's YAML is long (technical assets with a dozen fields each) and its tool finds the risks itself, which is the skill being taught; its last release is from July 2024. A line format of the lab's own reads like the diagram in text, is checkable by a short Python program in the image, and is readable by awk, which makes the write lab possible without Python (house rule 7).

**The format** (`tm-check`'s docstring is the specification; every lab and Checkpoint 4 part 1, if the critic agrees, uses it):

| Line | Shape | Rule the checker applies |
| --- | --- | --- |
| `zone` | `zone NAME words` | a trust zone |
| `element` | `element ID external\|process\|store ZONE words` | kind is one of three; zone must exist |
| `flow` | `flow ID FROM TO words` | both ends are elements; drawn from the side that starts |
| `threat` | `threat ID FLOW LETTER L I RISK words` | letter in STRIDE; L and I 1 to 3; RISK = L x I; words read "A/An ... can ..." and have at least 7 words; no two threats read the same once names and letters are masked |
| `none` | `none FLOW LETTERS words` | reviewed and nothing to record; several letters allowed (`TID`); at least 5 words of reason |
| `control` | `control ID THREAT TYPE words` | TYPE from a fixed list: authn, mfa, mutual-tls, signing, integrity, authz, input-validation, tls, encryption, minimise-data, audit-log, rate-limit, quota, redundancy, least-privilege, sandbox, allow-list, access-proxy |
| `accept` | `accept THREAT words` | only for a risk below 6 |
| `top` | `top THREAT ...` | every threat of risk 6 or more, highest first |
| `attack` | `attack THREAT TECHNIQUE` | an ATT&CK ID, `T1234` or `T1234.001` |
| tree | `goal ID THREAT words`, `node ID PARENT and\|or words`, `leaf ID PARENT COST words`, `cheapest GOAL COST` | the goal is a highest-risk threat; at least three leaves and an AND node with two children; `cheapest` equals OR-min, AND-sum |
| abuse | `abuse ID THREAT As a/an ..., I ... so that ...`, `test ID ABUSE words` | every risk of 6 or more has an abuse case with a test (used by the fill-in, not the build) |

**`tm-check PART MODEL REF.json [--quiet]`** prints `ok` or one sentence and exits 0 (Module 1's rule for multi-step checks). Parts: `reads`, `diagram`, `boundaries`, `stride`, `findings`, `ranking`, `controls`, `attack`, `tree`, `abuse`, `kept`. The generic rules (STRIDE per element, the control-kind table, the arithmetic) are in the image; **each lab's reference** (the design's elements and flows, the flows that must cross, the weaknesses with their allowed letters and ratings, the techniques accepted, the `none` lines the design forbids) is in that lab's `checks.yaml`, written into a temporary file by each check, so it is not in the image the learner can read. The `findings` part never names the flow or the weakness in its message ("the design describes a weakness the model has no threat for"); `--quiet` (debug labs) prints only the end state still missing for every part (content/README.md: a debug's check output doesn't say which part is missing). Prototype: `prototypes/tm-zt/tmlab/tm-check`, about 330 lines of standard-library Python.

**Inventing at check time, honestly.** A threat model is the learner's thinking, which can't be re-run on a system the checker makes up at check time. So the topic splits it: the **mechanical** rules (which flows cross, which letters are missing) are a script the learner writes in the **write lab**, and that lab's checks do invent a new model at check time (random names, kinds, zones, flows and reviews) and compare the script's output with their own. The **judgement** (where the boundaries are, what the design's weaknesses are, how they rate on the design's scales, which control fits) is checked in the build and the debug against a reference that the design document makes determinable: the design states the facts (password-only staff sign-in reachable from the internet; an unauthenticated hook; a bucket readable by anyone with the link) and the scales, so a careful reader reaches the reference ratings, while boilerplate fails (masked-duplicate texts, `none` where the design says weak, controls of the wrong kind). The fresh-version rule (ADR-0012, for the checkpoint) and the topic's two different systems (build and debug) keep a second try from being a memory test.

**What the checks can fairly test, and what they leave to the explain.** Fair to check: the diagram matches the design's named parts; every flow between the business and an outsider crosses a boundary; every crossing flow has all six letters reviewed; every weakness the design describes has a threat on the right flow with the design's ratings; nothing the design calls weak is marked `none`; the ranking is complete and ordered; every high risk has a control of a kind that answers its letter; the worst weaknesses carry an ATT&CK technique from an accepted set; the attack tree is a tree with the right sums. Not fair to check by machine, so graded in the explain: whether a threat sentence is insightful, whether a `none` reason is true beyond its length, which of two acceptable controls is better.

**Lab shape.** Every threat-modeling lab is a **plain lab** (no systemd, no network), Module 3's shared plain `RUN` line byte for byte, then `COPY tm-check` and the lab's design notes. `restart_trial: true` passes trivially (the model is a file). No package beyond the plain line.
