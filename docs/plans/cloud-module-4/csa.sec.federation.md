## 1. What the learner will be able to do

1. **Trace an OpenID Connect sign-in message by message,** playing the browser with `curl`: the redirect to the identity provider with `client_id`, `redirect_uri`, `response_type=code`, `scope`, `state`, `nonce` and the PKCE challenge; the login; the redirect back with `code`, `state` and `iss`; the token request the app makes directly (with the code verifier); the token response; the ID token's header and claims. Say which hop failed from the browser's last answer and the two sides' logs.
2. **Trace a SAML single sign-on:** the AuthnRequest sent through the browser in a URL (deflated and base64), the signed Response posted back in a form (base64), the assertion's Issuer, NameID, Audience, Recipient, InResponseTo and validity window, its attributes and signature, checked with `xmlsec1`. See the identity provider's own session sign the user into a second app without a password: that is single sign-on.
3. **Choose the right flow for an app,** and register it at an identity provider with only that flow: authorization code with PKCE (S256) for anything with a user and a browser, confidential or public; client credentials for a service with no user; the device grant for a device with no browser; never the implicit grant or the password grant (RFC 9700). Public against confidential clients, exact redirect URIs, refresh-token rotation.
4. **Validate a token by hand** with the shell, `openssl` and `jq`: split and decode it, refuse an unexpected `alg`, find the key by `kid` in the provider's JWKS (from its discovery document), verify the signature, then the issuer (exactly), the audience, the expiry and not-before with a stated leeway, and the nonce. Know which component validates which token, and why keys must never be pinned.
5. **Provision accounts with SCIM 2.0:** find a user by filter, create one (201, or 409 when the name is taken), update with PATCH, deactivate a leaver (`active: false`) rather than delete, change group membership, page through a list; and write the joiners-movers-leavers reconciliation so that running it twice changes nothing.
6. **Place the three clouds:** what Entra ID, IAM Identity Center, and Google's Cloud Identity with Workforce Identity Federation each are, which protocols each speaks to apps and to other identity providers, and how users reach each (SCIM in, SCIM out, a connector, or no copy at all).

**The six-month core.** What should still be there half a year on, and what the review pool is built around:

- The app never sees the password. The browser carries the requests and the code (the front channel); the app swaps the code for tokens directly with the provider (the back channel). PKCE makes a stolen code useless; `state` and `nonce` tie the answer to the request.
- Pick the flow by two questions: is there a user, and does their device have a browser? Code with PKCE, device grant, client credentials. Implicit and password grants are out.
- A token is valid only if its signature verifies with the issuer's published key and its `iss`, `aud`, `exp` (and `nonce` for an ID token) all check out. The ID token is for the app; the access token is for the API. Keys rotate, so fetch them from the JWKS by `kid`; never pin one.
- A SAML assertion is the same promise in XML: check the signature, Issuer, Audience, Recipient, InResponseTo and the time window.
- Provisioning: deactivate leavers (`active: false`), don't delete them; reconcile idempotently; the HR or identity system is the source of truth, and SCIM is how it tells everyone else.
- On the clouds: Entra ID is an identity provider and a SCIM client; IAM Identity Center takes SAML in and needs users provisioned first, usually by SCIM; Workforce Identity Federation needs no copy of the users at all.

## 4. Lesson plan

The lesson is about 2,100 words (16 minutes). Each idea names the resource section it pairs with and what the lesson itself must supply. Module 3 topics' layout: an `<Intro>` that teaches, the main resource, a `<Recap>`.

1. **Why federation (lesson only).** Topic 40's authentication and authorization, across organisations: an app that keeps its own passwords is one more place to steal them from and one more account to forget to remove. With **federation**, the app trusts an **identity provider** to authenticate people and vouch for them. Picture in words: the IdP is a passport office, the app a border post; the post never sees your birth certificate, it checks the passport's seal (a **signature**, HTTP and TLS's word), that it was issued for this border (**audience**), by an office it trusts (**issuer**), and that it hasn't expired. **Single sign-on** falls out: once the passport office knows you (its **session** cookie), the next border post you visit gets a passport without you queueing again. Where MFA and conditional access (topic 41) happen: at the IdP, once; the app reads what was done in two claims, `acr` and `amr`.
2. **Two channels (lesson only, the picture the resources lack).** Draw the three parties as three boxes: browser, app, IdP. The **front channel** is anything the browser carries, a letter handed to the traveller: redirects and form posts, visible to the user and to anything in the browser. The **back channel** is the app calling the IdP directly, a phone call between offices: the browser never sees it. Every flow is a mix of the two, and the security of each rests on what travels where. This is also how to debug: a failure after the browser came back with a code is on the back channel, and the evidence is in the app's log and the IdP's, not the browser.
3. **OAuth 2.0 and OIDC (main resource, the Okta illustrated guide, all of it).** OAuth 2.0 (RFC 6749) is delegation, the valet key: the **resource owner** lets a **client** act at a **resource server** within a **scope**, through tokens an **authorization server** issues. It says nothing about who the user is. **OpenID Connect** adds that: the `openid` scope, the **ID token** (a JWT about the user, for the client), and discovery. The resource is from 2019 and doesn't cover PKCE; the lesson does (idea 4) and says so.
4. **The code flow, message by message (the worked example's own capture).** Seven messages, each with what it carries, numbered as the worked example captures them (tried, `captured/oidc-trace.txt`):
   1. The app redirects the browser to the `authorization_endpoint` with `client_id`, `redirect_uri`, `response_type=code`, `scope=openid`, `state`, `nonce`, `code_challenge`, `code_challenge_method=S256`.
   2. The IdP shows its login page (the app never sees the password).
   3. The IdP redirects to the `redirect_uri` with `state`, `session_state`, `iss` and `code` (Keycloak's 302, captured: `...callback?state=ab12...&session_state=...&iss=https%3A%2F%2Fidp.shop.test%2Frealms%2Fshop&code=46ab...`).
   4. The app checks `state` against what it sent.
   5. The app posts `grant_type=authorization_code`, the `code`, the same `redirect_uri` and the `code_verifier` to the `token_endpoint`, authenticating itself if it is confidential: the back channel.
   6. The IdP answers JSON: `access_token`, `id_token`, `refresh_token`, `expires_in` (300 in the lab), `token_type: Bearer`.
   7. The app validates the ID token and starts its own session (a cookie of its own).

   **PKCE (oauth.com's "Protecting Apps with PKCE") as a sealed envelope:** the app makes a secret (the verifier, 43 to 128 characters), sends only its SHA-256 hash (the challenge) in message 1, and reveals the verifier in message 5; whoever steals the code from the front channel lacks the verifier. **`state`** ties the answer to this browser (no one can plant their own sign-in: login CSRF); **`nonce`** ties the ID token to this request (no replay of an old one); **`iss`** in the redirect (RFC 9207) tells an app that uses several IdPs which one answered (the mix-up attack). Tried: a replayed code is refused (`{"error":"invalid_grant","error_description":"Code not valid"}`); an authorization request without a challenge is refused for a client that requires S256 (`error=invalid_request&error_description=Missing+parameter%3A+code_challenge_method`), and so is `plain` (`...code challenge method is not matching the configured one`).
5. **Tokens (lesson only, a table).** ID token: for the client, about the user, a JWT the client validates. Access token: for the API, about what the client may do there, which the **client treats as opaque** (Entra's own words, F-E4) and only the API validates. Refresh token: for the client, to get new access tokens without the user, kept secret, rotated for public clients (RFC 9700). All are **bearer** tokens. Lifetimes in the lab: access and ID tokens 300 s, refresh 1,800 s idle (captured); Entra's access tokens 60 to 90 minutes, 75 on average (F-E3).
6. **A JWT by hand (jwt.io's introduction, "What is the JSON Web Token structure?"; the worked example).** Three base64url parts joined by dots. **base64url** is HTTP semantics' base64 with `-` and `_` for `+` and `/` and the `=` padding dropped, so decoding in the shell is `tr '_-' '/+'`, pad to a multiple of four, `base64 -d`. The header says `alg` and `kid`; the payload holds the claims; the signature covers `header.payload` exactly as sent. The payload is readable by anyone: never put a secret in a JWT. Tried in the lab: `openssl dgst -sha256 -verify key.pem -signature sig.bin signed.txt` prints `Verified OK`, and after one claim is changed, `Verification failure` (`captured/verify-by-hand.txt`).
7. **Validating, in order, and why each step (OIDC Core §3.1.3.7, RFC 8725; the lesson's table, the resources give the rules but not the "what it stops" column):**

   | Step | Check | Stops |
   | --- | --- | --- |
   | 1 | `alg` is one you expect (RS256 here), never "whatever the header says" | `alg: none`, and an RS256 token re-signed as HS256 with the public key as the secret (RFC 8725 §2.1) |
   | 2 | the key: discovery → `jwks_uri` → the key whose `kid` matches; unknown `kid` → fetch the JWKS once more, then refuse | tokens signed by anyone else; outages at key rotation |
   | 3 | the signature over `header.payload` | any change to a claim |
   | 4 | `iss` equals the issuer exactly (no prefix, no trailing-slash tolerance) | another realm or tenant on the same host |
   | 5 | `aud` is, or contains, you (an array or a string) | a token meant for another app used on you (the confused deputy) |
   | 6 | `exp` in the future and `nbf`/`iat` not, each within a small leeway (60 s in the write lab) | replay of old tokens; clock trouble beyond the leeway |
   | 7 | `nonce` (ID tokens) equals the one sent; `azp` is you if present | replay of an ID token into another sign-in |

   Two cases the lesson says plainly: getting the keys from a file copied once ("pinning") works until the provider rotates, and then fails for everyone at once; and the JWKS deliberately lists more than one key (tried: Keycloak lists its active and its passive key), so take the one the `kid` names, not the first. Entra's advice: check the keys at least every 24 hours (F-E5).
8. **Choosing the flow (RFC 9700 §2, "Best Practices": §2.1, 2.1.1, 2.1.2, 2.4 and 2.5; the lesson's decision tree).** Two questions. Is there a user? No: **client credentials** (RFC 6749 §4.4; no refresh token, tried: `refresh_expires_in: 0`), or, for a workload that already has an identity of its own, workload identity federation (Module 10, one sentence). Yes: does their device have a browser? Yes: **code with PKCE**, whether the app is a confidential web app (PKCE is recommended there too) or a public single-page or native app (PKCE required; a native app or CLI redirects to a loopback address, RFC 8252, as `aws sso login` has since AWS CLI 2.22.0, F-A6); a single-page app is best served by a backend that holds the tokens (the IETF's browser-based-apps draft, named as a draft). No browser: the **device grant** (RFC 8628): the device shows a short code and a URL, the user approves on their phone, the device polls every `interval` seconds and slows down by 5 when told `slow_down`. Its risk is remote phishing: someone sends you their code, so the IdP's approval page names the device and asks you to confirm (tried: Keycloak's "Grant Access to scanner ... grant these access privileges?"). The two never to use: the **implicit grant** (tokens in the URL, "SHOULD NOT"), and the **password grant**, ROPC ("MUST NOT", RFC 9700 §2.4; the app holds the user's password and MFA can't happen, as Microsoft says of its own, F-E6). Exact redirect URIs (RFC 9700 §2.1: "exact string matching"). **Confidential** clients can keep a secret (a server); **public** ones can't (anything shipped to a user's device); asymmetric client authentication (`private_key_jwt`) is "RECOMMENDED" over a shared secret (§2.5), and Entra says the same of certificates (F-E7).
9. **SAML (the OASIS Technical Overview, §4.4.2 and §5.1.2; OWASP's SAML cheat sheet, "Validate Protocol Processing Rules" and "Unsolicited Response").** The same promise as an ID token, in XML, older (2005) and still what most enterprise SaaS speaks. The lesson supplies the side-by-side the resources lack:

   | | OIDC | SAML |
   | --- | --- | --- |
   | The promise | ID token (JWT) | assertion (XML) |
   | Request | authorization request in the URL | AuthnRequest in the URL (HTTP-Redirect: deflated, base64, URL-encoded) |
   | Answer travels | code in the URL, tokens on the back channel | the whole signed Response posted through the browser (HTTP-POST) |
   | Who it's for | `aud` | `<Audience>` (the SP's entityID) |
   | Tied to the request | `nonce`, `state` | `InResponseTo`, `RelayState` |
   | Keys | JWKS from discovery | the signing certificate in the IdP's metadata |
   | APIs and mobile | yes (access tokens) | no |

   Tried (`captured/saml-read.txt`, `saml-authnrequest.txt`): the AuthnRequest's `ID="_200623..."` comes back as the Response's `InResponseTo`; the assertion's `Conditions` last one minute (NotBefore two seconds before issue, NotOnOrAfter a minute after) and its `SubjectConfirmationData NotOnOrAfter` five; the SP asked for a `transient` NameID and got `unspecified` with the username, because the IdP's client forces its format; `xmlsec1 --verify` says `OK`, and after the NameID is changed, `failed to verify`. IdP-initiated SSO has no request to answer, so nothing binds the Response to a browser that asked: OWASP's login-CSRF warning.
10. **Provisioning (Microsoft's SCIM tutorial, "Understand the Microsoft Entra SCIM implementation" and "User operations"; Keycloak's SCIM section for the lab).** SSO decides who may sign in; something must also create the account in the app before the first sign-in and switch it off the day someone leaves. **JIT** provisioning creates it at first sign-in (and never removes it); **SCIM** (RFC 7643 and 7644) is a REST API for the **source of truth** to tell every app about **joiners, movers and leavers**. The request sequence is Entra's own (F-E8): find (`GET /Users?filter=userName eq "carla"`), create if missing (`POST`, `201`), update (`PATCH` with a PatchOp), deactivate (`PATCH active false`), and only much later `DELETE` (Entra hard-deletes 30 days after a soft delete, F-E9). Why deactivate, not delete: the app's history stays attached to a person, and a mistake can be undone. Tried against Keycloak 26.8.2 (`captured/scim*.txt`): 201 then 409 with `"scimType":"uniqueness"`; `filter=userName eq "DAN"` finds `dan` (user names are case-insensitive, RFC 7643); a filter with a bare word is `400 invalidFilter`; paging `startIndex=1&count=2` gives `itemsPerPage: 2`; a deactivated user's sign-in is refused (`error="user_disabled"` in the IdP's events). Two real-server lessons the lab teaches on purpose: a user created without `"active": true` came out **inactive**, and Keycloak ignores `externalId` (RFC 7643 leaves `active`'s meaning to the provider; send what you mean, and read back what was stored). The SCIM client is itself an OAuth client: client credentials, a token whose audience is the SCIM endpoint (Keycloak refuses any other: `"detail":"Invalid token audience"`, tried), and only the roles it needs.
11. **The three clouds, side by side (each provider's pages, read 2026-11-12; section 5 has each fact).**

   | | Microsoft Entra ID | AWS IAM Identity Center | Google Cloud Identity and Workforce Identity Federation |
   | --- | --- | --- | --- |
   | What it is | an identity provider: apps sign in with it (OIDC, OAuth 2.0, SAML) | sign-in to AWS accounts and apps; one identity source per organisation: its own directory, Active Directory, or an external IdP | Cloud Identity: Google's identity service, which can delegate sign-in to another IdP through SSO profiles (SAML or OIDC). Workforce Identity Federation: lets an external IdP's users into Google Cloud directly |
   | Federating with another IdP | it is usually the other IdP | SAML 2.0 in from the external IdP; users and groups must be provisioned first, because "SAML ... does not provide a way to query the IdP" | WIF takes OIDC or SAML 2.0 from Entra, AD FS, Okta and others, with attributes mapped in CEL (`google.subject` ...) |

Building that is Module 10 (`csa.iam.sso`).

### 7.1 `example-trace-a-sign-in` (worked example, identity lab, ~30 min), skills `trace-oidc`, `trace-saml`, `validate-token`

If the identity base's first lab is topic 40's, that lab carries the "Before your first identity lab" note and this one links it. Labelled steps (all tried, `trace-oidc.sh`, `verify.sh`, `sso.sh`, `saml-read.sh`, `samlreq.sh`):

1. **The IdP's map:** `on office curl -s https://idp.shop.test/realms/shop/.well-known/openid-configuration | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri, code_challenge_methods_supported}'`. Save the issuer to `~/example/issuer.txt`.
2. **A PKCE pair:** `verifier=$(openssl rand 32 | base64 -w0 | tr '+/' '-_' | tr -d '=')` (43 characters), `challenge=$(printf '%s' "$verifier" | openssl dgst -sha256 -binary | base64 -w0 | tr '+/' '-_' | tr -d '=')`. Save both, with a random `state` and `nonce`.
3. **The authorization request (front channel):** `curl -s -c jar -b jar "$auth?client_id=trace-cli&response_type=code&scope=openid&redirect_uri=http://127.0.0.1:8400/callback&state=...&nonce=...&code_challenge=...&code_challenge_method=S256"` gives the login page; pick the form's `action` (`grep -o 'action="[^"]*"'`, `&amp;` back to `&`), post `username` and `password` (ana's, from `/etc/idlab/accounts`) with `--data-urlencode`, and read the `302`'s `Location`: `state`, `session_state`, `iss`, `code`. Compare the state.
4. **The token request (back channel):** `curl -s "$token" -d grant_type=authorization_code -d "code=$code" -d "redirect_uri=..." -d client_id=trace-cli -d "code_verifier=$verifier" > ~/example/tokens.json`. Send it again: `invalid_grant`, `Code not valid`.
5. **Read the ID token:** `jq -r .id_token`, `cut -d. -f1` and `-f2`, the lesson's three-line base64url decode, `jq`. Point at `iss`, `aud`, `exp - iat` (300), `nonce` against the one sent, `azp`. Save it to `~/example/id-token.jwt`.
6. **Check the signature by hand:** `jwks_uri` → `.keys[] | select(.kid == $k) | .x5c[0]` → a PEM (`fold -w 64` between the BEGIN and END lines) → `openssl x509 -pubkey -noout` → `openssl dgst -sha256 -verify` over `header.payload`: `Verified OK`. Change `ana` to `ben` in the payload and verify again: `Verification failure`. (The n and e route, for providers whose JWKS has no `x5c`, is shown once, read-only: `openssl asn1parse -genconf` then `openssl rsa -RSAPublicKey_in`; tried, both routes gave the same key.)
7. **The access token is the API's:** its payload's `aud` is `https://api.shop.test`; `curl -H "Authorization: Bearer $at" https://api.shop.test/stock/level` → 200; the ID token there → 401.
8. **Single sign-on into the SAML app:** with the same cookie jar, `https://app.shop.test/hr/me` → 303 → 303 to the IdP with `SAMLRequest` → 200, a form, **no password asked**. Pick `SAMLResponse` out of the form, `base64 -d > ~/example/response.xml`, show it one element a line (`sed 's/></>\n</g'`), and read Issuer, NameID, Audience, Recipient, InResponseTo, the two NotOnOrAfter times and the `email` attribute. Decode the AuthnRequest with the lesson's given pipeline (M7) and match its `ID` to `InResponseTo`. Post the form on: the page says `user=ana`.
9. **The signature on the assertion:** the IdP's certificate from its metadata (`https://idp.shop.test/realms/shop/protocol/saml/descriptor`), then `xmlsec1 --verify ...` (M6): `OK`; edit the NameID: `failed to verify`.
10. **Who logged what, and where the IdP's settings live:** `journalctl -u keycloak@idp` shows the logins (`type="LOGIN"`, `type="CODE_TO_TOKEN"`); the app's log shows nothing for a good sign-in, which is why the error lines matter. Then `trace-cli`'s block in idp's `/etc/keycloak/realms/shop.json` beside `kcadm.sh get clients -r shop -q clientId=trace-cli`: the same settings, the file being the one that lasts (section 7's preamble).

Checks (each computes the truth live): `issuer.txt` equals the discovery document's issuer; `challenge.txt` equals the S256 of `verifier.txt`, computed by the check; `id-token.jwt` verifies against the IdP's JWKS, has `aud` `trace-cli` and the nonce in `nonce.txt`; `response.xml` verifies with `xmlsec1` and its Audience is `https://app.shop.test/hr`. Wrong fixes: `plain-challenge.sh` (challenge.txt = the verifier), `access-token-saved.sh` (the access token saved as the ID token: wrong `aud`), `edited-assertion.sh` (response.xml with a changed NameID).

### 7.7 `write-check-token` (write, plain lab, ~35 min), skill `validate-token`

**Prototyped end to end** (`write-lab/`): the reference passed twice and each of nine wrong scripts failed, every run with new keys, issuer, audiences, subjects and nonces, in 16.5 s for eleven runs in a plain `ubuntu:24.04` with `python3 openssl curl jq`.

Prompt: write `~/bin/check-token ISSUER AUDIENCE [NONCE]`, reading a token on standard input, printing exactly one line, `valid sub=SUB` or `invalid: REASON`, where REASON is the first of `format alg key signature issuer audience expired not-yet-valid nonce` that fails, in that order; exit 0 when valid. Rules: three dot-separated parts (an unsigned token's third part is empty); only RS256; the key from ISSUER's discovery document's `jwks_uri`, the one whose `kid` matches, by its `x5c` certificate; `iss` equal to ISSUER exactly; AUDIENCE equal to `aud` or among its items; 60 seconds of leeway on `exp` and on `nbf` (or `iat` when there's no `nbf`); the nonce only when one is given. The prompt gives the base64url decode function and the PEM-wrapping lines (from the worked example), and says the checks run it against an issuer of their own on 127.0.0.1 with keys made at check time.

The check (`token-cases`, about 120 lines of Python, the checks' tool): two published keys in a random order, one never published; sixteen cases in a random order (a valid token; `aud` as a list; expired within the leeway; signed by the older published key; the right nonce; not a JWT; `alg: none`; `alg: HS256`; an unknown `kid`; a known `kid` signed by another key; a tampered payload; an issuer with a suffix; another audience; expired; not yet valid; a wrong nonce). It prints `all 16 right` or the first case and what the script printed. Wrong scripts, each failing deterministically, not by chance (tried): `no-signature-check`, `alg-from-token`, `aud-string-only`, `no-expiry`, `no-leeway`, `issuer-prefix`, `first-key` (always fails one of the two keys' cases), `ignores-nonce`, `no-nbf`. Plus `hard-coded.sh` (prints `valid sub=` for everything) for the contract.

### 8.3 Explain

**Prompt:** "The shop is moving four apps to single sign-on: the orders site (a server-side web app), a new mobile app that calls the stock API, the warehouse scanners (no browser), and an old HR system that speaks only SAML. A colleague who has only ever used passwords asks you to explain it. In your own words: what happens, message by message, when someone signs in to the orders site, and which messages the browser carries and which it never sees; which flow each of the four apps should use and why, and which two flows nobody should use; what the stock API must check about every token before trusting it, and why it must not keep a copy of the identity provider's key; how the HR system's SAML sign-in differs; and how accounts get created in each app and switched off the day someone leaves. Say one way the three clouds differ."

**Rubric:**

- `code-flow` (required): browser redirected to the IdP with client, redirect URI, state, nonce and PKCE challenge; login at the IdP only; code back through the browser; the app swaps code plus verifier for tokens directly (back channel); state and nonce checked.
- `flow-choice` (required): orders site code + PKCE (confidential); mobile app code + PKCE (public, no secret); scanners device grant (approve on another device, beware codes sent by others); HR SAML; never implicit or password grant, because of tokens in URLs and apps holding passwords (no MFA).
- `token-checks` (required): signature with the key named by `kid` from the IdP's published keys; issuer exactly; audience is the API; not expired (small leeway); keys rotate, so fetch them, never pin.
- `saml` (required): XML assertion posted through the browser, signed; check signature, audience, recipient, InResponseTo and the time window; no access tokens for APIs.
- `provisioning` (required): SCIM (or JIT) creates accounts; leavers deactivated (`active: false`) at once, deleted later; idempotent sync from the source of truth.
- `clouds-differ` (optional): any correct difference: Identity Center needs users provisioned (SCIM) before SAML sign-in; WIF needs no copy; Entra is a SCIM client; Entra's tokens and secret limits.

**Model answer:** the writer writes it in the shop's story (about 350 words), as DNS's does.

## 12. Open questions, each with a recommendation

1. **Which identity provider?** The base designer's call, and its prototype agrees. **Recommendation:** Keycloak 26.8.x (Apache-2.0): it is the one open-source provider found that serves this topic whole (OIDC with every grant, SAML, the device grant, client-secret rotation, and since 26.8 a supported SCIM server). If the base chose otherwise, the SCIM lab would need a SCIM server of its own (a stand-in written for the lab, about 250 lines, tested like `cors-verdict`).
2. **`jq` for the learner.** The base's prototype has no `jq` and gives the learner `jwt show` and `jwt verify` instead. **Recommendation:** both. `jwt show` is the everyday tool once the worked example has done it by hand (and it must not be in the write lab's plain image, whose point is doing it by hand); `jq` for the JSON that isn't a token (discovery documents, JWKS, token responses, SCIM resources and the `hr-sync` script), since Module 1 taught its syntax by recognition and the alternative is fragile `grep`. Checks keep `python3`; `predict_shell` items keep to `cut`, `tr`, `base64` and `grep` because Git Bash has no `jq`.
