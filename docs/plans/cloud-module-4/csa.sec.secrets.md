# Writing brief: `csa.sec.secrets` (topic 45), Secrets

Design only. Nothing here is in the repository. Sources were read on 2026-11-12 and each fact below carries its URL. Mechanisms marked **tried** were run on 2026-11-12 in Docker Desktop 29.8.2 on the owner's PC (kernel 6.18.33.2-microsoft-standard-WSL2), in privileged systemd containers started with the checker's arguments, on `ubuntu:24.04` with OpenBao 2.7.2 (its release `.deb`), PostgreSQL 16.15, podman 4.9.3, git 2.43.0 and gitleaks 8.16.0 from Ubuntu's archive (prototype Dockerfiles in `prototypes/cps/sec/` and `prototypes/cps/pod/`). Every container and image I started was removed; no prune was run.

The labs run on `lab-base-sec`, specified in `csa.sec.crypto.md` section 10 (topic 42 is a prerequisite, so its labs come first). This brief lists only what the secrets labs add to it.

## 1. What the learner will be able to do

1. Find where a secret has leaked on a server and its software: a repository's history, a container image's layers and history, a process's command line and environment, the journal. Say who can read each (another user, root, anyone with the image) and put the secret where it belongs instead: a file only the service's user can read, a systemd credential, a build secret mount, a secrets manager.
2. Catch leaks before and after they happen with a scanner (gitleaks): over a repository's whole history, on staged changes, and in a server-side hook that a developer can't skip and a pushed configuration can't silence; add a rule for the company's own key format; say what scanners miss.
3. Respond to a leak in the right order (revoke or rotate first, then remove, then find how), rotate without downtime (two keys or two users in turn), and work out how long a leaked secret was usable.
4. Explain the secret-zero problem (every secret store needs a first credential, including its own unseal key) and the real answers: the platform vouches for the workload (metadata-service credentials, a signed workload token), a trusted orchestrator delivers a single-use wrapped credential, and a cloud KMS unseals the vault.
5. Replace a static database password with dynamic secrets: OpenBao's database engine issuing short-lived credentials per workload, the workload signing in with its platform identity token, OpenBao Agent keeping the credentials fresh in a file, the root credential rotated so only OpenBao can use it; and say how the three clouds' secrets managers rotate.

**The six-month core.**

- A secret in git history, an image layer, a log line or a command line has leaked to everyone who can read those. Deleting it later doesn't un-leak it; revoking it does.
- Environment variables reach child processes and crash dumps and are readable by the same user and root; command lines are readable by every user. Pass secrets as files only the service can read, or systemd credentials, and to builds as secret mounts.
- Scan everywhere, but enforce where it can't be skipped: on the server, with the server's own rules.
- Rotation is two steps (add the new, retire the old) and the gap between them is the risk; two keys in turn close it.
- Secret zero is solved by identity, not by hiding a token better: let the platform vouch for the workload.
- Dynamic secrets are per workload, short-lived and revoked by the vault; the static secret that's left is the vault's own, and it's guarded hardest.

## 4. Lesson plan

About 3,300 words (26 minutes) with its tables.

1. **How secrets leak, in three stories (GitGuardian's 2026 report post; Codecov's security update; the FTC's Uber release).** The lesson opens with numbers and cases, briefly: 28.65 million new secrets were pushed to public GitHub commits in 2025, up 34%, and more than 64% of the ones that were valid in 2022 still worked in January 2026 (fact S7). In 2016 intruders used an access key an Uber engineer had posted to a code-sharing site, downloaded millions of people's records and were paid $100,000 to stay quiet (fact S6). From January 2021, someone used a credential extracted from Codecov's Docker image creation process to alter the script thousands of build pipelines ran, which then sent each pipeline's environment variables, secrets included, to the attacker (fact S5). Three lessons: a secret goes wherever it's written, it stays there, and the fix is to make it worthless.
2. **Out of code, and why history matters (lesson only, with the worked example's step 1).** The minimum git the lesson must teach: a repository is a folder whose history git keeps; each **commit** records every file as it was; `git log -p` shows every change ever made; deleting a file is a new commit, and the file is still in the old one, in every clone anyone made. Rewriting history (one sentence) changes your copy, not the clones, forks or caches. So the only fix for a pushed secret is to revoke it. Config that isn't secret (a hostname, a port) belongs in the repository; secrets don't.
3. **Out of the process table and the environment (lesson only, tried).** The table the lesson must give, from the prototype's file modes:

   | Where a service gets its secret | Who else can read it |
   | --- | --- |
   | a command-line argument (`--api-key=…`) | every user on the machine: `/proc/PID/cmdline` is `-r--r--r--`, so `ps -ef` shows it |
   | an environment variable | its own user and root (`/proc/PID/environ` is `-r--------`), every child it starts, crash reports, and any `env` a script prints into a log (Codecov's attacker collected exactly that) |
   | `Environment=` in a unit | everyone: unit files are world-readable and `systemctl show -p Environment` prints it |
   | a file, `0400`, owned by the service's user | that user and root |
   | a systemd credential (`LoadCredential=`) | that service only: not inherited, not in the environment, kept in memory (fact S20) |

   And logs: a secret printed once at debug level is in the journal, which the `adm` group reads, and in every place the journal is shipped. OWASP: secrets must "never be logged" (fact S9).
4. **Out of images (Docker's "Build secrets" page; `csa.linux.containers` for layers).** Retrieval: an image is a stack of layers, and a `RUN rm` adds a whiteout that hides a file from the layers below. The lesson's point, tried in the lab: the file is still there. `COPY deploy.token` then `RUN rm` left `tmp/deploy.token` in the second layer's tar and `tmp/.wh.deploy.token` in the third; `ARG API_KEY` with `--build-arg` appeared in `podman history` as `|1 API_KEY=sk_live_example1234 /bin/sh -c …`, and `ENV` values sit in the image's config (`podman inspect`). Docker's own words: build arguments and environment variables "are inappropriate for passing secrets", because they persist in the final image (fact S3). The fix: `RUN --mount=type=secret,id=pkg …` reads the secret from `/run/secrets/pkg` for that one instruction, and `podman build --secret id=pkg,src=FILE` (or `docker build --secret …`) supplies it; tried, the token was in no layer and no metadata. A multi-stage build keeps build tools out of the final image, but its first stage's layers still hold whatever it was given, on the builder. The labs use **podman**, a Docker-compatible tool that needs no daemon, because a lab can't reach Docker Desktop: every command shown works the same with `docker`.
5. **Catching leaks (gitleaks' README for v8.16; GitHub's push protection page).** How a scanner decides: **rules** that match known formats (an AWS key ID starts `AKIA`, a GitHub token `ghp_`, a private key has its PEM header), and **generic** rules that look for words like `key` or `password` next to a string that looks random (its **entropy**). Known formats are found reliably; a weak password next to an odd word may not be (a false negative), and a random test string may be (a false positive, which an allowlist or a `gitleaks:allow` comment answers). Where to scan, as a table: on the developer's machine before a commit (`gitleaks protect --staged` in a pre-commit hook; fast, but skippable with `--no-verify`); on the server when a push arrives (a `pre-receive` hook scanning every pushed commit, `gitleaks detect --log-opts=OLD..NEW`, tried: it refused a push whose middle commit added an AWS key that the last commit removed); in CI (later, and careful: tried, a scan run in a clone obeys the repository's own `.gitleaks.toml`, so a pushed allowlist of `.*` silenced it, while the same scan of the bare repository ignored it); on GitHub, push protection is on by default for users pushing to public repositories and off by default per repository, and anyone with write access can bypass it with a reason (fact S8). A company's own key format gets a custom rule (`[extend] useDefault = true` plus a `[[rules]]` block, tried in 8.16). trufflehog (AGPL-3.0) can **verify** what it finds by trying it against the provider's API, which says which leaks are live but sends your findings to those providers; offline, `--no-verification` (fact S2). Ubuntu's gitleaks is 8.16 from 2023; current releases rename `detect` and `protect` to `git`, `dir` and `stdin` (the lesson says so in a sentence, so nobody is surprised).
6. **Rotating and revoking (OWASP's cheat sheet, "Secrets Management" incident response; AWS's rotation-strategy page).** After a leak, in this order: revoke or rotate (make the leaked value worthless), then remove it from where it leaked, then find out how it got there. Rotation is two steps, add the new and retire the old, and the risk is the time between. **Single-user** rotation changes one password in place, and for a moment the database and the stored secret disagree; **alternating users** (AWS) keeps two users and changes the one not in use, so a client holding either works; API keys do the same with two active keys (the labs' payment gateway allows two). The lesson works the exposure window once, with numbers no item reuses: a key pushed at 14:40, found by the 18:00 scan, triaged in an hour and revoked 10 minutes later, was usable for 270 minutes. **Where the three clouds differ** (facts S17 to S19):

   | | AWS Secrets Manager | Azure Key Vault | Google Secret Manager |
   | --- | --- | --- | --- |
   | Who rotates | managed rotation for secrets other AWS services manage; otherwise a Lambda function Secrets Manager calls in four steps (`create_secret`, `set_secret`, `test_secret`, `finish_secret`), versions labelled `AWSCURRENT` and `AWSPREVIOUS` | your function: Key Vault publishes `SecretNearExpiry` 30 days before a secret's expiry to Event Grid, which calls it; Microsoft's own advice is a managed identity instead of a secret where possible | your code: Secret Manager sends `SECRET_ROTATE` messages to Pub/Sub on a schedule and doesn't rotate anything itself |
   | How often | as often as every four hours, at most 999 days apart | on the expiry you set | a rotation period of at least one hour |
   | Price, read 2026-11-12 | $0.40 a secret a month and $0.05 per 10,000 API calls (the page's example) | secret operations $0.03 per 10,000 (Standard) | not confirmed |

7. **Secret zero (OpenBao's response-wrapping and AppRole pages; OWASP's "Avoid static bootstrap credentials"; the lesson supplies the picture).** The picture: a key box by the door, for the cleaner; the box needs a code, and the code has to be given to the cleaner somehow. Moving secrets into a vault moves the problem to the vault's own front door: the app needs a token to ask, and the vault itself needs its unseal key. The real answers, each tried or named:
   - **Let the platform vouch for the workload.** The machine or orchestrator already knows which workload is which. A cloud VM's metadata service hands out short-lived role credentials (topic 11's IMDS); Kubernetes projects a signed token into each pod; a CI system signs a token for each job. The vault validates the platform's signature (topic 44's token validation) and checks which workload it names. In the labs, `platform-token` signs a 10-minute token for each workload into its own `/run/platform/WORKLOAD/token`, renewed by a timer. The bindings are the security: tried, an OpenBao JWT role without `bound_claims`, or with `bound_claims_type=glob` and `sub: "workload:*"`, gave a token to `workload:report-job` as readily as to `workload:shop-api`; a token whose audience the role doesn't name was refused (`audience claim found in JWT but no audiences bound to the role`).
   - **A trusted orchestrator and response wrapping.** Where there's no platform identity, a deployer that's already trusted asks for a single-use credential (an AppRole `secret_id`) and delivers it **wrapped**: a token that can be unwrapped once, for a short time. Tried: the second unwrap failed with `wrapping token is not valid or does not exist`, and a used `secret_id` was refused (`invalid role or secret ID`). A failed unwrap means someone else got there first: an alarm, not a retry.
   - **The vault's own key.** OpenBao starts sealed: its storage is encrypted and it needs its unseal key. People can hold Shamir shares of it (several must type theirs after every restart), or a cloud KMS can unseal it automatically, which works only for a VM whose identity may use that KMS key: secret zero answered by the platform again. The labs use OpenBao's `static` seal, a key in a file, which its documentation says to "carefully evaluate" (fact S15): acceptable for a lab whose whole state is throwaway, never for production.
8. **Dynamic secrets (OpenBao's database secrets engine page; the lesson supplies the timeline).** Instead of one password shared by every copy of an app for years, OpenBao creates a database user per request, with a **lease**: tried, `bao read database/creds/shop-read` returned `v-root-shop-rea-…` valid 60 seconds, PostgreSQL showed it with `VALID UNTIL`, it could `SELECT` and not `DELETE`, and it was gone after the lease ran out (fact S10). A timeline drawn in words: issued at 09:30 with a TTL of 30 minutes and a max TTL of 2 hours; renewed at 09:55, 10:20…; it can't outlive 11:30, when the app must get a new one. `bao lease revoke -prefix database/creds/shop-api` after an incident ends every one at once. **Rotate the root** credential OpenBao uses, so nobody but OpenBao can use it (tried: the original password was then refused). **OpenBao Agent** does the client's part: it signs in with the platform token (auto-auth), writes the credentials to a file only the app's user can read (a template), and replaces them before the max TTL (tried: re-rendered about every 110 seconds for a 120-second max TTL). Each credential's name says which workload asked (`v-jwt-work-shop-rea-…`), so the database's own logs point at the culprit. One sentence on where the clouds go further: their managed databases can accept the workload's cloud identity in place of a password, which Modules 10 and 13 build.
9. **The labs (lesson only).** One server. OpenBao (`openbao.service`, as in topic 42), PostgreSQL (`postgresql`), the shop's API (`shop-api.service`, user `shop`), a payment gateway stand-in (`paygate.service`, `127.0.0.1:9440`, with keys that look like `pg_live_…` and an admin API whose key is in OpenBao's KV at `secret/paygate/admin`), a package registry stand-in (`pkg-server`, `127.0.0.1:8081`), the shop's git server (a bare repository in `/srv/git/shop.git`), and `platform-token`. The rule of the module: change only what the lab asks for; and here a second rule, every key you see in a lab is a throwaway made when the lab started.

**Read now:** OWASP's Secrets Management Cheat Sheet, the main resource: sections 2 (General Secrets Management), 3 (CI/CD) and 5 (Containers & Orchestrators), about 3,000 of its 7,500 words. Then Docker's "Build secrets", OpenBao's database secrets engine ("Setup" and "Usage") and response wrapping ("Overview"), gitleaks' README for v8.16, and Codecov's security update. Optional: GitHub's push protection page, AWS's rotation strategies, GitGuardian's 2026 report post.

### 7.1 `example-follow-the-leaks` (worked example, lab), skills `keep-secrets-out`, `scan-for-leaks`, `rotate-and-revoke`

1. **History.** `git clone /srv/git/shop.git ~/shop`; `git log --oneline` (five commits); `gitleaks detect -s ~/shop -c /etc/gitleaks/shop.toml -v --redact` finds the payment key in `config/paygate.env` of a commit whose successor deleted the file, by the shop's own rule `paygate-key`; `git show COMMIT` shows the line.

### 8.1 Build: `build-shop-without-static-secrets` (systemd lab, 55 minutes), skills `dynamic-secrets`, `secret-zero`, `keep-secrets-out`

**Scenario.** `shop-api` (user `shop`) reads its database user and password from `/etc/shop/db.conf` (a static user `shop_app`, its password in the file). The DBA put PostgreSQL's admin credential in OpenBao's KV at `secret/db/admin`. `platform-token@shop-api.timer` keeps a fresh token for `workload:shop-api` in `/run/platform/shop-api/token` (`0400`, `shop`), signed by the platform's key; the public key is `/etc/lab-platform/signing.pub`, the issuer `https://platform.shop.test`. `shop-api` re-reads its credentials file on every new connection and serves `GET /orders` and `GET /whoami` (its database user) on `127.0.0.1:8080`.

**Brief.** Make the API run with no static database password anywhere:

1. OpenBao's database engine at `database/`, a connection `shop` from the KV credential, then the admin password rotated so only OpenBao knows it;
2. a role `shop-api` whose users can read and add orders and nothing else, lasting at most an hour and renewable to a day;
3. JWT sign-in at `auth/jwt` that trusts the platform's key and issuer, with a role for `workload:shop-api` only, audience `openbao`;
4. a policy for that role: its own database credentials, nothing more;
5. OpenBao Agent as `shop-api-agent.service`, as `shop`, signing in with the platform token and writing the credentials to `/run/shop-api/db.conf`, `0400`; `shop-api` pointed at that file; both enabled;
6. the old `shop_app` user unable to log in, and `/etc/shop/db.conf` gone.

**Checks:**

- `api-works` (`timeout: 60`, the one wait: PostgreSQL, OpenBao, the agent): `GET /orders` answers 200 with the right count; `GET /whoami` names a `v-…` user.
- `creds-short`: the role's `default_ttl` ≤ 3,600 and `max_ttl` ≤ 86,400; the API's current user's `VALID UNTIL` is within a day.
- `db-least`: that user isn't a superuser, can't create roles or databases, can `SELECT` and `INSERT` on `orders`, can't `DELETE` or `TRUNCATE` (`has_table_privilege`).
- `static-gone`: `shop_app` can't log in (missing or `NOLOGIN`), the seeded old password (kept root-only at first boot) logs in as no role, and `/etc/shop/db.conf` doesn't exist.
- `root-rotated`: the seeded admin password no longer logs in; OpenBao still issues credentials.
- `identity-bound`: tokens the check signs with the platform key: `workload:report-job` refused, audience `other` refused, an expired one refused, `workload:shop-api` accepted; the role isn't `glob` with a wildcard.
- `token-least`: the token from that login: `read` on `database/creds/shop-api` only; `deny` on `secret/db/admin`, `database/config/shop`, `database/creds/*` other roles, `sys/policies/acl`.
- `no-secret-zero-on-disk`: the agent's configuration uses method `jwt` with the platform token's path; no file readable by `shop` holds a live OpenBao token (each `s.` followed by 24 letters and digits found under `/etc /home /srv /var/lib /run` is tried with `bao token lookup`, ignoring root's and the learner's own token files); `shop-api.service` and the agent's unit have no `Environment=` holding a credential.
- `lasting` (with the restart trial): both units enabled; after the restart, `api-works` again (the agent signs in with the platform's fresh token).

**Wrong fixes:** `static-kept.sh` (dynamic creds set up, API still on `db.conf`), `kv-static-password.sh` (the old password moved into KV and rendered by the agent: `static-gone` fails), `root-not-rotated.sh`, `superuser-role.sh`, `any-workload.sh` (no `bound_claims`; tried), `glob-workload.sh` (tried), `long-ttl.sh` (30 days), `approle-secret-on-disk.sh` (agent signs in with an AppRole `secret_id` in a file), `token-in-env.sh` (a periodic token in the agent unit's `Environment=`), `policy-broad.sh` (`database/*`), `agent-not-enabled.sh`. Eleven.

### 8.2 Debug: `debug-the-export-leaks` (systemd lab, 45 minutes), skills `keep-secrets-out`, `rotate-and-revoke`, `scan-for-leaks`

**Scenario.** `shop-export.service` (user `export`, started by a timer every 10 minutes on the lab clock; nightly in the story) charges the day's orders through `paygate`. Its unit is `ExecStart=/usr/local/bin/shop-export --api-key ${PAYGATE_KEY}` with `EnvironmentFile=/etc/shop/export.env` (`0600 root`); `/etc/shop/export.conf` has `log_level = debug`, so each run logs its requests, headers included; last month's rotation added the current key but left the previous one active at `paygate`, and that previous key is in `/srv/git/shop.git`'s history. `shop-export` also accepts `--api-key-file PATH` (its `--help` says so). Another account, `audit`, stands for any ordinary user.

**Prompt:** "Every night `shop-export` charges the day's orders at the payment gateway. The gateway has warned that the shop's key was used from an address that isn't the shop's. The gateway's admin key is in OpenBao at `secret/paygate/admin`. There are three faults: ways the job's key leaks, or a leaked key still works. When you're done, no key that has leaked may still work at the gateway, nothing an ordinary user can read may show the key the job uses, and the job must still charge the orders." Checks listed only after a first try.

**Faults:** (1) the key on the command line (visible to `audit` in `ps` during a run); (2) `log_level = debug` (the key in the journal, which `adm` reads); (3) the previous key, in git history, still active. And, as a consequence the learner must see, the current key has leaked through (1) and (2), so it must be replaced and revoked too.

**Checks:** `job-works` (the check starts the job and the gateway records a successful charge with an active key), `no-leaked-key-works` (every key the scenario ever made, from its root-only list, and every `pg_live_` value found in the repository's history, the journal and `systemctl show` is refused by the gateway, except the one now in use, which must be new), `args-clean` (during a check-started run, `ps -eo args` as `audit` shows no `pg_live_`), `journal-clean` (the run's journal lines hold no `pg_live_`), `unit-clean` (`systemctl show shop-export -p Environment -p ExecStart`, and the unit files, as `audit`, hold no `pg_live_`), `key-file-private` (the key the job uses is readable by `export` and root only: a `0400` file or a systemd credential).

**Wrong fixes:** `rotated-not-revoked.sh` (new key, old ones still active), `revoked-everything.sh` (no working key: `job-works` fails), `journal-vacuumed.sh` (deletes the journal instead of fixing the logging), `env-instead-of-args.sh` (`Environment=PAYGATE_KEY=…` in the unit: `unit-clean` fails), `history-rewritten-only.sh` (force-pushes history without the old key, revokes nothing), `world-readable-key-file.sh` (`--api-key-file` on a `0644` file), `journal-hidden.sh` (takes `adm`'s right to read the journal away: the check reads as `audit`, who is in `adm`, and the rule "don't weaken auditing" is in the prompt), and three `two-of-three-*.sh`. Ten.

### 8.3 Explain

**Prompt:** "A teammate says: 'Secrets are fine as long as they're not in the code. We pass them as environment variables, keep the real values in a vault, and rotate them once a year.' Explain, in your own words, where secrets leak besides code and who can read each place; what you'd do in the first hour after a key turns up in a public repository; how a scanner fits in and where it can't be skipped; what the secret-zero problem is and how a workload should get its first credential; and what dynamic secrets change, with what is still static and how it's protected."

**Rubric:**

- `leak-paths` (required): git history (every clone), image layers and history (`ARG`, `ENV`, a file removed later), command lines (every user), environment variables (children, crash dumps, `env` in logs; Codecov), logs, unit files and `systemctl show`.
- `first-hour` (required): revoke or rotate first, then remove it, then find how; rewriting history doesn't un-leak; check the logs for use of the key.
- `scanning` (required): rules and entropy, false negatives; scan history and every pushed commit on the server with the server's config; pre-commit is skippable; push protection.
- `secret-zero` (required): the first credential; platform identity (IMDS, signed workload tokens) bound to the workload and audience; or a trusted orchestrator with single-use wrapping; the vault's own unseal by Shamir or a cloud KMS.
- `dynamic` (required): per-workload, short-lived credentials with leases, revoked by the vault, the root credential rotated so only the vault has it; what's left static is the vault's own key and the platform's trust, guarded hardest.
- `clouds` (optional): AWS Secrets Manager runs rotation (every 4 hours at most often), Azure Key Vault and Google Secret Manager tell your code when.

## 12. Open questions, each with a recommendation

1. **gitleaks from Ubuntu (8.16.0, 2023) or the current release (8.30.1, pinned download)?** Ubuntu's is in the archive, MIT, offline, and did everything the labs need (fact S1); the current one renames commands. **Recommendation: Ubuntu's 8.16**, with one sentence in the lesson on the newer commands.
2. **trufflehog in a lab?** It isn't in the archive, is AGPL-3.0 (fine to run), and its distinctive feature, verification, calls third-party APIs, which a lab can't. **Recommendation: taught, not installed.**
3. **Images: podman in the lab, or reading a saved image tarball only?** Building is what the learner will do at work, and the fix (a secret mount) can only be proved by building. podman works offline with `vfs` storage in the privileged lab container (fact S4) and is Apache-2.0. **Recommendation: podman**, with every command said to be `docker`'s too.
4. **Secret zero: JWT workload identity, AppRole with wrapping, or both in the build?** The platform-identity answer is the one OWASP and the clouds point to (fact S9) and survives a restart without anyone delivering anything; AppRole with a single-use `secret_id` can't pass the restart trial without an orchestrator re-delivering it, which is honest about its weakness. **Recommendation: JWT in the build; AppRole and wrapping in the recall items and the lesson**, both tried.
5. **Prerequisite on `csa.sec.federation`.** **Recommendation: yes**, so that a signed token's claims are known. If the module's critic prefers secrets before federation, the lesson's idea 7 gains a paragraph defining a JWT's `iss`, `sub`, `aud` and `exp` and the prerequisite becomes `csa.sec.authn-authz`.
6. **The lab clock.** Credentials last real times (1 hour, 1 day) because no check waits for them to run out; only the export timer runs every 10 minutes instead of nightly. **Recommendation: as designed**, said in the prompt.
7. **The time over 300 minutes.** **Recommendation: trim as section 11 says, and keep one topic**; the cold review decides whether the worked example needs the extra dynamic-credential step (7.9).
