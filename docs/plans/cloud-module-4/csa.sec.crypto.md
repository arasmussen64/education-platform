## 1. What the learner will be able to do

1. Choose the right primitive for a job: symmetric encryption for data, public-key cryptography for agreeing keys, wrapping keys for named recipients and signing, and the two together (hybrid encryption) almost always. Say why nobody encrypts a file with RSA, from the size limit and from real `openssl speed` numbers.
2. Tell a hash, a MAC and a signature apart by what each one proves and who can make one, and pick the right one: a checksum for a download, an HMAC for a webhook, a signature for a release, a slow salted hash (Argon2id) for a password, an HMAC with a secret key for a log that must not reveal card numbers. Say why encoding (base64) is none of these.
3. Use authenticated encryption (AES-GCM, ChaCha20-Poly1305) and show, with openssl, why encryption without authentication lets an attacker change "PAY 100" into "PAY 900" undetected. Keep a nonce unique per key, and work out from NIST's 2^32 rule when a key must be retired.
4. Design and run envelope encryption with a key management service: a fresh data key per object, the key encryption key that never leaves the KMS, the wrapped key stored beside the data, a policy that decides who may unwrap, rotation that creates key versions, rewrapping, and retiring old versions. Map it onto AWS KMS, Azure Key Vault and Google Cloud KMS, and cost it.
5. Read a key's security strength in bits (SP 800-57's table), do the brute-force arithmetic, and say what the post-quantum transition changes (NIST IR 8547, final in October 2026): public-key algorithms deprecated after 2030 and disallowed after 2035, symmetric keys of 128 bits and more unaffected.

**The six-month core.** What should still be there half a year on, and what the review pool is built around:

- Symmetric keys encrypt data; public keys agree or wrap symmetric keys and check signatures. A real system uses both.
- A hash proves nothing against an attacker who can recompute it; a MAC proves the sender had the shared key; a signature proves the holder of one private key made it, and anyone can check. Guessable data (a card number, a password) must never be stored as a plain hash.
- Encryption without authentication can be edited blind. Use AEAD, and never reuse a nonce with the same key: with random 96-bit nonces, at most 2^32 messages a key.
- Envelope encryption: data key per object, wrapped by a KMS key that never leaves the KMS; store the wrapped key with the data; the KMS policy and audit log are the real controls. Rotation adds versions and changes no data; rewrap moves old wrapped keys forward; only then retire the old version.
- 112-bit security (RSA-2048) is the floor today; everything public-key is deprecated after 2030 and disallowed after 2035; AES-256 stays.

## 4. Lesson plan

The lesson is about 3,100 words (25 minutes) with its tables. Each idea names the resource it pairs with and what the lesson must supply itself.

1. **What topic 31 left standing (lesson only).** One paragraph of retrieval: topic 31 said TLS uses symmetric encryption for the conversation, public-key cryptography to agree a key and to prove who the server is, and a cipher suite to name the algorithms. This topic is about using those tools yourself, outside TLS: on files, in databases, in a cloud's key service. The labs are one server running **OpenBao**, an open-source key and secret service with the same command-line and HTTP API as HashiCorp Vault, standing in for a cloud's KMS (`bao` at `127.0.0.1:8200`, as `openbao.service`). One paragraph on its words: a **path** (`transit/keys/orders`), `bao read` and `bao write`, a **token** (what proves who you are to it; yours is in `~/.vault-token`), a **policy** (topic 40's idea: which paths a token may use, and how), the **transit engine** (OpenBao's KMS: it keeps keys and does the encrypting, never handing the key out).
2. **Choosing the primitive (Nakov, "Symmetric and Asymmetric Encryption" is not a chapter; the lesson supplies this idea itself, with Nakov's "Digital Signatures" first section as reading).** A table the lesson must give, because no free resource puts it in one place for a beginner:

   | Job | Use | Why |
   | --- | --- | --- |
   | Encrypt a file, a disk, a database column | a symmetric key (AES-256-GCM) | fast: AES-256-GCM ran at 6.7 GB/s on the owner's PC (tried, `openssl speed -evp aes-256-gcm`, 8 KB blocks) |
   | Let several named people decrypt it | hybrid: a random file key, wrapped with each person's public key | one copy of the data, one small wrapped key per person; age does exactly this (tried: two recipients, two `-> X25519` lines in the header, the 3,893-byte file became 4,191 bytes) |
   | Prove who made something, to anyone | a signature (Ed25519, ECDSA, RSA-PSS) | only the private key can make it; anyone with the public key can check |
   | Agree a key with someone over an open network | key exchange (ECDHE, topic 31) | nobody watching can work the key out |
   | "Encrypt" a 1 GB file with RSA | don't | RSA-2048 with OAEP-SHA-256 takes at most 190 bytes at a time (AWS's Encrypt reference), and a private-key operation ran 1,772 times a second on the owner's PC (tried), against AES's gigabytes a second: `est-rsa-gigabyte` works out how long that is |

   And the trap: **encoding is not encryption.** base64 and hex turn bytes into text and anyone can turn them back (`base64 -d`). A Kubernetes Secret is stored unencrypted by default (fact 20); its base64 only makes binary values fit in YAML.
3. **Hashes, MACs and signatures, by what they prove (Nakov, "Hash Functions" and "MAC and Key Derivation"; the lesson supplies the comparison).** The resources define each; none sets them side by side as judgement. The lesson's picture in words: a hash is a fingerprint of the data, and anyone can take a fingerprint, including an attacker who has just changed the data. So a SHA-256 posted next to a download catches a broken download, not a swapped one, unless the hash itself arrives by a channel the attacker can't touch. A MAC is a fingerprint taken with a secret key: only someone with the key can make one, so it proves "someone who holds this key made it", but every holder can, so it can't say which. A signature is made with a private key only one party holds and checked with its public key: anyone can verify, only one could have signed. Then the table:

   | | Who can make it | Who can check it | Proves |
   | --- | --- | --- | --- |
   | hash (`sha256sum`) | anyone | anyone | the data wasn't damaged, if the hash came safely |
   | MAC (`openssl dgst -sha256 -hmac KEY`) | holders of the key | holders of the key | a key holder made it, and nothing changed since |
   | signature (`openssl pkeyutl -sign`) | the private key's holder | anyone with the public key | that one party made it, and nothing changed since |

   Three real uses the lesson names: GitHub signs each webhook delivery with HMAC-SHA256 of the body under the webhook's secret, in `X-Hub-Signature-256`, and says to compare it in constant time (fact 19); a software release is signed (topic 43's certificates, Module 20's Sigstore); OpenBao's audit log records every request but replaces each secret value with `hmac-sha256:…`, a MAC under a key only OpenBao holds, so the log can be searched for a known value (`sys/audit-hash`) without holding the values (tried, fact 17). The lesson asks why not plain SHA-256 there, and answers with arithmetic (numbers no item reuses): a 10-digit phone number has 10^10 possible values, which a machine doing a billion SHA-256s a second tries in ten seconds. A plain hash of guessable data is the data. Collision resistance in one paragraph: MD5 and SHA-1 have known collisions (SHA-1 is deprecated, IR 8547 Table 8 note), SHA-256 and SHA-3 have none.
4. **Passwords are different (OWASP Password Storage Cheat Sheet, "Password Hashing Algorithms" summary).** A password is low-entropy and reused, so it gets a slow, salted, memory-hard hash: Argon2id with at least 19 MiB, 2 iterations and parallelism 1 (OWASP); scrypt or bcrypt (work factor 10 or more, 72-byte limit) where Argon2id isn't available; PBKDF2-HMAC-SHA256 with 600,000 iterations where FIPS is required (fact 18). A salt is random, per password, stored beside the hash, and not secret; it stops one guess from testing every account at once. Encrypting passwords is wrong too: whoever gets the key gets every password. One sentence: the best stored password is none, which is topic 41's passkeys.
5. **Encryption that can be edited (lesson only, with the worked example's steps 2 and 3; Nakov, "Cipher Block Modes").** The demonstration no reading does, run by the learner in step 2 (tried): `printf 'PAY 100 TO ALEX' | openssl enc -aes-256-ctr -K … -iv …` encrypts with CTR mode; flipping one bit pattern of the fifth byte of the ciphertext with `dd` (XOR with `'1' ^ '9'`) and decrypting prints `PAY 900 TO ALEX`, with no error. CTR encrypts by XORing a keystream with the data, so the ciphertext's bits line up with the plaintext's: anyone who knows or guesses the message's layout can change it without the key. The fix is a tag: an HMAC over the ciphertext (step 2 shows the two HMAC lines differ), or an **AEAD** mode that does both at once. AES-GCM and ChaCha20-Poly1305 are the two in topic 31's cipher suites; GCM's decrypt refuses a changed byte (`cipher: message authentication failed` from OpenBao's transit, tried; `gcm: authentication failed` from the lab's helper). `openssl enc` itself refuses GCM: `enc: AEAD ciphers not supported` (tried), so the labs use a 30-line helper, `gcm`, around the Python cryptography library, as an app would use a library. **Associated data**: data the tag covers but that isn't encrypted (a record's ID), so a ciphertext copied to another record fails to open; AWS calls it the **encryption context** and recommends it on every symmetric call (fact 1).
6. **Nonces (lesson, with SP 800-38D §8.3 as the source).** GCM needs a nonce that is never reused with the same key: reusing one exposes the XOR of the two plaintexts and lets an attacker forge tags. With random 96-bit nonces, NIST's rule is at most 2^32 (4,294,967,296) encryptions per key (fact 10). Worked once in the lesson, with numbers no item reuses: 1,000 messages a second retire a key in about 50 days. Envelope encryption (idea 7) makes this rarely bite, because every object gets its own data key; it bites when an app caches one data key for millions of messages. OpenBao's transit page gives the same advice for its own keys: rotate before the count is reached (fact 15).
7. **Envelope encryption (Google Cloud's "Envelope encryption" page, the main resource, about 1,000 words; AWS's "Envelope encryption" section; the lesson supplies the picture).** The picture in words: a hotel. Every guest's room has its own key (the **data key**). The keys are kept in a safe at reception (the **KMS**), but not loose: each room key is sealed in an envelope that only the safe's master key opens (the **key encryption key**, which never leaves the safe). You can leave the sealed envelope taped to the room door (store the **wrapped data key** next to the data); it's useless without the safe. To get in, you hand the envelope to reception, who checks you're allowed (the **policy**) and writes it in the book (the **audit log**). The flow, which the worked example's step 4 runs:
   1. ask the KMS for a data key: it returns the key in plaintext and wrapped (OpenBao `transit/datakey/plaintext/orders`, AWS `GenerateDataKey`); or make one locally and ask the KMS to wrap it (Google's way: "Generate DEKs locally", fact 5; Azure Key Vault's `wrapKey`);
   2. encrypt the data locally with the plaintext key (AES-256-GCM), then forget the plaintext key;
   3. store the ciphertext and the wrapped key together;
   4. to read, send the wrapped key to the KMS to unwrap, decrypt locally, forget the key.

   Why not send the data to the KMS: AWS KMS `Encrypt` takes at most 4,096 bytes (fact 1) and Google's at most 64 KiB (fact 5), every byte would cross the network, and every read would cost a request. And the point people miss: **the control is the policy, not the algorithm.** Whoever may call unwrap can read everything; so the web front end that writes orders gets "make data keys" and not "unwrap" (topic 40's separation of duties), and the KMS's audit log says who unwrapped what.
8. **Rotation, rewrap and retirement (OpenBao transit page, "Usage" and "Working set management"; AWS's "Rotate AWS KMS keys"; Azure's rotation page).** Rotating a KMS key adds a **version**: new wraps use the newest, old wrapped keys still open with their own version (OpenBao's ciphertexts say which: `vault:v1:…`, `vault:v2:…`, tried). Rotation changes no data and no data keys (AWS: "Key rotation has no effect on the data that the KMS key protects", fact 3). To move old wrapped keys forward, **rewrap** them: the KMS unwraps and rewraps inside itself, and the data key never comes out (OpenBao `transit/rewrap`, AWS `ReEncrypt`). Only then raise the **minimum decryption version** so the old version can't be used (tried: a v1 ciphertext then fails with `ciphertext or signature version is disallowed by policy (too old)`; lowering it again restores it, because OpenBao archives rather than deletes). Order matters, and the debug turns on it. **Where the three clouds differ**, from their pages (facts 3 to 9):

   | | AWS KMS | Azure Key Vault | Google Cloud KMS |
   | --- | --- | --- | --- |
   | Data keys | `GenerateDataKey` returns plaintext and wrapped; `Encrypt` up to 4,096 bytes | your app makes the data key and calls `wrapKey`/`unwrapKey` (Azure Storage's customer-managed keys wrap the account's key this way, needing `wrapkey`, `unwrapkey`, `get`) | your app makes the data key and calls `Encrypt` on it; `Encrypt` up to 64 KiB |
   | Automatic rotation | yearly by default, any period from 90 to 2,560 days; key ID unchanged; old material kept | a rotation policy makes a new version; at least 7 days; rotate at least every two years; versionless key URI picks up the newest | a rotation period makes new versions; old versions stay until destroyed |
   | Old wrapped keys | `ReEncrypt` | rotation re-wraps the DEKs Azure services hold, both versions must stay enabled until done; Azure Storage checks daily, so wait 24 hours before disabling the old one | re-encrypt the wrapped DEKs yourself |
   | Price, read 2026-11-12 | $1 a key a month, plus $1 for each of the first two rotations; about $0.03 per 10,000 requests; 20,000 free a month | Standard: $0.03 per 10,000 operations, $0.15 for advanced keys; $1 per scheduled rotation; HSM keys (Premium) from $1 a key a month | not confirmed (the pricing page renders in the browser) |

9. **How strong is strong enough (SP 800-57 Part 1 Table 2; NIST IR 8547, final October 2026; the lesson supplies the arithmetic).** Security strength in bits: n bits means about 2^n tries to break it. AES-128 and RSA-3072 and ECC P-256 are all 128 bits; RSA-2048 is 112 (fact 11). Each extra bit doubles the work, so 128 bits is 2^16 = 65,536 times 112. Brute force in years, worked once with numbers no item reuses: at 10^18 keys a second in all, half of AES-128's keys take about 5 × 10^12 years. Then quantum computers, in four sentences: a large one would break RSA and elliptic curves outright (Shor's algorithm, named only), so NIST deprecates every quantum-vulnerable public-key algorithm after 2030 and disallows them after 2035, at 112 and 128 bits alike (IR 8547 Tables 2 and 4, fact 12); symmetric algorithms with at least 128-bit strength are unaffected enough to keep (its section 4.1.3); the replacements are ML-KEM for key establishment and ML-DSA for signatures (FIPS 203 and 204), which AWS KMS already offers (fact 2). Traffic recorded today can be decrypted later ("harvest now, decrypt later", IR 8547's own phrase), so key exchange moves first, often as a **hybrid** of X25519 and ML-KEM in one handshake, secure if either part is; IR 8547 calls hybrids "temporary measures" and says NIST will accommodate a hybrid key-establishment mode "when suitably combined with a NIST-approved scheme". Topic 31's AWS policy name ending in `PQ` is one such hybrid. Ubuntu 24.04's OpenSSL 3.0 has no ML-KEM, so the labs don't show it.
10. **The labs (lesson only).** One server, `lab`. OpenBao runs as `openbao.service` and unseals itself at boot from a key the lab made at its first start (topic 45 explains that choice). Your admin token is in `~/.vault-token`; scripts you write get their own token in `BAO_TOKEN`, as an app gets its own sign-in (topic 45). `gcm seal|open IN OUT` reads a base64 key from standard input. The rule of the module: change only what the lab asks for.

### 7.1 `example-seal-an-order` (worked example, lab), skills `hash-mac-signature`, `authenticated-encryption`, `envelope-encryption`

The shop's order exports. Labelled steps, each with its commands and the output to expect:

2. **Encryption that can be edited.** The CTR demonstration of idea 5 (tried): encrypt, flip the byte with `dd conv=notrunc`, decrypt to `PAY 900 TO ALEX`; then an HMAC tag over the ciphertext catches it.
3. **AEAD.** `bao write transit/encrypt/orders plaintext=$(base64 <<< "card 4111")`, then decrypt; change one character in the middle of the ciphertext and decrypt again: `cipher: message authentication failed` (tried). Note the `vault:v1:` prefix: the key version.
4. **An envelope.** `bao write -format=json -f transit/datakey/plaintext/orders` (tried: `ciphertext`, `key_version`, `plaintext`); `gcm seal` the export with the plaintext key on standard input; save the wrapped key as `export.csv.key`; `unset` the variable; open it again by unwrapping with `transit/decrypt`.

### 8.1 Build: `build-sealed-orders` (systemd lab, 50 minutes), skills `envelope-encryption`, `authenticated-encryption`, `choose-the-primitive`

**Brief.** The shop must keep its order exports encrypted at rest under keys it can rotate and take away. From blank, on the lab's OpenBao:

1. a transit key `orders` for AES-256-GCM that rotates itself every 30 days and can never be exported;
2. two policies: `order-writer` may only make data keys from it, `order-reader` may only unwrap with it;
3. `~/bin/seal-order FILE` writes `FILE.sealed` (AES-256-GCM under a fresh data key per file, with `gcm`) and `FILE.key` (that key, wrapped), and leaves no plaintext key anywhere; `~/bin/open-order FILE.sealed` prints the order; each uses the token in `BAO_TOKEN`;
4. the 14 orders already in `/srv/orders/archive` were sealed by an older script whose `.key` files are wrapped by versions 1 and 2 of `orders`: bring every one to the latest version without unwrapping any of them, then make versions older than the latest unusable.

**Checks** (the four marked **tried** kept their contract in the prototype):

- `bao-up` (`timeout: 60`, the one wait): OpenBao answers, unsealed. **Tried.**
- `key-ok`: type `aes256-gcm96`, `auto_rotate_period` 2,592,000 s, `exportable` and `allow_plaintext_backup` false. **Tried.**

### 8.3 Explain

**Prompt:** "A teammate says: 'Our database disk is encrypted, so the card data is safe. For lookups we'll store a SHA-256 of each card number, and we'll encrypt the exports with one AES key we keep in the config file.' Explain, in your own words, what disk encryption does and doesn't protect against; what's wrong with hashing card numbers and what to use instead; how you'd design the exports' encryption with a key management service, including who may read what, rotation and what an auditor can see; what a nonce is and why it matters; and how the three clouds' key services differ in how you'd do this."

**Rubric** (`required` unless marked):

- `layers`: disk encryption protects a stolen disk or snapshot, not anyone who can query the database or the app; encryption is only as good as who can use the key.
- `hash-vs-mac`: a hash of guessable data can be reversed by trying every candidate (10^9 for one bank's cards); use a keyed HMAC with the key in the KMS, or tokenization; passwords get Argon2id with a salt.
- `envelope`: a fresh data key per export, encrypted locally with AES-GCM, wrapped by a KMS key that never leaves the KMS, wrapped key stored beside the data; the writer can make data keys and not unwrap, the reader can unwrap; every unwrap is in the audit log.
- `rotation`: rotation adds a key version and changes no data; rewrap old wrapped keys, then retire the old version; deleting a key makes its data unreadable.
- `aead-nonce`: authenticated encryption, so a change is detected; a nonce never reused with one key, at most 2^32 random nonces per key.
- `clouds` (optional): AWS `GenerateDataKey` and `ReEncrypt`, yearly rotation by default (90 to 2,560 days); Azure Key Vault `wrapKey`/`unwrapKey`, rotation policy at least every two years, versionless URIs; Google: generate locally, `Encrypt` up to 64 KiB, versions; prices in requests.

A model answer is written with the lesson.

## 12. Open questions, each with a recommendation

1. **The key service stand-in: OpenBao, LocalStack's KMS, or openssl and age alone?** OpenBao: real software with Vault's API, used in industry, MPL-2.0, offline, one 182 MB binary; its transit engine has data keys, versions, rewrap, minimum versions, policies and an audit log, which are the ideas the topic exists to teach. LocalStack needs an account token since March 2026 (fact 21) and is much heavier. openssl and age alone have no service, so no policy, no audit, no rotation. **Recommendation: OpenBao**, from its pinned `.deb`, the second lab download from outside Ubuntu's archive after Module 3's step-ca (record it in the devlog and the owner queue's _Decided for you_).
2. **Local AEAD: the `gcm` helper, or openssl CTR plus HMAC written by the learner?** `openssl enc` can't do GCM (fact 13). Writing encrypt-then-MAC with two derived keys in bash is error-prone, long for a beginner, and not what apps do. **Recommendation: the helper** (30 readable lines over python3-cryptography, from the archive), with CTR plus HMAC done by hand once in the worked example so the learner sees what AEAD packages up.
3. **A real-cloud exercise (Azure Key Vault `wrapKey` inside the $150 credit)?** It would cost under a cent, but the learner meets the az CLI, subscriptions and budget alerts only in Module 8, and the spec puts key management on the clouds in Modules 10 and 20. **Recommendation: none here**; every cloud claim is from dated documentation, as Module 3 decided for networking.
4. **Prerequisite on `csa.sec.authn-authz`.** **Recommendation: yes** (section 2), so that policies are a known idea.
5. **One base for crypto and secrets, or a topic layer each?** One base keeps OpenBao's 182 MB in one cached layer and the first-boot units in one place. **Recommendation: `lab-base-sec`**, and the module critic decides whether the identity designer's `lab-base-id` and this base should share a parent (they need different first layers: this one is single-machine systemd, theirs is the network base).
