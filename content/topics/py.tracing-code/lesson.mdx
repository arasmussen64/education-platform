<Intro>

Programmers who can't read code rarely write it well. **Tracing** is reading code the way the computer runs it: one line at a time, writing down what each name refers to as you go. It's the skill behind predicting output, finding bugs, and understanding anyone else's program.

This topic's resource is Python Tutor, a website that traces for you. It's loaded with a short program. Press **Next >** to run one line at a time, and watch the names on the right change. As you step through it, keep your own **trace table** on paper or in a text file:

| line | `total` | `bonus` | printed |
|---|---|---|---|
| 1 | 10 | | |
| 2 | 10 | 3 | |
| 3 | 10 > 8 is `True`, so line 4 runs | | |
| 4 | 13 | 3 | |
| 7 | | | `13 3` |

Then change the first line to `total = 5` in Python Tutor and step through again. Which lines run now? Python Tutor is a good check, but the goal is to need it less and less.

</Intro>

<Recap>

- **A trace table** has a column for each name and a row for each line that changes something. When a line prints, write the output in its own column, exactly as it would appear.
- **Work in order, one line at a time.** The computer doesn't skip ahead, and neither should you. When a line uses a name, look up its *current* value in the table, not its first one.
- **At an `if`, work out the condition with the current values** and write down `True` or `False`. Then follow only that branch: cross out the lines in the branches that don't run.
- **Watch for lines that change a name using its own old value**, like `total = total + bonus`: the right-hand side is worked out first, with the old value, and then the name points at the result.
- **After the trace, say the output out loud**, line by line, before pressing Run. If the real output differs, the trace has found a misunderstanding, which is exactly what it's for.

</Recap>
