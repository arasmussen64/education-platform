<Intro>

Module 1 used `curl -v https://...` to see an HTTP exchange, DNS named the certificate in one sentence, and Congestion control and QUIC put HTTP/3 on QUIC. This topic is the layer in between: **HTTP** as it travels, in versions 1.1 and 2, and **TLS**, the protocol that encrypts it (HTTPS is HTTP inside TLS, on port 443). By the end you can say what HTTP/2 changes, read a TLS 1.3 and a TLS 1.2 handshake message by message and say what anyone watching the network still sees, and set up a web server for several sites on one address with the right versions, HTTP/2 and a stapled OCSP answer. The labs use the shop's web server, `web`, running nginx for `www.shop.test` and `api.shop.test`; a customer's laptop, `office`; `ca`, the shop's own certificate authority's OCSP responder; and `resolver`, the shop's name server.

**HTTP in one paragraph.** A client sends a **request**: a **method** (what it wants done: `GET` to fetch, `POST` to send something), a path (`/account/orders`), then **headers**, lines of `Name: value` such as `Host: www.shop.test`, the name of the site it wants, and sometimes a body. The server sends a **response**: a **status line** with a code (`HTTP/1.1 200 OK`; `404` for not found, `301` for moved), its own headers, and the body, the page itself. HTTP semantics, two topics on, is about what methods and codes promise; this one is about how they travel.

**HTTP/1.1: one request at a time.** HTTP/1.1 keeps its TCP connection open for the next request (a **persistent connection**), but a connection carries one request and its answer at a time: the second request waits until the first answer has arrived in full. One slow answer holds up everything queued behind it on that connection, which is **head-of-line blocking** at the HTTP level. Sending requests without waiting (pipelining) was tried and abandoned, so browsers open several connections to each site instead, commonly six (MDN), each paying for its own TCP and TLS handshakes.

**HTTP/2: many streams on one connection.** HTTP/2 cuts every request and response into binary **frames** (HTTP/2's own frames, not Layers and packets' Ethernet frames), each labelled with a **stream** number, and interleaves the frames of many streams on one connection: **multiplexing**. Each request and its answer is one stream, so a page and forty images travel at once, and a site needs one connection, not six. Headers that repeat in every request (cookies, the browser's name) are compressed with **HPACK**: both ends keep a table, and a header sent once is referred to by number afterwards. The meaning is unchanged (methods, headers and status codes are the same), and the first line becomes headers with names that start with a colon, `:method` and `:path`. What HTTP/2 can't fix is underneath it: TCP delivers bytes complete and in order (TCP and UDP's numbered postcards), so when one packet is lost, every stream waits until it is resent, the head-of-line blocking Congestion control and QUIC described. HTTP/3 runs on QUIC instead, which orders each stream on its own (that topic's). This topic stays with HTTP/1.1 and 2, which nginx speaks here.

**Which version? ALPN.** The two sides agree on HTTP's version inside the TLS handshake, with **ALPN** (Application-Layer Protocol Negotiation): the client lists what it speaks, the server picks one. `curl -v` shows both halves, `ALPN: curl offers h2,http/1.1` and `ALPN: server accepted h2` (`h2` is HTTP/2's name there), and `curl -w '%{http_version}'` prints just `2` or `1.1`.

**Two kinds of encryption.** **Symmetric** encryption uses one secret key both to lock and to unlock: fast, and what protects the conversation itself (AES and ChaCha20, in the labs' captures). Its problem is getting the same key to both ends over a network anyone can read. **Public-key** encryption uses a key pair, like Module 1's SSH keys: a private key kept secret and a public key handed to anyone. It is slow, but it makes two things possible: a **signature** (DNS's word), which proves that the holder of a private key made it, and key exchange.

**Key exchange and forward secrecy.** In a **key exchange** each side makes a throwaway key pair for this one connection and sends the other its public half (in TLS 1.3, the `key_share`). Each combines its own private half with the other's public half, and both arrive at the same secret, which someone who saw both public halves can't work out. The labs' connections use **ECDHE** (Diffie-Hellman on an elliptic curve, the `X25519` in the captures). Because the throwaway keys are deleted afterwards, a recording of today's traffic stays unreadable even to someone who steals the server's own private key next year: that's **forward secrecy**. The server's long-lived key pair is for proving who it is. Its public key is in its **certificate**: the file DNS called the one a server shows to prove which names it may answer for, signed by a certificate authority (CA). The client checks the CA's signature, then the signature on that CA's own certificate, and so on up to a **root CA** it already trusts, as DNSSEC's chain of trust climbs to the root; a CA in between, whose certificate a root signed, is an **intermediate**. It also checks that the name it asked for is among the certificate's names, a list called its **subjectAltName**. Topic 32 builds that chain. Every machine in the labs trusts the shop's own CA. A **cipher suite** names the algorithms a connection uses: `TLS_AES_256_GCM_SHA384` in TLS 1.3 is the symmetric cipher and the hash; TLS 1.2's names add the key exchange and the signature, `ECDHE-ECDSA-AES256-GCM-SHA384`.

**The TLS 1.3 handshake.** The **handshake** is the opening conversation in which the two sides agree on all this before any HTTP is sent. Here is the one the worked example captures with `openssl s_client -trace`:

| Message | From | What it carries | On the wire |
| --- | --- | --- | --- |
| ClientHello | client | the versions and cipher suites it speaks, its key share, the name it wants (SNI), the protocols it speaks (ALPN) | in clear |
| ServerHello | server | the version and suite chosen, its key share: from here both sides have keys | in clear |
| EncryptedExtensions | server | the rest of its answers, such as the ALPN choice | encrypted |
| Certificate | server | its certificate, and the intermediate CA's that signed it | encrypted |
| CertificateVerify | server | a signature over the handshake so far, made with the certificate's private key: proof that it holds it | encrypted |
| Finished | server, then client | a check value over the whole handshake: nobody changed a message on the way | encrypted |
| NewSessionTicket | server, afterwards | a ticket for resuming later without the whole handshake | encrypted |

After its Finished the client can send its request at once: **one round trip** after TCP's. In `-trace` each message sits inside a **record**, TLS's unit on the wire, whose header says `Content Type = Handshake (22)` for the two hellos. From EncryptedExtensions on, the outer type is `ApplicationData (23)`, and only the ends see the `Inner Content Type = Handshake (22)` inside. TLS 1.3's standard, RFC 9846 (July 2026, which replaced RFC 8446), says it in one line: all handshake messages after the ServerHello are encrypted. The `ChangeCipherSpec` records in a 1.3 trace mean nothing; they are sent only so that old boxes in the middle aren't confused.

**TLS 1.2, for comparison.** `ClientHello ServerHello Certificate ServerKeyExchange ServerHelloDone`, then the client's `ClientKeyExchange` and `Finished`, then the server's `NewSessionTicket` and `Finished`. The server sends its certificate in clear, straight after its hello, then its key share (signed) and "done"; the client's share and Finished make a second round trip, and only then may the request go.

**Round trips.** Count them before the first byte of the request leaves: TCP's handshake is one; a full TLS 1.2 handshake adds two (three in all, 240 ms at an 80 ms round trip); TLS 1.3 adds one (two in all); QUIC does both in one. A client that comes back can present its session ticket and resume, skipping the certificate, and TLS 1.3's **0-RTT** lets it send its request along with its very first message, the ClientHello. The price, in RFC 9846's words: "There are no guarantees of non-replay between connections." Someone who records those first packets can send them again, so a server accepts early data only for requests that are safe to repeat, if at all.

**What the wire still shows.** Someone watching sees the addresses and ports, and the ClientHello in clear, including its **SNI** (Server Name Indication), the name of the site. In TLS 1.3 everything after the ServerHello is hidden, the certificate, the path, the headers and cookies included; in TLS 1.2 the certificate crosses in clear too. The worked example counts it: `www.shop.test` appears once in a TLS 1.3 capture and three times in a TLS 1.2 one. **ECH** (Encrypted Client Hello, RFC 9849, March 2026) hides the name as well, with a key the server publishes in DNS; it needs both ends to support it, and Ubuntu 24.04's nginx and OpenSSL don't. To read your own encrypted traffic, a client can write its session keys to a file (`SSLKEYLOGFILE=keys.txt curl ...`), and Wireshark or `tshark` decrypts a capture with them: guard that file like a password.

**nginx's files, briefly.** nginx reads `/etc/nginx/nginx.conf`: settings for the whole server, and an `http { ... }` block whose last line, `include /etc/nginx/sites-enabled/*;`, pulls in one file per site. On Ubuntu a site is written in `sites-available/` and switched on by a link to it in `sites-enabled/` (`ln -s`). Each `server { ... }` block is one site: `listen 443 ssl` (the port, and that it speaks TLS), `server_name` (the names it answers for), `ssl_certificate` and `ssl_certificate_key` (its certificate file and private key), and `root` (the folder its pages come from). `nginx -t` tests the files, `nginx -T` prints every file it reads, `systemctl reload` makes the running nginx read them again without dropping connections, and `/var/log/nginx/error.log` says what it complained about. In the labs: `on web nginx -t`, `sudo systemctl reload nginx@web`.

**Many sites, one address: SNI.** The server must choose a certificate before anything is encrypted, long before the `Host` header arrives: that's what SNI is for. nginx picks the `server` block whose `server_name` matches the SNI name; a client that sends no name, or one no block holds, gets the **default server** for that address and port: the block whose `listen` says `default_server`, or else the first. Choose it on purpose. Either give such clients the site they most likely want, or refuse them: a default block with `ssl_reject_handshake on;` (nginx 1.19.4 on) ends the handshake with an `unrecognized name` alert and no certificate, so no client is handed a certificate for a name it didn't ask for, and a scanner learns nothing about which sites you host. The worked example's server does that.

**Which versions to allow.** TLS 1.0 and 1.1 have been deprecated since RFC 8996 (March 2021); TLS 1.2 is still fine, and plenty of clients stop there (older systems, embedded devices, a partner's integration), so a public server allows **TLS 1.2 and 1.3**: in nginx, `ssl_protocols TLSv1.2 TLSv1.3;`. Two things about nginx 1.24, the version in Ubuntu 24.04 and the labs, both tried in them:

- **It doesn't mean what it says by default.** nginx 1.24's own default still includes TLS 1.0 and 1.1 (nginx dropped them only in 1.27.3), and Ubuntu's `nginx.conf` names them: `ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;`. Ubuntu's OpenSSL refuses 1.0 and 1.1 anyway at its default security level, so a handshake test passes; but the file says otherwise, and a cipher setting that lowers the level (`DEFAULT@SECLEVEL=0`, which someone adds "for an old client") lets them in. Write the versions you mean.
- **The default server decides.** nginx chooses the version before it has chosen a site, so until nginx 1.29.2 an `ssl_protocols` line in any other `server` block on the same address and port is ignored. Set it once, in `nginx.conf`'s SSL Settings, where Ubuntu put it.

**HTTP/2 in nginx 1.24** is a word on the listen line, `listen 443 ssl http2;`, and one such line switches it on for every site on that port (from nginx 1.25.1 it's the `http2 on;` directive instead).

**OCSP stapling.** A CA can **revoke** a certificate before it expires, when its key is stolen, say. **OCSP** lets a client ask the CA's responder "is the certificate with this serial number still good?", and the responder answers with a signed reply that says `good`, `revoked` or `unknown`, and until when the reply holds. Asked by the browser, that costs a round trip to the CA and tells the CA which site its user is visiting. **Stapling** has the server fetch the signed answer itself and attach it to its handshake, and `openssl s_client -status` shows it: `OCSP response: no response sent`, or an `OCSP Response Status: successful` block with `Cert Status: good`. In nginx it takes three things, all in the worked example:

- `ssl_stapling on;`
- the full chain in `ssl_certificate` (the site's certificate followed by the intermediate's, the file usually called `fullchain.pem`): nginx must know who issued the certificate to ask about it and check the answer. With the site's certificate alone it logs `"ssl_stapling" ignored, issuer certificate not found`.
- a `resolver`. nginx looks the responder's name up once, with the machine's own resolver, when it loads its settings; `resolver 10.0.9.53;` tells it which name server to ask again each time it fetches an answer, so it follows a responder that moves. Without one it keeps the first address and warns `no resolver defined`. One that doesn't answer is worse than none: after its 30-second timeout every fetch fails, `could not be resolved (110: Operation timed out)`, and nothing is stapled.

nginx fetches the answer only when a handshake first asks for one, so **the first handshake after a start goes without**. nginx handles connections in several **worker processes**, copies of itself, and each fetches its own answer, which is why the labs run only one.

**Stapling today.** Let's Encrypt, the largest public CA, dropped OCSP addresses from its certificates on 7 May 2025 and turned its responders off on 6 August 2025, for privacy. It publishes revocations in lists (CRLs) instead, and certificates are getting shorter-lived (topic 32). A Let's Encrypt certificate has nothing to staple; stapling still matters with CAs that run OCSP, such as companies' own CAs, like the labs'.

**Where the three clouds differ.** Their layer 7 load balancers end TLS for you (the client's TLS connection stops at the load balancer, which holds the certificate), and their defaults aren't always the advice above (each provider's pages, read 2026-11-12):

| | AWS Application Load Balancer | Azure Application Gateway | Google Cloud's Application Load Balancers |
| --- | --- | --- | --- |
| TLS versions by default | a listener made in the console: 1.2 and 1.3; one made with the CLI, CloudFormation or the CDK: `ELBSecurityPolicy-2016-08`, TLS 1.0 to 1.2 and no 1.3 | a gateway made with API version 2023-02-01 or later: 1.2 and 1.3 (`AppGwSslPolicy20220101`); support for TLS 1.0 and 1.1 ended on 31 August 2025 | with no SSL policy attached: the `COMPATIBLE` profile, minimum TLS 1.0 |
| Several sites on one address | a certificate list on the listener, chosen by SNI | multi-site listeners, one per host name, with SNI choosing the certificate | several certificates on the proxy, chosen by SNI |
| A client with no SNI, or a name no certificate holds | the listener's default certificate | not stated on the pages read | the first certificate, "the default (primary)" |

So on every cloud the TLS policy is something to set, not to trust: name it whenever you create a load balancer, however you create it.

Then MDN's "Evolution of HTTP" for the three versions, nginx's pages on `ssl_protocols`, `ssl_stapling` and `ssl_reject_handshake`, and Let's Encrypt's post on ending OCSP. The rest are optional: the TLS 1.2 version of the illustrated connection, High Performance Browser Networking's chapter on HTTP/2, and the clouds' pages behind the table. The quick questions read `curl`, `openssl` and `tshark` output from the labs and count round trips. <Recap>

- **HTTP:** a request (method, path, headers such as `Host`, a body) and a response (status line, headers, body). HTTPS is HTTP inside TLS, on port 443.
- **HTTP/1.1** carries one request at a time per connection (head-of-line blocking at HTTP), so browsers open about six per site. **HTTP/2** multiplexes **streams** of binary frames on one connection, with **HPACK** header compression; one lost TCP packet still stalls every stream, which HTTP/3 on QUIC removes. **ALPN** picks the version in the handshake: `ALPN: server accepted h2` in `curl -v`, `curl -w '%{http_version}'`.
- **Encryption:** symmetric (one key, fast, the conversation) and public-key (a pair: signatures and key exchange). **ECDHE** key exchange with throwaway keys gives **forward secrecy**; the certificate's key only proves who the server is (CertificateVerify). A **cipher suite** names the algorithms.
- **TLS 1.3:** ClientHello (key share, SNI, ALPN) and ServerHello in clear; EncryptedExtensions, Certificate, CertificateVerify, Finished encrypted (`ApplicationData (23)` outside, `Inner Content Type = Handshake (22)`); the client's Finished; NewSessionTickets after. One round trip after TCP's. **TLS 1.2:** Certificate in clear, ServerKeyExchange, ServerHelloDone, ClientKeyExchange, Finished: two round trips.
- **Round trips before a request:** TCP 1, + TLS 1.2 2 = 3, + TLS 1.3 1 = 2; QUIC 1. **0-RTT** on resumption: "no guarantees of non-replay", so only requests safe to repeat.
- **An observer sees** addresses, ports and the SNI name (in TLS 1.2 the certificate too), never the path, headers or cookies. **ECH** (RFC 9849) hides the name where both ends support it. A key log (`SSLKEYLOGFILE`) decrypts your own captures.
- **nginx:** `nginx.conf`'s `http` block includes `sites-enabled/*` (links to `sites-available/`); a `server` block is a site (`listen 443 ssl http2`, `server_name`, `ssl_certificate` with the **full chain**, `ssl_certificate_key`, `root`). `nginx -t`, `nginx -T`, `systemctl reload`, the error log.
- **SNI and the default server:** no name or an unknown one gets the `default_server`; `ssl_reject_handshake on` there refuses with `unrecognized name` and no certificate.
- **Versions:** TLS 1.2 and 1.3 (RFC 8996 deprecated 1.0 and 1.1). nginx 1.24 allows 1.0 and 1.1 by default and Ubuntu's `nginx.conf` names them; set `ssl_protocols TLSv1.2 TLSv1.3;` in `nginx.conf`, since the default server's value decides for the whole port before nginx 1.29.2. HTTP/2 in 1.24: `listen ... http2` (one line is enough for the port).
- **OCSP stapling:** `ssl_stapling on`, the full chain, and a `resolver` that answers; `openssl s_client -status` shows `no response sent` or `OCSP Response Status: successful` and `Cert Status: good`. The first handshake after a start goes without. Let's Encrypt ended OCSP in 2025.
- **Clouds:** AWS's ALB from the CLI gets a 2016 policy with TLS 1.0, Google's load balancer with no policy starts at 1.0, Azure's gateways from API 2023-02-01 start at 1.2; all choose certificates by SNI, and AWS and Google give a client without SNI the default certificate. Set the policy yourself.

</Recap>
