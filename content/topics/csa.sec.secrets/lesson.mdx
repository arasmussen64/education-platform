<Intro>

<Puzzle question="A developer commits a file with a payment key in it by mistake, notices, and deletes the file in the next commit ten minutes later. Is the key safe now?">

No. Deleting a file in git doesn't remove it from the past. Every commit keeps a full copy of every file as it was at that moment, so the key is still in the earlier commit, and anyone who has the repository, or cloned it in those ten minutes, or clones it next year, can print it with one command. On a public code host, automated collectors read new commits within minutes. The only thing that makes that key safe again is to make it worthless: revoke it at the service it belongs to and issue a new one. The rest of this lesson follows from that: a secret can't be called back, so it has to be kept out of the places that copy it, and it has to be easy to kill.

</Puzzle>

A **secret** is a value that gives access to whoever holds it: a password, an API key, a token, a private key, a database connection string with a password in it. Applied cryptography was about keys that never leave a key service. Most secrets can't be like that: a program has to hold its database password to use it. So this topic's questions are plainer ones: where a secret gets copied to without anyone meaning it, and who can read it there; how to find the copies, and what to do when one is found; how a program gets its very first credential; and whether a secret can be made so short-lived that leaking it stops mattering.

The numbers say this goes wrong constantly. GitGuardian counted 28.65 million new secrets in public GitHub commits in 2025, up 34% on the year before; and of the leaked credentials it had confirmed as working in 2022, more than 64% still worked in January 2026. Secrets get out, and then nobody kills them. The name for the first half is **secret sprawl**: copies of a secret spreading to places nobody tracks. A place built to stop it is a **secrets manager**: a service that stores secrets encrypted, hands each one only to the callers its policy allows, and logs every read. OpenBao is one, with its key-value store under `secret/` (`bao kv put PATH name=value` stores, `bao kv get -field=NAME PATH` reads one field); AWS Secrets Manager, Azure Key Vault and Google Secret Manager are the clouds'.

**Out of the code, and why history matters.** The first leak is the oldest: the secret is typed into a file that goes into version control. You need the minimum of git to see why that is so bad, and no earlier topic used it, so here it is.

git is the tool nearly every team keeps its code in. A **git repository** is a folder whose every saved state git keeps, in a hidden `.git` folder inside it. Each saved state is a **git commit**: a full record of every file as it was, with an author, a date and a message, named by a long hex string (`62083d5...`; the first seven digits are enough to name it). A commit never changes afterwards. `git log --oneline` lists the commits, newest first. `git show COMMIT` prints what a commit changed, and `git show COMMIT:PATH` prints one file as that commit has it. `git clone` copies a repository, with all of its history, to another folder or another machine; `git push` sends your new commits to the server everyone shares, which holds a repository with no working files, only the history (a "bare" one).

Put those together, and you have the puzzle's answer: deleting a file makes a new commit without it, and the earlier commit still holds it, on the server and in every clone. Rewriting history on your own copy doesn't reach other people's clones, forks, backups and caches, so for a secret that has been pushed, cleaning is at best housekeeping. The fix is to revoke it. (Settings that aren't secret, a host name, a port, belong in the repository. Secrets never do.)

**Out of the process table, the environment and the logs.** A secret that isn't in the code still has to reach the running program, and the common ways of handing it over leak too. Linux shows every running process as a folder, `/proc/PID` (PID is the process's number, as `ps` prints it), and two files in it matter here: `cmdline`, the command the process was started with, arguments and all, and `environ`, its environment variables. In the lab, for a job running as the user `export`:

```
-r--r--r-- 1 export export 0 Nov 23 05:15 /proc/878/cmdline
-r-------- 1 export export 0 Nov 23 05:15 /proc/878/environ
```

The command line is readable by everyone. The environment is readable by the process's own user (and by root).

| How the program gets its secret | Who else can read it |
| --- | --- |
| a command-line argument (`--api-key=...`) | every user of the machine: `ps -eo user,args` prints it |
| an environment variable | the same user and root; every program the process starts, which inherits it; and whatever prints the environment: crash reports, debug pages, a script that runs `env` |
| `Environment=` in a systemd unit | everyone: unit files are readable by all, and `systemctl show NAME -p Environment` prints the line |
| a file with mode `0400`, owned by the service's user | that user and root |
| a **systemd credential** (`LoadCredential=NAME:FILE` in the unit) | that service alone: systemd hands it the secret as a file in a private folder (`$CREDENTIALS_DIRECTORY`), and it is not in the environment and not passed on to child processes |

"Put it in an environment variable" is common advice. It is better than the code and worse than a file. In 2021 an attacker added one line to a script that thousands of build pipelines downloaded and ran, a coverage tool's uploader: it sent the output of `env` to a server of theirs, and every pipeline that passed secrets as environment variables handed them over. (The attacker had got in through a credential left inside one of that company's container images, the next section's subject.) OWASP's advice is to use environment variables for secrets only when no other way is possible.

When you create a secret file, make the empty file first, with its owner and mode, and only then write the secret into it. A file made with the default mode and fixed afterwards is readable by others for a moment. In the labs: `sudo install -m 400 -o export -g export /dev/null FILE`, then pipe the secret in through `sudo tee FILE > /dev/null`.

Two more places catch people out. **Logs:** a program that logs its requests at debug level prints their headers, and an `Authorization` header is the secret. The journal is readable by everyone in the group `adm` and by every system the logs are shipped to. And command lines reach the journal by themselves: `sudo` writes every command it runs there, and beside each line a program logs, the journal stores that program's own command line. So a secret typed as an argument can end up in the logs without the program ever printing it. The rule that covers all of it: a secret travels through files and pipes, never as an argument. `bao kv put PATH name=-` reads a value from standard input for that reason, and `curl -H @-` reads a header from there.

**Out of images.** How containers work said an image is a stack of layers, each holding the files one build step added or changed, and that deleting a file in a later step adds a whiteout, a marker that hides it. Hiding is not removing. The first lab unpacks an image whose recipe did this:

```
ARG PAYGATE_KEY
COPY deploy.token /tmp/deploy.token
RUN echo "checked the gateway with $PAYGATE_KEY" > /opt/checked.txt && rm /tmp/deploy.token
```

Two secrets went in and both are still there. The token is in the layer that `COPY` made, as `tmp/deploy.token`; the next layer holds only `tmp/.wh.deploy.token`, the whiteout. And the build argument is in the image's **history**, the list of build steps that every image carries: `podman history` (or `docker history`) shows the `RUN` step as `|1 PAYGATE_KEY=pg_live_...` followed by the command. `ENV` values sit in the image's settings in the same way. Everyone who can pull the image can read all three. Docker's documentation puts it flatly: build arguments and environment variables are "inappropriate for passing secrets to your build".

The right tool is a **build secret**, also called a secret mount. The step that needs the secret asks for it:

```
RUN --mount=type=secret,id=pkg wget --header "Authorization: Bearer $(cat /run/secrets/pkg)" ...
```

and the build is given the file: `podman build --secret id=pkg,src=FILE ...` (the same words with `docker build`). For that one step the secret is a file at `/run/secrets/pkg`. It is mounted over the step, not written by it, so it is in no layer, and the history records the command as written, not the token. The second lab builds an image this way and then searches every layer, the history and the settings for the token, as text, as base64 and as hex.

The labs build with **podman**, a tool with docker's commands and file formats that needs no background service; what you learn there works with `docker` unchanged. A recipe is called a `Containerfile` there, and it is a Dockerfile by another name.

**Catching leaks: scanners.** A **secret scanner** searches files and git history for secrets. The labs use gitleaks; trufflehog is the other one you'll meet. A scanner decides in two ways:

- **Rules that know a format.** An AWS access key ID starts `AKIA` and has 16 more characters. A GitHub token starts `ghp_`. A private key has its `-----BEGIN ... PRIVATE KEY-----` line. These are found reliably, and you can add a rule for a format of your own: the labs add one for the payment gateway's keys, `pg_live_` and 32 letters and digits.
- **A general rule.** A word like `key`, `secret` or `password` next to a string that looks random. "Looks random" is measured as **entropy**: 40 hex digits score high, a word and a year score low.

So scanners are good at generated keys and bad at passwords people choose. In the lab, gitleaks' general rule reported `api_key = "` and 40 random hex digits, and passed straight over `db_password = "Summer2026!"` on the line above. That is a false negative, and it's why a clean scan means "nothing that looks like a secret", never "no secrets". The opposite mistake, a random-looking test value reported as a secret, is answered with an allowlist: a list of paths or patterns the scanner should let pass, kept as small as you can make it.

`gitleaks detect --source DIR` scans every commit of the repository in DIR and names, for each finding, the rule, the file and the commit that added it. `--no-git` scans the files as they are now, which misses everything that was added and deleted again. `--config FILE` names the settings: a TOML file where `[extend]` with `useDefault = true` keeps the built-in rules, each `[[rules]]` block adds one, and `[allowlist]` lists what may pass. `-v` prints the findings and `--redact` blanks the secrets in them, so that the scanner's own output isn't one more leak. It exits 1 when it finds something. (The labs have Ubuntu's gitleaks, 8.16; from 8.19 the same scans are called `gitleaks git` and `gitleaks dir`.)

Where the scan runs matters more than which scanner it is:

| Where | What it catches | How it's got round |
| --- | --- | --- |
| On the developer's machine, before a commit (a pre-commit hook running `gitleaks protect --staged`) | the mistake, before it is even a commit | `git commit --no-verify` skips it, and a fresh clone doesn't have it |
| On the git server, when a push arrives (a **pre-receive hook**) | every commit the push brings, before the server accepts any | it can't be skipped by the person pushing; it is as good as its scanner (below) |
| In CI, after the push | whatever is in the repository by then | too late to stop it, and a scan of a clone obeys the clone's own settings |
| On the code host (**push protection**) | formats the host knows | on GitHub, anyone with write access can bypass it by giving a reason |

A pre-receive hook is a script in the server's repository that git runs once for each push, before accepting anything. It reads one line for each branch pushed, `OLD NEW REF` (the commit the branch pointed at, the one it will point at, and the branch's name), and if it exits with an error the whole push is refused and its output is shown to the person pushing. Scanning the range `OLD..NEW`, the commits in NEW that aren't in OLD, catches a secret that one commit of the push adds and a later one removes. The third lab writes this hook.

One trap, tried in the lab. With no `--config`, gitleaks uses the `.gitleaks.toml` at the top of the folder it scans. In a clone that file comes from the repository, so a push can bring its own: a commit that added a key together with a `.gitleaks.toml` allowing everything passed a scan of a clone. The same scan inside the server's bare repository, which has no working files, found the key. Whoever is being scanned must not be able to write the scanner's rules: keep the settings on the server and name them.

And a hook can't be skipped, but its scanner can be fooled. Tried against the third lab's finished hook, each of these went through: a key on a line that ends with the comment `gitleaks:allow` (gitleaks' own way to mark a false positive, which 8.16 can't switch off); a key in a file under a folder called `vendor` or `node_modules`, which the built-in rules leave alone; a key split over two lines, or written as base64, or put in a commit's message. A server-side scan stops mistakes, which is most leaks. It doesn't stop someone who means to get a secret through, and what covers that is the rest of this lesson: secrets that are quick to revoke and short-lived to begin with.

GitHub's push protection is the hosted version: on by default for users pushing to public repositories, off by default for repositories until an owner enables it. And trufflehog adds one thing gitleaks doesn't do: it can **verify** a finding by trying the credential against the service it belongs to, which tells you which of 200 findings still work, and also means it sends what it finds to outside services (`--no-verification` turns that off).

**When one gets out: revoke first.** The order, for any leaked secret:

1. **Revoke it,** or rotate it: make the leaked value stop working. Minutes count, and nothing below can substitute.
2. **Give the service a new one,** delivered the right way.
3. **Read the record.** The service the secret belongs to usually logs each use. What was this key used for while it was out, and from where?
4. **Clean up** where it leaked, so that scanners stop tripping over it.
5. **Find the cause,** and fix that, or the new secret follows the old one out by the same path.

And one rule for judging any secret afterwards: one that has been anywhere it shouldn't be, a log, a command line, a chat message, is no longer a secret, even if nobody is known to have read it. It gets replaced.

How long was a leaked secret usable? From the leak to the revocation. Say a key is pushed at 14:40, the next scheduled scan runs at 18:00 and finds it, the person on call takes an hour to work out whose it is, and revoking takes ten minutes: 200 + 60 + 10 = 270 minutes. Each part has its own cure: a server-side hook removes the first, a good alert shortens the second, and revocation that is one command shortens the third.

<Story title="Uber's key on a code-sharing site, 2016" source="https://www.ftc.gov/news-events/news/press-releases/2018/04/uber-agrees-expanded-settlement-ftc-related-privacy-security-claims" sourceTitle="Uber Agrees to Expanded Settlement with FTC Related to Privacy, Security Claims" license="linked, not copied">

In November 2016 Uber learned that intruders had been in its cloud storage. They hadn't broken anything. An Uber engineer had posted an access key on a code-sharing website, the intruders found it there, and the key opened storage at Uber's cloud provider that held unencrypted files: more than 25 million names and email addresses, 22 million names and mobile phone numbers, and 600,000 names with driver's license numbers.

What Uber did next is why the case is remembered. It paid the intruders $100,000 through its bug bounty program, the scheme meant to reward people who report weaknesses responsibly, and told neither its customers nor the regulator, which was at that moment investigating an earlier, similar breach. The breach became public a year later, in November 2017, and the US Federal Trade Commission widened its settlement with the company to require that such incidents be reported.

In this lesson's terms: one static, long-lived key, copied to a place that keeps everything and shows it to everyone, and still working when it was found. No scanner stopped the push, nothing revoked the key, and the storage it opened had no second control behind it.

</Story>

**Rotating without downtime.** **Secret rotation** is replacing a secret with a new one and making the old one stop working: on a schedule, to limit how long an unnoticed leak lasts, and at once after a known one. It is two steps, and the trouble is the time between them. Change a database password first, and every program still holding the old one fails until it is told. Tell the programs first, and they fail until the database is changed.

The way out is to have two valid at once, briefly. The labs' payment gateway lets the shop have two active keys: make the new key, move the programs to it, and only then revoke the old. AWS Secrets Manager does the same for database passwords with alternating users: two database users with the same rights, where each rotation changes the password of the one not in use and then switches over, so a program that fetched the secret a moment earlier still holds a pair that works. Its simpler strategy, single user, changes one password in place and accepts a short moment when the database and the stored secret disagree.

Two things to remember about two-at-once. A rotation isn't finished until the old one is revoked: until then there are simply two secrets, and the older one opens as much as it ever did. And with alternating users each password lives for two rotation periods, so a scheduled period of 14 days means a leaked password can work for 28.

**Where the three clouds differ** (each provider's documentation, read 2026-11-23):

| | AWS Secrets Manager | Azure Key Vault | Google Secret Manager |
| --- | --- | --- | --- |
| Who rotates | AWS runs it: managed rotation for some services' secrets, otherwise a Lambda function of yours that it calls on schedule | your code: Key Vault publishes a "near expiry" event 30 days before a secret's expiry date, and a function you wrote makes the new password | your code: it sends a `SECRET_ROTATE` message on your schedule and rotates nothing itself |
| How often | as often as every four hours, at most 999 days apart | on the expiry dates you set | a period of at least one hour |

So "rotation is enabled" means something different on each. All three give the same advice underneath (Azure's page opens with it: use a managed identity, not a stored secret, wherever you can): the best stored secret is none, which is where the rest of this lesson goes.

**Secret zero.** Move every password into a secrets manager, and one question is left: how does the program prove to the manager who it is? If the answer is "with a token in a file beside it", you have swapped twenty static secrets for one static secret that opens the other twenty. That first credential is **secret zero**. Think of a key box by the front door for the cleaner: the keys are safe in the box, the box needs a code, and the code has to reach the cleaner somehow.

Hiding the token better doesn't solve it. Two things do.

**The platform vouches for the workload.** Something started this program and knows what it is. A cloud knows which VM it launched with which role, and its metadata service hands that VM temporary credentials (Boot, cloud-init and instance metadata showed it: no key stored on the VM). Kubernetes, the system that runs containers across many machines, gives each of its workloads a signed token. A CI system signs one for each job. In every case the workload holds no stored secret: it holds a short-lived, signed statement from the platform about who it is, a JWT as SAML, OAuth 2.0 and OIDC taught them, and the secrets manager validates it as that topic taught: the signature against the platform's public key, the issuer, the audience, the expiry.

In the build lab a small program plays the platform. Every three minutes it signs a ten-minute token for each workload on the machine, with the subject `workload:NAME` and the audience `openbao`, into a file only that workload's user can read. OpenBao is told to trust it like this:

```
bao auth enable jwt
bao write auth/jwt/config jwt_validation_pubkeys=@/etc/lab-platform/signing.pub bound_issuer=https://platform.shop.test
bao write auth/jwt/role/mailer role_type=jwt user_claim=sub bound_subject=workload:mailer bound_audiences=openbao token_policies=mailer token_ttl=1h
```

The first line switches on sign-in by JWT at `auth/jwt`. The second gives it the platform's public key (`@FILE` reads a value from a file) and the one issuer to accept. The third makes a role: which subject may use it, for which audience, and which policy the resulting OpenBao token gets. A workload signs in with `bao write auth/jwt/login role=mailer jwt=TOKEN` and gets an ordinary OpenBao token that lasts an hour.

**The bindings are the security.** A signature proves the platform made the token. It doesn't say which workload it is for: the subject does. In the lab, a role with `bound_audiences` and no `bound_subject` let every workload on the machine sign in and take the credentials meant for one; so did a pattern such as `workload:*`. With `bound_subject` set, another workload's token is refused with `invalid subject (sub) claim`, one meant for another audience with `invalid audience (aud) claim`, and an old one with `token is expired`. Name the subject exactly.

**A trusted deployer and a wrapper.** Where no platform identity exists, the next best is a first credential that barely lives. OpenBao's **AppRole** is a sign-in for programs: a RoleID, which names the role and isn't secret, and a SecretID, which is the password and can be limited to one use and a few minutes. The tool that deploys the program, which is already trusted, asks OpenBao for a SecretID and delivers it. To protect it on the way it asks for **response wrapping** (`bao write -wrap-ttl=120s -f auth/approle/role/NAME/secret-id`): OpenBao doesn't return the SecretID but a single-use token that can be exchanged for it once, within two minutes (`bao unwrap TOKEN`). If anyone intercepts the wrapper and opens it, the program's own unwrap fails with `wrapping token is not valid or does not exist`, and that failure is the alarm: someone else has the credential, so revoke it and find out who. (A used single-use SecretID is refused with `invalid role or secret ID`.) The cost: after every restart somebody has to deliver a new one.

**The manager's own key.** A secrets manager has a secret zero too. OpenBao encrypts its store and must be given its **unseal key** at each start. Three ways: people hold shares of it, and enough of them must type theirs after every restart (safe, and slow at three in the morning); or **auto-unseal**, where the key is stored wrapped and a cloud's KMS unwraps it for this server's platform identity, which is envelope encryption from Applied cryptography with the platform vouching again; or a key in a file beside it. The labs do the third, OpenBao's `static` seal: whoever can read `/etc/openbao/unseal.key` can open everything. Its documentation says to evaluate that choice carefully. It is fine for a lab whose every secret is made at boot and thrown away, and wrong for anything real.

**Dynamic secrets.** Now the idea that changes the most. A static secret is made once, shared by every copy of a program, and lives until someone remembers to rotate it. A **dynamic secret** is made on request, for one caller, with a **lease**: a lifetime, after which the secrets manager removes it. OpenBao's database engine does this for database accounts:

```
bao secrets enable database
bao kv get -field=password secret/db/admin | bao write database/config/shop plugin_name=postgresql-database-plugin allowed_roles=report connection_url='postgresql://{{username}}:{{password}}@127.0.0.1:5432/shop' username=bao_admin password=-
bao write -f database/rotate-root/shop
bao write database/roles/report db_name=shop default_ttl=10m max_ttl=1h creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON orders TO \"{{name}}\";"
```

The second line connects OpenBao to the database with an admin account that may create other accounts. The third, **rotate-root**, has OpenBao change that account's password to one only OpenBao knows: from then on no person and no file has it. The fourth makes a role: the SQL to run for each new account (OpenBao fills in the name, the password and the expiry), which is where least privilege lives, here reading one table; and two lifetimes.

Then `bao read database/creds/report` returns a new account every time it is asked:

```
lease_id           database/creds/report/X44P82iPIa3x7VetPK5WLU28
lease_duration     10m
password           K17DchdRr7-XRnxpbQUq
username           v-token-le-report-yW7dDR7lNUdnbNmjYl2E-1795410928
```

The name says who asked (`token-le`, the start of the asking token's name) and for which role, so the database's own logs name the workload behind every statement. In the lab that account could count the orders and was refused a `DELETE` with `permission denied for table orders`.

The two lifetimes work together. `default_ttl` is how long a lease lasts unless it is renewed; `max_ttl` is the ceiling, counted from the moment of issue, that no renewal can pass. A credential issued at 09:30 with a default of 30 minutes and a maximum of 2 hours can be renewed at 09:55, 10:20 and so on, and at 11:30 it ends whatever its holder does; the program must ask for a new one, which is a new account with a new password. A copy of the program that crashes stops renewing, and its account is gone within 30 minutes.

And it can be ended early. `bao lease revoke -prefix database/creds/report` ends every account that role ever issued, at once: in the lab the same user and password got `password authentication failed` two seconds later. That one command is the incident response for a dynamic secret. Compare it with hunting a shared password through every config file of every copy of an app.

The arithmetic is the argument. A static password rotated once a year and leaked at a random moment works for half a year more on average. A dynamic one that lasts an hour works for 30 minutes on average, and most leaked secrets are found by an attacker hours or days after they leak, when it is long dead. Dynamic secrets don't stop leaks. They make what leaks worthless.

**The agent.** A program doesn't have to learn any of this. **OpenBao Agent** is the same `bao` program run as a helper beside it (`bao agent -config=FILE`): it signs in for the program, fetches the secret, writes it to a file from a template, and fetches a new one before the old one ends. A whole configuration, for a workload called `mailer`:

```
vault {
  address = "http://127.0.0.1:8200"
}

auto_auth {
  method "jwt" {
    config = {
      path                     = "/run/platform/mailer/token"
      role                     = "mailer"
      remove_jwt_after_reading = false
    }
  }
}

template {
  destination = "/run/mailer/smtp.conf"
  perms       = "0400"
  contents    = <<EOT
{{ with secret "database/creds/mailer" }}user={{ .Data.username }}
password={{ .Data.password }}
{{ end }}
EOT
}
```

`vault` says where OpenBao is (the block keeps the name of the program OpenBao continues). `auto_auth` says how to sign in: with the platform's token file, as the role `mailer`, leaving the file alone (by default the agent deletes it after reading, and here the platform owns it). `template` says what to write where: `{{ with secret "PATH" }}` asks OpenBao for the secret at PATH, `{{ .Data.NAME }}` is one of its fields, and the lines between are written to `destination` with the mode `perms`. Run it from a unit as the program's own user, with `RuntimeDirectory=mailer` so that systemd makes `/run/mailer` for that user at each start. The program reads a file, as it always did, and nothing in the chain is a secret anybody has to keep: the platform token lasts ten minutes, the OpenBao token an hour, the database account a day at most.

What is still static? Three things: the admin account OpenBao uses at the database, which only OpenBao knows after rotate-root; OpenBao's own unseal key; and the platform's signing key. A design like this doesn't remove long-lived secrets. It reduces them to a few, in places built to guard them.

<Recap>

- **A leaked secret can't be called back.** git keeps every **commit** in every clone; deleting a file doesn't remove it from history. The fix for a pushed secret is to **revoke** it.
- **Who can read what:** command-line arguments, every user (`ps`); environment variables, the same user, root, every child process and anything that prints `env`; `Environment=` in a unit, everyone; a `0400` file owned by the service, that user and root; a systemd credential, that service alone. Secrets travel through files and pipes (`name=-`), never as arguments, and never into logs.
- **Images keep everything:** a build argument is in the history, `ENV` in the settings, a file deleted by a later step still in the earlier layer. Use a **build secret**: `RUN --mount=type=secret,id=NAME`, read from `/run/secrets/NAME`, given with `--secret id=NAME,src=FILE`.
- **Scanners** (`gitleaks detect --source DIR --config FILE`): format rules find generated keys; the general rule goes by **entropy** and misses chosen passwords. Scan the whole history. Enforce in a **pre-receive hook** on the server, scanning `OLD..NEW` with the server's own settings. It can't be skipped, and it can be fooled: it stops mistakes.
- **After a leak:** revoke, replace, read the provider's record, clean up, find the cause. Usable time = leak to revocation.
- **Rotation** is two steps; keep two valid at once (two keys, alternating users) and finish by revoking the old one. AWS Secrets Manager rotates for you; Azure Key Vault and Google Secret Manager send an event and your code rotates.
- **Secret zero**, the first credential, is solved with identity, not hiding: the platform signs a short-lived token for the workload, and the secrets manager checks signature, issuer, audience and the exact subject. Otherwise **AppRole** with a single-use SecretID delivered by **response wrapping**, where a failed unwrap is an alarm. The manager's own **unseal key**: shares, or **auto-unseal** with a cloud KMS.
- **Dynamic secrets:** `database/config/NAME` (then `rotate-root`), `database/roles/NAME` with its creation SQL, `default_ttl` and `max_ttl`; `bao read database/creds/NAME` makes an account with a lease; `bao lease revoke -prefix` ends them all.
- **OpenBao Agent** signs in with the platform token (`auto_auth`) and keeps the credentials fresh in a file (`template`). What stays static: the manager's admin account at the database, its unseal key, the platform's signing key.
