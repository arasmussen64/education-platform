<Intro>

"The server is slow." Nothing else. This topic is a method for turning that sentence into a cause in a few minutes, using tools from the earlier topics in a fixed order, so you never have to guess and never have to change a setting to see what happens.

**The USE method.** Brendan Gregg's checklist: for **every resource** (each CPU, memory, each disk, each network interface), ask three questions. **Utilisation**: how busy is it, as a percentage of time or capacity? **Saturation**: is work queueing because the resource can't keep up? **Errors**: is anything failing? The order of importance is the reverse of how people usually look. A CPU at 100% doing useful work is fine; a run queue longer than the number of CPUs means tasks are waiting, and that's slow. A disk at 90% utilisation may be fine; a queue of ten requests with 50 ms waits is not. Errors (an OOM kill, a disk timeout, dropped packets) are rare and decisive. Work through the resources, write down what you find, and the bottleneck is usually the one with saturation or errors.

**The first minute.** Netflix's engineers wrote down the ten commands they run on a slow Linux machine, and the list has held up:

1. `uptime`: the load averages. Rising from the 15-minute to the 1-minute figure means it's getting worse now.
2. `dmesg -T | tail`: the kernel's recent complaints. OOM kills, disk timeouts, "TCP: out of memory".
3. `vmstat 1`: every second: `r` (runnable tasks; more than the CPU count is saturation), `si`/`so` (swapping), `us`/`sy`/`id`/`wa` (CPU split; `wa` is time waiting on disk), `st` (steal).
4. `mpstat -P ALL 1`: the same per CPU. One CPU at 100% with the rest idle is a single-threaded program at its limit, which the average hides completely.
5. `pidstat 1`: which processes are using the CPU, second by second.
6. `iostat -xz 1`: each disk's `r/s`, `w/s`, kB/s, `await` (average time a request waits, in ms), `aqu-sz` (the queue) and `%util`. Near 100% busy, with a queue above 1 and rising await, is a saturated disk.
7. `free -m`: memory, and how much of "used" is really cache (the `available` column).
8. `sar -n DEV 1`: each interface's packets and kB/s in and out. A gigabit link carries about 125,000 kB/s; near that, it's saturated.
9. `sar -n TCP,ETCP 1`: new connections per second, and **retransmits**. Retransmits mean packets are being lost or the path is congested, which may be somewhere else entirely.
10. `top`: everything at once, to confirm.

Ten commands, one minute, and you know whether the machine is short of CPU, memory, disk or network, and which process is involved. Save the output: it's your baseline for "did the fix work?".

**Disk saturation in detail.** `iostat -xz 1` is where disk problems become visible. `%util` near 100 says the device was busy the whole second; `await` (or `r_await` and `w_await`) says how long each request took including queueing, and for an SSD anything above a few milliseconds is slow; `aqu-sz` says how many requests were waiting on average. Together with `wa` in `vmstat` and processes stuck in `D` state in `ps`, that's a saturated disk, and `pidstat -d 1` or `iotop` says who is writing. Cloud volumes also have IOPS and throughput limits, from the storage topic, and a disk pinned at its limit looks exactly like this.

**Once you know the process: `perf` or `strace`?** They answer different questions. If the process is *busy*, burning CPU, you want to know which code is running: **`perf top`** shows the hottest functions live, and `perf record -g` followed by `perf report` (or a **flame graph**, Gregg's visualisation of the same data) shows the call paths. A garbage collector or a hashing function at the top of the list tells you what to fix. If the process is *slow but not busy*, it's waiting: on a disk, on the network, on a lock. **`strace -c -p PID`** counts its system calls, how long they took in total and how many failed, and `strace -T` prints each call with its duration so the slow one stands out. Twenty thousand failed `stat` calls a second or a `fsync` that takes 1.7 ms every time are the kind of thing `strace -c` makes obvious. `strace` slows the process it attaches to, so use it briefly and never on a hot production path for long; `perf` is lighter.

**Network.** From the host, `sar -n DEV 1` and `sar -n EDEV 1` (errors and drops per interface) answer utilisation and errors; `sar -n ETCP 1` answers saturation of a kind: `retrans/s` climbing means loss, and `ss -s` or `nstat` show the totals. Loss on a path you don't control is a conversation with another team, armed with numbers.

The `vmstat` and `strace` manuals are for columns and flags. The quick questions read `dmesg`, `vmstat`, `pidstat`, `iostat`, `strace -c`, `perf report` and `sar` output with the text tools from Shell essentials, which is what triage mostly is. The labs put you on a slow server: you run the first-minute checklist and reach a verdict, finish a report of the signals, write a `top-cpu` and a `busiest-service`, and catch a runaway that's burning a CPU in a storm of failing system calls, confirming it with `strace -c` before you stop it.

<Recap>

- **USE:** for each CPU, memory, disk and interface: utilisation, **saturation** (queueing: `r` > CPUs, `si`/`so`, `aqu-sz`, drops), **errors** (`dmesg`, interface errors). Saturation and errors mark the bottleneck.
- **First minute:** `uptime`; `dmesg -T | tail`; `vmstat 1`; `mpstat -P ALL 1`; `pidstat 1`; `iostat -xz 1`; `free -m`; `sar -n DEV 1`; `sar -n TCP,ETCP 1`; `top`. Keep the output as the baseline.
- **`vmstat`:** `r` runnable, `si`/`so` swap, `us`/`sy`/`id`/`wa`/`st`. **`mpstat -P ALL`:** one CPU at 100% is a single-threaded limit the average hides.
- **`iostat -xz`:** `%util` near 100, `await` high (ms), `aqu-sz` above 1: saturated. `pidstat -d` or `iotop` for who. Cloud IOPS limits look the same.
- **Busy process:** `perf top`, `perf record -g`, `perf report`, flame graphs. **Waiting process:** `strace -c -p PID` (calls, time, errors), `strace -T` (slow calls). `strace` costs the process; keep it short.
- **Network:** `sar -n DEV` (kB/s against link capacity, ~125,000 for a gigabit), `sar -n EDEV` (errors, drops), `sar -n ETCP` (`retrans/s` means loss or congestion).
- **Method:** measure, change one thing, measure again.

</Recap>
