<Intro>

<Puzzle question="Two servers each have four CPUs. Server A's CPUs are 95% busy; server B's are 60% busy. Users complain that one of them is slow. Which one is more likely, and what would you need to know to be sure?">

You can't tell from how busy they are. A CPU that's 95% busy doing useful work may be serving everyone promptly; what makes things slow is work waiting in a queue. If server B has fourteen tasks waiting for its four CPUs and A has three, B is the slow one, at only 60%. How busy a resource is, and whether work is queuing for it, are separate questions, and this topic's method asks both.

</Puzzle>

"The server is slow." Nothing else. This topic is a method for turning that sentence into a cause in a few minutes, using tools from the earlier topics in a fixed order, so you never have to guess and never have to change a setting to see what happens.

**The USE method.** Brendan Gregg's checklist: for **every resource** (each CPU, memory, each disk, each network interface), ask three questions. **Utilisation**: how busy is it, as a percentage of time or capacity? **Saturation**: is work queueing because the resource can't keep up? **Errors**: is anything failing? The order of importance is the reverse of how people usually look. A CPU at 100% doing useful work is fine; a run queue longer than the number of CPUs means tasks are waiting, and that's slow. A disk at 90% utilisation may be fine; a queue of ten requests with 50 ms waits is not. Errors (an OOM kill, a disk timeout, dropped packets) are rare and decisive. Work through the resources, write down what you find, and the bottleneck is usually the one with saturation or errors.

Here is what the three questions look like for the four resources you'll check most. Every command in the table is on the first-minute list below.

| Resource | Utilisation: how busy? | Saturation: is work waiting? | Errors |
| --- | --- | --- | --- |
| CPU | the share of time spent running code, `us` plus `sy` in `vmstat`, and each CPU by itself in `mpstat` | more tasks wanting a CPU (`r` in `vmstat`) than there are CPUs (`nproc`) | rare; the kernel's log (`dmesg`) |
| Memory | how much is left: the `available` column of `free -m` | swapping: `si` and `so` in `vmstat` above zero, which means memory is being moved out to disk and back because there isn't room | an OOM kill in `dmesg`: the kernel stopped a process to free memory |
| Disk | `%util` in `iostat` | requests queueing (`aqu-sz`) and waiting longer (`await`) | I/O errors and timeouts in `dmesg` |
| Network interface | kB a second against what the link can carry (`sar -n DEV`) | packets dropped for want of room (`rxdrop/s`, `txdrop/s` in `sar -n EDEV`) | bad packets (`rxerr/s`, `txerr/s` in `sar -n EDEV`) |

Three things about the method are easy to miss. The resources are the machine's parts. "The application" isn't one of them: that is where you go afterwards, once you know which part is short. The method never sums a server up in one figure, because an average is what hides one overloaded CPU or disk among idle ones. And a resource that comes back clean on all three questions is a result too: it is ruled out, and the search is smaller.

**The first minute.** Netflix's engineers wrote down the ten commands they run on a slow Linux machine, and the list has held up:

1. `uptime`: the load averages for the last 1, 5 and 15 minutes. A load average is the average number of tasks that were running or waiting for a CPU, plus, on Linux, the tasks stuck waiting for a disk. A 1-minute figure above the 15-minute one means it's getting worse now. Read it against the number of CPUs, which `nproc` prints: with nothing waiting on a disk, a load of 12 on 8 CPUs is 8 tasks running and about 4 waiting for a turn, and the same 12 on 16 CPUs is CPUs standing idle.
2. `dmesg -T | tail`: the kernel's most recent messages. `-T` prints each one's time in a form you can read, so a message from ten seconds ago isn't taken for one from last week. Look for OOM kills, disk timeouts, "TCP: out of memory". These are the errors of USE, and they come this early because one such line can be the whole answer. `dmesg` only reads the messages: it clears nothing, and it returns at once.
3. `vmstat 1`: a line every second. `r` is the tasks running or wanting a CPU (more than the CPU count is saturation), and `b`, beside it, the tasks blocked waiting for a disk. `si` and `so` are memory swapped in from disk and out to it; anything but zero means the machine is short of memory. Then the CPUs' time, in percent: `us` in programs' own code, `sy` in the kernel, `id` idle, and `wa` idle while a disk request was still outstanding (the CPU was free; it's the disk that was slow). Last is `st`, steal: time the hypervisor, the host software that runs the virtual machines, gave to another machine when ours wanted to run. Nothing inside the server fixes that. The first line `vmstat` prints is the average since the machine started, so read from the second.
4. `mpstat -P ALL 1`: the same per CPU. One CPU at 100% with the rest idle is a single-threaded program at its limit, which the average hides completely: on four CPUs it reads 25%.
5. `pidstat 1`: which processes are using the CPU, second by second. `%usr` and `%system` split each one's time between its own code and the kernel, and `%CPU` is the two together, which can pass 100 (200 is two CPUs' worth). For one sorted list, `ps -eo pid,comm,%cpu --sort=-%cpu | head` prints every process (`-e`) with the columns you name after `-o` (its ID, its name, its CPU share), sorted by CPU share; the minus sign puts the biggest first, under a header line. `ps` works its percentage out over the process's whole life, so `pidstat` is the one that says what is happening now.
6. `iostat -xz 1`: `-x` adds the extended columns, `-z` leaves out disks that did nothing, and `1` reports every second. For each disk: `r/s`, `w/s`, kB/s, `await` (average time a request waits, in ms), `aqu-sz` (the queue) and `%util`. Near 100% busy, with a queue above 1 and rising await, is a saturated disk. Here too the first report is the average since the machine started.
7. `free -m`: memory, and how much of "used" is really cache (the `available` column).
8. `sar -n DEV 1`: each interface's packets and kB/s in (`rxkB/s`) and out (`txkB/s`). A gigabit link carries 1,000 megabits a second, which is 125 megabytes, or about 125,000 kB/s; near that, it's saturated. `%ifutil`, the last column, is that share worked out for you.
9. `sar -n TCP,ETCP 1`: the connections this server opened (`active/s`) and accepted (`passive/s`) each second, and **retransmits** (`retrans/s`; from version 12.7.6 of `sar` the column is named `retrseg/s`). TCP expects an acknowledgement for everything it sends, and when none comes back in time it sends that piece again: a retransmit. A few are normal. A steady stream means packets are being lost or the path is congested, which may be somewhere else entirely.
10. `top`: everything at once, to confirm.

Ten commands, one minute, and you know whether the machine is short of CPU, memory, disk or network, and which process is involved. Save the output: it's your baseline for "did the fix work?".

<Check item="tri-vmstat-saturated" />

**Disk saturation in detail.** `iostat -xz 1` is where disk problems become visible. `%util` near 100 says the device was busy the whole second; `await` (or `r_await` and `w_await`) says how long each request took including queueing, and for an SSD anything above a few milliseconds is slow; `aqu-sz` says how many requests were waiting on average. The numbers hang together: with 50 requests waiting at a disk that finishes 200 a second, a new one is done after about 50 ÷ 200 = 0.25 seconds, and `await` reads about 250 ms. One caution about `%util`: it is the share of the time the disk had at least one request in hand. A disk that works on one request at a time is at its limit near 100%, but an SSD or a cloud volume works on many at once and can read 100% with room to spare, which is why the queue and the wait decide, not `%util` alone. Together with `wa` in `vmstat` and processes stuck in `D` state in `ps`, that's a saturated disk, and `pidstat -d 1` or `iotop` says who is writing. Cloud volumes also have IOPS and throughput limits, from the storage topic, and a disk pinned at its limit looks exactly like this.

**Once you know the process: `perf` or `strace`?** They answer different questions. If the process is *busy*, burning CPU, you want to know which code is running: **`perf top`** shows the hottest functions live, and `perf record -g` followed by `perf report` (or a **flame graph**, Gregg's visualisation of the same data) shows the call paths. A garbage collector or a hashing function at the top of the list tells you what to fix. If the process is *slow but not busy*, it's waiting: on a disk, on the network, on a lock. **`strace -c -p PID`** counts its **system calls** (the requests a program makes to the kernel: open this file, read from that connection, wait this long), how long they took in total and how many failed, and `strace -T` prints each call with its duration so the slow one stands out. Twenty thousand failed `stat` calls a second or a `fsync` that takes 1.7 ms every time are the kind of thing `strace -c` makes obvious. There is a third case between the two. A process can be busy *asking the kernel for things* (opening files, reading, polling) with little work of its own to show for it. A program doing its own sums spends nearly all of its CPU time in its own code, which the tools call user time (`us`). This kind spends a sizeable share inside the kernel instead, which they call system time (`sy` in `vmstat` and `top`, `%system` in `pidstat`). That usually means a loop around a system call that fails or returns at once, and `strace -c` is the tool for it too, since it counts the calls and their errors. `strace` slows the process it attaches to, so use it briefly and never on a hot production path for long; `perf` is lighter.

**Reading the two reports.** `perf` works by sampling: many times a second it notes which function is running on each CPU. `perf report` lists the functions by their share of those samples, biggest first, one to a line: `Overhead` (the share), `Command` (the program), `Shared Object` (the file the code is in, the program itself or a library it loads) and `Symbol` (the function). Read from the top and ask whose code it is: the program's own, a library's or the kernel's. A flame graph draws the same samples as stacked bars, each as wide as its share. A process that is waiting is hardly ever on a CPU, so `perf` has next to nothing to sample there, and that is why it's the wrong tool for a waiting process.

`strace -c` prints one line for each system call: `% time` (its share of the time), `seconds` (the total), `usecs/call` (microseconds a call, on average), `calls` (how many), `errors` (how many failed) and `syscall` (its name). Look for two things: the call at the top, where the time went, and a call whose `errors` equals its `calls`, which fails every time it is made. The time it counts is CPU time inside the kernel, which suits the busy case. For a process that is waiting, add `-w` (`strace -c -w -p PID`): each call is then timed from its start to its end, waiting included, so a slow `fsync` shows as slow. `-p PID` attaches to a process that is already running (with `sudo`, for a process that isn't yours), and the table is printed when you stop watching with Ctrl+C; the process carries on. `-f` follows the process's threads, and the processes it starts, as well. To watch for a set time, let `timeout` do the stopping: `sudo timeout 3 strace -c -f -p PID` counts for three seconds.

<Check item="tri-strace-summary" />

**Network.** From the host, `sar -n DEV 1` and `sar -n EDEV 1` (errors and drops per interface) answer utilisation and errors; `sar -n ETCP 1` answers saturation of a kind: `retrans/s` climbing means loss, and `ss -s` or `nstat` show the totals. Loss on a path you don't control is a conversation with another team, armed with numbers.

<Story title="Cloudflare's one-second spikes, 2015" source="https://blog.cloudflare.com/the-story-of-one-latency-spike/" sourceTitle="The story of one latency spike" license="linked, not copied">

A Cloudflare customer reported that a few web requests were extremely slow. It was rare, monitoring didn't see it, and the web server's logs showed no slow requests. Thousands of test requests to one server found five that took up to a second.

The engineers narrowed it down layer by layer. A `ping` to the router in front of the servers never spiked; a `ping` to a server behind it sometimes took almost two seconds, so the trouble lay between the router and the server. `tcpdump` on that server showed a ping arriving and the kernel's reply leaving 1.3 seconds later: the delay was inside the kernel itself. Profiling the kernel's packet-receiving code found a function that tidies a connection's receive buffer when it fills up, like a garbage collector. On these servers the buffers could grow to 32 MB, and tidying one could hold up the processing of every other packet for over 20 milliseconds.

They lowered the buffers' maximum: with 2 MB the longest stall fell to 3 ms, and they settled on 4 MB as a compromise for long, fast connections. The lesson: rare spikes hide in averages, and splitting the path in halves finds them.

</Story>

<Recap>

- **USE:** for each CPU, memory, disk and interface: utilisation, **saturation** (queueing: `r` > CPUs, `si`/`so`, `aqu-sz`, drops), **errors** (`dmesg`, interface errors). Saturation and errors mark the bottleneck.
- **First minute:** `uptime`; `dmesg -T | tail`; `vmstat 1`; `mpstat -P ALL 1`; `pidstat 1`; `iostat -xz 1`; `free -m`; `sar -n DEV 1`; `sar -n TCP,ETCP 1`; `top`. Keep the output as the baseline.
- **`vmstat`:** `r` runnable, `si`/`so` swap, `us`/`sy`/`id`/`wa`/`st`. **`mpstat -P ALL`:** one CPU at 100% is a single-threaded limit the average hides.
- **`iostat -xz`:** `%util` near 100, `await` high (ms), `aqu-sz` above 1: saturated. `pidstat -d` or `iotop` for who. Cloud IOPS limits look the same.
- **One disk, by hand:** `findmnt /srv/data` names the device a folder is on. Often it isn't a plain disk but a **device-mapper** device, a disk the kernel builds on top of another one (LVM's logical volumes are these), called `/dev/dm-0`, `/dev/dm-1` and so on; `iostat` lists it as `dm-0`. `iostat -x /dev/dm-0 1 5` reports on that one disk, five times, a second apart. **The first report is the average since the machine started,** in which a disk that went wrong ten minutes ago still looks idle; each later report covers the second before it, so read those. `w/s` is the writes a second the disk got through, `w_await` how long each one waited (ms), `aqu-sz` how many were waiting, `%util` the share of the time it was busy.
- **Who is writing:** `sudo pidstat -d 1` lists the kB each process reads and writes a second (without `sudo` it shows only your own processes). It says how much, not where: `sudo lsof /srv/data` lists the files open on that disk and the program holding each one. A process that is waiting for a disk uses hardly any CPU (`pidstat 1`), which is why a saturated disk and idle CPUs so often turn up together.
- **The sums to do on sight:** `%util` is busy time over total time (busy for 3 seconds of 4 is 75%). Work that arrives faster than it is served piles up by the difference: 120 requests a second at a disk that finishes 100 leaves 20 more waiting every second. The wait is the queue divided by the rate: 32 waiting at 100 a second is about 0.32 seconds, 320 ms, which is what `await` shows. And a load average is read against `nproc`: 12 tasks wanting 8 CPUs means about 4 waiting at any moment.
- **Keep the evidence:** save the reports before you touch anything (`iostat -x /dev/dm-0 1 5 > ~/triage/iostat-before.txt`), fix one thing, and measure again. Once the fault is gone, so is the proof that it was there.
- **Busy process:** `perf top`, `perf record -g`, `perf report`, flame graphs. **Waiting process:** `strace -c -w -p PID` (calls, time, errors), `strace -T` (slow calls). **Busy, with a big share of system time** (`sy`, `%system`): `strace -c` again, for the call it repeats. `strace` costs the process; keep it short.
- **Network:** `sar -n DEV` (kB/s against link capacity, ~125,000 for a gigabit), `sar -n EDEV` (errors, drops), `sar -n ETCP` (`retrans/s` means loss or congestion).
- **Method:** measure, change one thing, measure again.

</Recap>
