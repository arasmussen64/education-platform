<Intro>

Sooner or later someone asks an architect for "a GPU server". This topic is how to answer well: what a GPU is good at, why its memory decides more than its speed, how to read what a GPU server reports and tell what it is waiting for, how to choose an instance on each cloud, and how one card can be shared. One thing first: **there is no GPU here.** No cloud's free tier includes one, and the labs run without one, so everything in this topic is read from saved output or worked out from dated tables. Nothing pretends to run on a GPU. Several questions ask you to work out a number; use a calculator whenever you like, because the skill is setting up the sum.

**What a GPU is for.** A **GPU** (graphics processing unit) was first built to draw pictures, which means doing the same small sum for millions of pixels at once. Picture a CPU as a kitchen with a handful of very good chefs: each can cook anything, one dish at a time, quickly. A GPU is a hall with thousands of people who can each do one small sum, all doing the *same* sum on different numbers at the same moment. Give the hall ten million multiplications and they are done almost at once. Give it a recipe whose steps depend on each other and it is no help at all: each step waits for the one before, and thousands of people stand idle. NVIDIA's article, the main resource below, makes the same comparison in cores and threads. **CUDA** is NVIDIA's software that lets an ordinary program hand its arithmetic to the hall instead of drawing pictures with it (it appeared in 2007); because it is NVIDIA's, "a CUDA GPU" means an NVIDIA card, and the cards in this topic are all NVIDIA's.

**Inside the card.** A card is a number of **streaming multiprocessors** (**SMs**), each a group of workers in the hall, sharing a cache and the card's own fast memory; an A100 has 108 SMs. Each SM has two kinds of desk. The general desks, **CUDA cores**, do any arithmetic, one number at a time, at whatever precision the program asks for. The special desks, **Tensor Cores**, do one thing: multiply grids of numbers (a grid of numbers is a **matrix**), and they do it several times faster when each number takes fewer bytes. A physics simulation that adds and compares single numbers uses the general desks and gains nothing from the special ones; a model that multiplies big grids in 16 bits is what the special desks are for. The card's own memory is called **VRAM** or **GPU memory**: it sits on the card, separate from the VM's RAM, and a program's data has to be copied into it before the card can use it. The card is plugged into the server's ordinary expansion slot, **PCIe**, the same kind of connection the hypervisors topic met for network cards.

**Models, as much as sizing needs.** A **model** is a very large table of numbers; the numbers are its **parameters**, also called **weights**, and a "7-billion-parameter model" is seven billion numbers. Running a model on an input, which is called **inference** (serving it), is mostly multiplying the input by those tables, which is why models run on GPUs. **Training** is how the numbers are found in the first place: the program adjusts every weight, again and again, and keeps several working copies of them while it does. A **batch** is many inputs pushed through together, which gives the hall enough work at once.

**Precision.** **Precision** is how many bytes store each number. Fewer bytes hold fewer digits, so each number is less exact, and they take less memory. The formats' names give their size in bits: FP is for **floating point**, the usual way a computer stores a number with a fraction in it, and INT for an integer, a whole number.

| Format | Bytes a number | 7 billion parameters take |
| --- | --- | --- |
| FP32 (32-bit) | 4 | 28 GB |
| FP16 or BF16 (16-bit, two layouts of the same size) | 2 | 14 GB |
| INT8 (8-bit) | 1 | 7 GB |
| 4-bit | a half | 3.5 GB |

Two words go with the table. **Mixed precision** is doing most of the arithmetic in 16 bits where it is safe and the rest in 32; NVIDIA's mixed-precision guide speaks of up to 3 times faster overall on the most arithmetic-heavy models, because the Tensor Cores do the grids. **Quantisation** is storing the weights in 8 or 4 bits to make a model fit a smaller card; the answers usually change a little, so a team checks they are still good enough.

**Memory is the first question.** A model's weights have to be in the card's memory, all of them, at the same time, before it can answer anything. Unlike the VM's memory, a GPU has no swap to fall back on: a program that asks for more memory than the card has stops with an **out-of-memory** error. That is why memory decides first and speed second. The sum is parameters × bytes each. 7 billion parameters at 2 bytes is 14,000,000,000 bytes: 14 GB, which is 13.0 GiB (the GB and GiB of "Memory tiers and disks": a GiB is 1,073,741,824 bytes). Hugging Face (a company whose site holds many published models and the software to run them) gives the same sum as a rule of thumb, per billion parameters: about 4 × X GB in 32 bits and 2 × X GB in 16.

The sum is the floor, not the bill. A running model also holds its inputs, the working numbers of its arithmetic, and any parts that weren't shrunk. Hugging Face's guide loads a model of 15.5 billion parameters in 4 bits: parameters × half a byte comes to about 7.2 GiB, and the card's peak was 9.5 GiB, about a third more. (Its code divides by 1,024 three times and calls the result GB: the units get mixed even in good guides.) Training needs far more: Hugging Face's memory estimator shows about **4 times the weights** for the usual training method. So a plan states its **headroom**, the room left on top of the weights, before it picks a card: "the card must hold the weights and 25% more" is weights × 1.25.

The label on a card is a name, not a measurement. NVIDIA's own guide shows an "H100 80GB" reporting 81,559 MiB to programs, which is 79.6 GiB, under driver 580.65.06 (the **driver** is the software that runs the card for the operating system); the same guide shows an A100 40GB reporting 40,537 MiB under a driver of 2020, and a user on NVIDIA's forum posted 40,960 MiB for the same card under a newer one. The providers' tables disagree too: AWS lists the L4 card as 22 GiB and Google Cloud lists it as 24 GB, which is 22.35 GiB; AWS lists the T4 as 16 GiB and Azure as 16 GB, which is 14.90 GiB. The labs' table keeps each provider's own figure beside a GiB figure worked out from it, and every sum uses the GiB one. When the figures disagree, plan with the smaller; on the machine itself, `nvidia-smi`'s total settles it.

**Reading `nvidia-smi`.** `nvidia-smi` is the command NVIDIA's driver installs to report on its cards. Here is a summary in the layout NVIDIA's guide shows for driver 580.65.06 (constructed: the numbers are made up, the layout is real):

```text
+-----------------------------------------------------------------------------------------+
| NVIDIA-SMI 580.65.06              Driver Version: 580.65.06      CUDA Version: 13.0     |
+-----------------------------------------+------------------------+----------------------+
| GPU  Name                 Persistence-M | Bus-Id          Disp.A | Volatile Uncorr. ECC |
| Fan  Temp   Perf          Pwr:Usage/Cap |           Memory-Usage | GPU-Util  Compute M. |
|                                         |                        |               MIG M. |
|=========================================+========================+======================|
|   0  NVIDIA H100 80GB HBM3          On  |   00000000:04:00.0 Off |                    0 |
| N/A   41C    P0            268W /  700W |   61250MiB /  81559MiB |     97%      Default |
|                                         |                        |             Disabled |
+-----------------------------------------+------------------------+----------------------+

+-----------------------------------------------------------------------------------------+
| Processes:                                                                              |
|  GPU   GI   CI              PID   Type   Process name                        GPU Memory |
|        ID   ID                                                               Usage      |
|=========================================================================================|
|    0   N/A  N/A            3718      C   python3                               61240MiB |
+-----------------------------------------------------------------------------------------+
```

Five things to read. The card's **name** and number, `0`, on the first line of its box. Under it, the power it draws against its cap, `268W / 700W`. Then **Memory-Usage**, in MiB: 61,250 in use of 81,559. Then **GPU-Util**, 97%. And at the bottom, the **process table**: which programs hold the card's memory, and how much each (`C` is a compute program, `G` a graphics one). `MIG M.` says whether the card is cut into partitions (below), here `Disabled`. Each line is a reading of one moment; monitoring tools take the same readings every second or so, per card and per program (Google's monitoring agent reads them from NVIDIA's management library), and the labs save them as a file of one line a second.

The sentence that matters most is NVIDIA's definition of GPU-Util: the share of the last sample period (between a sixth of a second and a second, depending on the card) "during which one or more kernels was executing on the GPU". A **kernel** here is NVIDIA's word for a program running on the GPU; it has nothing to do with the Linux kernel. So 100% means "something was running the whole time": a shop being open, not a shop being full. A small program that keeps a few of the card's thousands of units busy shows 100% as surely as a huge one. And a card with its memory nearly full can show 0%, because a model is loaded and nobody is asking it anything.

**What is starving it.** The work reaches a GPU along a line with three stations: the disk hands over raw data, the CPUs prepare it (reading, decoding, shaping each batch: the **input pipeline**), and the GPU does the arithmetic. The GPU is last, and it runs only as fast as the slowest station before it. TensorFlow, one of the toolkits programs use to build and run models, draws it in its guide: done naively, "while your pipeline is fetching the data, your model is sitting idle". So low utilisation is a question, "waiting for what?", and the host's own numbers from Module 1 answer it:

| What you see | What is starving the GPU | What helps | What doesn't |
| --- | --- | --- | --- |
| GPU-Util low or swinging; every vCPU near 100% `%usr`; `%iowait` near 0 | the CPUs preparing its input | more vCPUs per GPU; more preparation workers; input prepared ahead of time | a bigger GPU |
| GPU-Util low; the CPUs mostly idle, `%iowait` high; the data disk near 100% `%util` in `iostat` | the disk | the data on a local NVMe disk; a faster disk tier | more vCPUs |
| GPU-Util 0, no process listed, an out-of-memory error in the application's log | nothing: the model never loaded | fewer bits a weight; a card with more memory | waiting; more vCPUs |
| GPU-Util low and steady; CPUs, disk and card memory all with room to spare | the work arrives too small, one input at a time | batches; a smaller, cheaper card | more of anything |
| GPU-Util near 100%; CPUs and disk with room to spare | nothing: the GPU is the limit, which is what it was bought for | a faster card, or a second one | more vCPUs; a faster disk |
| GPU-Util swinging; two owners in the process table | another program taking turns on the card | a partition or a card of its own | tuning the job |

The disk row is "Memory tiers and disks" met again: a network disk at its allowance starves a GPU just as it slows a database. The tuning guide of PyTorch, another such toolkit, adds one detail worth knowing: its data loader prepares input in the main program by default, so "the main training process has to wait for the data".

**Choosing an instance.** Ask the questions in this order. Does the model, with its headroom, fit one card? If not, how many cards? Are there enough vCPUs to feed them? Is there a local disk for the data? Then price the **job**, not the hour: a card that costs seven times as much an hour and finishes ten times sooner is the cheaper one. For example, a model of 4 billion parameters in 16 bits takes 7.45 GiB, 9.31 GiB with 25% headroom, which every whole card in this topic's tables holds. The cheapest are AWS's `g4dn.xlarge` (16 GiB) and Azure's `NC4as_T4_v3` (14.90 GiB): the same T4 card at the same $0.526 an hour (read 2026-11-11), each with 4 vCPUs and a local disk. Two more words: a **quota** is a per-account limit on how many GPUs (or GPU vCPUs) you may start, which a new account may have to ask to raise, and **Spot** is a cheaper price for spare capacity that the provider can take back at short notice. Modules 8 and 12 come back to both. Where the clouds differ, from their pages read on 2026-11-11:

| | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Families | G (one to eight mid-size cards: T4, A10G, L4, L40S); P (eight large cards: A100, H100 and newer) | NC (compute: T4, A100, H100); NV (graphics and partial cards: A10) | G2 (L4), A2 (A100), A3 (H100 and newer), and N1 machines with a T4 attached |
| A small, older card | `g4dn.xlarge`, T4, $0.526 an hour | `NC4as_T4_v3`, T4, $0.526 an hour | the T4, which Google's page says reaches end of support on 1 August 2027 |
| Part of a card | `g6f.large`: an eighth of an L4, 2.79 GiB | `NV6ads_A10_v5`: a sixth of an A10, 4 GB | fractional sizes for virtual workstations on G4 |
| How the table states card memory | GiB, in whole numbers (the L4: 22 GiB, though four of them come to 89) | GB (the T4: 16 GB) | GB (the L4: 24 GB) |
| Free | no GPUs | no GPUs | "GPUs and TPUs are not included in the Free Tier" (a TPU is Google's own chip for the same kind of work), and a free-trial account can't add them |

The largest cards change every year, so the rows go stale; the method doesn't. Date every table you make, and look the prices up again before you decide.

**Sharing a card.** Most cloud VMs get a whole card by **pass-through** (the hypervisors topic's passthrough): the physical card is handed straight to one VM, whose own driver talks to it. Sharing one card between programs comes in two kinds, walls or turns.

**MIG** (Multi-Instance GPU) cuts a large card into up to seven smaller ones, called **GPU instances**, with walls between them: each has memory and compute of its own, and NVIDIA's guide says a fault stays inside the instance it happened in. MIG exists only on the large cards in NVIDIA's list: data-centre cards such as the A30, A100, H100, H200 and B200, and a few of its newest workstation cards, and no T4, L4, A10 or L40S. **Time-slicing** has no walls: programs take turns on the whole card and share all its memory, so one that fills the memory takes the others down with it. NVIDIA's time-slicing page says it plainly: "there is no memory or fault-isolation". A **virtual GPU** (vGPU) is a card shared between VMs by the hypervisor, which is how clouds sell **fractional GPUs** like Azure's sixth of an A10, made for light graphics work such as one person's remote desktop.

The MIG arithmetic is small. An A100 40GB is 8 memory slices of about 5 GB and 7 compute slices. A **profile** is a size of instance, and its name says what it takes: `2g.10gb` is 2 compute slices and 10 GB, so 2 memory slices. Read the GB for the memory: `3g.20gb` takes 3 compute slices but 4 memory slices. A layout can never use more than 8 memory slices or 7 compute slices: seven `1g.5gb` fit one card, using every compute slice and leaving a memory slice spare, and a `4g.20gb` with a `3g.20gb` fills it exactly. That rule rejects bad layouts but doesn't prove a good one, because instances also have fixed places on the card; NVIDIA's table of profiles and placements is the last word.

When a model is too big for one card, it is split across several, and the cards then exchange data at every step. **NVLink** is NVIDIA's direct link from card to card, far faster than PCIe. It matters when one job spans cards; it does nothing for eight separate jobs on eight cards. Its speed changes with each generation, so look it up rather than remember it.

<Recap>

- **A GPU** is thousands of small arithmetic units doing the same sum on many numbers at once: right for multiplying huge grids of numbers, no help for work done one step after another. **CUDA** is NVIDIA's software for using it; **CUDA cores** do any arithmetic, **Tensor Cores** multiply grids, fastest in fewer bits.
- **Precision:** 4 bytes a number in 32 bits, 2 in 16, 1 in 8, a half in 4. Fewer bits: less memory, faster Tensor Cores, slightly less exact. Quantisation stores the weights in 8 or 4 bits.
- **Memory first:** parameters × bytes each, all on the card at once, with no swap: too big is an out-of-memory error, not a slowdown. 7 billion in 16 bits is 14 GB, 13.0 GiB. The sum is the floor: add stated headroom; training needs about 4 times the weights.
- **Units:** a card's label is a name and providers state memory in GiB or GB; compute in one unit, plan with the smaller figure, and trust `nvidia-smi`'s total on the machine.
- **`nvidia-smi`:** name, power, `Memory-Usage` in MiB, GPU-Util, the process table. **GPU-Util** is the share of time some program ran on the card: open, not full. Memory full at 0% is a loaded model with nothing to do.
- **Starvation:** disk, then CPUs, then GPU. Low utilisation means waiting: CPUs flat out (more vCPUs), disk at its limit (local NVMe), never loaded (fewer bits, a bigger card), work too small (batches), another program's turns (a partition). Near 100% with the host idle is the GPU as the limit.
- **Choosing:** fit with headroom on one card, then the number of cards, vCPUs to feed them, a local disk, then the price of the job. Clouds name families differently, state memory differently and give no free GPUs.
- **Sharing:** MIG builds walls (own memory, faults contained) on large cards only, up to 7 instances, sized by profile: memory slices ≤ 8 and compute slices ≤ 7 on an A100 40GB, NVIDIA's table the last word. Time-slicing takes turns with no walls. NVLink matters when one model spans cards.

</Recap>
