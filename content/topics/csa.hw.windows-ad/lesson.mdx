<Intro>

In Module 1 every server kept its own list of people: `/etc/passwd`, `/etc/group`, a password for each account on each machine. With forty servers that's forty lists to keep in step, and the day someone leaves, forty places to lock them out. A **directory** solves that: one database of accounts, groups and machines that every server asks instead of keeping its own. Programs ask it questions with **LDAP** (Lightweight Directory Access Protocol), the language of directories. **Active Directory Domain Services** (AD DS) is Microsoft's directory, and most companies with Windows have one. Cloud servers join it, cloud networks have to be set up for it, and when it breaks, nobody can sign in to anything. This topic is about how it's arranged, how a machine finds it, and how it proves who someone is. Joining a server to it, Group Policy and how Microsoft's cloud directory differs are the next topic.

**What a domain holds.** A **domain** is one such directory with a name in DNS, the internet's naming system (more on it below), like `ad.shop.test`. A **domain controller** (DC) is a server that holds a full copy of the domain's directory and answers for it; a domain usually has two or more, so one can fail. Inside are **users**, **groups**, **computers** (every machine that joins gets an account of its own) and **service accounts** (accounts for programs rather than people). They're arranged in **organisational units** (OUs): folders you create, which can hold other OUs. A few folders exist from the start, like `CN=Users`, where new accounts land by default; those are plain **containers**, which can't carry settings the way an OU can. The rule to keep straight: **settings and who may manage things follow the folders (OUs); permissions follow groups.** Sales laptops that need one set of settings go in a Sales OU; Sales people who need a shared folder go in a Sales group. Some settings belong to the whole domain: the **password rules** (the shortest password allowed, how many wrong tries lock an account) apply to every account in it. One or more domains that share a design for their entries (the **schema**) make a **forest**. Domains in one forest trust each other automatically, so the **forest**, not the domain, is the security boundary: a part of the company that must not be run by the rest needs a forest of its own. The **global catalog** is a searchable index of every domain in a forest.

**A name read backwards.** Every entry has a **distinguished name** (DN), its full path: `CN=Alice Ng,OU=Engineering,OU=Staff,DC=ad,DC=shop,DC=test`. Read it from right to left, the way you'd read a postal address starting from the country: `DC=test`, `DC=shop`, `DC=ad` spell the domain `ad.shop.test`; `OU=Staff`, then `OU=Engineering`, are folders inside it, the second inside the first; `CN=Alice Ng` is the entry itself (CN, common name). So Alice is in Engineering, which is inside Staff. An LDAP search names where to start (`-b`, the base, a DN) and what to find (a filter in brackets, like `(sAMAccountName=alice)`, where `sAMAccountName` is the account's short login name).

**Making a domain.** Creating a domain on its first DC is called **provisioning**: it builds the directory database, the domain's DNS zone and its Kerberos keys (both below), and creates the **domain administrator**, the account allowed to change anything in the domain. Choose the name with care, because it can't be changed afterwards. Use a name under one you own, like `ad.example.com`, never one ending in `.local` (other software uses that), and in a lab, `.test`, which is reserved for testing and never answers on the internet. The labs' DC runs **Samba**, free software that acts as an Active Directory domain controller and speaks the same protocols; AWS's managed directory Simple AD is built on it (though it no longer takes new customers). Samba's `samba-tool` is what the labs use where a Windows administrator would use the Windows tools.

**DNS, from the beginning.** Module 1 used `dig` to look names up. Here are the words behind it. **DNS** (the Domain Name System) is the internet's way of turning names into addresses. A **name server** answers questions about names it's responsible for; a **zone** is the part of the name tree one name server answers for, like everything under `ad.shop.test`. A **resolver** is the name server a machine asks for everything (it's in `/etc/resolv.conf`): it answers what it knows and asks other name servers for the rest. The answers are **records** of several types: an **A** record turns a name into an address; an **SRV** record says which host, and which port, offers a service for a domain; a **PTR** record does the reverse of an A record, turning an address back into a name, and lives in a **reverse zone** whose name is the network's numbers backwards, so 10.0.9.10's name is kept as record `10` in the zone `9.0.10.in-addr.arpa`.

**How a member finds a DC: the domain's phone listing.** A machine that knows only the name `ad.shop.test` asks DNS one question: who offers LDAP here? The question is the SRV record `_ldap._tcp.ad.shop.test`, and the answer is a line like `0 100 389 dc1.ad.shop.test.`: priority 0 (lower is tried first), weight 100 (how to share among servers of the same priority), port 389 (LDAP's), and the host. Kerberos's own servers are under `_kerberos._tcp`, on port 88. Once a member has found a DC, the DC tells it which **site** it's in (Active Directory's word for the network addresses in one place, such as one office), so that it uses the DCs nearby. The domain's DNS usually runs on its DCs, which answer those questions, so a machine must ask a resolver that knows the domain. An ordinary resolver has never heard of it and answers `status: NXDOMAIN`, "no such name", and then nothing about the domain works. That's why names are the first thing to check when domain sign-ins break. There are two ways to fix it. Point the machine's resolver at the DCs, which is what a cloud network's DNS setting does (on Azure, the virtual network's custom DNS servers; a network lends each VM its address and settings for a while, and the VM picks the change up when it renews that lease), or keep the site's resolver and add a **conditional forwarder**: a rule that sends questions about one zone, and only that zone, to the DCs. Forward the reverse zone too, or the DC's address has no name. Typing a DC's name and address in by hand instead, in a hosts file or as a record of the site resolver's own, looks like a fix, and breaks the day that DC's address changes or a second DC arrives. Going the other way, a DC answers for its own domain and **forwards** everything else to the site's resolver, so machines that ask it can still find the rest of the world.

**Proving who you are: the ticket booth.** Two words first. **Authentication** is proving who you are; **authorisation** is being allowed to do the thing. A domain does the first with **Kerberos**, and it works like a ticket booth at a fair. At the start of the day you prove who you are once, at the booth: the **KDC** (Key Distribution Center), which runs on every DC. The KDC knows a **key derived from your password**: your computer can work out the same key from what you type, so the two can prove they share it without the password itself ever crossing the network. You get a day pass, the **ticket-granting ticket** (TGT), good for ten hours by default. For each ride (LDAP on dc1, SSH to a server, a file share) you show the day pass at the booth and get a **service ticket** for that ride only, stamped with its name. The ride never sees your password and never phones the booth: it can read the ticket because the booth sealed it with the ride's own key. Everything here has a name, a **principal**, written `name@REALM`. The **realm** is the domain's name in capitals, `AD.SHOP.TEST`. You are `alice@AD.SHOP.TEST`; the day pass is `krbtgt/AD.SHOP.TEST@AD.SHOP.TEST`; a service is `service/host`, like `ldap/dc1.ad.shop.test`, or `host/files1.ad.shop.test` for logging in to a machine; a service's name written this way is its **service principal name** (SPN). A program that has no one to type a password signs in with a **keytab**, a file holding an account's keys; whoever can read it can be that account, so it's guarded like a password. `kinit` gets the day pass, `klist` lists the tickets you hold, `kdestroy` throws them away.

**Kerberos leans on two things outside the directory.** **Time:** every request carries the time, and a KDC refuses one more than five minutes away from its own clock, which stops a copied request being replayed later. Machines keep their clocks agreed by asking a time server; when one drifts, the fix is its time source, never a longer tolerance. (Linux's Kerberos measures its own clock against the KDC's and makes up for the difference, so the lab turns that off to show the rule. Never set a lab's clock with `date`: every container shares the clock of the machine underneath.) **Names:** tickets are issued for names, not addresses, and before asking for a service ticket the client usually turns the server's address back into a name with a PTR record. With no reverse record it asks for a ticket for a name no service has, and the KDC answers `Server not found in Kerberos database`.

**Reading Kerberos's errors.** The error says which question failed:

| Error | What it means |
| --- | --- |
| `Cannot find KDC for realm "AD.SHOP.TEST"` | Names: this machine's resolver can't answer the domain's SRV records. |
| `Password incorrect` | The KDC was found and the password is wrong. |
| `Client's credentials have been revoked` | The account is disabled, locked or expired; the password may well be right. |
| `KDC reply did not match expectations` | The realm was typed in lower case: realms are capitals. |
| `Keytab contains no suitable keys for ...` | The keytab holds keys for another name, often the same one in another case. |
| `Preauthentication failed` (with a keytab) | The keytab's keys are stale: the account's password changed after the keytab was made. |
| `Clock skew too great` | Time: this machine and the KDC are more than five minutes apart. |
| `Server not found in Kerberos database` | The service name asked for doesn't exist: an address used where a name belongs, or no reverse record. |

A DC also refuses a password sent over plain, unencrypted LDAP (`Strong(er) authentication required`), so programs sign in with Kerberos instead. A fix never switches that off.

**Trusts: two houses, one key.** Two domains in different forests don't accept each other's accounts until they set up a **trust**. Picture two houses: the house with the files gives the other house's ID office a key, saying "whoever your office vouches for, I'll believe". So the domain that holds the **resources trusts** the domain that holds the **accounts**, and access flows the opposite way to the trust: if PARTNER trusts CORP, CORP's people can open PARTNER's files, not the other way round. A trust is **one-way** or **two-way**, and **transitive** (it passes along: if A trusts B and B trusts C, A trusts C) or not. Inside a forest, every domain trusts every other, two-way and transitively, automatically. An **external** trust, to a domain in another forest, doesn't pass along.

It's marked intermediate and assumes you know Windows Server; you have the words now, so read for the ideas and let the Windows tool names go by. In unit 3, skim the managed service accounts part, and skip unit 6, which is clicks in Windows tools. Then the short AD DS overview, the DC locator page's DNS-based tab and "Closest Active Directory site" (stop there), the Kerberos overview, and the trust page from the top to the end of "Forest trusts". MIT's dialogue is the optional deep read on why tickets look as they do. The quick questions read directory entries, SRV records, `klist` and Kerberos's errors from the labs' own domain, with Module 1's text tools. The labs give you a domain on `dc1` next to your shell: you find it through DNS and get and use a ticket, finish a script that stands up a domain controller, write a report signed in with a keytab, stand up a DC from a blank shell, and get a nightly report that gets no tickets working again.

<Recap>

- **A directory** is one database of accounts that every server asks; **LDAP** is how programs ask it. **AD DS** is Microsoft's. A **domain** is one directory with a DNS name; every **domain controller** holds a full copy.
- **Inside:** users, groups, computers, service accounts, in **OUs** (folders that carry settings and delegation) and default **containers** like `CN=Users` (which don't). Settings follow folders; permissions follow groups. **Password rules** apply to the whole domain. A **forest** of domains is the security boundary.
- **A DN reads right to left:** `CN=Alice Ng,OU=Engineering,OU=Staff,DC=ad,DC=shop,DC=test` is Alice, in Engineering, inside Staff, in `ad.shop.test`.
- **Provisioning** creates a domain on its first DC; its name can't change afterwards. Use a name under one you own, never `.local`; `.test` in labs.
- **DNS:** a **resolver** is what a machine asks; a **zone** is what a name server answers for; **A** turns a name into an address, **SRV** names the host and port of a service (`priority weight port host`), **PTR** turns an address back into a name, in a reverse zone (`9.0.10.in-addr.arpa` for 10.0.9.x).
- **Finding a DC:** ask for `_ldap._tcp.DOMAIN` (and `_kerberos._tcp` on 88) through a resolver that knows the domain: the network's DNS pointed at the DCs, or a **conditional forwarder** for the domain's zone and its reverse zone. NXDOMAIN means the resolver doesn't know the domain. A DC **forwards** everything else.
- **Kerberos:** prove who you are once to the **KDC** (on every DC) for a **TGT**, `krbtgt/REALM`, about ten hours; trade it for a **service ticket** per service name (`ldap/dc1.ad.shop.test`, `host/NAME`). The **realm** is the domain in capitals; a **principal** is `name@REALM`; a **keytab** holds an account's keys for programs, and is guarded like a password. `kinit`, `klist`, `kdestroy`.
- **Two dependencies:** time (more than five minutes apart: `Clock skew too great`; fix the time source) and names (no SRV answer: `Cannot find KDC`; no reverse record: `Server not found in Kerberos database`). Disabled, locked or expired: `Client's credentials have been revoked`. Lower-case realm: `KDC reply did not match expectations` with a password, `Keytab contains no suitable keys` with a keytab. Stale keytab: `Preauthentication failed`.
- **Trusts:** the domain with the resources trusts the domain with the accounts; access flows the opposite way. One-way or two-way; transitive or not. A forest's domains trust each other automatically; an external trust doesn't pass along.
- **The labs' DC is Samba:** the same protocols, not the Windows tools. Never set a lab's clock.

</Recap>
