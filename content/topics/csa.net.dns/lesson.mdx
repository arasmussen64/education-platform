<Intro>

Module 1 used `dig` to turn a name into an address (and if you took Module 2, its directory couldn't be found without it). This topic opens the box. **DNS**, the Domain Name System, is the internet's phone book, kept by thousands of organisations at once: no single server knows every name, yet any machine can find any name in a few milliseconds. By the end you can follow one lookup from a laptop to the server that answers for the name, read and write a zone file, move a name to a new address without stranding anyone, give the office a private answer without losing the rest of the zone, and tell a broken signature from a missing record.

**Names, labels and the tree.** A **name** is a row of **labels** separated by dots, read from right to left: `api.shop.test` is the label `api` inside `shop` inside `test`. Above `test` there is one more, empty, label: the **root**, written as a final dot. `dig` prints names that way, `api.shop.test.`, and a name written with its final dot is a **fully qualified** name. Picture the names as an upside-down tree, the root at the top, `test.` under it, `shop.test.` under that. A **domain** is a branch of the tree: `shop.test` and every name below it. A **zone** is the part of a domain that one set of servers answers for. `shop.test` is one zone until it hands `eu.shop.test` to another server; from then on `eu.shop.test` is a zone of its own, and `shop.test`'s zone no longer includes it. The top of a zone, `shop.test` itself, is its **apex**. Names under `.test` are reserved for testing and never exist on the real internet (RFC 6761: an RFC is one of the internet's numbered standards documents), which is why every lab uses them.

**Four kinds of server.** A machine's own **stub resolver** knows one thing: the address of a resolver to ask (it's in `/etc/resolv.conf`). The **recursive resolver** (also called a caching or full-service resolver) does the research: it asks other servers until it has an answer, then keeps it. **Authoritative servers** hold zones and answer only for them. At the top are the **root servers**: 13 root server names, `a` to `m`, each answered by many machines in many places. (The tutorial below, written in 2014, says "13 root servers in operation"; it's 13 names, each served by many machines.) Under the root, each **top-level domain** (TLD: `com`, `uk`, `test`) has its servers, run by a **registry**; you rent a name under one through a **registrar**, which tells the registry which servers answer for it. dnsmasq, Module 1's small name server, is usually set up as a fourth kind, a **forwarder**: it passes the questions it can't answer to another resolver and relays the reply. In this topic's labs Unbound runs the resolvers, and BIND the authoritative servers, set `recursion no;` so they answer only for their own zones. An authoritative server that recursed for anyone would be an **open resolver**, which attackers use to aim floods of answers at others.

A question and its answer usually travel as one UDP datagram each, to port 53: no connection to set up, which is why a lookup is fast. An answer too big for the datagram comes back marked truncated (the `tc` flag), and the resolver asks again over TCP, also on port 53.

**A lookup, step by step.** The laptop's stub asks the office's resolver for `api.shop.test`. The resolver asks a root server, which doesn't know the name but knows who runs `test.`: it answers with a **referral**, the NS (name server) records of the servers for `test.`, which is a **delegation** (the parent handing a branch to a child zone's servers). The resolver asks one of those, and gets a referral to `shop.test`'s servers; it asks one of those, and gets the answer. It hands the answer to the stub and keeps a copy. `dig +trace` shows each step, and `dig @SERVER +norecurse NAME` asks one server one question, the way a resolver does.

Every answer starts with a header. Its **status** is `NOERROR` (fine), `NXDOMAIN` (no such name), `SERVFAIL` (the server couldn't produce an answer), or `REFUSED` (it won't answer that question); `NOERROR` with an empty answer is **NODATA**: the name exists, but has no record of the type asked for. Its **flags**: `qr` (this is a reply), `rd` (recursion desired, set by the asker), `ra` (recursion available), `aa` (authoritative answer: the zone's own server speaking) and `ad` (authenticated data: the signatures checked out, below). A referral has an empty ANSWER section, the next servers' NS records in AUTHORITY, and no `aa`. When a resolver and the authority disagree, the authority's `+norecurse` answer is the zone right now.

A referral often carries the next servers' addresses in its ADDITIONAL section: **glue**. It's essential when a server's name is inside the zone being delegated: to find `ns1.shop.test` you'd have to ask `shop.test`'s servers, which you can't reach without its address, so the parent hands it over with the referral.

**Records and zone files.** A zone's data is **resource records**, each a name, a TTL, a class (always `IN`), a type and a value; all the records with one name and type form an **RRset**. The types to know:

| Type | Holds | Example |
| --- | --- | --- |
| A, AAAA | an IPv4 address, an IPv6 address | `api IN A 203.0.113.41` |
| CNAME | "this name is another name" | `www IN CNAME @` |
| MX | the domain's mail server, with a preference | `@ IN MX 10 mail` |
| TXT | free text, for conventions such as email rules | `@ IN TXT "v=spf1 mx -all"` |
| CAA | which certificate authorities may issue certificates | `@ IN CAA 0 issue "ca.shop.test"` |
| NS | the zone's name servers, or a child zone's | `eu IN NS ns-eu.eu` |
| SOA | the zone's start of authority, one per zone | below |
| PTR | an address's name, in a reverse zone | `41 IN PTR api.shop.test.` |

A **certificate**, in CAA's row, is the signed file a web server shows to prove which names it may answer for, issued by a **certificate authority** (topics 31 and 32). A **reverse zone** turns addresses back into names: 10.0.9.0/24's addresses are names under `9.0.10.in-addr.arpa`, the octets backwards, so in that zone the PTR row's `41` names 10.0.9.41. **SRV** records name the host and port of a service (it's how Windows computers find their domain's servers), and **HTTPS** and **SVCB** records tell a client how to connect to a service (topic 29).

A zone file lists the records, one a line. `@` is the apex; a name without a final dot gets the zone's name added; `$TTL` is the TTL of lines that don't give one; `;` starts a comment. The SOA's value is the primary server, the responsible person's mailbox written as a name (`hostmaster.shop.test.` is hostmaster@shop.test), and five numbers: the **serial**, **refresh**, **retry**, **expire** and **minimum**. Three of them matter here. The serial is the zone's version, below. Expire is how long a secondary keeps answering from its copy if it can't reach its primary (two weeks is common). Minimum caps negative caching, below.

**A CNAME can't share its name.** A CNAME says "this name is that other name, for every type", so a name with a CNAME can have no other record (RFC 2181). The apex always has the zone's SOA and NS records, so the apex can never be a CNAME, which is a problem when the shop wants `shop.test` itself to follow a load balancer whose addresses change. The clouds' DNS hosts solve it with records of their own, read on 2026-11-12:

| | AWS Route 53 | Azure DNS | Google Cloud DNS |
| --- | --- | --- | --- |
| At the apex | an **alias record**: answers as an A or AAAA with the AWS resource's addresses, using the resource's TTL; free to query for AWS resources | an **alias record set** (A, AAAA or CNAME) pointing at an Azure public IP address, or at one of the Azure services that stand in front of a site: Traffic Manager, a CDN (content delivery network) endpoint, Front Door | no apex alias on the pages read; A records with the balancer's addresses |

**Primary, secondary and the serial.** A zone has a **primary** server, whose file is the master copy, and **secondaries**, which copy the whole zone from it: a **zone transfer**, all of it (AXFR) or just the changes (IXFR). The primary sends a **NOTIFY** when the zone changes (BIND waits about 5 seconds first); a secondary also asks for the primary's SOA every refresh interval, and after a failure every retry interval. Either way, it copies the zone only if the primary's serial is higher than its own, and only if the primary allows it (`allow-transfer` in BIND, below). So **the serial is a promise, not a label**: an edit that doesn't raise it never reaches the secondaries. Date-style serials, `2026111201` for the first change on 12 November 2026, keep the order readable. BIND makes it stricter still when it signs a zone itself (the labs' `dnssec-policy` and `inline-signing`; signing is DNSSEC, the last part of this lesson): an edit without a higher serial isn't loaded at all. BIND's control tool, `rndc`, prints `zone reload queued` for `rndc reload shop.test` either way, and only the journal, `journalctl -u named@ns1`, says `not loaded due to errors`. The serial a signed zone serves is BIND's, not the file's: it raises it each time it signs. The rest of BIND's controls: `rndc reconfig` reads the settings files again, `rndc notify ZONE` sends a NOTIFY now, and on a secondary `rndc retransfer ZONE` copies the zone now instead of waiting for the retry. Who may copy a zone is the primary's choice: `allow-transfer { 198.51.100.14; };` names the secondaries' addresses, and since a transfer hands over every name in the zone, a primary lets its own secondaries copy it and nobody else, never `any`.

**Caching and TTLs.** A resolver keeps each answer for its **TTL** (time to live) and hands out what's left: two lookups two seconds apart show a TTL two lower. A resolver that fetched the old address a second before a change hands it out for the rest of its TTL, and nothing in DNS can make it forget sooner. You can flush caches you run (with Unbound's control tool, `unbound-control flush NAME`); the resolvers your customers use aren't yours. Resolvers may also cap TTLs: Unbound keeps an answer at most a day (`cache-max-ttl: 86400`) by default.

"No such name" is cached too: **negative caching**. An NXDOMAIN carries the zone's SOA, and a resolver may keep the "no such name" for the smaller of the SOA record's own TTL and its minimum (RFC 2308). With an SOA TTL of 300 and a minimum of 900, that's 300 seconds: a name somebody looked up a minute before it was created stays missing for them for five minutes. Unbound caps negative answers at an hour.

**Moving a name, as a procedure.** Suppose `api.shop.test` has a TTL of 86400, a day, and moves on Friday at 18:00.

1. At least one old TTL before the switch, by Thursday 18:00 at the latest, lower the TTL (to 300, say), with the serial raised, and check that every server gives out the new TTL. Count from then, not from when you typed it.
2. Wait out the old TTL: every copy fetched with it has then expired, and every resolver holds one that lasts 300 seconds at most.
3. Switch the address, with the TTL still 300. Within 300 seconds everyone has it.
4. Check through several resolvers, not just your own.
5. Raise the TTL again. Short TTLs multiply the queries your servers answer, and if your name servers fail, copies that last minutes run out in minutes.

Some resolvers ignore TTLs; the sums in this topic assume they don't, and your plan should leave room for the few that do. The build lab rehearses the move on a fast clock: 60 seconds stands for the day and 5 for the five minutes.

**Split-horizon: one name, two answers.** The office should reach the API on its private address, 10.0.8.51, while customers get the public one. That's **split-horizon** (or split-view) DNS: the office's resolver answers the name itself. In Unbound it's a **local zone** with **local data**:

```
local-zone: "shop.test." transparent
local-data: "api.shop.test. A 10.0.8.51"
```

The type decides everything else. **`transparent`** answers from the local data for names it holds and looks up every other name normally. **`static`** answers every name under the zone itself: names it holds get their data, and every other name gets NXDOMAIN. With `static`, `www.shop.test`, the mail server and every other public name vanish in the office. A local zone can also be narrower, `local-zone: "api.shop.test." static`, which touches nothing else. A setting made with `unbound-control local_zone ...` changes the running resolver only; the file is what a restart reads.

Cloud networks do the same with **private zones**: a zone that only resolvers inside a network see. All three clouds behave like `static`, which is why "we created a private zone for our domain and half our names stopped working inside" is a classic ticket:

| | AWS Route 53 | Azure Private DNS | Google Cloud DNS |
| --- | --- | --- | --- |
| A name missing from the private zone, asked from inside | NXDOMAIN: the VPC Resolver "doesn't forward the request to a public DNS resolver" | NXDOMAIN, except in the zones of Private Link (private addresses inside a network for Azure's own services, such as storage), whose network link can turn on "Enable fallback to internet" | NXDOMAIN "even if there is a record" in a public zone |
| Also | a VPC Resolver rule forwarding the same name to your own servers takes precedence over the private zone; the resolver is at the VPC's base address plus two | | |

The cure is the same everywhere: copy into the private zone every record that's needed inside, or make the private zone narrow (`internal.shop.test`, or just `api.shop.test`). And a machine sees the private answer only if it asks the resolver that holds it: a laptop with a public resolver set by hand gets the public one.

**DNSSEC: signed answers.** Plain DNS answers can be forged: anyone who can get a fake answer to a resolver first can send the shop's customers anywhere. **DNSSEC** (DNS Security Extensions) lets a resolver check each answer. It uses a pair of keys like Module 1's SSH keys: a **signature** is a short code worked out from the data with the private key, and anyone holding the matching public key can check that it was made with that key and that the data hasn't changed since, while nobody without the private key can make one. The zone's owner signs every RRset with a private key, and publishes the signatures as **RRSIG** records and the public key as a **DNSKEY** record. A key that signs the zone's other keys is a **KSK** (key-signing key, flags 257), one that signs the records a **ZSK** (zone-signing key, flags 256); one key that does both is a **CSK**, which is what BIND's default policy makes. The parent zone holds a **DS** record, a hash of the child's key (a short fingerprint worked out from the key, which any change to the key changes), signed by the parent; the parent's key has a DS in its parent; and so on up to the root, whose key the resolver is given in advance as its **trust anchor**. That **chain of trust** lets a **validating resolver** check any signed answer from the root down. A name that doesn't exist is proved missing with signed **NSEC** records (signed proof that no name sits between two others).

An answer that checks out is **secure**, and the resolver sets the `ad` flag. One from a zone with no DS in its parent is **insecure**: unsigned, accepted unchecked. One that should check out but doesn't is **bogus**, and the resolver answers SERVFAIL. What DNSSEC proves is that the answer came from the zone's keyholder and nobody changed it. It isn't secrecy: the question and the answer still travel in the clear.

**What broken looks like.** To users, every name in the zone fails, but only through resolvers that check signatures. Three things tell you it's DNSSEC:

- `dig +cd` (checking disabled) gets the records the plain lookup doesn't: the data is there, only validation fails.
- The answer carries an **Extended DNS Error** (EDE, RFC 8914) that names the cause: `EDE: 6 (DNSSEC Bogus)` with "no keys have a DS ..." when the parent's DS matches no key of the zone, `EDE: 7 (Signature Expired)` when the signatures have run out.
- The resolver's journal logs the same validation failure.

The fixes are on the zone's side: sign it again (and let the server sign it for you, as BIND's `dnssec-policy` does, so the signatures never lapse), or publish the right DS. When keys change, publish the new key and its DS before the old key goes. The anti-fixes are on the resolver's side: `val-permissive-mode`, `domain-insecure` or validation switched off would make every forged answer pass too, and fix nothing for the resolvers you don't run. Removing a DS to go back to unsigned has to wait out the DS's own TTL: on 30 September 2021 Slack removed its DS at the registrar to undo a DNSSEC rollout, resolvers had it cached for up to 24 hours, and validating ones answered SERVFAIL for slack.com for a day.

The clouds, from their own pages on 2026-11-12:

| | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Signing your public zone | Route 53 signs public hosted zones (not private ones); the key-signing key is a key you own in AWS's key service, KMS | Azure DNS signs public zones (ECDSAP256SHA256); a key-signing key change needs Microsoft support and a new DS | Cloud DNS makes, rotates and signs with the keys; nothing happens until your registrar publishes the DS |
| The network's own resolver | Route 53 VPC Resolver validates only once switched on per VPC ("could result in an outage"), and doesn't set `ad` | the default Azure-provided resolver (168.63.129.16): "DNSSEC response validation is not performed" | not stated on the page read |

<Recap>

- **Names:** labels read right to left, ending at the root, `.`. A **zone** is the part of a domain one set of servers answers for; its top is the **apex**. `.test` never exists on the internet.
- **Servers:** the **stub** asks a **recursive resolver**, which follows **referrals** (NS records, a **delegation**) from the **root** to the **TLD**'s servers to the zone's **authoritative** servers, and caches the answer. A **forwarder** passes questions on. Authoritative servers run `recursion no;`.
- **Reading dig:** status NOERROR, NXDOMAIN, NODATA (NOERROR, empty), SERVFAIL, REFUSED; flags `qr`, `rd`, `ra`, `aa` (the authority), `ad` (validated), `cd`. A referral: empty ANSWER, NS in AUTHORITY, **glue** in ADDITIONAL when the server's name is inside the delegated zone. `+trace` shows the steps, `@SERVER +norecurse` asks one server.
- **Records:** A, AAAA, CNAME (no other record beside it, so never at the apex: use Route 53's alias or Azure's alias record set), MX, TXT, CAA, NS, SOA, PTR (reverse zones, octets backwards). SOA: primary, mailbox, **serial**, refresh, retry, **expire**, **minimum**.
- **Secondaries** copy the zone by **zone transfer** (AXFR, IXFR) after a **NOTIFY** or a refresh, only when the serial is higher and `allow-transfer` lets them (the secondaries' addresses, never `any`: a transfer lists every name). Raise the serial with every edit; under BIND's own signing an edit without it isn't loaded (`zone reload queued`, then `not loaded due to errors` in the journal). `rndc reload`, `reconfig`, `notify`, `retransfer`.
- **Caching:** an answer lasts its TTL in every resolver that holds it; nobody can flush the world's caches. **Negative caching:** NXDOMAIN lasts min(SOA TTL, MINIMUM). Unbound caps answers at 86400 s and negative answers at 3600 s.
- **A move:** lower the TTL at least one old TTL before (serial raised, live everywhere), wait out the old TTL, switch, check through several resolvers, raise the TTL again.
- **Split-horizon:** Unbound's `local-zone` with `local-data`. `transparent` answers what it holds and resolves the rest; `static` gives NXDOMAIN for everything it doesn't hold. Cloud private zones act like `static` (Azure's fallback to the internet only for Private Link zones; Route 53's resolver rules beat private zones). `unbound-control` changes last only until a restart.
- **DNSSEC:** RRSIG signatures, DNSKEY keys (KSK, ZSK, CSK), the parent's DS, up to the **trust anchor**: the **chain of trust**. Secure (`ad`), insecure (no DS), bogus (SERVFAIL). Proves origin and integrity, not secrecy. Broken: SERVFAIL at validating resolvers, `+cd` still answers, **EDE** 6 (Bogus: DS matches no key) or 7 (Signature Expired). Fix: sign again, or publish the right DS; never `val-permissive-mode`, `domain-insecure` or validation off. A removed DS lives on for its TTL (Slack, 2021).
- **Clouds' resolvers:** Azure's default doesn't validate; Route 53's VPC Resolver validates once switched on per VPC; Cloud DNS signs once the registrar has the DS.

</Recap>
