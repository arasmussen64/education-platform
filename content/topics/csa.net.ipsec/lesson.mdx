<Intro>

BGP sessions and policy connected a shop to the internet and said that a VPN to a cloud runs a BGP session too; HTTP and TLS showed how two programs agree on keys over a network anyone can read. This topic puts the two together: a **site-to-site VPN**, a tunnel that joins two private networks across the internet, encrypted, so that they reach each other as if wired together. It is the quick, cheap way to connect an office or a data centre to AWS, Azure or Google Cloud (a dedicated circuit is the other way, which Steering traffic and cloud circuits covers), and the one you'll configure first. A **remote-access VPN**, one laptop dialling in, uses the same machinery for a single host. The labs build one: the office laptop, `office` (192.168.10.10), behind the office's VPN gateway, `vpn` (198.51.100.10 on the internet); across a router called `internet`, a cloud provider's VPN gateway, `cloud` (203.0.113.10), and behind it the shop's cloud network, 10.20.0.0/16, with the app at 10.20.1.10. vpn is yours; the provider's gateway isn't, and you see it the way a cloud's console shows a VPN connection. Each cloud has its own names for the two ends: AWS calls yours the **customer gateway** and its own a **virtual private gateway** (or a **transit gateway**, a hub that joins many networks); Azure calls its end a **VPN gateway** and its record of yours a **local network gateway**; Google's end is an **HA VPN gateway**, whose BGP a **Cloud Router** runs.

**IPsec, two protocols.** The standard for site-to-site VPNs is **IPsec** (IP security), which is two protocols with separate jobs:

- **IKE**, the Internet Key Exchange (version 2, IKEv2, in everything here), is the conversation in which the two gateways prove who they are and agree on keys and algorithms. It runs on UDP port 500, and later on 4500.
- **ESP**, the Encapsulating Security Payload, carries the traffic. It is its own IP protocol, number 50, beside TCP's 6 and UDP's 17, and it has no ports. In **tunnel mode**, the one site-to-site VPNs use, ESP encrypts the office's whole packet and puts it inside a new IP header from one gateway's outside address to the other's, so the internet sees only ESP packets between 198.51.100.10 and 203.0.113.10, each labelled with a number (its SPI, below) and nothing of the office's addresses. In **transport mode**, for two hosts talking to each other, only the payload is encrypted and the packet keeps its own addresses.

(IPsec has a third protocol, **AH**, which proves a packet wasn't changed on the way, its **integrity**, without encrypting it. It is rarely used, and it can't cross a NAT, because it protects the very addresses a NAT rewrites.)

On Linux the usual IPsec software is **strongSwan**, which the labs run on both gateways. Its daemon, **charon**, holds the IKE conversation and hands the keys it agrees to the kernel, which does ESP; `swanctl` is the command that loads charon's configuration and shows what it has agreed.

**Security associations, and the two phases.** What the two ends agree is kept as a **security association**, an SA: a set of keys and algorithms for one purpose, numbered by an **SPI** (security parameter index) that travels in every packet so the receiver knows which keys to use. IKE builds them in two steps, which everyone calls phases:

- **Phase 1** builds the **IKE_SA**, which protects IKE's own messages.
- **Phase 2** builds a **CHILD_SA** for the traffic: in the kernel, a pair of ESP SAs, one each way. The clouds call it the **IPsec SA**.

IKEv2 does this in four kinds of exchange, each a request and a response. **IKE_SA_INIT** agrees the IKE_SA's algorithms and does a key exchange (Diffie-Hellman, below). **IKE_AUTH**, already encrypted, proves who each end is and, in the same exchange, creates the first CHILD_SA. **CREATE_CHILD_SA** makes more CHILD_SAs and rekeys the existing ones. **INFORMATIONAL** carries deletes and liveness checks. Older IKEv1 did the same in more messages, "main mode" for phase 1 and "quick mode" for phase 2, which is why Azure's pages still use those names. On vpn, `swanctl --list-sas` shows both phases, captured in the worked example:

```text
cloud: #1, ESTABLISHED, IKEv2, 52fc2c20087bef21_i* df94620f929ad289_r
  local  '198.51.100.10' @ 198.51.100.10[4500]
  remote '203.0.113.10' @ 203.0.113.10[4500]
  AES_CBC-256/HMAC_SHA2_256_128/PRF_HMAC_SHA2_256/MODP_2048
  established 0s ago, rekeying in 13855s
  cloud-vti: #1, reqid 1, INSTALLED, TUNNEL, ESP:AES_GCM_16-256
    installed 0s ago, rekeying in 3500s, expires in 3960s
    in  c746e63c (0x0000002a),      0 bytes,     0 packets
    out c1923acc (0x0000002a),      0 bytes,     0 packets
    local  0.0.0.0/0
    remote 0.0.0.0/0
```

The first line is the IKE_SA, established; under it are its addresses and algorithms. `cloud-vti` is the CHILD_SA, installed in the kernel in tunnel mode, with its two SPIs, its mark (`0x2a`, 42, below) and its selectors (the addresses it carries, below).

**What crosses the wire.** A capture on the internet's router while vpn starts the tunnel shows IKE_SA_INIT on UDP 500 (`ikev2_init`), then IKE_AUTH on UDP 4500 (`ikev2_auth`). There is no NAT anywhere in the lab, so why 4500? Because both ends support **MOBIKE** (RFC 4555, which lets a tunnel move when an address changes), and that standard says such implementations move to 4500 even when no NAT was detected. 4500's real job is **NAT traversal**. NAT showed that a NAT tells its connections apart by their ports, and ESP has none, so a NAT can't carry it; when the two ends detect a NAT between them (IKE_SA_INIT carries two **notifies**, IKE's short status and error messages, `NATD_S_IP` and `NATD_D_IP`, for that), they wrap each ESP packet in UDP on port 4500 too. So a firewall in front of a VPN gateway allows **UDP 500, UDP 4500 and ESP**, and one that allows only 500 lets IKE_SA_INIT through and loses everything after it.

**Proposals.** A **proposal** is one set of algorithms: an encryption algorithm, an integrity algorithm (a keyed checksum that proves a message wasn't changed), for IKE a PRF (the function that derives keys), and a Diffie-Hellman group. strongSwan writes one as a string: `aes256-sha256-modp2048`. **AES-GCM** (`aes256gcm16`) is an **AEAD** cipher, authenticated encryption with associated data, which encrypts and checks integrity in one, so an ESP proposal with it names no separate integrity algorithm. Diffie-Hellman, the key exchange from HTTP and TLS, comes in **groups** with numbers: group 2 is MODP 1024-bit (too weak today), 14 MODP 2048-bit, 15 MODP 3072-bit, 20 ECP 384-bit (elliptic curve). Each end lists the proposals it accepts and they must share one; the **responder**, the end that answers (the one that starts is the **initiator**), chooses. Which one you get can depend on the provider's order, not yours: AWS's endpoints "evaluate proposals from your customer gateway starting with the lowest configured value from the list below, regardless of the proposal order from the customer gateway", so offering a weak proposal at all can get it chosen. Azure's route-based gateways, left at their defaults, start phase 1 with DH group 2 and AES256 with SHA-1. Offer only what the provider's sheet asks for.

**Perfect forward secrecy, and the hour-long trap.** A DH group in the ESP proposal (`aes256gcm16-modp2048`) gives each CHILD_SA keys from its own Diffie-Hellman exchange: **perfect forward secrecy** (PFS), HTTP and TLS's forward secrecy for the traffic. SAs don't live for ever: a CHILD_SA is **rekeyed**, replaced by a new one with fresh keys, every hour by strongSwan's default (less a random few minutes, so that the two ends don't both start a rekey at once), and has a hard lifetime 10% longer than the hour (the `rekeying in 3500s, expires in 3960s` above). Here is the trap. The first CHILD_SA is made inside IKE_AUTH and takes its keys from the IKE_SA's exchange, so its ESP proposal's DH group is never compared. If the two ends disagree about it, the tunnel comes up and works; an hour later the first rekey, a CREATE_CHILD_SA exchange, is refused, vpn logs `CHILD_SA rekeying failed`, and when the old CHILD_SA expires, 66 minutes after the start, the traffic stops. strongSwan's own reference warns that such a mismatch "might therefore not immediately be noticed".

**Who you are: keys and identities.** Each end sends an **identity**, the name it goes by (here its outside address, as AWS's and Azure's sheets give it), and proves it with a **pre-shared key** (PSK), a long password both ends were given, or with a certificate (Certificates and mutual TLS builds those). The responder first looks up the configuration for the identity it received, then checks the proof with that configuration's key. A PSK is a password: the file that holds it is readable by root alone.

**Policy-based and route-based.** A CHILD_SA has **traffic selectors**: the addresses it carries, both ways. In a **policy-based** VPN they are the two networks (192.168.10.0/24 and 10.20.0.0/16), and the selectors themselves decide what is encrypted. In a **route-based** VPN they are `0.0.0.0/0` both ways, and a **tunnel interface** decides: whatever routing sends into the interface is encrypted, and nothing else. Routing, which BGP can fill, then decides what crosses, so a new network is a new route, not a new negotiation, and a second tunnel is a second path. The clouds' BGP-based VPNs are route-based (Azure calls them RouteBased; PolicyBased gateways are its static ones).

On Linux the tunnel interface in the labs is a **VTI**, a virtual tunnel interface: `ip link add vti0 type vti local 198.51.100.10 remote 203.0.113.10 key 42`. Its **key** is a **mark**, a number the kernel attaches to every packet routed into vti0, and the CHILD_SA's `mark_in` and `mark_out` (42) tie its SAs to that interface: a packet marked 42 is encrypted with this SA. If the key and the marks differ, nothing matches, and vti0 drops every packet, counting transmit errors (`ip -s link show vti0`). strongSwan's route-based page adds two settings. First, charon must not install routes of its own (`install_routes = no`, set in every lab machine's strongSwan settings): by default it adds a route for each CHILD_SA's remote selector, ahead of the machine's own routes, and with 0.0.0.0/0 that is a route for everything, so routing, and BGP, would no longer decide. Second, it recommends `net.ipv4.conf.vti0.disable_policy = 1`, which saves the kernel a second policy lookup (traffic passes without it on the labs' kernels). The same page says **XFRM interfaces**, the newer kind, "provide a better solution than VTI devices" on kernels from 4.19; the labs use VTIs because Docker Desktop's kernel is built without XFRM interfaces (charon's log says so at every start: `failed to create XFRM interface`).

The policy-based habit breaks a route-based tunnel in a way worth knowing by its look: selectors of 192.168.10.0/24 and 10.20.0.0/16 on vpn, the provider narrows its 0.0.0.0/0 to them, the CHILD_SA is `INSTALLED`, and BGP sits in `Active` for ever, because BGP's own packets, between the inside addresses, are in neither selector and are never encrypted.

**Inside addresses, and BGP over the tunnel.** vti0 needs an address, and so does the provider's end: the **inside addresses**, a /30 of **link-local** addresses from 169.254.0.0/16, which never leave their link and so can't clash with either side's networks. AWS gives each tunnel a /30 from 169.254.0.0/16 (a few, like 169.254.169.252/30, are reserved), Azure's custom ones (it calls them APIPA addresses) come from 169.254.21.0 to 169.254.22.255, and Google's Cloud Router peers on link-local addresses too. BGP runs between them, exactly as in BGP sessions and policy: `neighbor 169.254.21.1 remote-as 64512`, with a route map each way. Send only the office's prefix; accept only what you expect, the cloud's own space. A cloud that offers `0.0.0.0/0` (the lab's provider does) would, if its route won, pull all the office's internet traffic into the tunnel. Learn the cloud's routes; don't type a static one: a static route for 10.20.0.0/16 works today and never hears about the next network the cloud adds, and the cloud never learns the office's.

AWS gives every VPN connection **two tunnels**, each to its own endpoint, and asks you to configure both: it maintains them one at a time. Before it works on one, it sets a lower **MED** on the other tunnel's routes, to move your traffic across. That works only if your router's local preference and weight are the same on both tunnels, because BGP compares them first (BGP sessions and policy's decision order): a router that prefers tunnel 1 by local preference ignores the hint and keeps sending into it until it drops.

**Making it last.** Three things a reboot or a provider's restart takes away, each with its line. **vti0** must be made at every boot: in the labs it goes in vpn's network file, `/etc/network/up`, with the BGP configuration saved (`write memory`) and the service enabled (`systemctl enable strongswan@vpn`). The **connection** must start by itself and come back: in the CHILD_SA, `start_action = start` starts it when charon loads the file, as at boot; `close_action = start` starts it again when the provider closes it, which is what a provider's maintenance does (it deletes the tunnel as its gateway stops, and without this line nothing starts it again); `dpd_action = restart`, with `dpd_delay = 10s` on the connection, is **dead peer detection**: it checks that the provider still answers when nothing else has arrived for 10 seconds, and starts again if it doesn't. And `keyingtries = 0` keeps trying at the start for as long as it takes, where the default, 1, gives up after one round of retransmits. (Even 0 stops at a refusal such as NO_PROPOSAL_CHOSEN, which no retry would change.) AWS's side never starts the tunnel by default (its "startup action" is `add`; `start` makes AWS initiate, IKEv2 only), so this is your gateway's job.

**Reading the logs.** No free resource lays the failures side by side, so here they are, captured from both ends in the labs. The name of the error notify and the exchange it came in say the phase:

| What went wrong | vpn, the initiator (`journalctl -u strongswan@vpn`) | The provider, the responder (`cloud-vpn-log`) |
| --- | --- | --- |
| IKE proposal (phase 1) | `parsed IKE_SA_INIT response 0 [ N(NO_PROP) ]`, `received NO_PROPOSAL_CHOSEN notify error` | `received proposals: IKE:AES_CBC_128/HMAC_SHA1_96/PRF_HMAC_SHA1/MODP_1024`, `configured proposals: ...`, `received proposals unacceptable` |
| Wrong pre-shared key (phase 1) | `parsed IKE_AUTH response 1 [ N(AUTH_FAILED) ]`, `received AUTHENTICATION_FAILED notify error` | `selected peer config 'office'`, `tried 1 shared key for '203.0.113.10' - '198.51.100.10', but MAC mismatched` |
| Wrong identity (phase 1) | the same two lines as a wrong key | `looking for peer configs matching ...198.51.100.10[branch.shop.test]`, `no matching peer config found` |
| ESP proposal (phase 2) | `IKE_SA cloud[12] established ...`, then `received NO_PROPOSAL_CHOSEN notify, no CHILD_SA built` | `received proposals: ESP:AES_CBC_256/HMAC_SHA1_96/NO_EXT_SEQ`, `configured proposals: ESP:AES_GCM_16_256/MODP_2048/NO_EXT_SEQ, ...`, `no acceptable proposal found` |
| Selectors the provider won't take (phase 2) | `received TS_UNACCEPTABLE notify, no CHILD_SA built` | `traffic selectors 10.20.0.0/16 === 192.168.10.0/24 unacceptable` |
| Selectors narrowed (route-based) | `CHILD_SA cloud-vti{14} established ... TS 192.168.10.0/24 === 10.20.0.0/16`, then BGP stays `Active` | `CHILD_SA office-vti{4} established ... TS 10.20.0.0/16 === 192.168.10.0/24` |
| No answer (UDP 4500 dropped on the path) | `sending packet: from 198.51.100.10[4500] ...`, `retransmit 1 of request with message ID 1`, 2, 3 | nothing after IKE_SA_INIT |
| PFS group (the first rekey) | up at first; an hour later `parsed CREATE_CHILD_SA response 2 [ N(NO_PROP) ]`, `CHILD_SA rekeying failed, trying again in 13 seconds` | `received proposals: ESP:AES_GCM_16_256/NO_EXT_SEQ`, `configured proposals: ESP:AES_GCM_16_256/MODP_2048/NO_EXT_SEQ, ...` |

The rules to take away. `NO_PROPOSAL_CHOSEN` in IKE_SA_INIT is phase 1; after `IKE_SA ... established` it is phase 2. `AUTHENTICATION_FAILED` is the key or the identity, and from your side the two look the same: only the responder's log can tell them apart. Retransmits with no answer are the path, not the configuration. A tunnel that dies about an hour after every restart is a rekey, usually PFS. In the labs, `cloud-vpn-log` shows the responder's log; in a cloud you get it only if you turn its VPN logs on (AWS's Site-to-Site VPN tunnel logs, Azure's gateway diagnostics), and without them the configuration sheet is your evidence.

**The tunnel's MTU.** ESP makes every packet bigger. With AES-GCM in tunnel mode it adds an outer IPv4 header (20 bytes), the ESP header (8: the SPI and a sequence number), an **IV** (initialisation vector, 8 bytes: a fresh starting value, so that the same data never encrypts the same way twice), a trailer (2 bytes, plus padding to a multiple of 4) and an integrity check (16): 54 bytes. So a 1500-byte link carries an inner packet of at most 1500 − 54 = 1446 bytes, and TCP's largest payload, the MSS, is 1446 − 40 = 1406: AWS's own figures. NAT traversal's UDP header costs 8 more (1438 and 1398), and AES-CBC more again, with a 16-byte IV and padding to 16-byte blocks. Layers and packets' path MTU black hole follows: if a link on the path is smaller and its routers' "fragmentation needed" messages are dropped, full-size segments vanish, so the front page loads and the report hangs at 0 bytes. The fix on your side is **MSS clamping** on the tunnel interface, which rewrites the MSS in each new connection's SYN so that no segment is too big. Clamp **both directions**: each side of a connection announces in its own SYN what it will accept, so `oifname "vti0" tcp flags syn tcp option maxseg size set 1300` makes the app send small segments (downloads work), and only `iifname "vti0"` with the same rule makes the office do the same (uploads). The number is arithmetic: on a 1400-byte line with AES-GCM, 1400 − 54 − 40 = 1306 at most.

**Where the three clouds differ.** No single page puts them side by side (each provider's pages, read 2026-11-12):

| | AWS Site-to-Site VPN | Azure VPN Gateway | Google Cloud HA VPN |
| --- | --- | --- | --- |
| Tunnels | two per connection, each to its own endpoint in its own Availability Zone (a separate group of data centres in the region); "It is important to configure both tunnels" | BGP needs a route-based gateway (not policy-based, and not the Basic SKU, Azure's smallest gateway size) | two interfaces and two tunnels for its 99.99% SLA (service level agreement: the availability Google promises); a single interface has no SLA |

| Proposals | many accepted, evaluated from the lowest configured value whatever your order; narrow them with `modify-vpn-connection-options` | route-based defaults start with DH group 2 (1,024-bit) and AES256 with SHA-1, and offer phase 2 without PFS; set a custom IPsec/IKE policy | IKEv1 or IKEv2, with a pre-shared key only |
| BGP | Amazon-side ASN 64512 unless you choose another, fixed once created; inside /30 from 169.254.0.0/16; takes up to 100 routes from you (on a virtual private gateway) | ASN 65515 by default; up to 4,000 prefixes, and more drops the session; keepalive 60 s, hold 180 s, fixed; custom inside addresses 169.254.21.0 to 169.254.22.255 | BGP only (through a Cloud Router); peering addresses link-local, from 169.254.0.0/16 |

<Recap>

- **A site-to-site VPN** joins two private networks across the internet, encrypted. **IPsec** is two protocols: **IKE** (UDP 500, then 4500) proves who each end is and agrees keys; **ESP** (IP protocol 50, no ports) carries the traffic, in **tunnel mode** a whole packet inside a new header between the gateways' outside addresses. AH checks integrity only and can't cross a NAT.
- **Two phases:** phase 1 builds the **IKE_SA**, phase 2 a **CHILD_SA** (the "IPsec SA", two kernel SAs numbered by SPIs). Exchanges: **IKE_SA_INIT** (proposal and Diffie-Hellman), **IKE_AUTH** (identities and the first CHILD_SA), **CREATE_CHILD_SA** (more, and rekeys), **INFORMATIONAL** (deletes, DPD). IKEv1's main and quick mode are the same phases.
- **On the wire:** UDP 500, then UDP 4500 (MOBIKE moves there even without a NAT; behind a NAT, **NAT traversal** wraps ESP in UDP 4500 too), and ESP. A firewall allows all three.
- **Proposals:** encryption, integrity or **AEAD** (AES-GCM does both), PRF, DH group (2 = MODP 1024, 14 = MODP 2048, 15 = MODP 3072, 20 = ECP 384). The responder chooses, maybe by its own order: offer only the sheet's. **PFS** = a DH group in the ESP proposal; the first CHILD_SA doesn't use it, so a mismatch fails at the first rekey, about 66 minutes in with strongSwan's defaults.
- **Identity and PSK:** the responder finds the configuration for the identity, then checks the proof with its key. Keep the key's file readable by root alone.
- **Route-based:** selectors 0.0.0.0/0 both ways and a tunnel interface (a **VTI**: `ip link add vti0 type vti local A remote B key 42`, with `mark_in`/`mark_out` 42); routing decides what is encrypted; `install_routes = no`. Narrow selectors leave BGP's inside addresses out: installed, and `Active` for ever. **XFRM interfaces** are better on kernels from 4.19, where built.
- **BGP over it:** between link-local inside addresses (a /30 from 169.254.0.0/16); send only your prefix, accept only the cloud's space (never a default route), learn rather than type routes. AWS: two tunnels, a lower MED on the one to use during maintenance, so keep local preference equal.
- **Lasting:** vti0 made at boot (the network file), the service enabled, BGP saved; `start_action = start`, `close_action = start` (the provider's maintenance), `dpd_delay` with `dpd_action = restart`, `keyingtries = 0`.
- **Logs:** `NO_PROPOSAL_CHOSEN` in IKE_SA_INIT = phase 1; after `IKE_SA ... established` = phase 2. `AUTHENTICATION_FAILED` = key or identity, told apart only by the responder (`MAC mismatched` against `no matching peer config found`). `TS_UNACCEPTABLE` = selectors. Retransmits = the path. Dies an hour in = rekey (PFS).
- **MTU:** AES-GCM's ESP costs 54 bytes (1500 → 1446, MSS 1406); NAT-T 8 more; CBC more. Big transfers hang where ICMP is dropped: clamp the MSS on the tunnel interface, both directions (`oifname` and `iifname "vti0"`), to at most link MTU − overhead − 40.
- **Clouds:** AWS two tunnels, ASN 64512, 100 routes from you, MTU 1446/MSS 1406; Azure ASN 65515, 4,000 prefixes, BGP 60/180 fixed, DH group 2 first by default, MSS clamped to 1,360 on its side; Google HA VPN 99.99% with two tunnels, BGP only, gateway MTU 1460.
- **Commands:** `swanctl --load-all`, `--list-sas`, `--list-conns`, `--initiate --child NAME`, `--terminate --ike NAME`; `journalctl -u strongswan@vpn`; `ip -s xfrm state`; `tcpdump -nn 'esp or udp port 500 or udp port 4500'`; `vtysh -c 'show bgp summary'`.
