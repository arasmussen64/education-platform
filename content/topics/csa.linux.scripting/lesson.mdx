<Intro>

<Puzzle question="A cleanup script has two lines: `cd /srv/build/tmp`, then `rm -rf *`. One night the folder `/srv/build/tmp` doesn't exist. What does the script delete?">

Everything in whatever folder the script was already in, often the home folder of the user running it. The `cd` fails and prints an error, and bash, by default, simply carries on to the next line, so `rm -rf *` runs where the script stands. One line at the top, `set -e`, makes bash stop at the first failed command instead. This topic is that line and the handful of other habits that make a script safe.

</Puzzle>

Every command from the earlier topics can be saved in a file and run again, and that file is a **shell script**. Scripts glue a server together: the deploy step, the backup, the health check, the commands a new cloud server runs on its first boot (cloud-init's `runcmd`, from the Boot topic). The trouble is that bash was designed to keep going whatever happens, which is fine at a prompt and dangerous in a script. This topic is about the handful of habits that make a script something you can trust.

**The shape of a script.** It starts with a **shebang**, `#!/usr/bin/env bash`, which tells the kernel what should run the file; `chmod +x deploy.sh` and `./deploy.sh` run it. Variables are set with `name=value` (no spaces around `=`) and read with `$name`. `$(command)` runs a command and gives you its output. `if [[ -f config.ini ]]; then … fi` tests things, `for f in *.log; do … done` loops, and `name() { …; }` defines a function. Arguments arrive as `$1`, `$2` and, all together, `"$@"`.

**Strict mode.** Three settings at the top change bash from "carry on regardless" to "stop when something's wrong":

- **`set -e`**: exit the moment a command fails. Without it, a failed `cd` is followed by an `rm` in the wrong directory.
- **`set -u`**: treat an unset variable as an error. Without it, a misspelt `$BUILD_DRI` is an empty string, and `rm -rf "$BUILD_DRI/"` is `rm -rf /`.
- **`set -o pipefail`**: a pipeline fails if *any* stage fails, and its exit status is that of the last stage that failed. Without it, `cat missing.txt | wc -l` succeeds, because `wc` did.

<Check item="scr-set-u" />

Together: `set -euo pipefail`. One trap to know: `set -e` deliberately doesn't fire where a result is being *tested*: inside an `if` condition, on the left of `||` or `&&`, and inside `$(…)` on a `local x=$(…)` line, where `local` succeeding masks the failure. For a command that's allowed to fail, say so: `grep pattern file || true`.

<Story title="Steam for Linux empties a home folder, 2015" source="https://github.com/ValveSoftware/steam-for-linux/issues/3671" sourceTitle="Moved ~/.local/share/steam. Ran steam. It deleted everything on system owned by user." license="linked, not copied">

In January 2015 a Steam for Linux user reported that the game launcher had deleted every file their account owned, from the root of the machine down, including a 3 TB external drive mounted under `/media`. They had moved Steam's folder to another drive and left a symbolic link where it used to be; Steam couldn't find its folder, crashed, and reinstalled itself.

Other users read Steam's launch script and pointed to one line: `rm -rf "$STEAMROOT/"*`, meant to empty Steam's own folder. If `STEAMROOT` came out empty, the line becomes `rm -rf "/"*`: delete everything under the root that this user may delete. The variable was set earlier in the script from the output of a `cd` inside `$(...)`, and one commenter suggested that this was probably coming out empty.

Note what would and wouldn't have helped. `set -u` stops on a variable that was never set, but this one was set, to nothing. The guard is a check that the value isn't empty before deleting; ShellCheck's warning SC2115 now suggests exactly that for this line, with `"${STEAMROOT:?}"`, which stops the script when the variable is empty or unset.

</Story>

**Quoting.** When bash sees an unquoted `$file`, it splits the value at spaces and treats it as a filename pattern. `"my notes.txt"` becomes two arguments; `*` becomes every file in the folder. **Quote every variable**: `"$file"`, `"$(command)"`. In a function or a script, `"$@"` passes the arguments on exactly as they came, each one its own word, which `$*` and unquoted `$@` do not. `[[ … ]]` is the modern test: it doesn't word-split its contents, so `[[ $count -gt 2 ]]` is safe where `[ $count -gt 2 ]` breaks on an empty `$count`.

<Check item="scr-quoting" />

**Failing well.** Exit status is the contract with whoever runs the script. `0` means success; anything else means failure, and CI, systemd and other scripts act on it. When something essential is missing, say so on stderr and stop: `cat config.ini >/dev/null || { echo "could not read config.ini" >&2; exit 2; }`. For cleanup that must happen no matter how the script ends, use a **trap**: `tmp=$(mktemp -d); trap 'rm -rf "$tmp"' EXIT` runs the removal on a normal exit, on a `set -e` failure and on Ctrl-C alike. Lock files, temporary directories and "put the service back" steps all belong in an `EXIT` trap.

<Check item="scr-trap-exit" />

**Safe to run twice.** A script that fails halfway *will* be run again: by you, by cloud-init on a new instance, by a retry loop. If step three failed, steps one and two already happened, and the second run must not break on them. That property is called **idempotency**: running the script once or ten times leaves the same result. The habits: `mkdir -p dir` instead of `mkdir dir` (which fails if it exists); `ln -sfn target link` instead of `ln -s` to make a **symbolic link** (a name that points at another path, like `current` → `releases/1.4`; plain `ln -s` fails if the link already exists); `grep -qxF "$line" file || echo "$line" >> file` instead of a plain append (which duplicates); `id deploy >/dev/null 2>&1 || useradd deploy`; `install -d -m 750 /srv/app` to create a directory with its mode in one step. Describe the state you want, and make each step check before it acts. Configuration-management tools later in the track are built on exactly this idea.

<Check item="scr-mkdir-twice" />

**Tooling.** **ShellCheck** reads a script and points out the quoting, `set -e` and portability mistakes above, with a wiki page for each; run it on every script, in your editor or in CI. Google's style guide is short and sensible: small functions, `main "$@"` at the bottom, errors to stderr, and the advice that a script which needs data structures or has passed about a hundred lines should be rewritten in Python. The Missing Semester's scripting half is the reading for the syntax; Bash Pitfalls is the list of ways it goes wrong.

<Recap>

- **Shape:** `#!/usr/bin/env bash`; `name=value`; `"$name"`; `"$(command)"`; `if [[ … ]]; then … fi`; `for x in …; do … done`; `name() { …; }`; arguments `$1`, `"$@"`.
- **`set -euo pipefail`:** stop on failure, unset variables are errors, pipelines fail if any stage fails (the pipeline's status is then that of the last stage that failed). `set -e` doesn't fire inside `if`, left of `||`/`&&`, or in `$(…)` on a `local x=` line. Allow a failure on purpose with `|| true`.
- **Quote everything:** `"$file"` (spaces, globs, empty values), `"$@"` (arguments passed on intact). `[[ ]]` over `[ ]`.
- **Exit status is the contract:** `0` success; `echo "…" >&2; exit 2` for a missing requirement; CI, systemd and other scripts read it. A script ended by a signal reports 128 plus the signal's number: 137 after `KILL`, which is signal 9.
- **`trap 'cleanup' EXIT`** runs on normal exit, failure and Ctrl-C; pair with `mktemp -d`.
- **Idempotent steps:** `mkdir -p`, `ln -sfn`, `grep -qxF … || echo … >>`, `id user || useradd`, `install -d -m`. State, not change. A failed script will be run again.
- **Tooling:** ShellCheck on every script; Google's style guide; past ~100 lines or real data structures, use Python.

</Recap>
