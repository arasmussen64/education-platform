<Intro>

Software on a Linux server arrives in **packages**: one file per program or library, holding the files to install, a version number, and a list of other packages it needs, its **dependencies**. A **package manager** downloads packages from **repositories** (servers run by the distribution, signed so they can't be tampered with), works out the dependencies, installs everything in the right order, and keeps a database of what's installed. Debian and Ubuntu use `apt` (with `dpkg` underneath); Red Hat, Fedora and their relatives use `dnf` (with `rpm` underneath). The ideas are the same; the spelling differs.

**The everyday commands.** `apt install nginx`, `apt remove nginx` (keeps its config files) or `apt purge nginx` (removes those too), `apt search text`, `apt show nginx`. `dpkg -l` lists every installed package with a two-letter state: `ii` means installed, `rc` means removed but its config files are still there. `apt policy nginx` shows the version installed and the version available (the **candidate**). On the dnf side: `dnf install`, `dnf remove`, `dnf search`, `dnf info`, `rpm -qa` to list, `dnf history` to see what changed when.

**Two different commands people confuse.** `apt update` downloads the *list* of available packages from the repositories. It installs nothing; it just refreshes what `apt` knows. `apt upgrade` installs the newer versions of what's already installed. So the ritual is `apt update` first, then `apt list --upgradable` to see what would change, then `apt upgrade`. (`dnf check-update` and `dnf upgrade` are the pair there.) `apt full-upgrade` may also remove packages to untangle dependencies, so read what it proposes.

**Where packages come from.** The files in `/etc/apt/sources.list.d/` (and the older `/etc/apt/sources.list`) name the repositories. Ubuntu 24.04 keeps its own in `ubuntu.sources`, one block with `URIs:`, `Suites:` and `Components:` lines; older one-line entries, `deb URL suite components`, still work and you'll meet both. Each entry names a **suite**: `noble` is the release as shipped, `noble-updates` its bug fixes, `noble-security` its security fixes. The security suite is how you tell a security update from the rest: `apt list --upgradable` names the suite on each line. Adding a third-party repository means adding its signing key, and that means trusting its owner with root on your server, because packages run scripts as root when they install. Prefer the distribution's own repositories, and read a third party's instructions with that in mind.

**Patching without breaking things.** Security updates first, and regularly: `unattended-upgrades` on Ubuntu and `dnf-automatic` on Fedora and RHEL can install them for you every night. A package you can't afford to have change under you, a database you've tested at one version, say, can be **held** (`apt-mark hold postgresql`; `apt-mark showhold` lists the holds, `unhold` releases one) or **version-locked** (`dnf versionlock add`), so it stays put while everything else updates; release the hold when you're ready to upgrade it deliberately. To upgrade a chosen few and nothing else, `apt install --only-upgrade pkg1 pkg2`. In a script nobody is watching, `apt`'s "Do you want to continue?" needs `-y`, and `dpkg-query -W -f='${Version}' pkg` prints just a package's installed version. Some updates only take effect after a restart. A new kernel or a new C library needs a **reboot**; Ubuntu writes `/var/run/reboot-required` (and lists the packages in `reboot-required.pkgs`) to tell you, and RHEL's `needs-restarting -r` answers the same question. Other services need restarting because a library they loaded has changed: `needs-restarting` lists them, and `checkrestart` does on Debian. On a fleet, patch one server and watch it before the rest.

**Mutable or immutable.** A server you patch in place is **mutable**: it changes over time, and after two years of hand-applied fixes no two servers are quite the same, which is why nobody dares touch the old one. The cloud makes the other approach cheap: build a new **image** with the updates baked in, test it once, and **replace** the running servers from it a few at a time behind the load balancer. Nothing is patched in place, every server is identical and known, and rolling back means redeploying the previous image. Martin Fowler's short *Immutable Server* and *Phoenix Server* notes are the classic statement of the idea; later modules build it with Packer and autoscaling groups.

**Read now:** the Ubuntu Server package-management page, the main resource below, for `apt`, `dpkg` and repositories, then chapter 6 of the Debian handbook for the deeper story, the Fedora page to see the same ideas in `dnf`, the automatic-updates page, and Fowler's two notes. The quick questions read `apt`, `dpkg` and repository files with the text tools from Shell essentials. The labs put you on a machine with a package repository of its own, so `apt` works without the internet and does the same thing for everyone: you refresh and read the list, hold a package while you patch the rest, remove one with and without its configuration, write a security-only updater, and fix a nightly patch script that patches nothing.

<Recap>

- **A package** has files, a version and dependencies; **repositories** supply them, signed; **suites** split a release into base, `-updates` and `-security`.
- **apt:** `install`, `remove` (keeps config), `purge` (removes config), `search`, `show`, `apt policy pkg` (installed versus candidate), `apt list --upgradable`; `dpkg -l` states `ii` installed, `rc` removed with config left.
- **dnf:** `install`, `remove`, `search`, `info`, `check-update`, `upgrade`, `history`; `rpm -qa` lists; `dnf versionlock add` pins.
- **`apt update` refreshes the list; `apt upgrade` installs newer versions.** Always update first. `full-upgrade` may remove packages.
- **Patching:** security updates first and automatically (`unattended-upgrades`, `dnf-automatic`); hold what must not change (`apt-mark hold`, `showhold`, `unhold`); `apt install --only-upgrade` for a chosen few; `-y` in scripts; patch one server, then the rest.
- **Restarts:** a kernel or libc update needs a reboot (`/var/run/reboot-required`, `needs-restarting -r`); services with changed libraries need a restart (`needs-restarting`, `checkrestart`).
- **Trust:** a third-party repository and key means trusting its owner with root.
- **Immutable servers:** bake a new image with the updates, test it, replace instances from it; identical servers, rollback by redeploying the previous image. Patching in place causes drift.

</Recap>
