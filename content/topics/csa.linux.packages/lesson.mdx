<Intro>

<Puzzle question="A script has run `apt update` on a server every night for a year, and succeeded every time. The server still has a year-old, well-known security hole in a library it uses. How?">

`apt update` installs nothing. It only downloads the latest list of what's available, so the server has known about the fix for a year without applying it. Installing the newer versions is a second command, `apt upgrade`, and some fixes need a restart or a reboot on top before the running programs use them. The two commands are this lesson's first trap.

</Puzzle>

Software on a Linux server arrives in **packages**: one file per program or library, holding the files to install, a version number, and a list of other packages it needs, its **dependencies**. A **package manager** downloads packages from **repositories** (servers run by the distribution, signed so they can't be tampered with), works out the dependencies, installs everything in the right order, and keeps a database of what's installed. Debian and Ubuntu use `apt` (with `dpkg` underneath); Red Hat, Fedora and their relatives use `dnf` (with `rpm` underneath). The ideas are the same; the spelling differs.

**Reading a version.** Package managers compare versions piece by piece as numbers, not as text, so `1.10` is newer than `1.9`. On Debian and Ubuntu a version has up to three parts. Take `1.24.0-2ubuntu7`. The `1.24.0` is the number the program's own authors gave it, the **upstream** version. What follows the last hyphen, `2ubuntu7`, counts the distribution's repackagings of it: Debian's second, with Ubuntu's seventh change on top. A security fix on a stable release usually moves only that last part, to `2ubuntu7.1`, say: the same program with one repair, which is why patching rarely changes how the software behaves. Now and then a number and a colon stand in front, as in `2:9.1.0016`. That is an **epoch**, a counter the packagers raise when a project's numbering starts over, and it outranks everything after it; no epoch means zero.

**The everyday commands.** `apt install nginx`, `apt remove nginx` (keeps its config files) or `apt purge nginx` (removes those too), `apt search text`, `apt show nginx`. `dpkg -l` lists every installed package with a two-letter state: `ii` means installed, `rc` means removed but its config files are still there. `apt policy nginx` shows the version installed and the version available (the **candidate**). On the dnf side: `dnf install`, `dnf remove`, `dnf search`, `dnf info`, `rpm -qa` to list, `dnf history` to see what changed when.

Three things about those commands. Anything that changes the system needs root, the administrator account, so it is typed with `sudo` in front (`sudo apt install nginx`); looking, with `apt list`, `apt policy` or `dpkg -l`, doesn't. Installing one package often brings others: `apt` names the dependencies it will add and asks before it goes on. Removing the package later leaves them behind, and `apt autoremove` clears the ones nothing needs any more. And `remove` keeps the configuration files on purpose, so that a reinstall finds your settings as you left them. When the settings are the trouble, `purge` is the word, and it works on an `rc` package too.

**Two different commands people confuse.** `apt update` downloads the *list* of available packages from the repositories. It installs nothing; it just refreshes what `apt` knows. `apt upgrade` installs the newer versions of what's already installed. So the ritual is `apt update` first, then `apt list --upgradable` to see what would change, then `apt upgrade`. (`dnf check-update` and `dnf upgrade` are the pair there.) `apt full-upgrade` may also remove packages to untangle dependencies, so read what it proposes.

Each line of `apt list --upgradable` has the form `name/suite version architecture [upgradable from: old-version]`, so the package's name is whatever stands before the slash, and the version you have now is the one in the brackets. `apt` is made for a person at a keyboard: when its output goes into a file or a pipe, it adds a warning that the layout may change. `apt-get update` and `apt-get upgrade` are the older tool's words for the same two steps, and you'll meet them in scripts.

**Where packages come from.** The files in `/etc/apt/sources.list.d/` (and the older `/etc/apt/sources.list`) name the repositories. Ubuntu 24.04 keeps its own in `ubuntu.sources`, one block with `URIs:`, `Suites:` and `Components:` lines; older one-line entries, `deb URL suite components`, still work and you'll meet both. Each entry names a **suite**: `noble` is the release as shipped, `noble-updates` its bug fixes, `noble-security` its security fixes. The security suite is how you tell a security update from the rest: `apt list --upgradable` names the suite on each line. Adding a third-party repository means adding its signing key, and that means trusting its owner with root on your server, because packages run scripts as root when they install. Prefer the distribution's own repositories, and read a third party's instructions with that in mind.

The **components** at the end of an entry divide a suite by who looks after the software: on Ubuntu, `main` and `restricted` are supported by Canonical, the company behind Ubuntu, and `universe` and `multiverse` by the community. Signing works through lists. A repository's owner signs an index of each suite with a private key; the index leads, by checksums (a checksum is a fingerprint worked out from a file's contents), to every package in it; and `apt` checks the signature with the public key it was given before it installs anything. That proves who published a package and that nobody changed it on the way. It doesn't prove the package is safe, or that anyone reviewed it, and the key puts no limit on what its holder may publish to you, now or in any later update.

<Story title="The xz backdoor, 2024" source="https://www.openwall.com/lists/oss-security/2024/03/29/4" sourceTitle="backdoor in upstream xz/liblzma leading to ssh server compromise" license="linked, not copied">

In March 2024 Andres Freund, a developer testing on Debian's unstable, pre-release branch, noticed that SSH logins were using a lot of CPU: a failed login took 0.8 seconds instead of 0.3, and a memory-checking tool reported errors. He traced it to a compression library, liblzma, from the xz package, versions 5.6.0 and 5.6.1.

Someone had hidden a backdoor in those releases. A line added to the release downloads, but not to the project's source history, ran a disguised script during the package build, and two obfuscated "test" files committed to the project carried more of it. The SSH server doesn't use liblzma itself, but Debian and several other distributions build it with systemd's library, which does, so the code ended up inside `sshd`, meddling with the key check before anyone had logged in.

Freund reported it to Debian's security team and the distributions, then published it on 29 March. The two versions had so far reached mostly pre-release distributions, so servers on stable releases had escaped. The lesson: installing a package trusts everyone who built it, and a stable release's suites give the world time to look.

</Story>

**Patching without breaking things.** Security updates first, and regularly: `unattended-upgrades` on Ubuntu and `dnf-automatic` on Fedora and RHEL can install them for you every night. A package you can't afford to have change under you, a database you've tested at one version, say, can be **held** (`apt-mark hold postgresql`; `apt-mark showhold` lists the holds, `unhold` releases one) or **version-locked** (`dnf versionlock add`), so it stays put while everything else updates; release the hold when you're ready to upgrade it deliberately. To upgrade a chosen few and nothing else, `apt install --only-upgrade pkg1 pkg2`. In a script nobody is watching, `apt`'s "Do you want to continue?" needs `-y`, and `dpkg-query -W -f='${Version}' pkg` prints just a package's installed version. Some updates only take effect after a restart. A new kernel or a new C library needs a **reboot**; Ubuntu writes `/var/run/reboot-required` (and lists the packages in `reboot-required.pkgs`) to tell you, and RHEL's `needs-restarting -r` answers the same question. Other services need restarting because a library they loaded has changed: `needs-restarting` lists them, and `checkrestart` does on Debian. On a fleet, patch one server and watch it before the rest.

**Holds and pins.** A hold freezes a package at the version that is installed. `apt list --upgradable` goes on showing that a newer one exists, and `apt upgrade` leaves it alone. Set the hold before the upgrade, and on the right package: a hold on the wrong one quietly skips that package's fixes instead. A held package gets no security fixes either, so a hold is a decision to come back to. A **pin** is the more general tool: a few lines in a file under `/etc/apt/preferences.d/` that give one version, or everything from one repository, a priority number. With no pins, the installed version has priority 100 and the versions in the repositories 500; `apt` takes the highest priority, and among equals the newest version. Those are the numbers in `apt policy`'s version table. A pin of 1000 or more wins even when it means stepping down to an older version:

```
Package: nginx
Pin: version 1.24.0*
Pin-Priority: 1001
```

To install one exact version by hand, name it after an equals sign: `apt install nginx=1.24.0-2ubuntu7`.

**Automatic updates, set up.** `unattended-upgrades` comes installed on Ubuntu Server and switched on, but check rather than assume. Two files in `/etc/apt/apt.conf.d/` control it. `20auto-upgrades` is the switch: the lines `APT::Periodic::Update-Package-Lists "1";` and `APT::Periodic::Unattended-Upgrade "1";`, where the number is the days between runs and `0` means never. `50unattended-upgrades` says what it may do. Its `Allowed-Origins` list names the suites it takes updates from: as shipped, the security suite and not `-updates`. `Package-Blacklist` names packages it must leave alone. `Automatic-Reboot` is `"false"` until you change it, so the server never restarts by itself. Each run is logged under `/var/log/unattended-upgrades/`. `dnf-automatic` reads `/etc/dnf/automatic.conf`, where `upgrade_type = security` keeps it to security fixes and `apply_updates = yes` makes it install them instead of only reporting. A nightly job running `apt upgrade -y` is not the same thing: it installs every update, the ones you meant to look at first included.

**A way back.** Before patching a server you couldn't easily rebuild, take a **snapshot**: a saved copy of its disk as it is now, which a cloud makes in moments, so that a bad update is undone by going back to it. That, and patching one server before the rest, is what keeps a bad update a small problem.

**Why some updates wait for a restart.** An upgrade replaces files on the disk. It doesn't touch what is already running. The kernel was loaded into memory when the machine booted, and a program loads its libraries when it starts; both carry on with the old code. So after a kernel update, `uname -r`, which prints the running kernel's version, shows the old one until the reboot, and a web server goes on using the old OpenSSL library until it is restarted. Nearly every program has loaded the C library, which is why its update asks for a reboot too. Ubuntu 24.04's `needrestart` restarts the affected services by itself after an upgrade; a new kernel still waits for you. `/var/run` is another name for `/run`, a folder that is emptied at every boot, so the reboot itself clears the note. A script asks the machine like this: `[ -f /run/reboot-required ] && echo "reboot needed"`.

**The same work with dnf.** On Red Hat's family (RHEL, Rocky Linux, AlmaLinux, Fedora) the ideas carry over, and four things differ.

- **The names.** `rpm -q shop-report` prints what is installed as one string, such as `shop-report-2.1-1.noarch` (`shop-report` is one of the labs' made-up packages). That is the name, the version (2.1), the **release** (1, which counts the packager's builds of that version, as the part after the hyphen does on Ubuntu) and the architecture (`noarch` means any processor). `dnf list --showduplicates shop-report` lists the installed version and then every version the repositories hold; on the installed line, the repository's name in the last column has an `@` in front.
- **No refresh step, and a false friend.** `dnf` fetches a new list by itself when its copy is stale, so nothing matches `apt update`. `dnf check-update` lists what an upgrade would change and installs nothing. (It ends with exit status 100 when updates are waiting: that is its way of saying yes, not an error.) `dnf upgrade` installs. And **`dnf update` is an old name for `dnf upgrade`:** someone who types it meaning only to refresh is asked whether to upgrade the whole server. Security fixes have no suite of their own here; `dnf upgrade --security` installs only the updates marked as security fixes.
- **A chosen version, and a lock.** `dnf install shop-report-2.0` installs that version: the name, a hyphen, the version, where `apt` uses `=`. `dnf downgrade shop-report` steps back one version. `dnf versionlock add shop-report` locks whichever version is installed at that moment, so move the package to the version you want first and lock it second. `dnf versionlock list` shows the locks and `dnf versionlock delete shop-report` takes one off.
- **A history.** `dnf history` lists every change `dnf` has made as a numbered **transaction**, newest first, with the start of the command that made it. `dnf history info 4` shows what transaction 4 changed, with the versions before and after, and `dnf history undo 4` reverses it. Ubuntu's plainer record is the file `/var/log/apt/history.log`.

**Mutable or immutable.** A server you patch in place is **mutable**: it changes over time, and after two years of hand-applied fixes no two servers are quite the same, which is why nobody dares touch the old one. The cloud makes the other approach cheap: build a new **image** with the updates baked in, test it once, and **replace** the running servers from it a few at a time behind the load balancer. Nothing is patched in place, every server is identical and known, and rolling back means redeploying the previous image. Martin Fowler's short *Immutable Server* and *Phoenix Server* notes are the classic statement of the idea; later modules build it with Packer and autoscaling groups.

The slow drifting apart of servers that were meant to be the same is called **configuration drift**, and nobody decides it: one server misses a round of patches, someone installs a tool by hand on another, and "it works on web-02" stops saying anything about web-01. The tested image that every server is made from is often called a **golden image**. An **immutable server** doesn't have a disk that can't be written: logs and data are still written. It means nobody logs in to change the software, because a change is a new image. So updates come more often this way, not less, and anything worth keeping, a database or uploaded files, lives outside the servers, which can then be thrown away. Replacing a few at a time matters for the same reason as patching one server first: if the new image misbehaves, most of the service is still on the old one, and patching all of them at the same moment leaves no way back.

<Recap>

- **A package** has files, a version and dependencies; **repositories** supply them, signed; **suites** split a release into base, `-updates` and `-security`.
- **apt:** `install`, `remove` (keeps config), `purge` (removes config), `search`, `show`, `apt policy pkg` (installed versus candidate), `apt list --upgradable`; `dpkg -l` states `ii` installed, `rc` removed with config left.
- **dnf:** `install`, `remove`, `search`, `info`, `check-update`, `upgrade`, `history`; `rpm -qa` lists; `dnf versionlock add` pins.
- **The same day's work on Red Hat's family** (RHEL, Rocky Linux, AlmaLinux, Fedora): `rpm -q nginx` prints the version that is installed, as `dpkg-query -W nginx` does. `dnf list --showduplicates nginx` lists the installed version and every version the repositories have, as `apt policy nginx` does. `dnf check-update` lists what an upgrade would change, as `apt list --upgradable` does. There is no refresh step to remember: `dnf` fetches a stale list by itself. **`dnf update` is not `apt update`:** it is an old name for `dnf upgrade`, and it installs.
- **A chosen version, and a lock:** `dnf install nginx-1.24.0` installs that version (the name, a hyphen, the version), where `apt` writes `nginx=1.24.0`; `dnf downgrade nginx` steps back one version. `dnf versionlock add nginx` locks the version that is installed, so put the package where you want it first; `dnf versionlock list` shows the locks, and `dnf versionlock delete nginx` takes one off. On RHEL's family the lock is a plugin that comes as a package of its own, `python3-dnf-plugin-versionlock`.
- **`dnf history`** numbers every change `dnf` has made to the server, newest first. `dnf history info 7` shows what transaction 7 changed, with the versions before and after, and `dnf history undo 7` reverses it. (`apt` keeps a plainer record, in `/var/log/apt/history.log`.)
- **`apt update` refreshes the list; `apt upgrade` installs newer versions.** Always update first. `full-upgrade` may remove packages.
- **Patching:** security updates first and automatically (`unattended-upgrades`, `dnf-automatic`); hold what must not change (`apt-mark hold`, `showhold`, `unhold`); `apt install --only-upgrade` for a chosen few; `-y` in scripts; patch one server, then the rest.
- **Restarts:** a kernel or libc update needs a reboot (`/var/run/reboot-required`, `needs-restarting -r`); services with changed libraries need a restart (`needs-restarting`, `checkrestart`).
- **Trust:** a third-party repository and key means trusting its owner with root.
- **Immutable servers:** bake a new image with the updates, test it, replace instances from it; identical servers, rollback by redeploying the previous image. Patching in place causes drift.

</Recap>
