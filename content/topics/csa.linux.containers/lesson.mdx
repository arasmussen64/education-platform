<Intro>

<Puzzle question="Run `ps` on a server that is running a container, and the container's program shows up in the list, beside the server's own programs. If a container were a small virtual machine with its own operating system, that couldn't happen. So what is a container?">

An ordinary process, or a group of them, running on the server's own kernel. What makes it feel like a separate machine is three things the kernel adds: namespaces, which give it its own view of process numbers, network and files; a cgroup, which limits what it may use; and a root filesystem of its own. Nothing is virtualised, which is why containers start in milliseconds, and why they share one kernel's weaknesses.

</Puzzle>

Everything in the last five topics was building up to this one. A **container** is a process, or a tree of processes, running on the host's own kernel, with three things added: **namespaces** that give it its own view of the system, a **cgroup** that limits what it may use, and a **root filesystem** assembled from an image. Nothing is virtualised. Run `ps` on the host and you'll see the container's processes sitting there among the rest, with different PIDs than they see themselves.

**Docker, in a few words.** The examples here use Docker, the best-known tool for containers; the kernel features underneath are the same whichever Linux tool is used. An **image** is the packaged files a container starts from: a program and everything it needs to run. A **Dockerfile** is a text file of instructions for building an image, and `docker build` follows it. `docker run nginx` starts a container from the image named `nginx`, `docker stop` ends it, `docker rm` removes it, and `docker images` lists the images on the machine. The program that sets a container up and starts it is called the **runtime**.

**Namespaces.** A namespace wraps a global resource so that a group of processes sees its own copy. The ones a container uses:

- **pid:** its own process numbering. The container's main process is PID 1 *inside*; the host sees it as, say, 2340. A new pid namespace is why a container can't see or signal the host's processes. PID 1 is special in the other direction too: it only receives signals it has installed a handler for, except `KILL` from outside, which is why `docker stop` sends `TERM` and then, after a grace period, `KILL`, and why images often run a small init such as `tini` as PID 1 to forward signals and reap children.
- **net:** its own network interfaces, IP address, routing table and ports. That's how every container can listen on port 8080.
- **mnt:** its own list of mounts, and so its own root filesystem.
- **uts:** its own hostname. **ipc:** its own shared memory and message queues.
- **user:** optionally, a mapping of user IDs, so that root inside the container is an ordinary user outside. Without it, root in a container *is* root on the host, held back only by the **capabilities** (root's powers split into pieces, most of which the runtime drops) and the **seccomp** filter (a list of system calls the container may make) that the runtime applies. That's why images should run as a non-root user (a `USER` line in the Dockerfile names the user the image's program runs as) and why "privileged" containers are a last resort: `docker run --privileged` hands every capability back and opens the host's devices to the container.

`unshare` creates namespaces from the shell and `nsenter` steps into a container's; the labs for this topic build a container out of exactly those pieces: `unshare --pid --fork --uts --mount --ipc chroot rootfs /bin/sh`, then `mount -t proc proc /proc` inside so `ps` works, and `hostname` to name the inside. (`--pid` needs `--fork`: the new process numbers apply to the children of the process that called `unshare`, so without it the shell inside can start one child, which becomes the namespace's PID 1, and once that exits every further start fails with `can't fork`.)

Three more details of that line matter in the labs. `unshare` makes only the namespaces it is asked for, and the process stays in the machine's own for every other kind: leave out `--uts`, and `hostname` inside renames the whole machine. `chroot rootfs /bin/sh` runs `/bin/sh` with the folder `rootfs` as its `/`, so no path it opens can lead outside that folder. That is all `chroot` does: it changes where paths start, and the namespaces do the rest. And `ps` reads its list from `/proc`, which is an empty folder in the new root until the `proc` filesystem is mounted on it. Mounted from inside the new pid namespace, it lists that namespace's processes and no others.

**cgroups.** The previous two topics covered them: a directory under `/sys/fs/cgroup` whose files cap the group. Every container gets one, and `--memory=256m`, `--cpus=1` and `--pids-limit=100` are just `memory.max`, `cpu.max` and `pids.max` being written. The numbers go in as the files hold them. `memory.max` is in bytes, so `256m` becomes `268435456` (256 × 1,048,576). `cpu.max` holds two numbers, the microseconds of CPU time the group may use and the length of the period they are counted over, so `--cpus=1` writes `100000 100000` and `--cpus=0.5` writes `50000 100000`. The pids limit is what stops a fork bomb (a program that keeps starting copies of itself) in one container from taking the host down.

**A cgroup by hand.** The labs make one without Docker, as root. `mkdir /sys/fs/cgroup/box` creates the group, writing to its files limits it (`echo 20 > pids.max`), and a process joins when its PID is written to the group's `cgroup.procs`. Every process started from inside the group is in it too, so a runtime joins first and starts the program second: `echo $$ > /sys/fs/cgroup/box/cgroup.procs && exec unshare ...`, where `$$` is the shell's own PID and `exec` turns that shell into `unshare`. The order matters, because `exec` replaces the shell: nothing written after it on the same line ever runs. `pids.max` counts every process in the group together, the ones already running included. At the limit the kernel refuses the next `fork`. The program that asked is told "Resource temporarily unavailable" (busybox's shell prints `can't fork`), and the `max` line in the group's `pids.events` goes up by one. `pids.current` says how many the group holds now. Once a group is empty, `rmdir` removes it.

**Images and layers.** An **image** is a stack of read-only **layers**, each a set of files that differ from the layer below. `FROM python:3.12-slim` brings in the base image's layers; then each `RUN`, `COPY` and `ADD` in the Dockerfile adds a layer with the files it changed, while `WORKDIR`, `ENV` and `CMD` only record metadata. Layers are cached and shared: ten images built `FROM` the same base share its layers on disk, and a rebuild reuses every layer up to the first instruction whose inputs changed. That's why a Dockerfile copies `requirements.txt` and runs `pip install` *before* copying the application code: the slow install layer survives every code change. A **tag** like `app:1.4.2` is just a name pointing at an image; `latest` is a tag like any other, not a promise of recency. Two tags can point at one image, and `docker images` then lists it twice with the same image ID.

**Reading a Dockerfile.** Each line is one instruction, and a build carries them out in order from the top:

- `FROM image` names the image to start from. With no tag given, `latest` is assumed.
- `WORKDIR /srv/site` sets the folder that the instructions after it, and later the container's program, work in.
- `COPY source destination` copies files into the image from the project folder the build was given. `ADD` does the same, and can also fetch a file from a web address or unpack a tar archive.
- `RUN command` runs a command while the image is being built, and keeps the files it changed.
- `ENV NAME=value` sets an environment variable for the rest of the build and for the running container.
- `USER name` sets the user that the rest of the build, and the container's program, run as.
- `CMD ["program", "argument"]` names the program a container starts with. It runs nothing during the build, and only the last `CMD` in the file counts.

To decide whether a cached layer can be reused, the build compares the text of a `RUN` command, and for `COPY` and `ADD` a checksum taken over the files to be copied. After the first instruction that doesn't match, every later one is built again.

**overlayfs.** When a container starts, the kernel's overlay filesystem mounts the image's layers as **lower** directories, read-only, puts a fresh empty **upper** directory on top, and shows the combination as one **merged** tree, which becomes the container's root. A read looks down through the layers until it finds the file. A write **copies the file up** into the upper directory first and changes it there, so the image is never modified; a delete leaves a "whiteout" marker in the upper layer that hides the file below. `mount | grep overlay` on a Docker host shows the `lowerdir=`, `upperdir=` and `workdir=` of every running container, and you can make one yourself: `mount -t overlay overlay -o lowerdir=app:deps:base,upperdir=rw/upper,workdir=rw/work merged`, with the lower layers listed from the top down and the writable upper directory on a filesystem that isn't itself an overlay.

Where two layers hold a file of the same name, the higher layer's is the one seen; where they hold a folder of the same name, the merged tree shows the contents of both. The `workdir` is a scratch folder for overlayfs's own use, and it has to be on the same filesystem as the upper directory. The labs put both on a **tmpfs**, a filesystem that lives in memory and is thrown away when it is unmounted (`mount -t tmpfs tmpfs /run/box/demo`). That suits a container twice over: the lab machine's own root is already an overlay, and unmounting the tmpfs is all the cleanup a container's writes need.

**Where the writes go.** Everything a container writes lands in its upper layer, and the upper layer is deleted with the container. Restart the same image and you get a clean upper layer. So a database's files, uploads, anything that must outlive the container, goes in a **volume** (a directory the runtime manages) or a **bind mount** (a host directory), and the container stays disposable. A volume is given a name when the container is started, as in `docker run -v shopdata:/var/lib/shop ...`: Docker creates `shopdata` the first time, and every later container started with the same option finds the same files at that path. The read-only layers are shared in another way: every container started from one image mounts the same lower directories, so the image is on the disk once, and each container adds only what it has written.

<Check item="ctr-writable-layer" />

**Not a VM.** A virtual machine boots its own kernel on a **hypervisor**, the software that runs several virtual machines on one physical machine and gives each what looks like hardware of its own. It takes seconds to start and costs hundreds of megabytes before the application runs, but a bug in the guest kernel stays in the guest, and two VMs that don't trust each other are properly separated. A container starts in milliseconds and dozens fit where a few VMs would, because there's one kernel doing the work, but that one kernel is also the weak point: a kernel vulnerability reaches every container on the host, and a container that escapes its namespaces is on the host. Multi-tenant platforms therefore wrap untrusted containers in small VMs (Firecracker) or in a sandbox such as gVisor, which is not a VM: it is a kernel that runs as an ordinary program on the host and answers the container's system calls (its requests to the kernel) itself: it passes none of them on to the host's kernel, and makes only a few calls of its own to it. Either way they get both. The runtime chain is worth knowing by name: the `docker` command talks to the `dockerd` daemon, which hands the work to `containerd`, which calls `runc` to create the namespaces and the cgroup and `exec` the process. `runc` then exits, and a small `containerd-shim` process stays behind as the container's parent: it is the name above a container's processes in the host's `ps`. Kubernetes talks to `containerd` directly.

<Story title="runc's container breakout, 2019" source="https://www.openwall.com/lists/oss-security/2019/02/11/2" sourceTitle="CVE-2019-5736: runc container breakout (all versions)" license="linked, not copied">

In February 2019, runc's maintainers announced a flaw in every version of runc, the last link in the chain above, which Docker, containerd and Kubernetes all relied on. Two researchers, Adam Iwaniuk and Borys Popławski, had found it.

A container whose process ran as root could overwrite the runc program on the host itself. The next time the host used runc, the attacker's code ran there, as the host's root, with every other container on the machine in reach. It took two ways in: starting a container from an image the attacker had built, or an administrator running `docker exec` into a container the attacker had already been able to write to. Root inside the container was the condition, and the user namespace from this topic was a defence: one that didn't map the host's root into the container blocked the attack, as did SELinux (a kernel security policy) on systems whose policy confined containers.

runc and LXC shipped fixes on a date agreed in advance, with the exploit held back for a week. The Kubernetes project's advice to its users was the same as this lesson's: upgrade runc, and run containers as a non-root user.

</Story>

<Recap>

- **A container is a process tree on the host kernel** with namespaces, a cgroup and its own root filesystem. The host's `ps` shows its processes under other PIDs.
- **Namespaces:** pid (own numbering, PID 1 inside), net (own interfaces and ports), mnt (own mounts and root), uts (hostname), ipc, user (root inside mapped to a normal user outside). `unshare --pid --fork --uts --mount --ipc chroot rootfs cmd`, then `mount -t proc proc /proc` inside; `nsenter` to step in.
- **Root in a container** without a user namespace is host root behind capabilities and seccomp: run as non-root, avoid privileged containers.
- **cgroups:** `memory.max`, `cpu.max`, `pids.max` behind `--memory`, `--cpus`, `--pids-limit`; the pids limit stops fork bombs.
- **Images are read-only layers:** `FROM` brings the base's; each `RUN`, `COPY`, `ADD` adds one; `WORKDIR`, `ENV`, `CMD` are metadata. Layers are cached and shared; put slow, stable steps (dependencies) before fast-changing ones (code). Tags are names; `latest` is just a tag.
- **overlayfs:** lower (image layers, read-only) + upper (the container's writes) = merged (its root). Copy-up on first write; whiteouts for deletes. `mount -t overlay overlay -o lowerdir=top:…:bottom,upperdir=…,workdir=… merged`.
- **cgroups by hand:** `mkdir /sys/fs/cgroup/box`, write `pids.max` or `memory.max`, put a PID in `cgroup.procs` before the `exec` that starts the program; `pids.events` counts the refusals; `rmdir` removes an empty group.
- **Writes die with the container.** Persistent data goes in a volume or bind mount.
- **Versus a VM:** own kernel on a hypervisor (slow start, more memory, strong isolation) against a shared kernel (milliseconds, dense, isolation only as good as the kernel). Chain: `docker` → `dockerd` → `containerd` → `runc`.

</Recap>
