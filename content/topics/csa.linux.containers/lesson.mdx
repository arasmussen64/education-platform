<Intro>

Everything in the last five topics was building up to this one. A **container** is a process, or a tree of processes, running on the host's own kernel, with three things added: **namespaces** that give it its own view of the system, a **cgroup** that limits what it may use, and a **root filesystem** assembled from an image. Nothing is virtualised. Run `ps` on the host and you'll see the container's processes sitting there among the rest, with different PIDs than they see themselves.

**Namespaces.** A namespace wraps a global resource so that a group of processes sees its own copy. The ones a container uses:

- **pid:** its own process numbering. The container's main process is PID 1 *inside*; the host sees it as, say, 2340. A new pid namespace is why a container can't see or signal the host's processes. PID 1 is special in the other direction too: it only receives signals it has installed a handler for, except `KILL` from outside, which is why `docker stop` sends `TERM` and then, after a grace period, `KILL`, and why images often run a small init such as `tini` as PID 1 to forward signals and reap children.
- **net:** its own network interfaces, IP address, routing table and ports. That's how every container can listen on port 8080.
- **mnt:** its own list of mounts, and so its own root filesystem.
- **uts:** its own hostname. **ipc:** its own shared memory and message queues.
- **user:** optionally, a mapping of user IDs, so that root inside the container is an ordinary user outside. Without it, root in a container *is* root on the host, held back only by the **capabilities** (root's powers split into pieces, most of which the runtime drops) and the **seccomp** filter (a list of system calls the container may make) that the runtime applies. That's why images should run as a non-root user and why "privileged" containers are a last resort.

`unshare` creates namespaces from the shell and `nsenter` steps into a container's; the labs for this topic build a container out of exactly those pieces: `unshare --pid --fork --uts --mount --ipc chroot rootfs /bin/sh`, then `mount -t proc proc /proc` inside so `ps` works, and `hostname` to name the inside. (`--pid` needs `--fork`: the new process numbers apply to the children of the process that called `unshare`, so without it the shell inside can start one child, which becomes the namespace's PID 1, and once that exits every further start fails with `can't fork`.)

**cgroups.** The previous two topics covered them: a directory under `/sys/fs/cgroup` whose files cap the group. Every container gets one, and `--memory=256m`, `--cpus=1` and `--pids-limit=100` are just `memory.max`, `cpu.max` and `pids.max` being written. The pids limit is what stops a fork bomb in one container from taking the host down.

**Images and layers.** An **image** is a stack of read-only **layers**, each a set of files that differ from the layer below. `FROM python:3.12-slim` brings in the base image's layers; then each `RUN`, `COPY` and `ADD` in the Dockerfile adds a layer with the files it changed, while `WORKDIR`, `ENV` and `CMD` only record metadata. Layers are cached and shared: ten images built `FROM` the same base share its layers on disk, and a rebuild reuses every layer up to the first instruction whose inputs changed. That's why a Dockerfile copies `requirements.txt` and runs `pip install` *before* copying the application code: the slow install layer survives every code change. A **tag** like `app:1.4.2` is just a name pointing at an image; `latest` is a tag like any other, not a promise of recency.

**overlayfs.** When a container starts, the kernel's overlay filesystem mounts the image's layers as **lower** directories, read-only, puts a fresh empty **upper** directory on top, and shows the combination as one **merged** tree, which becomes the container's root. A read looks down through the layers until it finds the file. A write **copies the file up** into the upper directory first and changes it there, so the image is never modified; a delete leaves a "whiteout" marker in the upper layer that hides the file below. `mount | grep overlay` on a Docker host shows the `lowerdir=`, `upperdir=` and `workdir=` of every running container, and you can make one yourself: `mount -t overlay overlay -o lowerdir=app:deps:base,upperdir=rw/upper,workdir=rw/work merged`, with the lower layers listed from the top down and the writable upper directory on a filesystem that isn't itself an overlay.

**Where the writes go.** Everything a container writes lands in its upper layer, and the upper layer is deleted with the container. Restart the same image and you get a clean upper layer. So a database's files, uploads, anything that must outlive the container, goes in a **volume** (a directory the runtime manages) or a **bind mount** (a host directory), and the container stays disposable.

**Not a VM.** A virtual machine boots its own kernel on a **hypervisor**. It takes seconds to start and costs hundreds of megabytes before the application runs, but a bug in the guest kernel stays in the guest, and two VMs that don't trust each other are properly separated. A container starts in milliseconds and dozens fit where a few VMs would, because there's one kernel doing the work, but that one kernel is also the weak point: a kernel vulnerability reaches every container on the host, and a container that escapes its namespaces is on the host. Multi-tenant platforms therefore wrap untrusted containers in small VMs (Firecracker) or in a sandbox such as gVisor, which is not a VM: it is a kernel that runs as an ordinary program on the host and answers the container's system calls (its requests to the kernel) itself, so only a few of them reach the host's kernel. Either way they get both. The runtime chain is worth knowing by name: the `docker` command talks to the `dockerd` daemon, which hands the work to `containerd`, which calls `runc` to create the namespaces and the cgroup and `exec` the process. Kubernetes talks to `containerd` directly.

Then skim `namespaces(7)` for the full list, the overview of `cgroups(7)`, Docker's page on image layers, and the kernel's overlayfs document for lower, upper and merged. The labs have no Docker on the machine, only the parts: you put a process in its own namespaces with a busybox folder as its root, hold it to twenty processes with a cgroup, stack image layers with overlayfs, build a thirty-line container runtime, and fix one that leaks.

<Recap>

- **A container is a process tree on the host kernel** with namespaces, a cgroup and its own root filesystem. The host's `ps` shows its processes under other PIDs.
- **Namespaces:** pid (own numbering, PID 1 inside), net (own interfaces and ports), mnt (own mounts and root), uts (hostname), ipc, user (root inside mapped to a normal user outside). `unshare --pid --fork --uts --mount --ipc chroot rootfs cmd`, then `mount -t proc proc /proc` inside; `nsenter` to step in.
- **Root in a container** without a user namespace is host root behind capabilities and seccomp: run as non-root, avoid privileged containers.
- **cgroups:** `memory.max`, `cpu.max`, `pids.max` behind `--memory`, `--cpus`, `--pids-limit`; the pids limit stops fork bombs.
- **Images are read-only layers:** `FROM` brings the base's; each `RUN`, `COPY`, `ADD` adds one; `WORKDIR`, `ENV`, `CMD` are metadata. Layers are cached and shared; put slow, stable steps (dependencies) before fast-changing ones (code). Tags are names; `latest` is just a tag.
- **overlayfs:** lower (image layers, read-only) + upper (the container's writes) = merged (its root). Copy-up on first write; whiteouts for deletes. `mount -t overlay overlay -o lowerdir=top:…:bottom,upperdir=…,workdir=… merged`.
- **cgroups by hand:** `mkdir /sys/fs/cgroup/box`, write `pids.max` or `memory.max`, put a PID in `cgroup.procs`; `pids.events` counts the refusals.
- **Writes die with the container.** Persistent data goes in a volume or bind mount.
- **Versus a VM:** own kernel on a hypervisor (slow start, more memory, strong isolation) against a shared kernel (milliseconds, dense, isolation only as good as the kernel). Chain: `docker` → `dockerd` → `containerd` → `runc`.

</Recap>
