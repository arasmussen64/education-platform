<Intro>

Nearly everything a server does is a **service**: a program that should be running all the time, start by itself at boot, come back when it crashes, and leave its output somewhere you can find it. On Linux the program that makes that happen is **systemd**, PID 1 from the last topic. You describe the service in a small text file, a **unit file**, and systemd does the rest.

**A unit file** has three sections. Here is one for a small Python web app, which is close to what most services need:

```
[Unit]
Description=Example web app
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=app
WorkingDirectory=/srv/app
Environment=PORT=8080
ExecStart=/usr/bin/python3 /srv/app/app.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

- **`[Unit]`** describes the service and says where it fits. `After=` is about *order*: start this after the network is up. `Wants=` is about *dependency*: if nobody else has started the network target, start it. You usually want both.
- **`[Service]`** says how to run it. `ExecStart=` is the command, with a full path. `User=` runs it as an unprivileged user instead of root. `WorkingDirectory=` and `Environment=` set up the room it runs in. `Restart=on-failure` restarts it when it exits with an error or is killed by a signal, after `RestartSec=` seconds; `Restart=always` restarts it even after a clean exit. `Type=simple` means "the command *is* the service"; `Type=oneshot` is for a script that runs and finishes.
- **`[Install]`** says when the service is wanted. `WantedBy=multi-user.target` means "part of a normally booted server", which is what `systemctl enable` uses.

**Where units live.** Packages install theirs in `/usr/lib/systemd/system/`. Yours go in `/etc/systemd/system/`, which wins when both have the same name. To change a packaged unit without editing it, add a **drop-in**: a file in `/etc/systemd/system/app.service.d/override.conf` holding just the lines that differ; `systemctl edit app` creates one for you. systemd reads unit files once, so after any change: `systemctl daemon-reload`, then restart the service.

**`systemctl`** is how you talk to systemd. `systemctl start app`, `stop`, `restart`. `reload` asks the service to reread its config without stopping, if it supports that. `systemctl status app` shows whether it's loaded and enabled, whether it's active and since when, its main PID, and the last few log lines, all in one screen. `enable` makes it start at boot, `disable` undoes that, and `enable --now` enables and starts in one go. `systemctl list-units --type=service` lists what's running, `systemctl --failed` what has failed, `systemctl list-unit-files` what's enabled, and `systemctl cat app` prints the unit as systemd sees it, drop-ins included.

**The journal.** Whatever a service prints goes to the **journal**, a structured log that systemd's `journald` keeps for every unit, with timestamps, priorities and the unit name attached. `journalctl -u app` shows one service's log; `-n 50` the last fifty lines; `-f` follows it live, like `tail -f`; `-b` shows this boot only, `-b -1` the one before; `--since "1 hour ago"` or `--since today` cut by time; `-p err` keeps only errors and worse. The priorities are the old syslog levels: 0 `emerg` down to 7 `debug`, with 3 `err`, 4 `warning` and 6 `info` the ones you'll see most. `-o json` prints each entry as a JSON object, which is how other tools read it. By default the journal may live only in memory and vanish at reboot. To keep it, create `/var/log/journal` (or set `Storage=persistent` in `/etc/systemd/journald.conf`); then `systemd-tmpfiles --create --prefix /var/log/journal` gives the folder the group and permissions the journal expects, so that administrators can read it, and `journalctl --flush` moves the log there right away instead of at the next boot. `journalctl --disk-usage` and `--vacuum-time=2weeks` keep its size in hand.

**Why not just `nohup python3 app.py &`?** Because nobody restarts it when it crashes, nothing starts it at boot, it runs as whoever typed it, its output lands in a file in that person's home folder, and it starts before or after the network by luck. A unit file is a dozen lines that answer all of those, once.

<Recap>

- **A unit file** (`/etc/systemd/system/app.service`) has `[Unit]` (Description, `After=`, `Wants=`), `[Service]` (`ExecStart=`, `User=`, `WorkingDirectory=`, `Environment=`, `Restart=on-failure`, `RestartSec=`, `Type=`) and `[Install]` (`WantedBy=multi-user.target`).
- **Drop-ins** in `app.service.d/override.conf` change a packaged unit without editing it; `systemctl edit` makes one. After any change: `systemctl daemon-reload`, then `restart`.
- **`systemctl`:** `start`, `stop`, `restart`, `reload`, `status`, `is-active`, `enable`, `disable`, `enable --now`, `is-enabled`, `--failed`, `list-units --type=service`, `list-unit-files`, `cat`.
- **`journalctl`:** `-u app`, `-n 50`, `-f`, `-b`, `--since "1 hour ago"`, `-p err`, `-o json`, `--disk-usage`, `--vacuum-time=2weeks`. Priorities 0 `emerg` to 7 `debug`; 3 is `err`, 4 `warning`, 6 `info`.
- **Persistent logs:** `/var/log/journal` exists, or `Storage=persistent` in `journald.conf`. After creating the folder: `systemd-tmpfiles --create --prefix /var/log/journal` for its permissions, then `journalctl --flush` to move the log there now.
- **A service, not `nohup`:** starts at boot, restarts on failure, runs as its own user, logs to the journal, starts in the right order.

</Recap>
