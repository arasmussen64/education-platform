<Intro>

A program spends much of its life waiting for data. Where that data sits decides how long it waits, and the gaps are not small: from one place to the next the wait can grow a hundred times or more. This topic is about those places, the **memory hierarchy**, and about the two kinds of disk a cloud VM can have, which differ in speed, in price and in what they keep when the VM stops. Most of the slow servers and lost data an architect meets come back to one of three questions: which tier is this program waiting on, which disk is this file on, and which cap is holding this disk back?

**The memory hierarchy.** Closest to the work are the CPU's **caches**: small, very fast memories inside the processor that keep copies of what was used last. **L1** is the smallest and fastest, one for each core; **L2** is bigger and a little slower; **L3** is bigger again and shared by the cores of one processor. Then comes the machine's **memory** (RAM, what `free` measured in Module 1), then a disk inside the machine, then a disk across the network. Rough figures, to reason with and not to quote as anyone's specification:

| Where the data is | One read takes roughly | If a read from L1 took one second |
|---|---|---|
| The CPU's L1 cache | 1 ns | 1 second |
| Memory | 100 ns | under 2 minutes |
| A local NVMe disk, one random read | tens of µs | several hours |
| A network SSD disk, one operation | about a millisecond, or a few; under one on the fastest tiers | one or two weeks |

The units: a **ns** (nanosecond) is a billionth of a second; a **µs** (microsecond) is 1,000 ns; a **ms** (millisecond) is 1,000 µs, a thousandth of a second. The first three rows come from Colin Scott's interactive page (listed after the lesson), which works them out from trend formulas rather than measuring a machine, and whose slider stops at 2020: good for orders of magnitude, nothing finer. The network row is the providers' own words, read on 2026-11-11: AWS's gp3 disks promise "single-digit millisecond latency", its faster io2 Block Express disks under 500 µs on average for operations of 16 KiB (a KiB is 1,024 bytes; the units come up again below), and Azure's Premium SSD v2 and Ultra Disk "submillisecond" latency. What to remember is the gaps: one read from a network disk costs as much time as ten thousand reads from memory. A program that reads one thing at a time and waits for each feels the disk more than anything else, which is why databases keep what they use most in memory.

**NVMe.** **NVMe** (Non-Volatile Memory Express) is a way for a computer to talk to flash storage: over the fast connections the processor uses for its own devices, with many queues of requests at once, so a fast disk can work on many requests together. Linux names NVMe disks `/dev/nvme0n1`, `/dev/nvme1n1` and so on, the names you met in the storage topic. NVMe says *how* the VM talks to a disk, not *where* the disk is: a disk at the other end of a network can show up as an NVMe device too, as the next paragraph shows.

**Two kinds of cloud disk.** A **local disk**, also called an **ephemeral** disk (ephemeral means short-lived), is a disk physically inside the host the VM runs on: AWS calls it the **instance store**, Azure the **temporary disk**, Google **Local SSD**. It is fast, because nothing stands between the VM and the disk but the host, and it is included in the price (AWS: "no additional charge"). Not every **size** has one (a VM's size is the shape you rent, so many CPUs and so much memory; AWS calls its VMs **instances** and a size an **instance type**): AWS says not every instance type provides instance store volumes, and Azure keeps a list of VM sizes with no local temporary disk. A **network-attached disk** lives in the provider's storage service, on other machines, and reaches the VM over the network: AWS calls it an **EBS volume** (Elastic Block Store), Azure a **managed disk**, Google a **Persistent Disk**, or the newer **Hyperdisk**. It keeps its data whatever happens to the VM (Azure keeps three copies of every managed disk), and it can be detached and attached to another VM. It is slower than a local disk, and it is capped. On AWS's Nitro-based instances, EBS volumes show up as NVMe devices, beside any instance store ones, and only the model name in `sudo nvme list` (`Amazon Elastic Block Store` or `Amazon EC2 NVMe Instance Storage`) tells them apart.

**What survives.** The rule is simple once you picture where each disk is: a local disk stays with its host, and anything that moves the VM to another host, or hands the host back, leaves it behind. AWS's table of events, Azure's temporary disk section and Google's Local SSD page (all read 2026-11-11):

| Event | Local disk | Network disk |
|---|---|---|
| Reboot: the operating system restarts on the same host | kept, on all three | kept |
| Stop, then start | lost, on all three: AWS erases every block; Azure says the data might be lost; Google discards it unless you opt in to keeping it, a preview feature (offered to try, not yet finished) | kept |
| The host fails and the VM is started on another | count it lost: AWS says it doesn't persist, Google that it might be lost, Azure that a redeploy or a maintenance event can lose it | kept |
| Change of size (a stop and a start in between) | lost: on AWS the data doesn't move to the new size, even when the new size has a local disk | kept |

Google can also keep Local SSD data through a **live migration**, when it moves a running VM to another host for maintenance without stopping it. So a local disk is for what can be lost: caches, scratch space, temporary files, swap, and data that is copied from elsewhere and can be copied again (AWS names data you replicate across a fleet of instances). The only copy of anything goes on a network disk.

**Allowances.** A network disk is **provisioned** (set up, and paid for) for so many **IOPS** (operations a second) and so much **throughput** (bytes a second), the terms you met in the storage topic; buying more of either is buying **provisioned IOPS** or throughput. AWS's general-purpose EBS volume, gp3, includes 3,000 IOPS and 125 MiB/s (mebibytes a second; the units are explained below) whatever its size, and sells more up to 80,000 IOPS and 2,000 MiB/s. Azure's Premium SSD v2 includes 3,000 IOPS and 125 MB/s free, and its Ultra Disk goes up to 400,000 IOPS. Google's Balanced Persistent Disk starts at 3,000 IOPS and 140 MiB/s for each VM and grows with the disk's size and the VM's. Three rules turn those figures into what a program gets:

1. **Throughput is IOPS × block size, until the throughput cap takes over.** On gp3, a database writing 16 KiB at a time gets 3,000 × 16 KiB = 48,000 KiB, about 46.9 MiB a second, well under 125: the IOPS cap binds. A backup writing 256 KiB at a time would need 750 MiB a second for 3,000 writes, so the throughput cap binds instead, and it gets 125 MiB ÷ 256 KiB = 500 writes a second. (AWS counts an SSD operation of up to 256 KiB as one, and splits bigger ones.)
2. **You get the smaller of the disk's allowance and the VM's.** The VM has an allowance of its own for all its disks together, set by its size. Azure's page, the main resource, shows it both ways on a `Standard_D8s_v3`, which is allowed 12,800 IOPS: three disks allowed 500 each give 1,500, whatever the application asks; three allowed 5,000 each give 12,800, not 15,000. A faster disk can't help a VM that is at its own cap, and a bigger VM can't help a disk that is at its cap.
3. **A deeper queue doesn't beat a cap.** **Queue depth** is how many requests are in flight at once. Below a cap, more in flight gets more done. At a cap, the disk hands out its slots at a fixed rate and every extra request waits in line for one: the average wait is about the queue depth divided by the rate, so 16 in flight at 500 a second wait 32 ms each. The rate stays where it was.

**Units.** Storage is sold in two kinds of unit, and the providers mix them. A **GB** is 1,000,000,000 bytes and a **GiB** is 1,073,741,824 (1,024 × 1,024 × 1,024), about 7% more; a **MB** is 1,000,000 bytes and a **MiB** is 1,048,576, about 5% more; **KiB** is 1,024 bytes, **kB** 1,000. AWS and Google quote throughput in MiB/s, Azure in MB/s (its page says so: 10^6 bytes a second), so gp3's 125 MiB/s is about 5% more than Premium SSD v2's 125 MB/s. Compare like with like.

**Caps on the lab machine.** The labs' disks are files on your own computer, far faster than a cloud's network disk, so to see what an allowance does you hold a service to one, the way a cloud holds a VM. A cgroup (the folder of limits the CPU and memory topics used) whose disk settings systemd looks after has an **`io.max`** file with a line for each capped disk: `7:2 rbps=max wbps=8388608 riops=max wiops=500` means at most 500 writes a second (`wiops`) and 8,388,608 bytes a second (`wbps`) to the disk whose device number is `7:2` (`lsblk` shows it under `MAJ:MIN`), and no cap on reads (`max`). Its partner **`io.stat`** counts what the cgroup has done since it started: `wios=` writes and `wbytes=` bytes written, so two readings a few seconds apart give a rate; `io.pressure` says how much of the time the service waited on its disk. In systemd, **`IOWriteIOPSMax=/dev/lab/data 500`** and **`IOWriteBandwidthMax=/dev/lab/data 8388608`** in a unit or drop-in write `io.max` (the `IORead...` pair caps reads, which is a different thing); `systemd-run -p` runs one command under them, as `CPUQuota=` did for the CPU; `systemctl show NAME -p IOWriteIOPSMax` reads them back. Give the bandwidth in bytes: to systemd, `8M` means 8,000,000, a megabyte to the base 1,000, not 8 MiB. And a service's settings live in a file under `/etc`, which lasts. `systemctl set-property NAME SETTING=value` changes a running service's setting on the spot and saves it under `/etc` too; with `--runtime` it saves it under `/run`, which a reboot forgets.

One more systemd word. A **slice** is a group of services that share limits: systemd puts most services in `system.slice`, but a unit can say `Slice=batch.slice`, and a setting made on a slice holds all its services together, the way one disk's allowance is shared by every program on a VM that writes to it. `systemctl status NAME` shows which slice a service is in (its `CGroup:` line), and `systemctl show NAME -p ControlGroup --value` gives its folder under `/sys/fs/cgroup`, so a script doesn't have to guess.

**Read now:** Azure's "Virtual machine and disk performance", the main resource below, down to the end of "Virtual machine I/O capping": its two capping examples are rule 2 above, once from each side, in Azure's words (the sections on host caching after them are optional). Then AWS's table of instance store events, the "Temporary disk" section of Azure's disk storage overview, the "Local SSD data persistence" section of Google's Local SSD page, the gp3 section of AWS's General Purpose SSD page, the comparison table and the Premium SSD v2 sections of Azure's disk types page, and Colin Scott's latency page (move the slider and watch which numbers change). AWS's page on EBS I/O characteristics is there for more on queue length and block sizes. Bring a calculator: the estimate questions are about setting up the sum, and the lesson's rough figures are all you need for them. The labs put you on a machine with real disks attached (the lab labels them under `/dev/lab/`). Only the disks labelled there belong to the lab: `lsblk` also lists Docker's own disks, which must be left alone, so point `fio` (a tool that writes to a disk as fast as it is allowed and reports what it got) only at a file on a lab disk, never at a disk's own name. In the labs you measure a capped disk with `fio`, hold a database to a disk tier, write `io-rate` to read a service's write rate and the cap that holds it, rehearse a database's move to a new tier, and find out why a shop's checkout is slow every night and its weekend orders went missing.

<Recap>

- **The tiers**, roughly: L1 cache 1 ns, memory 100 ns, a local NVMe disk tens of µs, a network disk about 1 ms (under on the fastest tiers). A network read costs as much as ten thousand memory reads. 1 ms = 1,000 µs = 1,000,000 ns.
- **NVMe** is how a disk is reached, not where it is: on AWS, EBS volumes are NVMe devices too; `nvme list`'s model names them.
- **Local disk** (instance store, temporary disk, Local SSD): in the host, fast, included in the price, kept through a reboot, lost on a stop, a change of size, or a move to another host. For caches, scratch, temporary files and data that can be copied again.
- **Network disk** (EBS, managed disk, Persistent Disk and Hyperdisk): kept through everything, detachable, slower, and capped. The only copy of anything goes here.
- **Throughput = IOPS × block size**, until the throughput cap binds: small blocks hit the IOPS cap, big blocks the throughput cap. gp3: 3,000 IOPS and 125 MiB/s included.
- **The smaller of the disk's allowance and the VM's** is what you get. A deeper queue at a cap only adds waiting: wait ≈ queue depth ÷ rate.
- **Units:** GB vs GiB (about 7% apart), MB vs MiB (about 5%); AWS and Google quote MiB/s, Azure MB/s; systemd's `M` is a million bytes.
- **On Linux:** `io.max` (`wiops=`, `wbps=`) and `io.stat` (`wios=`, `wbytes=`) in a cgroup's folder; `IOWriteIOPSMax=` and `IOWriteBandwidthMax=` (in bytes) in a unit, drop-in or `systemd-run -p`; a **slice** holds a group of services to one setting; `systemctl show -p ControlGroup` finds a unit's folder; settings in `/etc` last, `--runtime` ones don't.

</Recap>
