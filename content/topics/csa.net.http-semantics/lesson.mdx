<Intro>

HTTP and TLS showed how a request travels: the connection, the versions, the handshake. This topic is about what a request and its answer *mean*: what a method promises, what a status code tells an operator, how long a copy of an answer may be kept and by whom, which other websites may read it, and which style of API fits a flow. Every cloud's CDN and load balancer obeys these meanings, and most of their surprises come from one of them being misread.

**Methods are promises.** A **safe** method is "essentially read-only" (RFC 9110, HTTP's standard): `GET`, `HEAD` and `OPTIONS` change nothing on the server. An **idempotent** method is one where sending the request twice has the same effect as sending it once: the safe methods, and `PUT` (set this resource to exactly this) and `DELETE` (remove it). Think of a lift's call button against a vending machine: pressing the lift button twice changes nothing more, pressing the vending machine's twice buys two. `POST` is the vending machine: two `POST /orders` may make two orders. That's why RFC 9110 says an idempotent request "can be repeated automatically if a communication failure occurs", and why client libraries, proxies and load balancers retry `GET` and `PUT` on a dropped connection and never `POST`. Payment APIs make a `POST` safe to retry with an **idempotency key**: a random value the client sends with one payment, every time it tries it, so the provider recognises a repeat and answers it without charging again.

**Status codes come in classes**, by their first digit:

| Class | Means | The ones to know |
| --- | --- | --- |
| 2xx | it worked | 200 OK; 204 No Content, success with no body |
| 3xx | look elsewhere, or use your copy | 301 a permanent redirect; 304 Not Modified, your copy is still good |
| 4xx | the client's mistake: the same request won't work again | 404 not found; 405 Method Not Allowed; 412 Precondition Failed, below; 429 Too Many Requests, slow down |
| 5xx | the server's failure | 502 and 504, below; 503 not available for now |

Two of them are an operator's daily bread. A **proxy** is a server that passes requests on to another one, the **upstream** (RFC 9110 also calls it the inbound server): nginx in front of an app is one, and so is a load balancer. **502 Bad Gateway**: the proxy "received an invalid response" from the upstream, which usually means the app crashed or closed the connection. **504 Gateway Timeout**: the proxy "did not receive a timely response", so the app is slow or the proxy's timer is short. A 504 after exactly 60 seconds, every time, is nginx's `proxy_read_timeout` (60 s by default) running out.

**Caching, the picture.** A **cache** keeps a copy of an answer so the next request can be answered without asking the server again. The browser has a **private cache**, for one person. Between the browser and the shop's server, the **origin**, there can be **shared caches**, whose copies serve many people: a company's proxy, a reverse proxy such as nginx, and a **CDN** (content delivery network: a provider's servers in many cities, each keeping copies near the customers; Module 11 builds one). It is DNS's TTL one layer up. `Cache-Control: max-age=600` says a copy stays **fresh**, usable without asking, for 600 seconds from when the origin made it; a shared cache that answers from its copy adds `Age`, how long it has kept it, so the copy has `max-age - Age` seconds left. After that it is **stale**, and stale isn't broken: the cache asks again with the copy's **validator**, an `ETag` (a tag for this version of the content) in `If-None-Match`, or its `Last-Modified` date in `If-Modified-Since`. That's a **conditional request**, and if nothing changed the answer is `304 Not Modified`: a few headers and no body. (`If-Match` turns the test round for changes: "change it only if it is still this version", answered `412` when someone else changed it first.)

**Four patterns cover most sites:**

- **Fingerprinted assets**, files whose name comes from their content (`app.3f9a.js`), so the next build is a new name: `public, max-age=31536000, immutable`. Any cache may keep them a year, and `immutable` (RFC 8246) tells a browser not even to ask on a reload. The URL's content never changes, so a long life can't serve a wrong copy.
- **Pages** that keep their name and change (`news.html`): `no-cache`. It doesn't mean "don't store". RFC 9111, HTTP's caching standard, says such an answer must not be used "without forwarding it for validation": keep it, ask every time, and with an `ETag` the asking costs a 304. "Don't store at all" is `no-store`.
- **Personal pages** (an account, a basket): `private`, because "a shared cache MUST NOT store the response"; or `no-store`, which keeps it out of the browser too.
- **APIs**: usually `no-store`. And where a shared cache should keep something longer or shorter than browsers, `s-maxage` overrides `max-age` for shared caches only.

With no caching headers at all, a cache may guess: RFC 9111 suggests a fraction of the time since `Last-Modified`, "a typical setting of this fraction might be 10%". That's why "we never set caching headers" still caches. And a cache keys its copies on the URL; an answer that depends on a request header must say so with **`Vary`** (`Vary: Accept-Language`), which adds that header to the key.

**The day a cache shared a page.** In the walkthrough, `/account` sent with `public, max-age=60` was kept by the edge for alice and handed to bob: the copy was keyed on the URL, not on who asked. On Christmas Day 2015 Steam did the same at scale: during an attack, a second caching configuration "incorrectly cached web traffic for authenticated users", and for 90 minutes store pages made for about 34,000 users, some with billing addresses, could be seen by others (Valve's statement). Mending the header isn't the end, either: copies already kept stay good for their lifetime. A CDN can be **purged** (its "invalidation", CloudFront and Cloud CDN call it), which the labs' edge does with `sudo edge-purge`; a copy in a customer's browser can't be reached by anything, which is why long lifetimes are only for URLs that never change.

**Not every cache reads the headers alike** (each provider's page, read 2026-11-12):

| | AWS CloudFront | Azure Front Door | Google Cloud CDN |
| --- | --- | --- | --- |
| No caching headers | its default TTL (24 hours unless set) | one to three days, chosen at random | 1 hour in the default mode, for static files |
| `no-cache` | respected, when the minimum TTL is 0 | not stored at all | stored, and checked with the origin before every use |
| `private`, `no-store` | respected only when the minimum TTL is 0: above 0, it caches them anyway | never stored | not stored (unless a mode forces it) |
| Taking a copy back early | invalidation | purge | invalidation |

CloudFront's minimum TTL is a trap worth remembering: a CDN's own settings can override the origin's `private`. And the labs' edge, nginx, stores nothing marked `no-cache`, `private` or `no-store` (tried in this topic's lab), never guesses a lifetime, and doesn't send `Age`.

**nginx, for the labs.** `add_header Cache-Control "...";` in a `location` block adds a header to that location's answers; with `always` it is added to error answers too (without it, only to successes and redirects). A cache obeys the headers of the server *behind* it, so the labs have an origin that sets headers and a separate edge that caches, as a real CDN works. nginx makes an `ETag` and a `Last-Modified` for every file it serves by itself, and `sudo systemctl reload nginx@origin` makes it read its file again: new workers start with the new settings and the old ones finish, which takes a moment.

**Same origin, and CORS.** A page's **origin** is its scheme, host and port together: `https://www.shop.test` and `https://api.shop.test` are different origins, and so are `http://shop.test` and `https://shop.test`. A **cookie** is a small named value a site asks the browser to keep (with `Set-Cookie`) and that the browser sends back on every request to that site (in `Cookie`): it is how a site remembers that you're signed in. Cookies and HTTP sign-ins are a request's **credentials**. The trouble: a page from `evil.test` open in the same browser can send requests to `api.shop.test`, and the browser attaches the shop's cookies. The **same-origin policy** is the browser's rule that the evil page may send but may not *read* the answers. **CORS** (cross-origin resource sharing) is how an API tells the browser which other origins *may* read its answers. It protects the people using browsers from other websites; it doesn't protect the API, because `curl`, a script or a server ignores it. The API still checks who is calling, every time.

The browser sends a **simple request** straight out: `GET`, `HEAD` or `POST`, with no headers beyond a short safelist, and a `Content-Type`, if any, of `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`: what an HTML form could always send. Anything else, a JSON `PUT` for instance, gets a **preflight** first: an `OPTIONS` request with `Origin`, `Access-Control-Request-Method` and `Access-Control-Request-Headers`. The answer must name the origin in `Access-Control-Allow-Origin`, list the method in `Access-Control-Allow-Methods` and the headers in `Access-Control-Allow-Headers`; then the browser sends the request, and checks its answer's `Access-Control-Allow-Origin` too. With credentials (`credentials: "include"` in the page's code), the rules tighten: the origin must be named exactly, `*` is refused in the origin, methods and headers, and `Access-Control-Allow-Credentials: true` must be sent. `Access-Control-Max-Age` lets the browser remember a preflight's answer: 5 seconds without it, at most 7,200 in Chromium (since version 76) and 86,400 in Firefox (MDN, read 2026-11-12). An answer that names an origin chosen from a list also sends `Vary: Origin`, so a cache never hands one site's answer to another.

In nginx, a `map` outside the `server` block turns the request's `Origin` into `$cors_origin`, the origin itself for the allowed ones and empty otherwise (nginx leaves out a header whose value is empty), and the API's `location` answers the preflight itself:

```nginx
map $http_origin $cors_origin {
    default                 "";
    "https://www.shop.test" $http_origin;
}

location /api/ {
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Allow-Methods "GET, PUT, DELETE" always;
        add_header Access-Control-Allow-Headers "Content-Type" always;
        add_header Access-Control-Max-Age 600 always;
        add_header Vary Origin always;
        return 204;
    }
    proxy_pass http://127.0.0.1:8080;
    add_header Access-Control-Allow-Origin $cors_origin always;
    add_header Access-Control-Allow-Credentials "true" always;
    add_header Vary Origin always;
}
```

`$http_origin` is nginx's name for the request's `Origin` header (`$http_` and the header's name in lower case, dashes as underscores). Headers inside the `if` replace the location's own for the preflight's answer.

**Allow-list mistakes**, each of which the labs' checks try with origins made up as they run: echoing back whatever `Origin` arrives (every site allowed, cookies included); a pattern that matches a suffix, `shop\.test$`, which `https://evilshop.test` also ends with; allowing `null`, the origin that sandboxed frames and local files send, so any site can get it; and forgetting `Vary: Origin`. The labs have no browser: their checks send the browser's two requests with `curl` and apply the browser's rules, from the Fetch standard that browsers implement, to the real answers. That's what you do too, in the write lab.

**WebSockets.** A **WebSocket** is a two-way message channel that starts as an HTTP request: `Connection: Upgrade` and `Upgrade: websocket`, with a random key. The server answers `101 Switching Protocols` with `Sec-WebSocket-Accept` (the key with a fixed string from RFC 6455 joined on, hashed with SHA-1, in base64), and from then on the same TCP connection carries messages both ways until either side closes it. Two things break it at proxies:

- `Upgrade` and `Connection` are **hop-by-hop** headers: they describe one connection, so a proxy doesn't pass them on unless told. In nginx: `proxy_http_version 1.1;` (nginx speaks HTTP/1.0 to the upstream by default; its page says the line is needed "before version 1.29.7", so in Ubuntu 24.04's 1.24), `proxy_set_header Upgrade $http_upgrade;` and `proxy_set_header Connection "upgrade";`. Without them, captured in this topic's lab, the board answered `400 Bad Request`.
- Every stateful hop has an **idle timeout**, the rule from TCP and UDP: nginx closes a WebSocket that has carried nothing for `proxy_read_timeout` (60 s by default), and so does each load balancer on the path. A WebSocket **ping** (answered by a pong) counts as traffic, so the fix is a ping more often than the smallest idle timer on the path, and where a hop allows it, a longer timer.

| | AWS Application Load Balancer | Azure Application Gateway | Google Cloud's Application Load Balancers |
| --- | --- | --- | --- |
| WebSockets | "native support", on HTTP and HTTPS listeners | always on, no setting to switch | proxied with no configuration needed |
| The idle limit | its idle timeout, 60 s by default | the backend setting's request timeout covers the whole session: keep it above the ping interval | depends on the load balancer type |

**Server-sent events** (SSE) are the one-way cousin: an HTTP answer that never ends, to which the server adds a line per event, read in the browser with `EventSource`. Same proxy rules, no upgrade.

**gRPC** is a way of calling a function on another computer (an **RPC**, remote procedure call) over HTTP/2. A service and its messages are described in a **protocol buffers** file, from which both sides' code is generated, so a message that doesn't fit fails at build time. There are four kinds of call: **unary** (one request, one answer), **server streaming**, **client streaming** and **bidirectional streaming**; every call can carry a **deadline** and end with `DEADLINE_EXCEEDED`. On the wire it needs HTTP/2 all the way, `content-type: application/grpc`, and the call's status in **trailers**, headers sent after the body ("even if the status code is OK", gRPC's protocol document); clients send `te: trailers` "to detect incompatible proxies". nginx proxies it with `grpc_pass`, which needs its HTTP/2 module. A browser's page can't send gRPC's frames or read trailers, so browsers use **gRPC-Web** through a proxy such as Envoy, which translates.

**REST**, the style of most public APIs, treats each thing as a **resource** with a URL (`/basket/items/42`) and uses the methods for what they mean: `GET` to read, `PUT` to set, `DELETE` to remove, `POST` to create or act. Its strengths are the ones this topic is about: caches, CDNs, status codes and CORS all understand it.

**Choosing.** Pick the simplest style that carries the flow's direction and timing, then check that every proxy on the path can carry it:

| Flow | Choice |
| --- | --- |
| A product catalogue browsers read | REST, with caching |
| A live order board pushed to staff screens | server-sent events, or WebSockets |
| A chat, both ways | WebSockets |
| Internal service-to-service calls with a strict contract and streaming | gRPC |
| A public partner API | REST (every tool, cache and browser knows it) |

<Recap>

- **Methods:** safe (`GET`, `HEAD`, `OPTIONS`) change nothing; idempotent (the safe ones, `PUT`, `DELETE`) can be repeated, so they are retried automatically; `POST` isn't, so a retry can buy twice, unless the API takes an idempotency key.
- **Status:** 2xx worked, 3xx elsewhere or use your copy (304), 4xx the client's mistake (405, 412, 429), 5xx the server's. At a proxy, **502** a bad answer or none (the app crashed), **504** no answer in time (slow app, or a short timeout: nginx's `proxy_read_timeout` is 60 s).
- **Freshness:** `max-age` is a TTL from when the origin made the answer; `Age` is time already used; fresh for `max-age - Age`; then revalidate with `ETag`/`If-None-Match` or `Last-Modified`/`If-Modified-Since`, and `304` costs a few headers. No headers: a cache may guess, typically 10% of the time since `Last-Modified`.
- **Patterns:** fingerprinted assets `public, max-age=31536000, immutable`; pages `no-cache` (store, but ask every time); personal pages `private` (or `no-store`); APIs `no-store`; `s-maxage` for shared caches only; `Vary` for answers that depend on a request header.
- **What a shared cache stored stays stored:** fix the header, then purge the CDN; a browser's copy can't be purged. CDNs differ: CloudFront's minimum TTL can override `private`, Front Door stores no `no-cache` and guesses one to three days, Cloud CDN stores `no-cache` and checks every time.
- **CORS:** an origin is scheme, host and port. The browser lets a page from another origin read an API's answers only if the API says so. Simple requests go straight out; anything else is preflighted with `OPTIONS`. With credentials (cookies): the exact origin, `Access-Control-Allow-Credentials: true`, no `*` anywhere; `Vary: Origin`; `Access-Control-Max-Age` (5 s default; Chromium 7,200, Firefox 86,400 at most). Never reflect, suffix-match or allow `null`. CORS isn't authentication: only browsers apply it.
- **WebSockets:** an HTTP upgrade (`101`, `Sec-WebSocket-Accept`), then messages both ways. Proxies must pass the hop-by-hop `Upgrade` and `Connection` (nginx: `proxy_http_version 1.1` and two `proxy_set_header` lines) and keep a quiet connection open: ping more often than the smallest idle timer on the path.
- **gRPC:** protocol buffers, four kinds of call, deadlines; HTTP/2 end to end with trailers; gRPC-Web and a proxy for browsers. **SSE:** one-way push over a never-ending HTTP answer. **REST:** resources and methods, which every cache and browser understands.
- The WebSocket standard, RFC 6455, explains the opening handshake in its sections 1.2 and 1.3, listed under More resources for the curious.

</Recap>
