<Intro>

"It doesn't work from here" is the most common sentence in operations, and the shell can answer it in minutes if you know which tool answers which question. This topic is the toolkit, read from the host's point of view; the networking module later in the track explains the protocols underneath in depth. Here you need five ideas: an **interface** has an **address**; a **route** says which interface and gateway a packet to a given destination uses; a program **listens** on an address and **port**; a connection is a pair of address-and-port endpoints with a state; and a **firewall** decides, packet by packet, what gets through.

**Interfaces and routes: `ip`.** `ip -brief addr` lists each interface with its state and addresses: `lo` is the loopback (always `127.0.0.1`), `eth0` or `ens5` the real one, `docker0` a bridge for containers. `ip route` lists the routes; the line starting `default via 10.0.1.1 dev eth0` is the **default gateway**, where everything not matched by a more specific route goes. `10.0.1.0/24 dev eth0` means addresses in that block are on the local network, no gateway needed. `ip neigh` shows the neighbours the host has recently talked to (the ARP table: which hardware address answers for each IP address on the local network).

**Sockets: `ss`.** `ss -ltnp` lists **l**istening **T**CP sockets, **n**umerically, with the **p**rocess: the one command that answers "what is this server offering?". (The process column is filled in only for processes you're allowed to see, so for a server's services it needs `sudo`.) The local address matters as much as the port: `0.0.0.0:80` listens on every interface, `127.0.0.1:5432` only on loopback, so the database is reachable from this machine and nowhere else, which is what you want for a database and the opposite of what you want for a web app. The address a program listens on is one of its own settings: a line in its config file, a flag on its command line, or a variable its systemd unit sets, which `systemctl cat SERVICE` shows. `ss -tan` shows every TCP connection with its **state**: `LISTEN` waiting, `ESTAB` open, `TIME-WAIT` a normal minute of aftermath (60 seconds on Linux) on the side that closed first, `CLOSE-WAIT` the other side closed and *our program hasn't*: a pile of those is a socket leak in the application. The client side of a connection gets an **ephemeral port** picked by the kernel from `/proc/sys/net/ipv4/ip_local_port_range` (32768 to 60999 by default), which is why a busy client can run out of ports to one destination.

**Testing, one layer at a time.** `dig api.example.com` resolves the name: in its `ANSWER SECTION` a `CNAME` line points at another name, `A` lines are the addresses, and the number before `IN` is the TTL in seconds (`dig +short` prints only the names and addresses, with no types or TTLs). `dig` always asks a name server. `curl`, like most programs, looks in the file `/etc/hosts` first, so a line there can make `curl` work on one machine while every other machine is still given the wrong address. The labs' name server is **dnsmasq**: one name is one line, `host-record=NAME,ADDRESS`, in a file under `/etc/dnsmasq.d/`, and dnsmasq reads those files only when it starts (a `reload` doesn't reread them), so after a change, `sudo systemctl restart dnsmasq`. `nc -zv host 5432` asks only "does this TCP port answer?", with no protocol on top: the cleanest test of reachability. `curl -v https://host/` shows the whole HTTP exchange, `curl -I` just the response headers (status line, `Location` on a redirect). `traceroute host` (or `mtr`, which keeps measuring) shows the routers on the path; a hop of `* * *` is a router that doesn't answer probes, not necessarily a fault, as long as later hops answer. The order matters: name, port, protocol.

**The truth on the wire: `tcpdump`.** When tests disagree, `tcpdump -nn -i eth0 port 8080` shows the packets themselves (`-nn`: don't turn addresses and ports into names, which is slow and confusing; `-i`: the interface; then a filter, because an unfiltered capture on a busy server is a firehose). A TCP connection opens with the **three-way handshake**: a packet with flags `[S]` (SYN) from the client, `[S.]` (SYN-ACK) from the server, `[.]` (ACK) back, then data with `[P.]`. A `[R.]` (RST, with the ACK dot) in reply to the SYN means **refused**: nothing is listening there. A SYN with no reply, sent again a second later and again after that, means **dropped**: a firewall, a security group or a routing hole swallowed it. `-w capture.pcap` saves the packets for Wireshark.

**The firewall's path.** Modern kernels filter with **nftables** (`iptables` is the older interface to the same place). `nft list ruleset` prints the tables and chains. A chain attaches to a **hook**: `prerouting` as a packet arrives, then the routing decision sends it to `input` (for this host) or `forward` (for another), locally generated packets go through `output`, and everything leaving goes through `postrouting`. Each base chain has a **policy**, what happens when no rule matches, and a serious server's `input` chain is `policy drop` with a short list of accepts. The first of those is nearly always `ct state established,related accept`: **connection tracking** remembers every connection the host has accepted or started and lets their later packets and the replies through, so you only need a rule for the *first* packet of a new connection, `tcp dport 22 accept`. `conntrack -L` shows the table. Rules added with `nft add rule` live until the next reboot; the ones that come back are in `/etc/nftables.conf`, which `nftables.service` loads at boot (`nft -f /etc/nftables.conf` loads it now, `systemctl enable nftables` makes it stick), so a fix belongs in the file, not just in the running rules. And `drop` and `reject` differ: a rejected connection is answered at once (plain `reject` sends an ICMP port-unreachable, `reject with tcp reset` the same reset a closed port sends), so the client sees 'connection refused'; a dropped one gets nothing, which is what security groups do and what makes a blocked port look like a dead host.

**A whole `/etc/nftables.conf`** is short. This one is for a web server that offers SSH and HTTPS and nothing else:

```
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;
        iif lo accept
        ct state established,related accept
        tcp dport { 22, 443 } accept
    }
    chain forward {
        type filter hook forward priority filter; policy drop;
    }
    chain output {
        type filter hook output priority filter; policy accept;
    }
}
```

The first line is a shebang, as in a script; to `nft`, a line starting `#` is a comment. `flush ruleset` empties whatever is loaded, so loading the file replaces the rules instead of adding a second copy of each. A **table** holds chains, and `inet` makes it cover IPv4 and IPv6 at once. A chain's first line attaches it to its hook and sets its policy; the rules under it are tried in order, and a packet that matches none of them gets the policy. Braces make a **set**: `tcp dport { 22, 443 }` is one rule for both ports. `sudo nft -c -f /etc/nftables.conf` checks the file without loading it. Keep it on separate lines, as here: squeezed onto one line, `nft` also wants a `;` after each chain's closing `}`.

**Containers.** A container's processes run in their own **network namespace** with their own interfaces and ports. The runtime connects it to the host with a **veth pair**, a virtual cable with one end inside the namespace and one end plugged into a bridge like `docker0`; outgoing traffic has its source address rewritten to the host's (**NAT**, network address translation) in `postrouting`, and "publishing" a port is a `prerouting` rule that rewrites the *destination* instead (DNAT), sending packets for the host's port 8080 on to the container's address. `ip netns`, `nsenter --net` and `tcpdump -i docker0` let you look inside, and `ip netns exec NAME COMMAND` runs a command in a namespace as if from another machine. The labs use exactly that: the "office" on the far side of the lab server's `eth1` is a network namespace joined to it by a veth pair, and `from-office COMMAND` is `ip netns exec` under another name.

**Read now:** the networking terminology tutorial, the main resource below, for the vocabulary; then the ArchWiki's network-configuration page for `ip`, the `ss` and `tcpdump` manuals for the flags, the nftables page for a readable example of a stateful firewall, and the state diagram in the TCP RFC when you want the states exactly. The quick questions read `ip`, `ss`, `dig`, `curl`, `tcpdump` and `nft` output with the text tools from Shell essentials. The labs hand you a server with an office on the far side of `eth1`, a name server of its own, and a leaking cache: you find what it offers and watch a handshake and a refusal on the wire, finish a report, write a socket-state report, build the host firewall and prove it from the office, and then work a "doesn't work from the office" ticket one layer at a time.

<Recap>

- **`ip -brief addr`** (interfaces, states, addresses), **`ip route`** (`default via GATEWAY dev IFACE`; `NET/24 dev IFACE` is local), `ip neigh`.
- **`ss -ltnp`**: listening TCP sockets with process. `0.0.0.0:PORT` is every interface; `127.0.0.1:PORT` is local only; the address is the program's own setting (its config file, a flag, or its unit: `systemctl cat SERVICE`). `ss -tan` for states: `ESTAB` open, `TIME-WAIT` normal after closing first, `CLOSE-WAIT` our program isn't closing.
- **Ephemeral ports:** the client-side range, `/proc/sys/net/ipv4/ip_local_port_range`, default 32768 to 60999.
- **Tests in order:** `dig name` (CNAME, then A records, with TTLs; `+short` for just the names and addresses; `dig` skips `/etc/hosts`, `curl` reads it first) → `nc -zv host port` (does the port answer?) → `curl -v` or `curl -I` (the HTTP exchange) → `traceroute`/`mtr` (the path; `* * *` is a silent router, not a fault by itself).
- **The labs' name server, dnsmasq:** `host-record=NAME,ADDRESS` in a file under `/etc/dnsmasq.d/`; it reads its files only when it starts, so `systemctl restart dnsmasq` after a change.
- **`tcpdump -nn -i eth0 port N [and host X]`**; `-w file.pcap`. Handshake `[S]`, `[S.]`, `[.]`; `[R.]` to a SYN means refused; unanswered, repeated SYNs mean dropped (firewall or security group).
- **nftables:** hooks `prerouting` → `input`/`forward`, `output`, `postrouting`; `policy drop` plus accepts; `ct state established,related accept` so only new connections need a port rule; `iif lo accept` so the machine can talk to itself; `nft list ruleset`, `conntrack -L`. Rules that survive a reboot live in `/etc/nftables.conf` (`flush ruleset`, then `table inet filter { chain input { ... } ... }`; `{ 22, 443 }` is a set of ports; `nft -c -f` checks it) with `nftables.service` enabled. `drop` answers nothing; `reject` answers at once (ICMP unreachable, or a reset with `reject with tcp reset`).
- **Containers:** own network namespace, a veth pair to a bridge, NAT out, published ports are DNAT rules in `prerouting`. `ip netns exec NAME COMMAND` runs a command inside a namespace.

</Recap>
