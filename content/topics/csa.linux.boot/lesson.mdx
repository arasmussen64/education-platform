<Intro>

A cloud server goes from nothing to serving traffic in under a minute, and when that doesn't happen, "it won't come up" is all you'll be told. This topic follows the minute step by step, so you know where to look.

**From power-on to PID 1.** The **firmware** (UEFI on modern machines, BIOS on old ones) runs first, finds a disk, and starts the **bootloader** from it, usually **GRUB**. GRUB loads two files into memory: the **kernel**, and the **initramfs**, a small temporary root filesystem holding the drivers and tools the kernel needs to find the real disk. The kernel starts, uses the initramfs to mount the real root filesystem, and starts exactly one program: **systemd**, as PID 1. From there it's the previous topics: systemd works towards its default target, `multi-user.target` on a server, starting units in dependency order, and the machine is "up" when that target is reached. `systemd-analyze` tells you how long each phase took, `systemd-analyze blame` which units took longest, `journalctl -b` shows this boot's log (and `-b -1` the previous one), and `dmesg` the kernel's own messages. When a VM "never comes up", the cloud console's **serial console** or boot log shows the same messages from outside.

**cloud-init.** Every cloud image is the same for everyone, so something has to turn it into *your* server on first boot: the hostname, your SSH key, the packages, the one script that starts your app. That something is **cloud-init**, a set of systemd services that run early in the boot and ask the cloud for instructions. It finds its **datasource** (on a cloud, the metadata service described below) and runs in four **stages**: *local*, before networking, which applies network configuration; *network*, which fetches the metadata and user data and sets the hostname, users and keys; *config*, which runs most configuration modules; and *final*, which installs packages and runs your `runcmd` commands last. Its output lands in `/var/log/cloud-init-output.log`, its own log in `/var/log/cloud-init.log`, and `cloud-init status --long` summarises what happened. Those three places answer "why didn't my package install?" nearly every time.

**User data.** The instructions you attach at launch come in two forms, told apart by their first line. A document starting `#cloud-config` is YAML describing what you want: `users` with their SSH keys, `packages` to install, `write_files`, `runcmd` to run at the end. A file starting `#!/bin/bash` (any shebang) is a script that cloud-init simply runs. Cloud-config is the better habit: it's declarative, readable, and each module knows how to behave sensibly on a rerun. Most of cloud-init's work is **once per instance**: it records the instance ID it configured, and on later boots of the same instance it skips the per-instance modules, so `runcmd` doesn't run again on every reboot (use `bootcmd` for that). It also means that editing the user data of an existing instance changes nothing; you launch a new instance, or run `cloud-init clean` and reboot. A machine image made from a configured instance gets a new instance ID when launched, so cloud-init runs the per-instance steps again on it, which is what you want.

**The instance metadata service.** Every cloud gives an instance a private HTTP endpoint that answers only to the instance itself: **IMDS**, at `169.254.169.254` on AWS and Azure, and `metadata.google.internal` (the same address) on Google Cloud. It hands out the instance's identity (ID, type, zone), its network details, its tags, the user data, and, the important part, **temporary credentials** for the IAM role attached to the instance. That's how software on the instance calls cloud APIs with no key on disk: it asks the metadata service, gets credentials that expire in hours, and asks again later. `curl http://169.254.169.254/latest/meta-data/` on AWS lists the paths; entries ending in `/` are directories.

**Why the newer form matters.** In 2019 a web application with a **server-side request forgery** bug, one that fetched a URL a user supplied, was tricked into fetching the metadata URL for its instance's credentials and handing them to an attacker, who used them to read a bank's data from storage. The original protocol, **IMDSv1**, answered any plain `GET`. **IMDSv2** requires a session: first a `PUT` to `/latest/api/token` with a header saying how long the token should live (up to six hours), then that token in an `X-aws-ec2-metadata-token` header on every `GET`. A forged request from a web app is a `GET` without custom headers, so it gets `401`. The token also has a **hop limit** of 1 by default, so a request forwarded through a container or a proxy fails. You require v2 by setting the instance's metadata options to tokens-required, and in every launch template. Azure requires a `Metadata: true` header and rejects requests carrying `X-Forwarded-For`; Google requires a `Metadata-Flavor: Google` header. Same idea: something a naive forwarder won't add.

**Read now:** the ArchWiki's boot-process page, the main resource below (written for Arch, true everywhere), then cloud-init's introduction and boot stages, the AWS page on requiring IMDSv2, and skim the Azure and Google pages for their headers; `systemd-analyze`'s manual is for when a boot is slow. The practice reads `systemd-analyze`, the boot journal, a user-data file, cloud-init's log, a metadata listing and a log of metadata requests with the text tools from Shell essentials, and uses bash for the instance-ID check cloud-init itself makes.

</Intro>

<Recap>

- **Boot:** firmware (UEFI) → bootloader (GRUB) → kernel + initramfs → root filesystem → systemd (PID 1) → `multi-user.target`. `systemd-analyze`, `systemd-analyze blame`, `journalctl -b`, `dmesg`, the cloud's serial console.
- **cloud-init** runs as systemd services in four stages: local, network, config, final (`runcmd` and packages last). Logs: `/var/log/cloud-init-output.log`, `/var/log/cloud-init.log`; `cloud-init status --long`.
- **User data:** `#cloud-config` YAML (`users`, `packages`, `write_files`, `runcmd`) or a `#!` script. Per-instance modules run once per instance ID; edits after first boot do nothing until a new instance or `cloud-init clean`. `bootcmd` runs every boot.
- **IMDS** at `169.254.169.254` (AWS, Azure; Google's `metadata.google.internal`): identity, network, tags, user data, and temporary role credentials, so no keys on disk.
- **IMDSv2:** `PUT /latest/api/token` with a TTL header (max 21600 s), then `X-aws-ec2-metadata-token` on every `GET`; hop limit 1; plain GETs get `401`. Require it. **Azure:** `Metadata: true`, no `X-Forwarded-For`. **Google:** `Metadata-Flavor: Google`. All defend against server-side request forgery.

</Recap>
