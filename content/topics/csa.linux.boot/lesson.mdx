<Intro>

<Puzzle question="A program on a cloud server uploads files to the cloud's storage service. There is no password, key or secret anywhere on the server's disk, in its settings or in its environment. How does the storage service know the program is allowed?">

The server asks the cloud for credentials, over a private address only it can reach: the instance metadata service. It hands out short-lived credentials for the role attached to the server, and the program asks again before they expire. Nothing secret is stored, which is good, and anything that can make the server send a web request may be able to ask too, which is why the newer, session-based way of asking matters. Both come at the end of this lesson, after the boot itself.

</Puzzle>

A cloud server goes from nothing to serving traffic in under a minute, and when that doesn't happen, "it won't come up" is all you'll be told. This topic follows the minute step by step, so you know where to look.

**From power-on to PID 1.** The **firmware** (UEFI on modern machines, BIOS on old ones) runs first, finds a disk, and starts the **bootloader** from it, usually **GRUB**. GRUB loads two files into memory: the **kernel**, and the **initramfs**, a small temporary root filesystem holding the drivers and tools the kernel needs to find the real disk. The kernel starts, uses the initramfs to mount the real root filesystem, and starts exactly one program: **systemd**, as PID 1. From there it's the previous topics: systemd works towards its default target (on Ubuntu that is `graphical.target` even on a server; it pulls in `multi-user.target`, the 'server fully up' target), starting units in dependency order, and the machine is "up" when that target is reached. `systemd-analyze` tells you how long each phase took, `systemd-analyze blame` which units took longest, `journalctl -b` shows this boot's log (and `-b -1` the previous one), and `dmesg` the kernel's own messages. When a VM "never comes up", the cloud console's **serial console** or boot log shows the same messages from outside.

**cloud-init.** Every cloud image is the same for everyone, so something has to turn it into *your* server on first boot: the hostname, your SSH key, the packages, the one script that starts your app. That something is **cloud-init**, a set of systemd services that run early in the boot and ask the cloud for instructions. It finds its **datasource** (on a cloud, the metadata service described below) and runs in four **stages**: *local*, before networking is up, which finds the datasource and applies network configuration (on AWS, Azure and Google Cloud it already reads the metadata and user data here, over a short-lived connection of its own); *network*, once networking is up, which works through the user data and runs the first modules, among them `bootcmd`, `write_files`, the hostname, users and their SSH keys; *config*, which runs most of the other configuration modules; and *final*, which installs packages and runs your `runcmd` commands last. Its output lands in `/var/log/cloud-init-output.log`, its own log in `/var/log/cloud-init.log`, and `cloud-init status --long` summarises what happened. Those three places answer "why didn't my package install?" nearly every time.

<Check item="boot-cloud-init-stages" />

**User data.** The instructions you attach at launch come in two forms, told apart by their first line. A document starting `#cloud-config` is **YAML**, a plain-text format in which a line `key: value` sets a value, a line starting `- ` is one item of a list, and indentation (spaces, never tabs) shows what belongs to what. It describes what you want: `users` with their SSH keys, `packages` to install, `write_files`, `runcmd` to run at the end. `packages` takes the names exactly as `apt` knows them, and a name apt can't find makes that step fail, with the name in the log. `write_files` writes each file at exactly the `path:` it is given, with the `content:` below it. A file starting `#!/bin/bash` (any shebang) is a script that cloud-init simply runs. Cloud-config is the better habit: it's declarative, readable, and each module knows how to behave sensibly on a rerun. Most of cloud-init's work is **once per instance**: it records the instance ID it configured, and on later boots of the same instance it skips the per-instance modules, so `runcmd` doesn't run again on every reboot (use `bootcmd` for that). They are skipped whether or not they worked the first time, so a reboot doesn't repair a first boot that failed, and `cloud-init status` can then say `done` on a server that was never set up. It also means that editing the user data of an existing instance changes nothing by itself. `cloud-init clean` followed by a reboot makes the same instance go through its first boot again, from whatever user data it has by then, on top of whatever the failed boot left behind; that's a quick way to try a fix on one server. Only a fresh instance launched from the file proves that the file works on its own, so that's how you finish. A machine image made from a configured instance gets a new instance ID when launched, so cloud-init runs the per-instance steps again on it, which is what you want.

<Check item="boot-instance-id" />

**The instance metadata service.** Every cloud gives an instance a private HTTP endpoint that answers only to the instance itself: **IMDS**, at `169.254.169.254` on AWS and Azure, and `metadata.google.internal` (the same address) on Google Cloud. It hands out the instance's identity (ID, type, zone), its network details, its tags, the user data, and, the important part, **temporary credentials** for the IAM role attached to the instance. That's how software on the instance calls cloud APIs with no key on disk: it asks the metadata service, gets credentials that expire in hours, and asks again later. `curl http://169.254.169.254/latest/meta-data/` on AWS lists the paths; entries ending in `/` are directories.

**Why the newer form matters.** A web application with a **server-side request forgery** bug, one that fetches a URL a user supplies, can be tricked into fetching the metadata URL for its instance's credentials and handing them to an attacker; the story below is a real case. The original protocol, **IMDSv1**, answered any plain `GET`. **IMDSv2** requires a session: first a `PUT` to `/latest/api/token` with a header saying how long the token should live (up to six hours), then that token in an `X-aws-ec2-metadata-token` header on every `GET`. A forged request from a web app is a `GET` without custom headers, so it gets `401`. The token also has a **hop limit** of 1 by default, so a request forwarded through a container or a proxy fails. You require v2 by setting the instance's metadata options to tokens-required, and in every launch template. Azure requires a `Metadata: true` header and rejects requests carrying `X-Forwarded-For`; Google requires a `Metadata-Flavor: Google` header. Same idea: something a naive forwarder won't add.

<Check item="meta-token-requests" />

<Story title="Capital One's stolen credentials, 2019" source="https://krebsonsecurity.com/2019/08/what-we-can-learn-from-the-capital-one-hack/" sourceTitle="What We Can Learn from the Capital One Hack" license="linked, not copied">

In 2019 an intruder took the data of more than 100 million credit card applications from the bank Capital One, whose systems ran on AWS.

The way in was the metadata service. Capital One ran a web application firewall, a program that sits in front of websites and filters out attacks, on an AWS server. According to a source close to the investigation, it was misconfigured, so an outsider could make it pass requests on to the instance's metadata service: a server-side request forgery. The metadata service handed over the temporary credentials of the role attached to that server, and the role had far more permission than a firewall needs, enough to list the bank's storage buckets and read the files inside them.

Amazon said the fault lay in the firewall's configuration, not in its own services. A Cloudflare security engineer quoted in the report suggested that AWS make metadata requests carry something identifying, as Google's already had to, even at the cost of breaking old software. IMDSv2's session token is that kind of defence. The lesson is two layers: make the metadata service refuse forwarded requests, and give each role only the permissions its server needs.

</Story>

<Recap>

- **Boot:** firmware (UEFI) → bootloader (GRUB) → kernel + initramfs → root filesystem → systemd (PID 1) → `multi-user.target`. `systemd-analyze`, `systemd-analyze blame`, `journalctl -b`, `dmesg`, the cloud's serial console.
- **cloud-init** runs as systemd services in four stages: local, network, config, final (`runcmd` and packages last). Logs: `/var/log/cloud-init-output.log`, `/var/log/cloud-init.log`; `cloud-init status --long`.
- **User data:** `#cloud-config` YAML (`key: value`, `- ` for a list item, indentation with spaces) with `users`, `packages` (apt's exact names), `write_files` (exactly the `path:` given), `runcmd`; or a `#!` script. Per-instance modules run once per instance ID, even when they failed, so a reboot repairs nothing and `status` can say `done`; edits after first boot do nothing until a new instance (or `cloud-init clean` and a reboot, on top of what's there). `bootcmd` runs every boot.
- **IMDS** at `169.254.169.254` (AWS, Azure; Google's `metadata.google.internal`): identity, network, tags, user data, and temporary role credentials, so no keys on disk.
- **IMDSv2:** `PUT /latest/api/token` with a TTL header (max 21600 s), then `X-aws-ec2-metadata-token` on every `GET`; hop limit 1; plain GETs get `401`. Require it. **Azure:** `Metadata: true`, no `X-Forwarded-For`. **Google:** `Metadata-Flavor: Google`. All defend against server-side request forgery.

</Recap>
