<Intro>

Most cloud servers run **Linux**: an operating system, the software that runs a machine and every program on it, as Windows does on a PC. A server has no screen of its own, so you work on it through a **shell**: a program that reads a line of text you type, runs it as a command, and prints the result. No windows, no mouse. It feels bare at first, and then it becomes the fastest way there is to ask a machine a question. This topic is about reading and writing those commands.

**Open a terminal and type along.** A **terminal** is the window a shell runs in. On Windows, open **Git Bash**, which is installed with Git: it runs `bash`, the shell most Linux servers use, and nearly every command in this topic works in it. (PowerShell is a different shell with different commands. WSL, if you have it, is a real Linux and works too.) On a Mac, open Terminal. The shell shows a **prompt**, a short line that ends in `$`, and waits. Type a command after it and press Enter. Start with a scratch folder and a small file to practise on, so nothing you try touches your real files:

```
mkdir scratch
cd scratch
echo "INFO started" > app.log
echo "ERROR disk full" >> app.log
echo "error: retrying" >> app.log
```

`mkdir` makes a folder, `cd` moves into it, and `echo` prints whatever follows it. The `>` and `>>`, explained below, send that into a file instead of the screen, so you now have a three-line file called `app.log`. None of the five lines printed anything: in the shell, silence usually means it worked. From here on, try each command as you meet it. If one seems stuck, it's usually waiting for input you didn't mean to give it: **Ctrl+C** stops it and gives you the prompt back.

**How a command is built.** A line like `grep -n error app.log` has three parts: the **program** to run (`grep`), **options** that change how it behaves (`-n`: show line numbers), and **arguments**, the things to work on (`error`, the text to look for, and `app.log`, the file to look in). Try it: it prints `3:error: retrying`, the third line, the only one that spells `error` in small letters. Spaces separate the parts, which is why a file name with a space in it needs quotes: `cat "my notes.txt"`. Every program explains itself: `grep --help` prints a summary of its options, and works everywhere. On a full Linux machine `man grep` opens the whole manual (arrow keys scroll, `q` leaves); Git Bash and the labs' small machines don't have the manuals installed.

**Where you are.** Files live in a tree of folders (the readings call them **directories**) that starts at `/`, the root. `/var/log/app.log` is an *absolute* path: it starts from the root. `logs/app.log` is *relative*: it starts from where you are now, which `pwd` prints. `cd logs` moves into a folder, `cd ..` moves up one, `cd` on its own goes to your home folder, which the shell also calls `~`, and `ls` lists what's here. `cat` prints a whole file, `head -n 20` and `tail -n 20` print its first or last twenty lines, and `find . -name '*.log'` walks every folder below you looking for names that end in `.log`: the `.` means "here", `*` stands for any run of characters, and the quotes hand the `*` to `find` untouched, where the shell would otherwise fill it in itself.

**Everything is text, flowing.** This is the idea that makes the shell powerful. Every program reads from an input stream and writes to an output stream, plus a second output stream, **stderr**, for complaints. The pipe, `|`, connects one program's output to the next program's input. So `grep -i error app.log | wc -l` runs `grep` to keep only the lines that mention an error, in capitals or not, and `wc -l` counts the lines it was handed: `2`, for your file. Small tools, each doing one thing well, joined into a **pipeline** that answers your question. `>` sends output into a file instead of the screen (replacing the file), `>>` adds to the end of a file, and `<` goes the other way, feeding a file into a program's input: `wc -l < app.log`. `2>/dev/null` throws the complaints away, and `2>&1` folds them into the main output so you can see or search them. Every command also leaves an **exit status**, a number that says how it went: `0` means it worked, anything else means it didn't. `echo $?` prints the last one.

**The question-answering tools.** The readings show most of them at work, and the practice below exercises every one. Two kinds of file come up again and again. A web server's **access log** has one line per request, like `GET /cart 200 512`: the method (`GET` asks for a page, `POST` sends something in), the path (which page), the **status code** (three digits for how it went: `200` is fine, the 400s mean the request was wrong, as in `404` for a page that isn't there, and the 500s mean the server itself failed) and the number of bytes sent back. A **CSV** file (comma-separated values) is a table as text: one row per line, commas between the columns, and often a **header**, a first line that names the columns. You have neither kind in your scratch folder, so read the examples that use them; the first lab's machine has both.

- To keep the lines that mention something: `grep pattern file`, with `-i` to ignore case, `-v` for the lines that *don't* match, `-c` to count, `-n` for line numbers, `-r` to search whole folders. `grep` looks at the whole line, so `grep 500 access.log` also finds a request that sent back `1500` bytes. Quotes make spaces part of the pattern: `grep ' 500 '` only matches a `500` with a space on each side, which in an access log is the status.
- To take one column: `cut -d, -f2` (split on commas, keep field 2), or `awk '{print $2}'` (split on spaces, however many there are, and print the second field, which `awk` calls `$2`: in an access log, the path).
- To count how many of each: `sort`, then `uniq -c`, then `sort -rn`. Group, count, biggest first. `uniq` only merges lines that sit next to each other, which is why the `sort` comes first. `uniq -c` writes each count in front of its line, and `sort -rn` reads that count as a number (plain `sort` compares text, where `10` comes before `9`). `sort -u` on its own keeps one copy of each different line.
- To count lines: `wc -l`.
- To skip a header: `tail -n +2` prints from the second line on.
- To change text: `sed 's/old/new/g'`. Without the `g`, only the first match on each line changes.
- To test one column or add one up: `awk '$4 > 1000' access.log` keeps the requests that sent back more than 1,000 bytes; `awk -F, '$3 > 100 {print $1}'` splits on commas and prints the first field of every row whose third is over 100; `awk -F, '{total += $3} END {print total}'` adds the third field up. A header's words aren't numbers, so skip the header, or it can slip through a test like these: `tail -n +2` first, or `NR > 1 &&` in front of the test (`NR` is the number of the line `awk` is on).
- The same for **JSON**, a text format that cloud tools print constantly: names and values inside braces, like `{"name": "web-1", "port": 8080}`, with lists in square brackets. `jq '.servers[0].name'` reads as "the `name` of the first item, counting from 0, in the list called `servers`". Git Bash has no `jq`; here you only need to recognise it.

**Build pipelines one stage at a time.** Run the first command and look at what it prints. Add the next stage, look again. The up-arrow key brings back the line you typed last, ready to add to. A pipeline you can't predict is one you can't trust, which is why the practice here asks you to predict a command's output before anything runs.

**Your first script.** A pipeline worth keeping goes in a file. A **script** is a text file of commands that the shell runs from top to bottom, exactly as if you had typed them. The labs hand you scripts to finish and to fix, and ask you to write one, so make one now. You need an **editor**, a program for changing text files. The simplest one, installed in Git Bash and in every lab, is `nano`:

```
nano hello
```

The terminal turns into a page. Type these two lines:

```
#!/usr/bin/env bash
echo "Hello from a script"
```

Save with **Ctrl+O** and then **Enter** (nano calls saving "Write Out", and Enter accepts the file name it shows), and leave with **Ctrl+X**. The two rows at the bottom of nano's screen list its keys, and `^` there means the Ctrl key, so `^X` is Ctrl+X. If you leave with changes unsaved, nano asks whether to save them: `Y` and then Enter keeps them, `N` throws them away. The arrow keys move around; the mouse doesn't.

The first line is the **shebang**. `#!` followed by the path of a program says which program should run this file, and `#!/usr/bin/env bash` says "find `bash` and use that". It must be the very first line. Any other line that starts with `#` is a **comment**: a note for people, which the shell skips.

A new file is only text. On Linux it has to be marked as a program before it will run, which you do once, with `chmod +x` (what that changes is the permissions topic's subject). After that you run it by its path:

```
chmod +x hello
./hello
```

`./hello` means "the file `hello` in this folder". A bare name like `grep` is looked up in the shell's own list of program folders, and your folder isn't on that list, so a script needs a path: `./hello` here, `~/bin/report` in the labs. Without the `chmod`, a Linux machine answers `Permission denied` (Git Bash is more forgiving; the labs are not).

A script gets its arguments the way `grep` gets its: you type them after its name. Inside the script the first one is `$1` and the second is `$2`. Open the script again with `nano hello`, change its second line to this, and save:

```
echo "Hello, $1"
```

Now `./hello Ada` prints `Hello, Ada`. Scripts usually give an argument a clearer name straight away by putting it in a **variable**: `log="$1"` stores it under the name `log` (no spaces around the `=`), and `"$log"` reads it back. Keep the double quotes: they hold a value with a space in it together as one argument. One thing to keep straight: inside the single quotes of `awk '{print $2}'`, `$2` is awk's second field, because single quotes stop the shell from touching what's between them. Anywhere else in a script, `$2` is the script's second argument.

The last piece is `$(...)`, which runs the command inside the brackets and puts what it printed in its place, so one command's answer can sit in the middle of another's sentence:

```
echo "Today is $(date)"
echo "This folder holds $(ls | wc -l) things"
```

Those are all the parts the labs' scripts are made of. Put together, this one says how many lines a file has:

```
#!/usr/bin/env bash
# Usage: count-lines FILE
file="$1"
echo "$file has $(wc -l < "$file") lines"
```

Saved as `count-lines` and made executable, `./count-lines app.log` prints `app.log has 3 lines`. Read its last line from the inside out: `wc -l < "$file"` counts the lines of the file named by the first argument, `$(...)` drops that number into the sentence, and `echo` prints the sentence. The quotes inside `$(...)` are a pair of their own and don't end the pair outside. Scripts get a whole topic later in this module; this much is enough to save a pipeline and run it again.

**When a program misbehaves,** the shell has tools that look *at the program* rather than at files. A running program is called a **process**. It can't reach a file, the disk or the network by itself: it has to ask the **kernel**, the core of the operating system, and each of those requests is a **system call**. `strace` shows the system calls a process is making right now, so you can see what it's stuck waiting for. `lsof` shows which files and network ports a process has open (a **port** is a numbered door on a machine, where one program listens for connections), so you can see who is holding port 8080. `iostat` shows whether a disk is saturated: busy all the time, with work queuing up for it. `vmstat` shows whether the machine is **swapping**: so short of memory that it keeps moving data out to the much slower disk and back, which makes everything crawl. None of the four is in Git Bash. You'll use them properly in the performance-triage topic; for now, learn which question each one answers.

<Recap>

- **A command** is a program, its options (`-n`, `--count`) and its arguments. `cmd --help` explains them everywhere; `man cmd` on a full Linux machine (`q` leaves). Ctrl+C stops a command that's stuck.
- **Paths:** `/` is the root. `pwd` says where you are; `cd folder`, `cd ..` (up one), `cd` (home, `~`). Absolute paths start at `/`; relative ones start where you are, and `.` is "here". `mkdir name` makes a folder.
- **Looking:** `ls`, `cat`, `head -n N`, `tail -n N`, `find . -name 'pattern'`. Quote patterns so the shell doesn't expand them before the program sees them.
- **Streams:** stdin in, stdout out, stderr for errors. `|` joins stdout to the next command's stdin. `>` replaces a file, `>>` appends, `<` feeds a file to stdin, `2>/dev/null` discards errors, `2>&1` merges them into stdout. `$?` is the last command's exit status: `0` means it worked.
- **Filtering:** `grep` (`-i`, `-v`, `-c`, `-n`, `-r`) matches anywhere on the line. **Fields:** `cut -d, -fN`, `awk '{print $N}'`. **Counting:** `wc -l`; `sort | uniq -c | sort -rn | head` for "which most"; `sort -u` for one of each.
- **`sort` compares text** unless you say `-n`; `uniq` only merges neighbouring lines, so sort first; `tail -n +2` skips a header line.
- **Editing and computing:** `sed 's/old/new/g'` (without `g`, only the first match on each line changes); `awk '$4 > 1000'` tests one field; `awk -F, 'NR > 1 && $3 > 100 {print $1}'` (skip the header, or `awk` compares its text with `100` as text, and `amount` sorts after `100`, so the header line gets through); `jq` for JSON.
- **A script** is a file of commands. First line `#!/usr/bin/env bash`; `#` starts a comment; `chmod +x file` once, then run it by its path (`./file`, `~/bin/file`). `$1` and `$2` are its arguments; `log="$1"` names one and `"$log"` reads it; `$(command)` is replaced by what the command prints.
- **`nano file`** edits a file: Ctrl+O then Enter saves, Ctrl+X leaves. `^` in its menu means Ctrl.
- **Diagnosis:** `strace` (the system calls a process makes: its requests to the kernel), `lsof` (open files and ports), `iostat` (is a disk saturated), `vmstat` (memory, swapping, CPU).

</Recap>
