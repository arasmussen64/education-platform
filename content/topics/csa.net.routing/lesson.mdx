<Intro>

Module 1 showed you a host's `ip route` and its default gateway. This topic is about the machines in the middle: **routers**, machines whose job is to pass packets from one network to another. Every cloud network is full of them, mostly invisible, and every "it works from here but not from there" eventually comes down to one of them deciding something you didn't expect. Five ideas carry the topic: how a router picks a route, how routes get there, when a router can and can't notice a failure, why the reply is a separate story, and where packets go to die.

**What a router does.** A router reads one thing in each packet, its destination address, looks it up in its **routing table**, and hands the packet to the **next hop**: the neighbouring router, or the destination itself, on one of the router's own networks, one step closer. Picture a chain of sorting offices, each with its own list, "letters for addresses that start like this go to that office". No office knows the whole route, and none remembers the letter once it has passed it on. Building the list is **routing**; using it, packet by packet, is **forwarding**. A **route** is three things: a **prefix** (a block of addresses, written as in IPv4 and CIDR), a next hop, and the interface to send the packet out of.

**The routing table.** Three kinds of route appear in every table. A **connected route** appears by itself for each network the router has an address on: r1, at 10.1.0.1/24 on its interface `lan`, knows that 10.1.0.0/24 is right there. A **static route** is one a person typed in. The **default route**, 0.0.0.0/0 (`default` in `ip route`), holds every address there is. A prefix written without a length, `10.40.12.7 via ...`, is a **host route**: a /32, a single address. Linux's `ip route` shows the kernel's table, the one packets follow. The labs' routers run **FRR** (FRRouting), the routing software many real networks run on Linux. Its console, **vtysh**, is in the style of Cisco's routers: `on r1 vtysh` opens it at an `r1#` prompt, `show ip route` lists FRR's table, `configure terminal` starts a change, and `end` finishes it. In `show ip route`, the first letter says where a route came from (`C` connected, `S` static, `B` BGP), `>` marks the route FRR chose for that prefix, `*` that it's in the kernel's table, and `[1/0]` is the route's distance and metric.

**Longest-prefix match.** Think of each prefix as a box of addresses. Boxes nest: a /24 inside a /16 inside 0.0.0.0/0. A packet goes by the **smallest box that holds its address**: the route with the longest prefix that matches. Take a branch router's table:

```
default via 192.0.2.1 dev wan
10.40.0.0/16 via 10.255.0.5 dev east
10.40.8.0/21 via 10.255.0.9 dev branch
10.40.9.0/24 dev shop proto kernel scope link src 10.40.9.1
10.40.12.7 via 10.255.0.13 dev mgmt
```

10.40.9.20 is in four boxes (the default, the /16, the /21 and the /24), and the /24 is longest: it's on the connected network `shop`. 10.40.13.1 is the interesting one. A /21 leaves 11 bits for hosts, 2,048 addresses, 8 in the third number, so 10.40.8.0/21 runs from 10.40.8.0 to 10.40.15.255 and holds .13.1; the /24 at 10.40.9.0 holds only 10.40.9.x, however close its numbers look. So .13.1 goes to 10.255.0.9. 10.40.20.1 is outside the /21 and goes by the /16; 10.40.12.7 matches its own host route, the longest prefix of all; 172.16.0.1 is in no box but the default. Three wrong ways to read a table, all common: taking the first line that matches (a routing table isn't read top to bottom like a firewall's rules), taking the route whose numbers look most like the address, and taking the widest route. IPv6 works the same way, with longer addresses.

**When two routes have the same prefix.** Then the route's source decides. Each kind of source has an **administrative distance** (FRR calls it simply distance), and the lowest wins. FRR 8.4's: connected 0, static 1, eBGP 20 (BGP from another network; BGP itself is a later topic), OSPF 110, iBGP 200 (BGP inside one network), and 255, which means "never install". Within one source, a routing protocol compares its own cost, the **metric**, lower winning; a static route's is 0. When prefix, distance and metric all tie, Linux installs both routes and shares the traffic between them (ECMP, below). The clouds have no distances, but each ranks its kinds of route in a fixed order (their pages, read 2026-11-12):

| | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| First | the longest prefix | the longest prefix | a subnet route that matches is used, full stop; no static route may match or fit inside one |
| Same prefix | a static route (one you added), then a prefix-list route, then a propagated one (Direct Connect BGP, then VPN static, then VPN BGP) | a user-defined route (UDR), then a BGP route, then a system route | the most specific route, then the lowest priority number; equal routes share traffic only within one kind |
| The surprise | a longer propagated route still beats a static one | the virtual network's own system routes win even against a longer BGP route | a route you write can't take a subnet's traffic away |

A **system route** is one the cloud made (Azure's word; for the virtual network itself, its peerings, the internet), a **UDR** one you wrote, and a **propagated route** one that a VPN or private-circuit gateway learned over BGP and placed in the table for you (AWS's word; Azure calls them BGP routes, Google dynamic routes). Azure's exception is the one that bites: if the office announces 10.0.5.0/24 and the virtual network is 10.0.0.0/16, Azure keeps 10.0.5.20 inside the virtual network, and that part of the office is unreachable from the cloud with no error anywhere.

**RIB and FIB.** FRR keeps every candidate route it has been given, its **RIB** (routing information base): a backup that isn't in use still shows as `S`, without `>*`. The kernel holds only the winners, its **FIB** (forwarding information base), which `ip route` shows. `ip route get ADDRESS` asks the kernel what it would do with a packet for that address, which is what packets actually follow. FRR's view can disagree with the kernel's (a route typed straight into the kernel with `ip route add` is in the FIB and not in FRR, and is gone at the next boot), so the kernel's answer is the one to trust.

**Static routes in FRR.** In vtysh: `configure terminal`, then `ip route 10.3.0.0/24 10.0.13.2 r3`, then `end`. That says "to reach 10.3.0.0/24, hand packets to 10.0.13.2, out of interface `r3`". Naming the interface is optional, and worth the habit. FRR finds the way to a next hop in its own table, and if the cable to 10.0.13.2 goes, it looks again: if any wider route still holds 10.0.13.2 (a blackhole for 10.0.0.0/8, say, which also holds the cables' own addresses), the dead route stays in use, marked `(recursive)`, and its packets go into the blackhole. Named, the route goes `inactive` with its cable. (FRR never looks a next hop up through the default route unless told to, so a default alone doesn't do this.) A **floating static route** is a second route for the same prefix with a higher distance, `ip route 10.3.0.0/24 10.0.12.2 r2 200`: it waits unused and is installed only when the first one goes. Any distance from 2 to 254 works. 255 doesn't: FRR's static-route page shows a "high-distance blackhole" at 255 in an example, but its zebra page says 255 is never installed, and the router agrees with the zebra page. A **blackhole route** (`ip route 10.0.0.0/8 blackhole`) drops packets in silence; a **reject route** (`... reject`) drops them and answers with an ICMP unreachable. Both are useful on purpose: for addresses nobody uses, so they die at the edge instead of wandering. `no` in front of a line removes it. Everything typed in vtysh is FRR's **running configuration**, in memory; `write memory` saves it to `/etc/frr/frr.conf`, the **saved configuration** FRR loads at every boot. An unsaved change is gone after a reboot.

**Static or dynamic.** A static route knows only what its own router can see. If a cable loses its link, the router notices at once, drops the routes through it, and a floating backup takes over in a fraction of a second: a **loud failure**. If the path dies while the link stays up, a fault in a provider's equipment between two offices, say, the static route keeps sending traffic into the hole for as long as the fault lasts: a **silent failure**. A **routing protocol** (OSPF and BGP are two) has routers tell their neighbours what they can reach and keep talking: when a neighbour goes quiet, they reroute by themselves, which is **dynamic routing**. The time until every router agrees on the new paths is **convergence**. Static suits a stub with one way out, a handful of routes, or a route that must never move; a protocol pays for itself with redundant paths, many prefixes, or networks that change. The clouds mix both: a subnet's route table is mostly static entries you write, and the routes a VPN or circuit gateway learns over BGP are propagated into it.

**The way back is its own route.** The reply is a new packet with its own destination, and every router on the way back looks it up afresh. Draw the trip out and the trip back as two separate arrows: they may take different roads, an **asymmetric** path. Routers don't mind, but two things do. A **stateful firewall**, one that follows conversations with connection tracking (Module 1's `ct state`), sees the client's SYN on the way out and never the server's SYN-ACK, so it treats the client's next packet as `invalid` and drops it: the web app times out while ping still works, because each echo is allowed by itself. `conntrack -L` shows the entry stuck at `[UNREPLIED]`. And **reverse-path filtering** (`rp_filter`) drops a packet that arrives on an interface the router wouldn't use to reach its source: strict mode, 1, drops asymmetric replies; loose mode, 2, only asks that some route back exists; 0 doesn't check. The fixes: make the routes symmetric, or have the firewall rewrite the source to its own address (source NAT, the next topic), so replies must come back through it, at the cost of the server no longer seeing who the client was.

**Kernel settings: sysctl.** `rp_filter` is one of the kernel's settings, which the command `sysctl` reads and sets: `sysctl net.ipv4.ip_forward` prints whether this machine forwards packets between its interfaces (1, as a router must) or drops whatever isn't for itself (0, a fresh Linux machine). `sysctl -w net.ipv4.ip_forward=1` sets it until the next boot. Settings that last go in files under `/etc/sysctl.d/`, one `key = value` a line, which every boot applies in name order, a later file winning over an earlier one, so `90-router.conf` beats `10-defaults.conf`; `sysctl -p FILE` applies one file now. In the labs, each machine has its own `/etc/sysctl.d/` (`on r2 nano /etc/sysctl.d/90-forward.conf`). One trap from the kernel's documentation: changing `ip_forward` resets other per-interface settings to their defaults, so set it first.

**How packets vanish, and what shows it.** Each cause has its own evidence (all of these were captured in this topic's labs):

| Cause | What the sender sees | What shows it |
| --- | --- | --- |
| No route | `!N` at the last hop that answers | `ip route get` on that router: `Network is unreachable` |
| Blackhole route | silence, `*` from that hop on | `ip route get`: `Invalid argument`; FRR: `unreachable (blackhole)` |
| Reject route | `!H` | FRR: `unreachable (ICMP unreachable)`; kernel: `unreachable PREFIX` |
| Forwarding off | silence from that router on | `nstat`'s `IpInAddrErrors` climbing; `sysctl net.ipv4.ip_forward` is 0 |
| The next hop doesn't answer ARP | silence; the route looks fine | `ip neigh` on the router: the next hop `INCOMPLETE`, then `FAILED` |
| Missing return route | requests time out | tcpdump at the far end: requests arrive, replies leave and never get back |
| Loop | two hops alternating; `Time to live exceeded` | `ip route get` on the two routers points each at the other |

The fifth row is Layers and packets again: a route only names a next hop, and the router still has to find that neighbour's hardware address with ARP. A static route through an address nobody holds is installed (the next hop is on a connected network), and every packet waits for an ARP answer that never comes. The method: `traceroute -n` from the source to find the last hop that answers; `ip route get` on that router and the next; `tcpdump` on the interfaces either side to see where packets stop; then read the configuration. A `*` in traceroute isn't proof by itself: routers limit how often they answer, and firewalls often drop traceroute's probes (`traceroute -I` sends pings instead).

**ECMP.** Two routes with the same prefix and the same distance are both installed, and the kernel shares the traffic: **equal-cost multipath**. It sends each connection one way or the other, chosen by a hash of its addresses (and with `net.ipv4.fib_multipath_hash_policy = 1`, its ports too), so a connection's packets stay in order. If one path is dead, the connections hashed to it fail and the rest work, which looks intermittent: some tries from one laptop fail, the next one works. `ip route` shows both next hops under one prefix, and only a capture on each outgoing interface shows which way a connection went.

**A VM as a router in the cloud.** A cloud network normally delivers to a VM only packets addressed to it, and refuses what it sends from addresses that aren't its own. A firewall or router VM, which handles other machines' packets, needs a switch in the cloud as well as `ip_forward` inside: on AWS, stop the instance's **source/destination check**; on Azure, turn on **IP forwarding** on its network interface (NIC, the VM's virtual network card); on Google Cloud, set **`canIpForward`** on the instance. A missing switch is a black hole with nothing in the VM's logs.

<Recap>

- **A router** looks only at the destination, finds the routes whose prefix holds it, and hands the packet to the **next hop**. Routing builds the table; forwarding uses it. A **route** is a prefix, a next hop and an interface.
- **Longest prefix wins**: the smallest box that holds the address. The default route, 0.0.0.0/0, only when nothing else does. A prefix without a length is a **host route**, a /32. Line order doesn't matter.
- **Same prefix:** the lowest **administrative distance** (FRR: connected 0, static 1, eBGP 20, OSPF 110, iBGP 200; 255 never installed), then the **metric**; a full tie is **ECMP**. AWS: static, then prefix-list, then propagated, but a longer propagated route still wins. Azure: UDR, then BGP, then system, but the virtual network's own routes beat even longer BGP routes. Google: a matching subnet route always; no static route may match or fit inside one.
- **RIB** (FRR's candidates, `show ip route`: `>` chosen, `*` in the kernel, `[distance/metric]`) against **FIB** (the kernel's, `ip route`). `ip route get ADDRESS` is what packets follow.
- **FRR:** `on r1 vtysh`, `configure terminal`, `ip route PREFIX NEXT-HOP INTERFACE [DISTANCE]`, `end`, `write memory` (running against saved). Name the interface, or a wider route can keep a dead next hop alive (`(recursive)`). **Floating static**: the same prefix at a higher distance, 2 to 254. **Blackhole** drops silently; **reject** answers `!H`.
- **Static or dynamic:** a static route sees a **loud** failure (carrier lost) and fails over in a fraction of a second; it never sees a **silent** one. A **routing protocol** notices quiet neighbours and reroutes (**convergence**). Static for stubs and a few fixed routes; dynamic for redundant paths and change.
- **The way back is its own route.** Asymmetric paths break a **stateful firewall** (SYN seen, SYN-ACK not: `invalid`, `[UNREPLIED]`, ping still works) and strict **`rp_filter`** (1; loose is 2). Fix with symmetric routes, or source NAT at the firewall.
- **`sysctl`** reads and sets kernel settings; `-w` lasts until the next boot; **`/etc/sysctl.d/*.conf`** apply at every boot in name order, later winning. `net.ipv4.ip_forward = 1` makes a router; set it first.
- **Where packets vanish:** `!N` no route; silence for a blackhole (`Invalid argument`) or forwarding off (`IpInAddrErrors`); `!H` a reject route; a `FAILED` neighbour for a dead next hop; requests in and replies lost for a missing return route; alternating hops and `Time to live exceeded` for a loop; some connections failing for ECMP with one dead path. Method: traceroute, `ip route get` hop by hop, tcpdump either side.
- **Cloud VMs that forward** need the cloud's switch too: AWS's source/destination check stopped, Azure's IP forwarding on the NIC, Google's `canIpForward`.

</Recap>
