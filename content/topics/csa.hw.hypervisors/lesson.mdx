<Intro>

Steal time, the `st` in `top` from CPU scheduling, was the first sign that a cloud server isn't a computer of its own: something under it took the CPU away. That something is the **hypervisor**. This topic is about what it does, how the three big clouds build theirs, and how to tell from inside a Linux machine what is underneath it.

**What a hypervisor does.** A **virtual machine** (VM) is a computer made of software: it boots its own kernel and believes it has a machine to itself. The VM is a **guest**; the physical machine it runs on is the **host**; the **hypervisor** (also called a virtual machine monitor) is the software on the host that runs several guests side by side. It has three jobs. It shares out the processors: each **vCPU**, a virtual CPU as the guest sees it, is really a **thread** on the host (one line of work inside a program: a program can run several at once, and the scheduler treats each like a process of its own), scheduled onto the host's real cores like any other, which is how the host can take it away. It shares out memory: each guest's "physical" memory is really the host's memory mapped a second time, privately, the trick from virtual memory one level further down. And it hands out devices, network cards and disks, which is the hard part and most of this topic.

**Trapping: how a guest can think it owns the machine.** A processor runs code in two modes. In **kernel mode** the kernel may do anything; programs run in **user mode** and must ask the kernel for anything that touches the hardware. Some instructions, the **privileged instructions**, only work in kernel mode: switching off interrupts (the signals devices send to get the processor's attention), talking to the chip that runs a disk, changing how memory is mapped. A guest's kernel runs those too, believing it owns the machine, and if they ran on the real processor one guest could stop the whole host. Modern processors have **virtualization extensions** for this (Intel's are called VT-x, AMD's AMD-V; on Arm processors a separate privilege level, EL2, plays the part). With them switched on, the processor runs the guest's code directly, at full speed, and keeps the effect of each privileged instruction inside that one guest. Some it carries out on a private copy of the machine's settings that belongs to the guest (a guest that switches off interrupts switches off only its own). At the rest, such as talking to a disk's chip, it **traps**: it stops and hands control to the hypervisor, which does the safe equivalent for that one guest and hands back.

Without the extensions, every instruction has to be imitated in software: **emulation**. **QEMU** is a program that builds a whole virtual machine, its processor, memory and devices. On its own it emulates the processor with its built-in translator, **TCG**, which works anywhere and is slow. **KVM** is a part of the Linux kernel that lets QEMU use the extensions instead; QEMU reaches it through the file `/dev/kvm`. A container on Docker Desktop has no `/dev/kvm`, so the VMs you boot in this topic's labs use TCG: a counting loop took 0.29 seconds on the lab machine and 4.96 inside an emulated guest, 17 times slower. Running a hypervisor inside a VM (an Android phone emulator in the automatic tests a project runs on cloud VMs, say) needs the extensions passed through to that VM: **nested virtualization**, which only some instance types offer.

**Type 1 and type 2.** A **type 2** hypervisor is a program on an ordinary operating system, which owns the hardware: VirtualBox on a laptop, or QEMU on its own. A **type 1** owns the hardware itself, with nothing under it: Hyper-V, Xen, VMware's ESXi. A computer running with no hypervisor at all is **bare metal**. KVM blurs the line: it turns the Linux kernel itself into the hypervisor, and Red Hat counts it as type 1, while QEMU's documentation treats it as one accelerator among several. The more useful question is what else runs with full control of the hardware. Hyper-V keeps a **root partition** running Windows, which owns the devices; Xen has a privileged control domain, **dom0**; KVM has a whole Linux system around it; AWS's Nitro hypervisor has nothing beside it at all.

**Three ways to give a guest a network card.** Two words first. A **device driver** is the part of a kernel that knows how to talk to one kind of device. **PCI** (PCI Express, PCIe, on modern machines) is the connection most cards plug into; `lspci -k` lists a machine's PCI devices and the driver in use for each. Now picture a restaurant with one kitchen, the host's physical network card, and many tables, the guests.

- **Emulated:** a waiter pretends to be a real, ordinary card (QEMU's imitation of an Intel card from the early 2000s), and the guest speaks to him in that card's own language, register by register (a **register** is one of the small slots a card reads its orders from and writes its answers to), through its ordinary `e1000` driver. Any guest can do it, since every operating system has that driver. Every step is a trap into the host, so it is slow.
- **Paravirtual:** the guest knows it's in a restaurant and uses an order pad both sides agreed on: a driver made for VMs, which hands the host whole batches of packets through queues in shared memory. On KVM and QEMU that standard is **virtio** (`virtio_net` for a network card, `virtio_blk` for a disk). On Hyper-V it is the **VMBus**, a channel between the guest and the root partition that carries **synthetic devices** (`hv_netvsc`, `hv_storvsc`) to a guest that knows about the hypervisor, an **enlightened** guest in Microsoft's word. Much faster, but the guest needs those drivers, and the host's software still carries every plate.
- **SR-IOV** (single-root I/O virtualization, a feature of some PCIe cards): the kitchen has many hatches. A card that supports SR-IOV shows itself as one **physical function**, which the host manages, and many **virtual functions** (VFs), each a small PCI device of its own that can be handed straight to a guest, which is called **passthrough**. The guest's packets skip the host's software: nearly the hardware's own speed. The price is that the guest is tied to that card on that host, which is awkward when the host needs maintenance.

AWS's **Nitro** moved the kitchen out of the building. A **Nitro card** is an **offload card**: a separate small computer on the host's PCIe bus that runs the network, the EBS disks (AWS's network-attached disks, which live outside the host) and the management. The hypervisor on the main board only divides the CPUs and memory and hands each instance virtual functions of the cards: an **ENA** network card and **NVMe** disks (NVMe is the way a modern fast disk talks over PCIe; the disks topic covers it). Azure Boost does much the same on Azure's newer sizes, moving networking and storage onto hardware of Microsoft's own. The main resource tells this story in eight stages, from full emulation to bare metal, in Xen's words: a **PV** guest is a paravirtualized one, whose kernel was changed to ask the hypervisor instead of running privileged instructions, from before processors had the extensions; an **HVM** guest is a hardware-assisted one, using them; **PVHVM** is an HVM guest with paravirtual drivers for its devices.

**The three clouds, side by side,** as their documentation stood on 2026-11-11. A **region** is an area of the world a cloud runs in, such as East US, and a **zone** one of the separate data centres a region is made of. **Host maintenance** is the provider updating or repairing the physical host under your VM.

| | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Hypervisor | Nitro, built on KVM (Xen on the old T2 family) | Hyper-V, with a root partition | KVM-based |
| Network card the guest sees | ENA, a virtual function of a Nitro card | `hv_netvsc` on VMBus, plus an `mlx4`, `mlx5` or `mana` virtual function with Accelerated Networking | virtio-net, or gVNIC (`gve`), the only one newer series offer |
| Disks the guest sees | NVMe | SCSI disks on VMBus; NVMe on Azure Boost sizes | SCSI or NVMe, by machine series |
| Host maintenance | the hypervisor is replaced in place while instances run | the VM is paused for up to 30 seconds; the virtual function is taken away for about 30 seconds and traffic falls back to the synthetic card | **live migration** to another host in the same zone: a pause typically well under a second, and the clock may jump up to 5 seconds |
| A host of your own | Dedicated Instances, Dedicated Hosts | isolated sizes (about 10% dearer), Dedicated Host | sole-tenant nodes |

**Reading the guest.** Five places, in the order to try them:

1. `systemd-detect-virt --vm` names the VM: `amazon`, `microsoft`, `google`, `kvm`, `qemu`, `xen`, or `none`, with a non-zero exit status, on bare metal. Without `--vm` it names the innermost layer it can see, which is a container if there is one: on Docker Desktop for Windows it says `wsl`.
2. `lscpu`'s `Hypervisor vendor` (`Microsoft`, `KVM`, `Xen`) and `Virtualization type`. Don't mix them up with `Virtualization: VT-x`, which says the processor offers the extensions to this kernel.
3. The `hypervisor` flag in `/proc/cpuinfo`, which a hypervisor sets in the description of the processor it shows its guest.
4. The firmware's name plate, **DMI**: `/sys/class/dmi/id/sys_vendor` and `product_name` (`QEMU`, `Google Compute Engine`). A container on WSL 2 can't see one.
5. The boot log, `journalctl -k -b` or `dmesg`: `Hypervisor detected`, the `DMI:` line, the drivers as they start.

Then the driver behind each network card and disk: `/sys/class/net/eth0/device/driver` and `/sys/block/vda/device/driver` are links to it. Two surprises wait in the labs' recordings. Under QEMU's emulator, `lscpu` names no vendor at all, although `systemd-detect-virt` says `qemu` from the name plate. And the lab machine's own `eth0` has no driver, because it is a veth, one end of a virtual cable to the VM the container runs on. The lab machine is a container, and on Docker Desktop that container runs on a Linux VM on your computer, so it can't show you a cloud VM's devices: that's what the recordings in its `/srv` folders are for. Each says in its `SOURCE.txt` whether it was **captured** from a real machine (your kind of laptop, QEMU guests) or **constructed** from the providers' documentation (the cloud servers in the build, until real captures exist). `lab-capture`, the labs' recorder, writes one small file per question.

Three more commands are new. `tee FILE` copies what comes through a pipe into a file as well as onto the screen. `qemu-system-x86_64` starts a VM: `-smp` sets its vCPUs, `-m` its memory in MiB (mebibytes of 1,048,576 bytes, a little more than a million; a GiB is 1,024 of them), `-nic user,model=...` gives it a network card of that model, and `-drive file=...,if=...` attaches a disk on that kind of interface. `qemu-img create` makes an empty disk image.

**What a hypervisor can't isolate.** It keeps guests out of each other's memory and devices. On its own it doesn't give you:

- **steady speed:** neighbours share the processor's largest **cache** (a small, fast memory on the processor chip that keeps recently used data close at hand) and its memory bandwidth, and on burstable sizes a core, in turns. A **noisy neighbour** can slow you down without touching anything of yours.
- **freedom from side channels:** a **side channel** is a way to learn another program's secrets by watching hardware you share with it at the same moment, such as a core's caches. That's why AWS never runs two customers on one core at the same time, not even on its two **hyperthreads** (or SMT threads: one physical core showing itself as two vCPUs), and why `lscpu` lists a `Vulnerability` line for each known flaw.
- **a host that doesn't fail:** when the host stops, every guest on it stops. Spread VMs over hosts and zones.
- **privacy from the operator,** unless the platform is built without operator access (AWS says Nitro has none) or the guest's memory is encrypted from the host (a **confidential VM**, a later topic).
- **immunity from a hypervisor bug,** which is the argument for a small hypervisor.

What you can buy is a host to yourself: an AWS **Dedicated Host** or Dedicated Instances, an Azure **isolated size** or Dedicated Host, a Google **sole-tenant node**. It removes other **tenants** (customers sharing the provider's hardware), and with them noisy neighbours and side channels between customers. It removes nothing else on that list. A **bare metal instance** removes the hypervisor too: you rent the whole server, with nothing under your kernel.

<Recap>

- **Hypervisor:** runs guests on a host. It shares out the CPUs (a vCPU is a thread the host schedules), memory (the host's, mapped a second time) and devices.
- **Trapping:** with VT-x or AMD-V (EL2 on Arm), guest code runs directly; a privileged instruction acts on the guest's own copy of the settings or traps to the hypervisor. Without them, **emulation** (QEMU's TCG): 17 times slower in the lab. **KVM** lets QEMU use the extensions, through `/dev/kvm`. **Nested virtualization** passes them into a VM, on some instance types only.
- **Type 2** is a program on an operating system (VirtualBox); **type 1** owns the hardware (Hyper-V, Xen, ESXi); KVM makes Linux the hypervisor and counts as type 1. Ask what else has full control: a root partition, dom0, a Linux host, or nothing (Nitro).
- **Device paths:** emulated (`e1000`; any guest, slow), paravirtual (`virtio_net`, `virtio_blk`; `hv_netvsc`, `hv_storvsc` on VMBus; needs the driver, the host still carries it), SR-IOV virtual function (`mlx5_core`, `mana`, `ena`; near the hardware's speed, tied to the card).
- **AWS Nitro:** a small KVM-based hypervisor, I/O on Nitro cards (ENA, NVMe), updated in place. **Azure:** Hyper-V, `hv_netvsc` plus a virtual function with Accelerated Networking, taken away for about 30 seconds during host servicing, pauses of up to 30 seconds. **Google:** KVM-based, virtio or gVNIC, live migration with a pause usually under a second.
- **Reading the guest:** `systemd-detect-virt --vm` (without `--vm`, the innermost layer, perhaps a container), `lscpu`'s `Hypervisor vendor`, the `hypervisor` flag, DMI, the boot log; then the driver behind each card and disk under `/sys`.
- **Not isolated:** steady speed, side channels on shared hardware, host failure, the operator (unless the platform prevents it), hypervisor bugs. A dedicated host, isolated size or sole-tenant node removes other tenants only; bare metal removes the hypervisor too.

</Recap>
