<Intro>

Every cloud now rents out two kinds of machine: ones with Intel or AMD chips, and ones with Arm chips, which usually cost less. Whether a service can move to the cheaper kind depends on what's inside its files, and whether the move saves what the brochure says depends on sums you can do from a price list. This topic gives you both.

**What a CPU runs.** A CPU does one small operation at a time: add two numbers, compare them, copy a value from memory, jump to another place in the list. Each operation is an **instruction**, and each instruction is written as a number. A program, as the CPU sees it, is a long run of those numbers: **machine code**. The set of instructions a family of CPUs understands, and the numbers that stand for them, is its **instruction set**, also called its **architecture**. The main video below builds a tiny CPU and runs a program on it, one instruction at a time; that picture is the one to keep. The second video, listed after the lesson, shows the CPU itself if it's new to you.

**Source, compiler, binary.** People don't write machine code. They write **source code**, text in a language like C or Go, and a **compiler** translates it, once and ahead of time, into one architecture's machine code. That's **compiling**, or **building**, and the result is a **binary**: a program file. On Linux a binary is an **ELF** file, whose first bytes say which architecture it's for. The scripts you wrote in Module 1 are different: they're text that an **interpreter**, `bash`, reads every time they run, and `bash` itself is the binary. So a script moves to another architecture untouched, as long as its interpreter exists there; a compiled program has to be built again. Python and Ruby scripts are like Bash ones. Java sits between: its compiler makes **bytecode**, instructions for the Java runtime (the **JVM**, the Java virtual machine) rather than for a CPU, so a `.jar` of bytecode runs on any machine that has a JVM of its own architecture. The catch, every time, is compiled code hidden inside something portable: a **native extension** (the compiled part of a Python package) or a **shared library** (a `.so` file: compiled code that programs load when they start) inside a jar.

**Two families, four names.** Two architectures run nearly every machine the clouds rent out. **x86-64** is Intel's and AMD's, also written **amd64**, because AMD designed the 64-bit version; the name covers Intel's chips too. **64-bit Arm** is also written **aarch64** or **arm64**. The kernel says `x86_64` and `aarch64` (`uname -m` prints it); Debian, Ubuntu, Docker and Go say `amd64` and `arm64` (`dpkg --print-architecture`). Each pair is one architecture with two names. `file PROGRAM` reads a file's header and says what it's built for, `x86-64` or `ARM aarch64`, and how it's linked: **dynamically linked** means it loads the C library and other shared libraries from the machine when it starts, through a small program called the **loader**; **statically linked** means everything it needs is inside. A file's name is a claim someone typed. `file` reads what's inside.

**The first failure: the wrong architecture.** Start an x86-64 binary on an Arm server, or the other way round, and the kernel reads the header and refuses. Bash says `cannot execute binary file: Exec format error`, and the exit status is 126. An **emulator** can run it anyway: a program that reads another architecture's instructions and does the same work with its own. In Hypervisors you met QEMU emulating a whole machine; `qemu-aarch64-static` emulates a single Arm program. Its messages are worth knowing. Given an x86-64 file, it says `Invalid ELF image for this architecture`. Given a dynamically linked Arm program on a machine without the Arm C library, it says `Could not open '/lib/ld-linux-aarch64.so.1'`, the Arm loader. Emulation is slow: in this topic's lab, from under twice as slow to more than eight times, depending on the work. It's for checking that something runs, never for running a service. Linux can also be told to hand foreign programs to an emulator by itself, and Docker Desktop builds and runs other architectures' images under emulation without any setup. A plain Linux server has nothing of the kind until someone installs it (Docker's guide gives the command), which is why a two-architecture build that works on a laptop can fail in CI with `exec format error`. The labs always name the emulator, so they behave the same on every machine. The other way to make an Arm binary on an x86-64 machine needs no emulator: **cross-compile** it, with a compiler that runs here and writes Arm machine code (`aarch64-linux-gnu-gcc`, used just like `gcc`).

**The second failure: the right architecture, a missing feature.** An architecture grows. Newer chips add instructions, most of them **vector instructions**, which do one operation on many numbers at once: AVX2 and AVX-512 on x86, Neon and **SVE** on Arm. On x86-64 the steps have names, **feature levels**: x86-64-v2, v3 (which adds AVX2) and v4 (some of AVX-512). A program compiled to use newer instructions starts on an older CPU of the same architecture, runs until it meets the first instruction that CPU lacks, and dies: `Illegal instruction`, signal 4, exit status 132. You read 137 the same way in the memory topic: 128 plus the signal's number. On Arm the cloud example is SVE: Graviton3 and later have it, Graviton2 doesn't. Compiler flags decide what a build may use: `-march=x86-64-v3`, `-march=armv8.2-a+sve`, or `-mcpu=native` ("everything the build machine has") make code that's faster on new chips and dies on old ones. The rule for a fleet: **build for the oldest CPU you run on**, and test on that one. The emulator can pretend to be a particular core (`-cpu neoverse-n1` is Graviton2's); its default model has every feature it knows, so a test on the default proves nothing about the old machines.

**Who makes Arm chips.** **Arm** is a company that designs CPUs and licenses the designs to others; it doesn't make chips. **Neoverse** is its family of designs for servers. Each cloud has built its own chip from them: **Graviton** at AWS (Graviton2 on Neoverse N1, Graviton3 on V1, Graviton4 on V2, Graviton5 on V3), **Cobalt 100** at Microsoft (on N2) and **Axion** at Google (on V2 for the C4A series, N3 for N4A). **Ampere Altra**, from the chip company Ampere, is rented out by Azure and Google too.

**Reading an instance name.** An **instance type** is one size of machine a cloud rents out: so many vCPUs, so much memory. (A **vCPU**, a virtual CPU, is what the cloud sells as one CPU; the next topics take it apart.) Types come in **families**, one shape in several **sizes**, and each new **generation** of a family runs on newer chips. The name says which chip, if you know where to look:

- **AWS:** the family letter, the generation, option letters, then the size. In `m8g.large`, `m` is general purpose, `8` the generation, `g` Graviton. A small `a` means AMD and an `i` Intel: `m7a.large` is x86-64.
- **Azure:** the family, the number of vCPUs, small letters for features, the version. `Standard_D4ps_v6` is the D family, 4 vCPUs, `p` for an Arm processor, `s` for premium disks, version 6. A small `a` means AMD here too: `Standard_D4as_v6` is x86-64.
- **Google Cloud:** the series says it. C4A and N4A (Axion) and T2A (Ampere Altra) are Arm; C4D and N4D are AMD; C4 and N4 are Intel. So `c4a-standard-4` is Arm and `c4d-standard-4` isn't.

On all these Arm types a vCPU is a whole physical core. On most Intel types it's one of a core's two **hyperthreads** (a core can run two streams of instructions at once, sharing its parts between them, and each stream is a hyperthread), so two vCPUs of each aren't the same hardware. What runs on them: Linux, everywhere. AWS says Graviton runs Linux only; Azure adds Windows 11, the desktop edition, on Cobalt; Google's Arm images are all Linux. None of the three offers Windows Server on Arm today (November 2026).

**Images.** A container image holds binaries, so each one is built for a **platform**: an operating system and an architecture, written `linux/amd64` or `linux/arm64`. A **registry** (where images are kept, such as Docker Hub) can keep several under one tag, listed in an **image index**: one entry per platform, each naming its `os` and `architecture`. A **multi-architecture image** is a tag with such an index, and the runtime picks the entry for its own platform. If the index has no entry for yours, or the tag points at a single image with no index at all, the image can't run there; Microsoft's SQL Server image is like that, `amd64` only. `docker buildx imagetools inspect --raw IMAGE` prints what the registry holds, on one line. You'll build multi-architecture images yourself in Module 6; here you read them.

**The inventory.** "Can we move this to Arm?" is answered part by part. Scripts and bytecode run as they are. Programs you have the source of are rebuilt for `arm64`, for the oldest CPU you'll run on. Compiled parts you don't have the source of, like a vendor's **agent** (a program installed on every server to monitor or protect it) or a library inside someone else's jar, need an `arm64` build from whoever makes them. Anything with no Arm version at all stays on x86-64 for now. In a script, `find DIR -type f` walks every file, `file` sorts them, and `basename PATH` gives a path's last part, the file's own name, for finding its source beside it. Then roll the move out a few servers at a time, with both kinds side by side until the numbers agree. AWS's transition guide is this method in full, and it holds on all three clouds.

**The money, honestly.** Prices below are **on-demand** (paying by the hour with no commitment) for Linux, in one **region** each (a region is one of a cloud's locations, and prices differ between them), read on 2026-11-11:

- AWS, US East: `m7i.large` (Intel) $0.1008 an hour, `m7g.large` (Graviton3) $0.0816: 19% less.
- Azure, East US: `Standard_D2s_v6` (Intel) $0.101, `Standard_D2ps_v6` (Cobalt 100) $0.0702: 30% less.
- Google Cloud, Iowa: `n4-standard-2` (Intel) $0.0907, `n4a-standard-2` (Axion) $0.077: 15% less.

Across the generations on the three clouds, the gap against Intel ran from 7% to 31%. Three things the price list won't tell you. First, the "up to 40%" you'll read is a claim about price performance, work done per dollar, not about price; AWS's own Graviton page claims a price up to a fifth below comparable x86 instances. Second, equal vCPUs aren't equal hardware, so a service may do more work per Arm vCPU, or less: measure requests per dollar on your own service before you promise anything. Third, Arm isn't a price class. Google's cost-optimised x86 `e2-standard-2`, at $0.0670, lists below every Arm type of that size there, and anything on Windows Server can't move at all. The sums are short. The percentage saved is the hourly difference divided by the x86 price, times 100. A month's saving is the hourly difference times 730 hours (365 days of 24 hours, divided by 12) times the number of machines. The months to pay back the work are its cost divided by the monthly saving, rounded up. A calculator of your own is fine for the number questions: the skill is setting up the sum. Nothing here needs Python; the labs do the sums with `awk`.

If you haven't seen a CPU taken apart, watch the second Crash Course video too. **Then read:** AWS's transition guide, which is the inventory method; Docker's "Multi-platform builds" as far as its three strategies; Red Hat's short post on x86-64-v2; Google's and Azure's pages on their Arm machines and AWS's Graviton page (its numbers are claims); the Graviton guide's table of generations; the two naming pages; and the platform part of the OCI index specification. The quick questions read `uname`, `dpkg`, `file`, `unzip` and image indexes with the text tools from Shell essentials, and work out savings from dated prices. The labs put you on an x86-64 machine with a cross-compiler and the Arm emulator, where you build one program for two machines and look inside an archive, finish a script that tells programs' architectures apart, write one that prices a move to Arm, take a whole service's inventory and rebuild its programs for the fleet's oldest Arm CPU, and mend a release recipe whose program won't start on Arm.

<Recap>

- An **instruction set** (architecture) is the list of operations a CPU family understands; a **binary** is **machine code** for one of them, made from **source code** by a **compiler**. Scripts (read by an interpreter) and Java **bytecode** (run by the JVM) move between architectures; compiled programs, **native extensions** and **shared libraries** (`.so`) must be rebuilt.
- **x86-64 = amd64** (Intel and AMD); **64-bit Arm = aarch64 = arm64**. `uname -m` gives the kernel's name, `dpkg --print-architecture` Debian's. `file` reads a file's header: the architecture after the first comma, and **dynamically** or **statically linked**. Names lie; contents don't. `unzip -l` lists an archive, and `unzip -p ARCHIVE FILE | file -b -` says what a file inside it is.
- **Wrong architecture:** `Exec format error`, exit 126, before the program starts. Under `qemu-aarch64-static`: `Invalid ELF image for this architecture`, and a dynamically linked Arm program without the Arm libraries: `Could not open '/lib/ld-linux-aarch64.so.1'`. **Cross-compile** with `aarch64-linux-gnu-gcc -static`; check with the emulator.
- **Emulators** run another architecture's programs slowly (from under twice to about nine times as slow in the lab, 33 times for a shell loop): fine for a check, not for a service. Docker Desktop emulates without setup; a plain Linux CI machine doesn't until one is installed.
- **Missing feature:** `Illegal instruction`, signal 4, exit 132, after the program starts. **Feature levels** (x86-64-v2, v3 with AVX2, v4) and Arm's **SVE** (Graviton3 and later, not Graviton2). Build for the oldest CPU in the fleet, and test on that model (`-cpu neoverse-n1`), not the emulator's default.
- **Arm** licenses designs (**Neoverse**); the clouds build chips: **Graviton** 2, 3, 4, 5 (AWS: N1, V1, V2, V3), **Cobalt 100** (Azure, N2), **Axion** (Google: C4A on V2, N4A on N3); **Ampere Altra** on Azure and Google.
- **Names:** AWS `m8g` (a `g` after the generation); Azure `D4ps_v6` (a `p` in the size); Google C4A, N4A, T2A. A small `a` is AMD on AWS and Azure (`m7a`, `D4as_v6`), and C4D is AMD on Google. On these Arm types a vCPU is a whole core. They run Linux (and Windows 11 on Cobalt), and no cloud offers Windows Server on them yet.
- **Images:** built per **platform** (`linux/arm64`); an **image index** lists one image per platform under a tag; no `arm64` entry, or no index at all, means it can't run on Arm.
- **Inventory:** runs as it is (scripts, bytecode), rebuild (your own compiled code), vendor (agents, others' libraries), can't move yet (no Arm version: Windows Server, SQL Server's image). `find DIR -type f`, `file` and `basename` take the inventory. Roll out a few servers at a time beside the x86 ones.
- **Money:** percent = (x86 price minus Arm price) / x86 price × 100; month = hourly saving × 730 × machines; pay-back = cost of the work / monthly saving, rounded up. At list price Arm ran 7 to 31% below Intel on 2026-11-11, not 40%; that's a price-performance claim. Measure work per dollar first, and remember an x86 type can be the cheaper one.

</Recap>
