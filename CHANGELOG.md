- **Estimate questions** (#220, [ADR-0024](docs/decisions/0024-estimate-questions.md), Proposed): a fifth kind of recall item. The learner works out a number and types it, and it's right within the item's tolerance (`absolute`, where 0 means exact, or `percent`, up to 30). The item lists the numbers its prompt states (`given`), the sum over them that gives the answer (`working`), and at least one likely mistake with its own sum. The validator works every sum out exactly with `tools/arithmetic.py`, which reads plain arithmetic and six functions and never runs the text as code, and proves that the working gives the answer, that each mistake's sum gives its value, that the tolerance accepts the answer and none of the mistakes, that every given number is in the prompt, and that a prompt with prices says when they were read. The page has a number box with the unit beside it. It forgives a sign, a currency sign in front, commas between thousands and a % on a percentage; anything else gets a note on how to type a number and counts nothing. Afterwards it says how far off the answer was and, when a wrong answer matches a known mistake, what went wrong. The answer is saved as the usual `answer` event, so the database needed no change, and in reviews an estimate counts as an answer the learner produces, like a prediction. No topic uses it yet; Module 2's topics will.
- **A lab check can ask for more than 30 seconds** (#222, [ADR-0018](docs/decisions/0018-lab-checker-local-mode.md), second amendment of 2026-11-11, Proposed). A check in `checks.yaml` may set `timeout:`, a whole number of seconds from 1 to 300 (30 without it), and a lab's checks may add up to 600 seconds in all; the validator refuses anything else with a message that names the check. Module 2's hypervisors topic needs it, to boot the learner's small virtual machine in the check itself instead of trusting a log the learner could write by hand. A check that ran out of time used to keep running inside the container. It now runs under `timeout` there, so it's stopped along with what it started (a process that ignores the signal to stop, or leaves the check's process group, can still escape; the ADR says when), and it fails with a sentence saying it ran out of time. `check` prints each result as it finishes.
- **A checkpoint can have more than two parts** (#221, [ADR-0012](docs/decisions/0012-checkpoint-support.md), amended 2026-11-11, Proposed): `prove.more` lists further builds or debugs, each with optional fresh versions (a build part needs at least one). The page shows the build as Part 1, the debug as Part 2 and the further parts after them as Part 3, Part 4 and so on, and the checkpoint is Passed only once every part has passed. The explain still opens once the Part 1 build passes. The rule that the main build stops counting once its steps are opened is the main build's alone: a further part counts whenever it passed. Checkpoints without `more` are unchanged. Cloud Checkpoint 2's third part, standing up a domain, is the first to need it.
- **Module 2's topics are bundled with the app** (#231): `csa.hw.*` and `csa.m2.checkpoint` load with it like Module 1's, because the Today page and the follow-ups only look at bundled topics. Nothing on the page changes until one of them is `ready`.

### Added (cloud Module 3: the platform it needs)

- **One shared image for every network lab** (this pull request, [ADR-0018](docs/decisions/0018-lab-checker-local-mode.md), third amendment of 2026-11-11, Proposed): `content/lab-bases/net/`, which each Module 3 lab starts from with `FROM lab-base-net`. Inside one container it builds several "machines", each a network namespace with its own `/etc`, wired by the cables and switches a short topology file lists, and runs every daemon as a service per machine (`frr@r1`, `strongswan@vpn-a`, `nginx@web` and the rest). A machine keeps lasting kernel settings in its own `/etc/sysctl.d` (only `net.` keys apply) and its addresses and routes in its own `/etc/network/up`; `sudo netlab restart` rebuilds the network the way a reboot would. `netlab verify` builds a throwaway copy of every machine from its files and compares it with the live one, so a route typed by hand, a firewall rule never saved or a kernel setting changed only live is caught. `netlab link` cuts a cable loudly or silently and restores it, for checks that prove a backup path. Helpers for checks and learners (`looking-glass`, `holdconns`, `bgp-best`, `web-svc` and others) are built in, each service's journal lines carry its name and machine (`unbound@resolver`), a habit-typed `systemctl restart frr` says what to type instead, and its README tells a lab's author everything above. Its first layer is the same as the 88 existing systemd labs', so Docker shares it; the image is 659 MB.
- **`tools/labcheck.py` builds the base first, and an unchanged base keeps its image ID**, so labs on it come from Docker's cache (the default build attestation stamped every build with the time). The validator rejects a lab that names a base that doesn't exist.
- **The restart trial**: a lab may set `lab: { restart_trial: true }`, and then `labcheck test` restarts its container once the solution passes and runs every check again. A check that fails then is reported as "the fix didn't survive a restart". Every Module 3 lab opts in.
- **Estimate questions read an IP address as four numbers**: `10.20.30.77` in a prompt states 10, 20, 30 and 77, not two decimals.
- **Labs CI runs on eight machines, not four**, and also when a lab base changes.
- **Six probe labs** in a draft topic, `csa.net.base-probes`, which run in CI before any Module 3 topic is written: BGP over a VTI IPsec tunnel; name servers, a load balancer, NAT and a slow link; topic 23's debug (big downloads hang across a GRE tunnel); topic 25's debug (IPv6 half works); topic 27's worked example (a NAT gateway); and BBR on a long, lossy link, which must reach 25 Mbit/s three times. Each keeps its contract with the restart trial. They move into their topics as those are written. A cold review fixed a race when two commands entered one lab machine at once, made `netlab intact` fail when a sealed file changed, and gave the probes checks for a fix made only live, a tunnel started by hand and a change to the cloud's router.

### Fixed (cloud Module 1, hardened after the audit)

- **The lab checker opens a lab's shell itself, and `start` keeps a lab in progress** (#209, [ADR-0018](docs/decisions/0018-lab-checker-local-mode.md), amended 2026-11-11, Proposed). `start` used to print a `docker exec` line to paste, which Git Bash mangled (Docker answered "Cwd must be an absolute path"), and running `start` twice, or following `check`'s advice after a reboot, deleted the lab and the work in it. Now `shell <topic> <exercise>` runs Docker itself; `start` leaves a running lab alone, starts a stopped one again with its files and unpauses a paused one, and only `start --fresh` removes one. `status` lists the labs the tool started and `stop --all` removes them; `check` ends by saying the lab is still running and how to stop it. Before a lab with disks boots, `start` lets go of the disks that dead labs left attached to Docker's machine, and only those it can prove nobody uses. Docker not running, Docker being slow and Ctrl+C end in a sentence, not a traceback. The lab page lists the commands as four steps (start, shell, check, stop), says that running `start` again keeps the work and `--fresh` begins again, and says in one sentence what the lab's container may touch: 69 of the 79 labs run privileged. A pasted lab result counts only when its checks are exactly the lab's own; one with other checks, or with some missing, records nothing and says to run `check` again. CI's Labs workflow also proves every lab once a week (Mondays, 04:23 UTC, on `main`), and can be started by hand.

### Fixed (the AI proxy)

### Fixed (lab checker)

- `labcheck test --all --jobs N` builds the first lab of each topic on its own before the parallel run, so the heavy first layer a topic's labs share is built once instead of four times at once; and a build may take up to 30 minutes instead of 15. On a busy CI runner, twelve builds had run out of time.
